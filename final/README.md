## 一、先认清：一个主线，四个模块

36 周里你会建六个代码项目。**它们不是并列的**，关系是这样的：

| 项目 | 在哪建的 | 是什么 | 要不要并回主线 |
|---|---|---|---|
| **`chat-app`** | 第 18 节课（W3 第 4 节） | **主线产品。** 从"能对话"长到"能交付" | —— 它就是主线 |
| `auth-lab` | 第 50 节课（W8 第 1 节） | 登录、权限、后台、上传的实验室 | **✅ 要。第 70 节收口后并回 `chat-app`，见第三节** |
| `rag-app` | 第 85 节课（W13 第 1 节） | 检索增强问答，能读客户自己的资料 | ❌ 不并。独立作品，客户要就单独交付 |
| `mm-app` | 第 99 节课（W15 第 1 节） | 识图、生图、语音转录 | ❌ 不并。独立作品 |
| `saas-lab` | 第 162 节课（W24 第 1 节） | 多租户 + Postgres + RLS | ❌ 不并。**这是"架构能力"的实验场**，不是产品 |
| `qwen` 私有化包 | 第 232 节起（W34） | 能装进客户内网的一整套 | ❌ 不并。它是 `chat-app` 的另一种交付形态 |

**为什么多租户不直接做在 `chat-app` 上：**

第 24 周的实验会 `DROP TABLE`、会故意越权、会清库。**在你要交付的那份代码上做这些，等于拿客户数据练手。** 所以它单独建库。

**那 `chat-app` 怎么变成多租户？** 等真有第二个客户再改 —— 第 24 周教的是"改的时候动哪几张表、哪几条 SQL、哪个入口"，不是"现在就必须改"。**没有第二个客户就改多租户，是纯浪费。**

## 三、合并清单：第 70 节收口后，把 `auth-lab` 并回 `chat-app`

**这一步课上没单独占一节，但它必须做。** 不做的话，第 29 周你要容器化、第 31 周要上服务器的那个 `chat-app`，里面没有登录、没有后台、没有上传 —— 等于把一个半成品部署上线。

### 要搬的四类东西

| # | 搬什么 | 从 `auth-lab` 的哪 | 到 `chat-app` 的哪 | 注意 |
|---|---|---|---|---|
| 1 | **认证四件套** | `src/db.js` `src/users.js` `src/auth.js` `src/config.js` | `src/` 同名 | `db.js` 里的建表语句要保留，`chat-app` 原来是 JSON 存对话，现在改成 SQLite |
| 2 | **后台页面** | `public/admin*.html` 和 `src/admin-*.js`（第 9 周加的） | `public/` 和 `src/` | 页面里的接口路径如果带 `/api/admin/`，接口也要一起搬 |
| 3 | **上传四件套** | `src/upload.js` `src/files.js` `src/image.js` `src/files-routes.js` | `src/` 同名 | 依赖要装：`busboy`、`sharp`（装不上换 `jimp`） |
| 4 | **上传目录** | `uploads/`（整个目录，含 `.gitkeep`） | `chat-app/uploads/` | **确认 `.gitignore` 里有 `uploads/`**，别把客户的图提交上去 |

### 具体六步

```text
① 先存档：在 chat-app 里 commit 一次，写上"合并前"
   —— 合坏了能一键退回去，这是第 4 周学的

② 装依赖：在 chat-app 里 npm install busboy sharp
   （sharp 装不上就 npm install jimp，代码里改成 jimp 的调用）

③ 拷文件：按上表 1—4 把文件复制过去，不要剪切
   —— auth-lab 还要留着查，第 33 周做安全自查时要用它当靶子

④ 改入口：在 chat-app/src/app.js 里挂上新的路由
   import filesRoutes from './files-routes.js';
   app.use('/api/files', filesRoutes);
   后台路由同理

⑤ 改存储：chat-app 原来把对话存 JSON 文件，现在改存 SQLite
   —— 建三张表：users / messages / files，用第 5 周学的 SQL 写建表语句
   —— 老数据要不要迁？自己定。建议不迁，反正是测试数据

⑥ 验一遍：起服务，走完整流程
   注册 → 登录 → 发一条对话 → 进后台改个东西 → 上传一张图 → 看列表 → 退出
   六步全过，合并才算完
```

### 合并完的验收

```text
[ ] 一个没注册的人打开 chat-app，被挡在登录页
[ ] 注册 → 能收到"假短信"验证码（第 8 周的 mock）
[ ] 登录后能对话，对话记录存在 SQLite 里（关掉服务再起，记录还在）
[ ] 用 admin 账号进后台，能改配置、能看到用户列表
[ ] 能传一张 5MB 的图，列表里有缩略图，点开能看大图
[ ] 传一个改名成 .jpg 的 .exe，被拒绝
[ ] git status 里没有 uploads/ 和 .env
```

**七条全过，你的主线就是"一个有登录、有后台、有上传的 AI 应用"。** 后面 26 周的所有能力，才有地方挂。

## 四、四个独立模块怎么算"作品"

它们不用并回主线，但**必须各自能单独演示**。第 35 周写提案、第 36 周谈合同时，客户看的是这些：

| 模块 | 一句话卖点 | 演示时必须能做什么 |
|---|---|---|
| `rag-app` | "把你公司的资料变成能问答的助手" | 现场丢一份客户的 PDF 进去，问一个只有那份文件里才有答案的问题 |
| `mm-app` | "拍张照就能录进系统" | 现场拍一张发票/名片，结构化字段正确填出来 |
| `saas-lab` | "一套代码服务多个客户，数据互不可见" | 用 A 的登录态去拿 B 的数据，返回 404 |
| `qwen` 私有化包 | "数据不出你的内网" | 拔掉网线，整套还能跑 |

**共同要求：每个模块都要有 `README.md`，写明"怎么跑起来"。** 第 20 周教过标准：

```text
这是什么（一句话）
怎么跑起来（三条命令）
需要哪些环境变量（指向 .env.example）
部署方式
已知问题
```

**"一个没参与这个项目的人，照着 README 能跑起来" —— 这是唯一标准。**
