# AI 编程工具手册 · 怎么让 AI 替你写代码，又不被它带进坑

> 这是整条路线的**元技能**。后面 35 周你都在用 AI 写代码，但没人教过你怎么用。
>
> **用得好省一半时间。用不好，你会花更多时间在调试它写的烂代码上。**

---

# 第一部分 · 先认清它是什么

## AI 编程工具不是"自动写代码"

**它是"一个非常快、非常自信、但不会负责的初级程序员"。**

三个特点必须记住：

| 特点 | 后果 |
|---|---|
| **极快** | 你写两小时的，它 20 秒。所以你会想什么都交给它 |
| **极自信** | 它错了也用同样肯定的语气说"这样就可以了" |
| **不负责** | 它不知道你的业务、不知道你的数据、不知道上线会出什么事 |

> **核心认知：它负责"写出来"，你负责"对不对"。**
>
> **这个分工不能反。** 反了就是"AI 写完，你上线，然后出事"。

## 它擅长什么、不擅长什么

| 擅长 | 不擅长 |
|---|---|
| 写样板代码（表单、列表、CRUD） | **判断业务逻辑对不对** |
| 解释报错 | **处理并发和边界情况** |
| 转换格式（JSON→TS 类型） | **安全性**（鉴权、注入、越权） |
| 写正则、SQL | **知道你的真实数据结构** |
| 补全重复代码 | **跨文件的整体设计** |
| 生成测试用例 | **性能问题**（它写的东西常常有 N+1） |

> **规律：越是"有标准答案"的事，它越强。越是"要判断"的事，它越弱。**
>
> **所以：让它写代码，你判断逻辑。**

# 第二部分 · 怎么下指令（这是最值钱的技能）

## 一个坏指令长什么样

```
帮我做一个用户管理功能
```

**为什么坏**：它不知道你有几张表、用什么框架、要不要分页、要不要权限。

**结果**：它猜着写一套，你花两小时改成自己要的样子。**比自己写还慢。**

## 好指令的五个要素

```
【背景】这是一个 Node.js + express + Supabase 的项目，
        现有 users 表：id, phone, name, role, created_at

【任务】加一个"用户列表"接口

【要求】
- 分页，每页 20 条，参数是 page
- 支持按 name 模糊搜索
- 只能管理员（role='admin'）访问
- 返回 { list: [...], total: 数字 }

【约束】
- 放在 routes/users.js
- 不要改现有的其他文件
- 用现有的 authMiddleware 做鉴权

【验收】
- 普通用户请求返回 403
- 不带 page 参数默认第 1 页
```

**五个要素**：**背景 / 任务 / 要求 / 约束 / 验收**。

> **少了任何一个，它就开始猜。** 猜对了省事，猜错了你返工。
>
> **写这五行花两分钟，能省二十分钟返工。这是最划算的投入。**

## 三个必须避免的指令

### ❌ "优化一下这段代码"

**为什么坏**：它不知道你要优化什么（速度？可读性？包体积？），也不知道哪些不能动。

**改法**：「这段代码查 1000 条数据要 8 秒。瓶颈可能在 N+1（每次循环都查一次数据库）。请改成一次批量查询，保持返回结构不变。」

### ❌ "这个报错怎么解决"

**为什么坏**：它没看到你的代码，只能给你通用答案。

**改法**：「完整报错：`Cannot read properties of undefined (reading 'map')`。相关代码：……（贴代码）。我预期是拿到数组，实际拿到的是 undefined。」

### ❌ "按最佳实践改一下"

**为什么坏**："最佳实践"是空的。它会按自己的偏好大改一通，把你的风格全打乱。

**改法**：「统一改成 async/await，不要用 .then()。其他不动。」

# 第三部分 · 怎么验收（最容易被跳过的一步）

## "看起来对"是最危险的

**AI 写的代码最大的特点是：能跑，看起来对，但有坑。**

**例如**：

```javascript
// AI 写的"获取用户列表"
const list = await db.select("*").from("users")
res.json(list)
```

**看起来完全正常。但**：

- **没有分页** → 用户涨到 1 万条，一次返回 1 万条，接口 8 秒
- **没有权限检查** → 任何登录用户都能拿到全部用户
- **没过滤软删除** → 已删除的用户也在里面

**这些都不会报错。** 只有到客户真用了才暴露。

## 验收五步（每步都要真做）

### 第一步：读一遍，逐行说出它在干什么

**不是"大致看懂了"，是"能用话讲出每一行"。**

**讲不出来的那几行，就是你不懂的地方 —— 也是将来出事的地方。**

> **这一条最重要，也最容易被跳过。**
>
> 你觉得"AI 写的我就直接用吧"，那这个代码对你就是个黑盒。**黑盒在出问题的时候会要你的命。**

### 第二步：问它三个问题

**直接在对话框里问**：

1. **"这段代码可能的边界情况有哪些？"**
2. **"如果数据量是现在的 1000 倍，哪里会出问题？"**
3. **"这段代码有安全隐患吗？"**

> **为什么问这三个**：因为 AI 默认只写"正常路径"。你问了，它才会补边界。
>
> **注意：它答的不一定对，但答出来的东西一般是它没写在代码里的真问题。**

### 第三步：故意输入坏数据

**必须测的六种输入**：

| 输入 | 期望结果 |
|---|---|
| 空字符串 | 不崩 |
| 超长字符串（1 万字符） | 不崩，或被拒绝 |
| 特殊字符 `'";<>` | 不崩，不执行 |
| 数字 0 | 不被当成"没输入" |
| `null` / `undefined` | 不崩 |
| 上一条不存在的 ID | 返回 404 而不是 500 |

> **这是最有效的一步。** 大部分问题在这一步就暴露了。

### 第四步：看它改了几个文件

**如果只改了你说的那一个**：好，风险低。

**如果改了五六个文件**：**停下来，逐个看。**

> **AI 有时候会"顺手"改别的文件**（改个变量名、调整格式、甚至重构）。**这些附带改动可能是你不想动的。**
>
> **判断标准：超出范围的改动，一律先回退，再单独提需求。**

### 第五步：跑一遍完整流程

**不是"这个接口返回对了"，是"整个功能从点到尾都能用"。**

**例如改了登录**：不是"能登录了"，是"能注册 → 能登录 → 能看到自己的数据 → 退出 → 再登录还在"。

# 第四部分 · 改坏了怎么退回（必须会）

## 退出的三层，从轻到重

| 层级 | 怎么退 | 退掉什么 |
|---|---|---|
| **撤销一次编辑** | VS Code 里 `Ctrl + Z`（可连按） | 最近的编辑（关掉文件就没了） |
| **撤销未提交的改动** | `git restore .` | 所有未提交的改动，**回到上次 commit** |
| **回到某个历史版本** | `git reset --hard <commit>` | 回到指定 commit，**之后的提交全丢** |
| **只退一个文件** | `git checkout <commit> -- 文件路径` | 只把那个文件退回去 |

> **最常用的是第二个**：`git restore .`
>
> **注意它会连你自己写的也一起丢。** 用之前先 `git status` 看清单。

## 一个救命习惯：AI 大改之前先提交

**在让 AI 做"可能改很多文件"的任务之前，先提交一次。**

```
git add -A
git commit -m "wip: 改之前先存一下"
```

> **为什么**：这样 AI 改崩了你一键就能退回来。
>
> **这一步只花 5 秒，但能救你两小时。**
>
> **我把它叫做"存档点"。** 打游戏进 boss 前存个档，同理。

## 最惨的情况：它把项目搞崩了

**顺序**：

1. **不要慌，不要继续改**（越改越乱）
2. `git status` 看它改了哪些文件
3. `git restore .` 全部退回上次提交
4. **如果连上次提交也是坏的**：`git log --oneline` 找到上一个好的 commit，`git reset --hard <那个commit>`

> **为什么强调"不要继续改"**：因为人急了会乱改，最后连哪里坏的都说不清。
>
> **退回永远比修快。**

# 第五部分 · 什么时候不该用 AI（最容易被忽略）

## 五件事绝对不要让它代劳

| 场景 | 为什么 |
|---|---|
| **密钥、鉴权逻辑** | 它可能写出看起来对但有漏洞的鉴权。**这类漏洞你看不出来** |
| **金额计算** | 它可能用浮点数算钱。**这个错要一个月后对账才发现** |
| **数据库删除、批量更新** | 它可能漏 `WHERE` 条件。**一条 SQL 删掉全表** |
| **上线部署脚本** | 它不知道你的服务器状态，可能把线上搞崩 |
| **合同、报价** | 这是你的生意判断，它没这个信息 |

> **共同点：错了的后果不可逆，或者很久才发现。**
>
> **这类代码你必须自己写，或者自己逐行验。**

## 三件事可以让它做，但要复核

| 场景 | 复核什么 |
|---|---|
| **SQL 查询** | 有没有漏条件、有没有全表扫 |
| **正则表达式** | 拿真实数据试，别信它说"这个能匹配" |
| **日期时区处理** | 跨时区、跨月、闰年、夏令时 |

# 第六部分 · 让 AI 高效率干活的四个技巧

## 技巧一：给它"上下文文件"

**每次新开对话，它不知道你的项目。**

**做法**：在项目根目录放一个 `CONTEXT.md`，写清：

```markdown
# 项目上下文

## 技术栈
Node.js 22 + express 5 + Supabase（Postgres）+ 原生 JS 前端

## 目录结构
- routes/   接口
- services/ 业务逻辑
- db.js     数据库连接

## 约定
- 所有接口返回 { data, error } 结构
- 错误用 res.status(4xx).json({ error: "..." })
- 时间统一 ISO 字符串
- 中文注释

## 已有的表
users: id, phone, name, role, created_at
messages: id, user_id, role, content, created_at
```

**每次提问带上它**：`"（项目上下文见 CONTEXT.md）……"`

> **为什么有效**：它省掉了你每次重复解释的时间，也让它的输出风格统一。
>
> **这是长期项目里最值钱的一个小文件。**

## 技巧二：一次只改一件事

**❌ 差**：「加个登录，再改下首页样式，顺便把数据库换成 MySQL」

**✅ 好**：先只做登录，验完，再说样式。

> **为什么**：三件事一起改，出错了你不知道是哪件导致的。
>
> **而且它一次改五六个文件，你根本没法逐个看。**

## 技巧三：让它先给方案，你确认了再写

**指令末尾加一句**：

> 「先不要写代码。先说你的方案：改哪几个文件、每个文件改什么、可能有什么风险。我确认了你再动手。」

> **为什么有效**：方案比代码好读十倍。**你在这一步就能发现它理解错了，省掉一轮返工。**

## 技巧四：让它自己复查

**写完代码后追加一句**：

> 「现在换一个角度，作为 code reviewer 审查你刚才写的代码。找三个最可能出问题的地方。」

> **AI 审查自己的代码，效果比它写代码本身好。** 因为它在这个环节不需要"自信"，只需要"挑刺"。

# 第七部分 · 你现在就该做的三件事

## ① 建一个 CONTEXT.md

在你现在正在做的项目里（不是学习仓库，是你真实的项目），新建 `CONTEXT.md`，按上面那个模板填。

**这一件事能立刻提升你后续每次和 AI 对话的效率。**

## ② 养成"存档点"习惯

**每次让 AI 做可能大改的任务之前，先 commit 一次。**

从本节课起就这么做。**这一个习惯能救你无数次。**

## ③ 从本节课起，AI 写完的代码必须过"验收五步"

**至少做到第一步（逐行说出它在干什么）和第三（故意输入坏数据）。**

这两步花的时间最少，挡掉的问题最多。

---

# 第八部分 · 一句话总结

> **AI 负责写出来，你负责对不对。这个分工不能反。**
>
> **指令给五个要素：背景、任务、要求、约束、验收。**
>
> **验收看五步：逐行读、问边界、喂坏数据、看改了哪些文件、跑完整流程。**
>
> **大改之前先 commit。退回永远比修快。**
>
> **密钥、钱、删数据、部署、合同——这五件事自己写。**
