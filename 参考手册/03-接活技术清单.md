# 接活清单 · 一个人做真实项目要会什么

> **这份清单不是"还要学的技术"，是"会卡住你交付的东西"。**
>
> 这门课教的是"怎么把 AI 用起来"。这份文档讲的是**"怎么把它交到一个真实的中国企业客户手上"**。
>
> **现在不用全看。谈单前翻一遍就够。**

---

## 先说清楚：你还缺什么

252 节课路线里，AI 相关能力是完整的。但一个真实项目里，"做出来"只占一半。

另一半是这些事：

| 客户会问 | 不会答的后果 |
|---|---|
| "能微信登录吗？" | 谈不成，或者你要临时补 |
| "我们数据都在 Excel 里，能导进去吗？" | **客户用不起来** |
| "能在企业微信里用吗？" | 一半以上的 B 端需求 |
| "回答能不能一个字一个字出来？" | 客户觉得你的东西很卡 |
| "数据会不会泄露？" | 信任崩塌 |
| **"数据能不能不出我们内网？"** | **这条能直接改变报价** |

**这六个问题，任何一个答不上来，单子就谈不成，或者谈成了做不完。**

## 第一级 · 不做就交付不了

### 1. 登录与账号体系

**为什么必须**：任何真实项目都要知道"这是谁"。没有登录，就没有"我的数据"这个概念。

**中国场景下的三种，各有各的用法：**

| 方式 | 用户成本 | 你需要什么 | 适合 |
|---|---|---|---|
| **微信扫码** | 最低 | 微信开放平台账号（**要企业认证，300 元/年**） | C 端、员工都有微信 |
| **手机号 + 验证码** | 低 | 短信服务商 | **最通用，B 端首选** |
| **账号密码** | 高 | 自己实现 | 客户明确要求时 |

**最小可用：手机号 + 验证码。** 不要企业认证，个人也能申请短信服务，用户不用记密码。

**三个坑：**

1. **验证码必须走后端**，不能前端直连短信服务（否则 key 泄露，别人拿你的号发垃圾短信，一夜几千块）
2. **必须限频**：同手机号 60 秒一次，同 IP 每小时 20 次。**不限频等于给攻击者一个免费短信发送器**
3. **验证码要存过期时间**（5 分钟），用完立刻删

> **成本参考**：短信约 0.04 元/条。一个用户一年几毛钱。**但要限频，失控时能烧几千。**

### 2. 多租户

**这是整个架构里最重要的一个决定，做错了只能重写。**

**场景**：给 A 公司做了系统，B 公司也想要。

| 方案 | 怎么存 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **独立部署** | 每客户一套服务器+数据库 | 物理隔离，客户最放心，能卖高价 | **运维成本 × N** | 客户少、单价高（10 万+） |
| **共享库 + `tenant_id`** | 一张表，每行标记归属 | 一套代码一套运维 | **每个查询都必须带 `tenant_id`**，漏一处就是数据泄露 | 客户多、单价低 |

**一人公司优先做"共享库 + tenant_id"。** 你没有运维团队，独立部署 5 个客户就能把你拖死。

**共享库最大的风险**：

```javascript
// 致命错误：A 客户能查到 B 客户的数据
const { data } = await supabase.from("messages").select("*")

// 正确：永远带租户条件
const { data } = await supabase.from("messages").select("*").eq("tenant_id", req.tenantId)
```

> **怎么防**：把查询封装成一个函数，**只有这个函数能查库**。这样只需要在一处保证带上 `tenant_id`。
>
> **不要到处写裸查询。** 漏一次，客户数据串了，信誉就没了。

**现在就该做的**：即使只有一个客户，**也给表加 `tenant_id` 字段**，默认值填固定值。以后加客户不用改表结构。

### 3. 支付

**关键认知：接支付 90% 的坑不在"发起支付"，在"回调"。**

```
用户点支付 → 你调下单接口 → 拿到支付链接
    ↓
用户在微信里付钱
    ↓
微信服务器 → 主动请求你的 /notify 接口（回调）
    ↓
你收到回调 → 改订单状态 → 加额度
```

**四个必须处理的坑：**

| 坑 | 后果 | 怎么办 |
|---|---|---|
| **回调会重复发** | 用户充 100，加了两次额度 | **幂等**：处理前先查订单状态 |
| **回调可以伪造** | 别人假装微信发回调，白拿额度 | **必须验签** |
| **自己的接口可能挂** | 微信发了你没收到，订单永远"未支付" | 微信会重试，但**你也要主动查单** |
| **金额单位是分不是元** | 收 100 元写成 `100`，实际收 1 元 | 微信所有金额**单位是分**，100 元写 `10000` |

> **"重复回调"是支付第一大 bug。** 几乎所有第一次接支付的人都踩过。
>
> **症状**：客户说"我付了钱，但额度加两次了"。

**个人能接吗**：微信支付和支付宝都需要**企业主体**。纯个人不行。**这是现实门槛，谈单前要确认。**

### 4. Excel 导入导出

**为什么必须**：**中国企业的数据基本都在 Excel 里。**

客户说"我们有三万条客户记录"，你问"能给我什么格式"，答案 99% 是 Excel。

**导入**：
- 用 `xlsx` 这个 npm 包
- **必须做三件事**：表头校验、逐行校验（必填/格式/重复）、**报告错误行号**
- **必须支持"部分成功"**：不要 30000 行里第 29999 行错就全部回滚，用户会崩。**成功的先存，失败的列出来让他改**

**导出**：
- 大数据量要**分段写**（3 万行以上一次性生成会内存爆炸）
- **中文文件名要编码**：`Content-Disposition` 里的中文要 `encodeURIComponent`，否则下载是乱码名

> **这个功能看起来土，但它决定客户能不能用起来。**
>
> 客户不会手动录 30000 条数据。**你不能导入，他就用不了**——不管你 AI 做得多好。

### 5. 流式输出（SSE）

**为什么必须**：**AI 应用没有流式，客户第一反应是"卡住了"。**

| 方式 | 用户体验 |
|---|---|
| 一次性返回 | 点发送 → **等 8 秒，屏幕一动不动** → 突然出现整段 |
| 流式 | 点发送 → 0.5 秒后开始一个字一个字往外蹦 |

**8 秒空白，用户会以为坏了，会再点一次，会刷新。**

**SSE**（Server-Sent Events）比 WebSocket 简单得多，单向，走普通 HTTP。

```javascript
res.setHeader("Content-Type", "text/event-stream")
res.setHeader("Cache-Control", "no-cache")
res.write(`data: ${JSON.stringify({ delta: chunk })}\n\n`)
```

**两个必踩的坑：**

1. **Nginx 默认会缓冲**，导致你写了 10 块浏览器一次性收到。要关：
   ```nginx
   proxy_buffering off;
   ```
2. **必须发心跳**：长时间没数据，中间代理会断开。每 15 秒发一个 `: ping\n\n`

> **这是"专业感"最直接的来源。** 同样的模型，不做流式就像个卡死的网页。

### 6. 异步任务与超时

| 耗时 | 做法 |
|---|---|
| < 10 秒 | 同步等，正常返回 |
| 10 秒 – 1 分钟 | 流式返回（SSE） |
| > 1 分钟 | **提交任务 → 立刻返回任务 ID → 前端轮询进度** |

**最小可用**（不用上消息队列）：

1. 建 `jobs` 表：`id` `status` `result` `created_at`
2. 接口收到 → 插一条 `pending` → **立刻返回 `{ jobId }`**
3. 后台异步跑
4. 前端每 2 秒查一次状态

> **别一上来就用 Redis + BullMQ。** 一人公司的小项目，**数据库当队列够用**，还少一个要运维的东西。

**必须做：给所有外部请求加超时。**

```javascript
const controller = new AbortController()
setTimeout(() => controller.abort(), 30000)
fetch(url, { signal: controller.signal })
```

> **`fetch` 默认没有超时。** 模型接口卡住时，你的请求永远挂着，用户浏览器永远转圈。**这是真实隐患。**

## 第二级 · 强烈建议

### 7. 企业微信 / 飞书 / 钉钉

**中国 B 端交付，一半以上的入口在这些平台里。**

| 平台 | 你要做什么 | 难点 |
|---|---|---|
| **企业微信** | 建自建应用，配 `corp_id` + `secret` | 回调要公网可达 + 验签 + **5 秒内响应** |
| **飞书** | 建自建应用，事件订阅 | 和企微类似，文档更清楚 |
| **钉钉** | 建机器人 | 相对简单 |

**关键认知：这些平台的"回调"和你接支付的"回调"是同一类问题** —— 都要验签、都要幂等、都要快速响应。

> **企业微信要求回调 5 秒内响应。AI 生成要 8 秒，一定超时。**
>
> **解法**：收到消息先回"正在思考"，然后用"主动发消息"接口把答案推过去。**这个模式必须掌握。**

### 8. 定时任务

客户一定会要"每节课早上 9 点给我发昨天的报表"。

| 做法 | 适合 |
|---|---|
| Linux `crontab -e` | 单机，最简单 |
| `node-cron` | 和程序一起跑 |
| 云函数定时触发 | 无服务器 |

**必须处理**：重复执行（多台机器会跑两次）、静默失败（**必须加告警**）、时区（服务器 UTC，统一用 `Asia/Shanghai`）。

### 9. Webhook 接收（通用能力）

**所有第三方服务都是"有事来通知你"，形式就是 Webhook。**

**统一四件事，不管对接谁：**

1. **验签**（确认真是对方发的）
2. **幂等**（同一条事件只处理一次）
3. **快速响应**（先回 200，再异步处理）
4. **记录原始请求**（出问题时能查）

> **写成一个通用函数**，以后接谁都套用。**能省几十小时。**

### 10. 文件上传

- 前端 → **不走后端中转**（大文件会撑爆内存），走"预签名 URL"直传对象存储
- 后端只负责生成凭证 + 记录文件信息
- **必须限制类型和大小**（否则用户传个 2GB 视频，流量费爆炸）
- **文件名不能直接用用户给的**（可能含 `../` 路径穿越），要生成随机名

### 11. 自动部署（GitHub Actions）

配一次，以后 `git push` 就自动部署。

```yaml
name: deploy
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: appleboy/ssh-action@master
        with:
          host: ${{ secrets.HOST }}
          username: root
          key: ${{ secrets.SSH_KEY }}
          script: |
            cd /root/app
            git pull
            npm install
            pm2 restart my-app
```

> **一人公司特别需要这个。** 你没有运维，**能自动化的都必须自动化**，否则时间全被杂事吃掉。

### 12. 冒烟测试

**注意：这和"评测"不是一回事。**

- **评测**：判断 AI 回答得好不好
- **冒烟测试**：判断"系统还活着吗"

部署后跑一遍核心流程，30 秒内知道有没有崩。

## 第三级 · 按需

| 项 | 我的判断 |
|---|---|
| **微信小程序** | 先问客户："手机上能用，还是要应用商店能搜到？" 前者 PWA 就够，**成本差十倍** |
| **图表** | ECharts（国内最常用，中文文档全） |
| **导出 PDF** | `puppeteer` 把网页转 PDF，样式所见即所得 |
| **邮件短信** | `nodemailer` + 腾讯企业邮；短信必须提前报备模板 |
| **TypeScript** | **你现在不用学。** 但必须能读（找开源模板时大部分是 TS） |
| **数据库迁移** | 现在不做也行，但你改第三次表结构、忘了改过啥时就需要了 |
| **Redis** | **你现在不需要。** 数据库查询够快，加 Redis 只是多一个会挂要备份的东西 |

## 第四级 · 不是技术，但会卡死你

### 数据出境（**最重要**）

**你在用 OpenAI 格式的接口。如果模型实际在境外服务器上，客户的业务数据就"出境"了。**

| 情况 | 风险 |
|---|---|
| 客户是国内企业，数据含个人信息，模型在境外 | **需要数据出境合规流程，小项目基本做不了** |
| 数据是公开信息或已脱敏 | 风险低 |
| 用国内模型（通义/豆包/DeepSeek/文心） | 无出境问题 |

> **谈单时必须问清**："这些数据里有客户个人信息吗？"
>
> **如果答案是"有"，你又用境外模型，这个项目你接不了** —— 或者必须换国内模型。
>
> **这一条决定技术选型，必须在报价之前问。谈完再改，成本翻倍。**

### 隐私政策与用户协议

**只要收集任何用户信息（手机号、聊天内容），就需要。**

最省事：找模板改一下，注册页让用户勾"我已阅读并同意"。

### 等保（网络安全等级保护）

**客户是国企、政府、医院、学校时会问"你们过等保了吗"。**

- 等保二级：几万块 + 几个月
- **一人公司基本做不了**

**判断**：客户是这个背景，提前问"需不需要过等保"。**需要的话，这个单你可能要放弃，或者找有资质的公司合作。**

### 合同的四条

| 条款 | 怎么写 |
|---|---|
| **范围以书面确认为准** | "本合同范围以上述功能清单为准，新增需求另行报价" |
| **验收标准写清** | **可验证的标准**："能导入 1 万条数据，错误行有提示" |
| **上线后运维另计** | "上线后运维按 X 元/月，含 N 次修改" |
| **数据归属** | "数据所有权归甲方，乙方不得用于其他用途" |

**还有一条 AI 项目特有，必须写：**

> **"模型输出内容仅供参考，乙方不对生成内容的准确性承担责任。"**
>
> **因为 AI 会答错。客户拿它做决策出了事，责任可能落到你头上。**

### 发票与收款

- 你要能开票（个体户或公司，**纯个人开不了**）
- 付款节点：常见 3-4-3（签约 30%、交付 40%、验收 30%）
- **不要做"验收后一次性付"** —— 你垫两个月，客户不认，你没有任何筹码

### 交接文档

**这是"能带人"和"只能自己干"的分界。**

- `README.md`：怎么装、怎么跑、怎么部署
- `.env.example`：需要哪些环境变量（**只写名字不写值**）
- 一份"常见问题"：客户会问的十个问题加答案
- **一段 3 分钟录屏**

> **为什么不能省**：你**一定**会在半夜接到"网站打不开了"的电话。有文档能让他先自己看一眼；没文档你每次都从头问。

## 最后：22 个谈单问题

**这是整份文档最有用的部分。谈单时照着问，问完就能决定接不接、报多少。**

### 用户和身份（4 个）

1. 谁来用？只有内部员工，还是外部客户也要用？
2. 大概几个人？同时在线最多几个？
3. 怎么登录？手机号、微信、还是要和我们现有账号打通？
4. 要不要分角色（管理员/普通用户/只看数据）？

### 数据（5 个）

5. 数据从哪来？手工录、Excel 导入、还是对接现有系统？
6. 数据量多大？现在多少条，一年后大概多少？
7. **数据里有客户个人信息吗？**（← 决定能不能用境外模型）
8. **数据能不能出你们内网？**（← 决定要不要私有化部署，**能改变整个报价**）
9. 数据丢了怎么办？有没有备份要求？

### AI 部分（5 个）

10. 它具体要干什么活？（**逼客户说具体场景，不要说"智能"**）
11. 回答错了会有什么后果？（决定要不要加人工确认）
12. 每次回答能接受等多久？3 秒、10 秒、还是 1 分钟？
13. 每天大概有多少人在用？每人每天大概用多少次？
14. **模型费用谁付？** 含在报价里，还是客户自己充？

### 交付（5 个）

15. 要在哪用？电脑浏览器、手机、企业微信、还是独立 App？
16. 上线时间？有没有必须赶的节点？
17. 部署在哪？你们的服务器，还是我帮你们买？
18. 需要过等保吗？（← 国企/政府/医院必问）
19. 上线后谁来运维？我要提供多久支持？

### 商务（3 个）

20. 验收标准是什么？怎么算"做完了"？
21. 付款节点怎么安排？
22. 后续加功能怎么算？

> **这 22 个问题，问完大概 40 分钟。**
>
> **但它能挡掉三种最坏情况**：接了做不完的单、接了一个月亏钱的单、接了一个有法律风险的单。
>
> **问了客户还觉得你专业。** 因为不专业的人上来就报价格，专业的人先问清楚。

---

## 一句话总结

> **技术不缺深，缺"最后一公里"。**
>
> **一人公司最大的优势是决策快，最大的风险是什么都得自己干。**
>
> **所以不要追求全会，要追求"知道有哪些、什么时候需要、最小可用怎么做"。**
