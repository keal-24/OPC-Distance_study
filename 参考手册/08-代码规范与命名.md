# 代码规范与命名 · 让项目三个月后你还读得懂

> 这一份讲的全是"看起来不重要"的东西。
>
> **但它们决定你的项目能不能长大、AI 写的东西能不能接上、三个月后你还敢不敢改。**

---

# 为什么要有规范（先说服你）

## 一个真实场景

```
你三个月后回来改一个功能。
打开文件夹，看到：
  utils.js
  helper.js
  common.js
  tools.js
  service.js
  api.js
  index.js
```

**七个文件，名字都差不多。你不知道哪个是干什么的。**

打开 `utils.js`，八百行。里面混着：日期格式化、手机号校验、发邮件的封装、一个跟数据库有关的函数。

**你要找一个格式化日期的函数。** 找了十五分钟。

> **这就是没有规范的代价。** 不是你写不出来，是你找不到、不敢改。
>
> **而 AI 会更糟**：你让 AI 改一个功能，它会在 `utils.js` 里再加一个函数。三个月后这个文件变成两千行。

## 规范的实际作用（不是"好看"）

| 你以为的规范作用 | 实际作用 |
|---|---|
| 让代码好看 | ❌ 没人看你的代码 |
| 显得专业 | ❌ 客户根本看不到 |
| **让你三个月后找得到、敢改** | ✅ **这才是目的** |
| **让 AI 能接上你的代码** | ✅ **这个比上一条更实际** |

> **第二条特别重要。**
>
> 你 90% 的代码是 AI 写的。**AI 会模仿你现有的风格。** 你的命名乱，它写的也乱；你有清晰的目录结构，它就会把新文件放对地方。
>
> **规范不是为了人类同事，是为了让 AI 能接着干。**

# 第一部分 · 命名

## 一条底线：名字要说出"它是什么"，不是"它怎么实现"

| 差 | 好 | 为什么 |
|---|---|---|
| `data` | `userProfile` | data 是什么数据？ |
| `list` | `pendingOrders` | 什么列表？ |
| `temp` | `formattedDate` | 临时存什么？ |
| `flag` | `isEmailVerified` | 什么标志？ |
| `doIt()` | `sendVerificationCode()` | 做什么？ |
| `handleData()` | `normalizePhoneNumber()` | 处理成什么样？ |
| `x`、`y`、`a1` | `retryCount`、`maxAttempts` | 完全不知道是什么 |

> **判断方法：把名字念出来，如果不看代码就能猜到它是干什么的，就是好名字。**
>
> **念出来像"数据处理"，那就是坏名字。**

## 六种命名法，各用在哪

这是最容易乱的地方。**记住这张表，命名就不会乱。**

| 类型 | 写法 | 例子 | 用在哪 |
|---|---|---|---|
| **变量、函数** | 小驼峰 `camelCase` | `userName`、`getUserById()` | JS 里 99% 的情况 |
| **常量** | 全大写下划线 `UPPER_SNAKE` | `MAX_RETRY_COUNT`、`API_BASE_URL` | 配置值、不会变的东西 |
| **类、组件** | 大驼峰 `PascalCase` | `UserService`、`MessageList` | class、React 组件 |
| **文件名** | 小写连字符 `kebab-case` | `user-service.js`、`send-email.js` | **JS 文件**（Windows/mac 大小写不敏感，别用大写） |
| **数据库表、字段** | 小写下划线 `snake_case` | `user_profiles`、`created_at` | **SQL 里统一这个** |
| **布尔值** | `is` / `has` / `can` 开头 | `isActive`、`hasPermission`、`canEdit` | 一眼看出是判断 |

> **为什么数据库用 `snake_case` 而 JS 用 `camelCase`**：因为 SQL 大小写不敏感，很多数据库默认把列名转小写。**用下划线最稳。**
>
> **那不就两套了吗？** 对，是两套。**在数据进出数据库的那一层做转换**（叫"映射"），别在业务代码里混着写。

## 八个最常见的命名错误

### ❌ 错误一：用拼音

```
yonghu.js
shijian()
xiaoxiList
```

**为什么错**：拼音有歧义（`shi` 是"是"还是"事"？），而且 AI 完全看不懂。

**改成**：`user.js`、`formatTime()`、`messages`

> **例外**：真正的中文业务概念，用英文表达不清时，**在注释里写中文**，代码里还是英文。比如 `merchantSettlement`（商户结算），注释里再解释。

### ❌ 错误二：缩写

```
usrMgr
btnClkHdl
cfg
```

**为什么错**：`usrMgr` 你要多花 0.5 秒反应，一节课看一百次就是 50 秒。**而且 AI 会猜错。**

**改成**：`userManager`、`handleButtonClick`、`config`

> **唯一的例外**：行业通用缩写。`id`、`url`、`api`、`http`、`db`、`msg`、`btn`（HTML 里）。**这些不算缩写，算词汇。**

### ❌ 错误三：一个名字表多种东西

```
data      // 有时候是用户，有时候是列表，有时候是错误信息
result    // 同上
item      // 同上
```

**为什么错**：你在同一个文件里，`data` 指的是三样东西。**读到第三处你就糊涂了。**

**改成**：`userData`、`orderList`、`errorMessage`

### ❌ 错误四：数字后缀

```
user1
user2
dataNew
dataOld
```

**为什么错**：`dataNew` 过三个月就不新了。

**改成**：说出区别。`currentUser` / `previousUser`、`cachedProfile` / `freshProfile`

### ❌ 错误五：正反问混用

```
isNotReady
hasNoPermission
canNotEdit
```

**为什么错**：双重否定，脑子要多转一圈。`!isNotReady` 是什么？

**改成**：`isReady`、`hasPermission`、`canEdit`

### ❌ 错误六：函数名不带动词

```
userList()      // 是获取？还是设置？
phoneNumber()   // 是校验？还是格式化？
```

**为什么错**：看不出它做什么。

**改成**：`getUserList()`、`validatePhoneNumber()`

### ❌ 错误七：函数名带一堆动词

```
getAndProcessAndSaveUserData()
```

**为什么错**：一个函数干三件事。**这种函数改一处就会坏两处。**

**改成**：拆成三个。`fetchUserData()`、`normalizeUserData()`、`saveUserData()`

### ❌ 错误八：单复数不分

```
const user = await getUsers()      // 拿到的是数组，却叫 user
const users = await getUser(id)    // 拿到的是单个，却叫 users
```

**为什么错**：看名字会误判类型。**数组和单个对象搞错，是最常见的 bug 来源之一。**

**规则**：**数组用复数，单个用单数。** `users` / `user`、`messages` / `message`

# 第二部分 · 文件与目录

## 目录结构：按"职责"分，不按"类型"分

### ❌ 常见错误：按技术类型分

```
src/
├── controllers/    ← 所有控制器
├── models/         ← 所有数据模型
├── services/       ← 所有业务逻辑
├── utils/          ← 所有工具
└── config/
```

**为什么错**：改一个功能要动四个目录。**而且 `utils/` 会变成垃圾桶。**

> 这种分法叫"按层分"，适合团队。**一人公司不合适**，因为你没有"层"的概念，你只有"功能"。

### ✅ 推荐：按功能分

```
src/
├── auth/                     登录相关，全在这
│   ├── login.js
│   ├── verify-code.js
│   └── jwt.js
├── chat/                     聊天相关，全在这
│   ├── send-message.js
│   ├── load-history.js
│   └── sse-stream.js
├── admin/                    后台管理
│   ├── user-list.js
│   └── operation-log.js
├── shared/                   真正共用的东西
│   ├── db.js
│   ├── logger.js
│   └── config.js
└── server.js                 入口
```

**好处**：**改一个功能，只动一个文件夹。**

> **判断标准：如果你要改"登录"，能不能只在 `auth/` 里改完？** 能，结构就对了。

### `utils/` 是垃圾桶，尽量别建

**如果你建了 `utils/`，三个月后它一定有 20 个不相关的函数。**

**替代做法**：

- 跟某个功能强相关的 → 放进那个功能的文件夹
- 真正通用的（日期格式化、字符串处理）→ 放进 `shared/format.js`、`shared/string.js`，**按类型分开**
- **超过 200 行的"工具文件"，说明它该拆了**

## 文件命名：一眼看出它是什么

**规则：小写、连字符、动词开头（如果是函数）。**

| 好 | 差 | 为什么 |
|---|---|---|
| `send-message.js` | `msgSvc.js` | 不知道干什么 |
| `load-history.js` | `history.js` | 是加载还是保存？ |
| `validate-phone.js` | `phone.js` | 不知道做什么 |
| `user-service.js` | `UserService.js` | Windows 大小写不敏感，混用会出问题 |

> **为什么文件用 `kebab-case`**：Windows 和 Mac 默认**大小写不敏感**，Linux **敏感**。
>
> 你写 `UserService.js`，本地能跑；部署到 Linux 写成 `import './userservice.js'` 就找不到文件。**这个 bug 在本地永远复现不出来。**

## 一个文件多长算太长

| 行数 | 状态 |
|---|---|
| < 100 | 舒服 |
| 100–200 | 正常 |
| 200–400 | **该考虑拆了** |
| > 400 | **一定要拆，否则你读不完** |

> **一个函数多长**：超过 50 行就该拆。**超过一屏（大约 40 行）就要滚动，说明它做的太多了。**
>
> **AI 特别容易写长函数**，因为它是一次性生成的，不觉得长。**你要主动要求它拆。**

# 第三部分 · 代码写法规则（AI 最爱犯错的地方）

## 十条硬规则

### 1. 永远用 `===`，不用 `==`

```javascript
if (a == 1)    // ❌ 会做类型转换，"1" == 1 是 true
if (a === 1)   // ✅ 严格相等
```

> **为什么**：`==` 会偷偷转类型。`"" == 0` 是 `true`，`null == undefined` 是 `true`。**这些行为会让你在深夜怀疑人生。**

### 2. 声明先 `const`，真需要改才 `let`，`var` 永不使用

```javascript
const name = "凯旋"     // ✅ 不会变
let count = 0           // ✅ 会变
var old = 1             // ❌ 别用（作用域规则反直觉）
```

### 3. 异步统一用 `async` / `await`，不混 `.then()`

```javascript
// ✅
const data = await fetchData()

// ❌ 同一个项目里不要混用两种风格
fetchData().then(data => { ... })
```

> **为什么**：混用会让代码读起来像两种语言。**而且 AI 会跟着你混。**

### 4. 所有外部请求必须有超时

```javascript
const controller = new AbortController()
const timer = setTimeout(() => controller.abort(), 30000)
try {
  const res = await fetch(url, { signal: controller.signal })
} finally {
  clearTimeout(timer)
}
```

> **`fetch` 默认没有超时。** 上游卡住时你的连接会永远挂着——**这是你现在代码里的隐患。**

### 5. 错误必须处理，不许空 catch

```javascript
// ❌
try { doSomething() } catch (e) {}

// ✅
try {
  doSomething()
} catch (e) {
  logger.error("doSomething 失败", { error: e.message })
  return res.status(500).json({ error: "操作失败" })
}
```

> **空 `catch` 等于把错误藏起来。** 出问题时你什么线索都没有。
>
> **这条对 AI 写的代码要专门检查** —— 它很爱写空 catch。

### 6. 不用 `console.log` 调试，用结构化日志

```javascript
// ❌ 上线后日志里全是这种东西，没法查
console.log("进来了")
console.log(data)

// ✅
logger.info("用户登录成功", { userId: user.id, ip: req.ip })
```

> **为什么**：`console.log` 上线后是噪音。**结构化日志能按字段搜**，比如"查出 userId=123 的所有操作"。

### 7. 密钥、配置一律从环境变量读，不硬编码

```javascript
// ❌ 提交到 GitHub 就等于泄露
const key = "sk-abc123..."

// ✅
const key = process.env.LLM_API_KEY
if (!key) throw new Error("缺少 LLM_API_KEY")
```

> **第二行的检查很重要**：缺变量时**启动就报错**，而不是运行到一半才炸。

### 8. 字符串拼 SQL 一律禁止，必须用参数化

```javascript
// ❌ SQL 注入
db.query(`SELECT * FROM users WHERE phone = '${phone}'`)

// ✅
db.query("SELECT * FROM users WHERE phone = ?", [phone])
```

> **没有例外。** 看到一处就要求改。

### 9. 数字金额一律整数（分），不用浮点

```javascript
// ❌ 0.1 + 0.2 = 0.30000000000000004
const price = 0.1 + 0.2

// ✅ 用最小单位（分）
const priceInCents = 10 + 20    // 30 分 = 0.3 元
```

> **涉及钱的地方永远用整数。** 这是所有支付系统的第一条铁律。

### 10. 时间统一存 ISO 字符串（UTC），显示时才转本地

```javascript
// 存库
created_at: new Date().toISOString()    // "2026-11-16T04:30:00.000Z"

// 显示时才转
new Date(created_at).toLocaleString("zh-CN")
```

> **为什么**：如果存本地时间，用户换时区、或者服务器在别的时区，时间就全乱了。

## 五个"看起来对但有坑"的 AI 写法

### 坑一：`arr.map` 里做异步

```javascript
// ❌ map 不会等 await，返回的是一堆 Promise
const results = items.map(async (item) => await process(item))

// ✅
const results = []
for (const item of items) {
  results.push(await process(item))
}
// 或者要并发：
const results = await Promise.all(items.map(item => process(item)))
```

> **这个坑极隐蔽**：代码不报错，`results` 里是一堆 `Promise {<pending>}`。**AI 非常爱这么写。**

### 坑二：`forEach` 里 `return` 不能中断

```javascript
// ❌ return 只是跳过当前这次，不会停止整个循环
list.forEach(item => {
  if (item.id === target) return item    // 没用的
})

// ✅
const found = list.find(item => item.id === target)
```

### 坑三：对象和数组的比较

```javascript
{} === {}      // false
[] === []      // false
{a:1} === {a:1}  // false
```

> **判断"相等"要比较内容，不是引用。** 用 `JSON.stringify(a) === JSON.stringify(b)`（有顺序问题），或者专门的深比较库。

### 坑四：`0` 和 `""` 被当成"没值"

```javascript
// ❌ 用户输入 0（比如数量填 0），这里会当成"没输入"
if (!input) return "请输入"

// ✅ 明确判断
if (input === "" || input === null || input === undefined) return "请输入"
```

> **这是真实业务 bug**：用户填数量 0，系统说"请输入数量"。

### 坑五：`async` 函数忘了 `await`

```javascript
// ❌ saveData 是 async 的，没 await，主流程不会等它
saveData(user)
res.json({ ok: true })    // 可能数据还没存进去就返回了

// ✅
await saveData(user)
res.json({ ok: true })
```

> **AI 常犯这个**。而且不报错，只是"有时候数据没存上"。

# 第四部分 · 注释与文档

## 什么时候该写注释

**只写三种，不要写第四种。**

### ✅ 写"为什么"，不写"是什么"

```javascript
// ❌ 废话注释
// 把 a 和 b 相加
const sum = a + b

// ✅ 解释为什么
// 用 0.9 而不是 1.0，因为上游返回的 token 数偏少 10%
const adjustedCost = rawCost * 0.9
```

> **代码本身能说明"是什么"。注释只该解释"为什么这么写"。**

### ✅ 写"坑"和"业务规则"

```javascript
// 注意：这个接口超时设 120 秒，因为大模型生成长文本可能要 60 秒以上
// 不要改成 30 秒，会导致长回答被中断
const LLM_TIMEOUT = 120000

// 业务规则：每月 1 号 0 点重置额度，按北京时间（不是 UTC）
const RESET_TIMEZONE = "Asia/Shanghai"
```

> **这类注释能救命。** 三个月后你想"这个超时是不是设太长了"，看到注释就不会改。

### ✅ 写"TODO"和"已知问题"

```javascript
// TODO: 这里现在是同步查询，数据量大了要改成异步任务
// 已知问题：并发 100 以上时偶尔会有重复插入，暂时靠唯一索引兜底
```

> **比假装没问题好。** 至少下一个改这里的人（可能是你）知道有雷。

## 什么时候不该写注释

| 情况 | 为什么 |
|---|---|
| 代码本身够清楚 | `const user = getUser(id)` 不需要注释 |
| 用注释"注释掉"代码 | 用 Git 记录，别留在文件里 |
| 过时的注释 | **比没注释更糟**——它会让读的人走错方向 |
| 大段的"文件说明" | 放在 `README.md` 里 |

> **一条判断**：注释写的是"这行代码做了什么"，就删掉；写的是"为什么这样做"，保留。

## 每个项目必须有 `README.md`

**最小内容（五段）**：

```markdown
# 项目名

## 这是什么
一句话说清。

## 怎么跑起来
1. npm install
2. 复制 .env.example 成 .env，填上值
3. npm run dev

## 需要哪些环境变量
见 .env.example

## 部署
见 参考手册/02-deployment-and-operations.md 或 参考手册/02-deployment-and-operations.md

## 已知问题
- xxx
```

> **标准**：**一个没参与这个项目的人，照着 README 能跑起来。**
>
> 这一条测试方法很简单：三个月后你自己照着 README 重装一次，卡在哪就补哪。

## `CONTEXT.md`：给 AI 看的项目说明

**这是 AI 时代新增的一类文件，非常重要。**

在新项目根目录建 `CONTEXT.md`：

```markdown
# 项目上下文

## 技术栈
Node.js 22 + express 5 + Supabase (Postgres) + 原生 JS

## 目录结构
- routes/     接口路由
- services/   业务逻辑
- shared/     公共模块
- public/     前端静态文件

## 代码约定
- 返回统一 { data, error }
- 错误用 res.status(4xx).json({ error: "中文说明" })
- 时间统一 ISO 字符串
- 命名：变量 camelCase，数据库 snake_case
- 异步统一 async/await

## 数据表
users: id, phone, name, role, created_at
messages: id, user_id, role, content, created_at

## 不要做的事
- 不要在 routes/ 里直接写数据库查询
- 不要用 var
- 不要 console.log，用 logger
```

**每次让 AI 改代码时，把它的内容一起贴上，或者直接说"参考 CONTEXT.md"**。

> **为什么这个最值钱**：它省掉了你每次重复解释项目的时间，**也让 AI 的输出风格统一**。
>
> **没有它，AI 每次都在猜你的项目是什么样。**

# 第五部分 · 让 AI 遵守规范的三个技巧

## 技巧一：规范和代码放在同一个仓库

**不要写在你的笔记里。** 写进项目根目录的 `CONTEXT.md`，跟代码一起提交。

**理由**：AI 能看到仓库里的文件，看不到你的笔记。

## 技巧二：让 AI 先读规范再动手

**指令开头加一句**：

> 「先读 `CONTEXT.md` 里的代码约定，然后按约定改。」

> **不加这句，它会用自己的默认风格**（比如喜欢用 `var`、喜欢 `.then()`、喜欢 `console.log`）。

## 技巧三：让它自己检查规范

**写完代码后追加**：

> 「对照 `CONTEXT.md` 的约定，检查你刚才的代码有没有违反。列出所有违反的地方并修正。」

> **AI 检查自己的代码，效果比它写代码本身好。** 因为这一步它不需要"自信"，只需要"对照"。

# 第六部分 · 你现在就该做的三件事

## ① 建一个 `CONTEXT.md`（30 分钟）

在你真实在做的项目里（不是学习仓库），按上面的模板填。

**这一件事能立刻提升你后续每次和 AI 对话的准确度。**

## ② 定下你的命名规则，写进 `CONTEXT.md`（15 分钟）

**最小一套**：

```
变量、函数：camelCase
常量：UPPER_SNAKE_CASE
类、组件：PascalCase
文件名：kebab-case（全小写，连字符）
数据库表字段：snake_case
布尔值：is/has/can 开头
数组：复数（users）
单个：单数（user）
```

**定下来就不要再变。** 一套乱的规则也比两套好的规则强——因为两套会混着用。

## ③ 把"十条硬规则"抄进 `CONTEXT.md`（10 分钟）

就是你上面看到的那十条。**抄进去，让 AI 每次都能看到。**

# 一句话总结

> **规范不是为了好看，是为了三个月后你还敢改，以及 AI 能接上你。**
>
> **命名说出"它是什么"；目录按功能分不按类型分；文件小写连字符；数据库下划线。**
>
> **十条硬规则里，最要紧的是：不用 `==`、不拼 SQL、金额用整数、请求有超时、错误不空 catch。**
>
> **而 `CONTEXT.md` 是 AI 时代最重要的一个文件——它把"你脑子里的约定"变成了"AI 能读到的规则"。**
