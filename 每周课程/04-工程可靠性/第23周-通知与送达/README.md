# 第23周 · 通知与送达 · 第 155—161 节课

## 你发出去的邮件，别人真的收到了吗

---

## 这一周的目标

前六周你把系统做稳了。**但有一个环节你一直没验过：通知真的到了吗？**

```text
· 你写了 sendMail()，调用成功，日志显示"已发送"
· 客户说"我没收到验证码"
· 你查日志：确实发出去了
· 那问题在哪？
```

**答案通常在三个地方，你一个都没查过：**

```text
① 进了垃圾箱（SPF/DKIM/DMARC 没配，或者发信域名信誉差）
② 被退信（收件地址不存在、对方服务器拒收）
③ 根本没发出（API 返回 200 但内部 failed，或者你连错了环境）
```

**这一周要把"我发了"变成"我确认到了"。** 七件事：

1. **会发邮件** —— 从 SMTP 到 API 服务，选一个能查送达的；
2. **知道邮件的规矩** —— 验证码类、通知类、营销类的写法完全不同；
3. **模板要能验** —— 变量漏了、链接错了、文字乱码，测试能抓住；
4. **失败要重试，但不能无限重试** —— 退信和临时失败要分开处理；
5. **能查送达状态** —— 不是"已发送"，是"已投递 / 已打开 / 已退信";
6. **配好发信域名** —— SPF / DKIM / DMARC 三件套，缺一个就容易被判垃圾；
7. **留一份送达率档案** —— 你的真实送达率是多少，退信率是多少。

## 为什么排在这一周

**因为这是你唯一"发出去就查不到"的环节。**

```text
第 17 周的 SSE：连接断了你立刻知道
第 19 周的超时：超过 30 秒你能看到
第 23 周的邮件：发出去了，然后呢？
```

**而它恰好是"用户能不能注册成功"的直接决定因素。**

```text
验证码进垃圾箱 → 用户注册失败 → 用户流失 → 你以为"产品不行"
```

**这是最冤枉的一种失败** —— 你的代码完全正确，但用户用不了。

## 这一周的核心认知

```text
你以为的"发送成功"：API 返回 200
真实的"送达成功"：收件方的 MTA 接受了这封信
真正的"用户看到"：邮件进了收件箱，不是垃圾箱
```

**三个层次，你只能控制第一个。后两个要靠配置和信誉。**

```text
层次 1：API 200          → 你代码没 bug
层次 2：MTA 接受（250）   → 地址有效、对方没拒
层次 3：进收件箱          → 域名信誉 + 认证配置 + 内容合规
```

**这一周做 1 和 2，第 3 层讲清怎么提高但不敢承诺。**

## 这一周最反直觉的一点

```text
邮件"发送成功"和"送达成功"是两个完全不同的指标，
而大多数 API 只告诉你第一个。
```

**具体说：**

```text
调用 sendMail() 返回 200
  → 只证明"你的请求被接受了"
  → 不证明"邮件发出去了"
  → 更不证明"对方收到了"

要看"真的到了"，必须：
  ① 用支持 webhook / 事件回调的服务
  ② 或者查 message-id 的投递状态
  ③ 或者看退信邮箱（bounce mailbox）
```

**这一周会把这三种都实现一遍。**

## 这一周的技术选择

```text
邮件发送：
  ① SMTP（nodemailer）—— 通用，但要自己处理退信
  ② 邮件 API 服务（Resend / SendGrid / 阿里云邮推）—— 有 webhook，能查状态
  
  我们选 ②（因为有 webhook），但第 155 节先用"假 SMTP"把原理跑通。
  这样你没有账号也能做完整练习。

短信：
  阿里云 / 腾讯云 SMS。这一周只讲规则和模板，不真发（要报备+充值）。
  → 用假短信网关，把所有分支跑通。

测试：
  本地起一个假 SMTP（smtp-server 库，或自己写 40 行）
  → 能收到真实邮件原文（含头部），这是理解 SPF/DKIM 的唯一办法
```

**为什么必须自己起假 SMTP？**

```text
你用真服务发一封测试邮件：
  · 看不到原始头部（看不到 SPF 验证结果）
  · 看不到 DKIM 签名
  · 不知道邮件实际长什么样
  · 每次测试花钱

假 SMTP：
  · 拿到完整原文（含所有头部）
  · 免费
  · 可以模拟 550 退信、421 临时失败
```

## 这一周的五条铁律

```text
一、"API 返回 200"不等于"发出去了"，更不等于"收到了"。
    必须用退信/回调/查询三件事之一来确认。

二、硬退信（550）绝不重试。
    地址不存在，重试 100 次还是不存在。重试只会损害你的域名信誉。

三、软退信（421 / 4xx）才重试，且指数退避。
    对方服务器临时忙，等 1 秒、2 秒、4 秒再试。

四、模板渲染失败必须报错，不能发出半成品。
    "尊敬的{{name}}，您的验证码是" 这种邮件发出去就是灾难。

五、SPF / DKIM / DMARC 三条记录缺一条，进垃圾箱的概率翻倍。
    这三条不是"高级优化"，是入门门槛。
```

## 这一周最容易白干的五件事

**第一：只看"发送成功"**

```text
你写：await sendMail(...); log.info("邮件已发送");
客户：没收到
你：日志说发了啊
→ 你没有任何办法证明"到底发没发"
```

**必须记录 `message-id`，并用它查状态。**

**第二：用个人邮箱（QQ/163/Gmail）发业务邮件**

```text
个人邮箱的发信额度极低（QQ 邮箱每天 50 封）
而且发信域名不是你的，SPF/DKIM 你控制不了
→ 大量邮件被判垃圾
→ 更糟：你的个人邮箱可能被封
```

**必须用专门的发信服务 + 自己的域名。**

**第三：验证码邮件写得像营销邮件**

```text
标题写"【限时】您的专属验证码已送达，快来领取！"
正文有大图、有按钮、有"点击了解详情"
→ 被判垃圾的概率极高
```

**验证码邮件的正确写法：** 纯文本、无图、标题直白、正文一句话。

**第四：短信模板临时改**

```text
短信模板必须报备审核（1–3 个工作日）
你临时改了文案 → 审核不过 → 短信发不出去 → 用户注册不了
```

**必须提前报备，且准备 2–3 个备用模板。**

**第五：不区分"用户没收到"和"我们没发出"**

```text
客户说"没收到"
你的第一反应是"再发一次"
→ 如果是地址错了，再发 10 次也没用
→ 而且每次都在损害你的退信率
```

**必须先查状态，再决定重发还是让用户改地址。**

## 这一周不用学什么

明确排除，避免你分心：

```text
自建邮件服务器（Postfix）    运维地狱，且 IP 信誉从零开始。用服务商
邮件营销平台（Mailchimp 等）  那是"发广告"，你发的是事务邮件
IMAP / POP3 收邮件           你只发不收
短信语音验证码               成本高 10 倍，且体验更差
推送（APNs / FCM）           第 28 周小程序/App 时再说
微信模板消息                 需要公众号，第 28 周
Webhook 签名验证的密码学      第 31 周安全时讲。这一周用简单的 HMAC
邮件模板设计（HTML/CSS）       验证码要纯文本，通知类简单 HTML 就够
```
