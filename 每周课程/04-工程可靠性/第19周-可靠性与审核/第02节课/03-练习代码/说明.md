## 五种失败，五种处置

```text
RETRY     网络抖动 / 408      → 重试一次
FALLBACK  连接错 / 429 / 5xx  → 切备用
FATAL     401 / 400 / 404     → 报错给人看，不切
SLOW      超时                → 交给第 129 节的三层超时
EMPTY     200 但内容是垃圾    → 重试一次，仍空则切备用
```

**EMPTY 这一档是最多人漏的**，因为他们的代码里 `if (res.ok)` 就认为成功了。

## 必须自己观察的七件事

**① 200 不等于成功**

```text
空字符串         → 内容过滤误伤 / 上游 bug
<!DOCTYPE html>  → 代理层返回了 502 页面（状态码仍是 200）
没有 { }         → 模型没按格式输出 / 被截断
```

**这三种，你的 `res.ok` 全是 true。不做内容检查，你会把垃圾当结果返回给用户。**

**② 401 不切备用**

因为"key 错了"切到备用也一样错 —— **除非你的主备 key 是独立的**（推荐）。

**自动切换会掩盖配置错误。** 有人会三个月后发现自己一直在用备用模型。

**③ 熔断必须按模型分开记**

不分开的后果：备用模型偶发一次失败 → 也熔断 → 两边都开 → 全部报错。

**④ 熔断时长的按类型区分更有效**

```text
429  → 5 秒   （限流很快恢复）
5xx  → 30 秒  （服务挂恢复慢）
超时 → 15 秒
```

**统一 30 秒能跑，但恢复慢一倍。**

**⑤ 切换耗时决定"无感知"成不成立**

```text
正常 3.2 秒，降级 4.1 秒 → 用户感觉不到（差 0.9 秒）
正常 3.2 秒，降级 30 秒  → 用户直接骂
```

**门槛约 1 秒。** 超过就是第 129 节要解决的。

**⑥ 假上游关掉 ≠ 真杀进程**

假上游 close 之后是 `ECONNREFUSED`（立刻返回）；真实断网是 `ETIMEDOUT`（等 20 秒）。**两条代码路径完全不同。**

**至少用"不存在的端口"测一次，确认你真的走到了连接错误分支。**

**⑦ `degraded` 必须传到底**

```text
① 返回值 → ② 数据库 → ③ 日志 → ④ 报表
```

**只停在 ①的人，等于没做。** 因为那条信息活不过这次请求。
