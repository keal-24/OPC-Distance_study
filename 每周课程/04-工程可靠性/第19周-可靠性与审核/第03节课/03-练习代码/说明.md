## 三层超时的关系

```text
connect 3s  <  firstByte 8s  <  total 30s

最坏等待 = 3 + 8 = 11 秒（主模型连不上 + 备用首字慢）
```

**只要有任意一层没设，剩下两层形同虚设。**

## 必须自己观察的七件事

**① `AbortSignal.timeout` 不够用**

它只能设一个点，**不能中途撤销**。

首字超时必须能撤 —— 第一块数据到了就该关掉看门狗。不关的话，它会在 8 秒后把一个已经成功的请求打断。

**症状：偶发的"成功但结果不完整"。**

**② 必须手动读 `res.body`**

```text
await res.json()     ← 一次性等完，首字超时管不到
reader.read() 循环   ← 每块都能检查，首字到了就撤看门狗
```

**不这样写，你的"首字超时"实际上等于"总超时"。**

**③ 真实原因藏在 `err.cause`**

```javascript
err.message          → "fetch failed"      ← 永远这一句
err.cause.message    → "total_timeout"     ← 真正的原因
```

**只看 `message` 你会调试两小时。**

**④ 用假上游测五种故障**

```text
响应头慢  → connect 超时
body 慢   → first_byte 超时
滴灌      → total 超时
黑洞      → connect 超时
```

**四种都必须各有一个用例。** 少测一个，你就不知道那一层是不是真的在工作。

**⑤ 超时后必须落库**

超时的时候模型什么都没返回，**`input` 变量是这条客户消息的唯一副本。**

不落库 = 消息彻底消失。不报错、不告警、日志里看不到，只有用户投诉时你才知道。

**⑥ 文案里必须有"不需要重复发送"**

超时的时候用户第一反应是再发一次。**然后你收到 3 条一样的请求，3 条都超时。**

这一句话能减少约 40% 的重复提交。

**⑦ 参数要用 P99 × 1.5，不是抄的**

```text
抄"首字 3 秒" → 你的 P90 是 2.1 秒，P99 是 3.8 秒 → 12% 正常请求被误杀
```

**误杀的代价：每天 120 条转人工 = 3 小时。**
**超时设长的代价：故障时多等 20 秒 × 5 次/天 = 100 秒。**

**100 秒 vs 3 小时，差 100 倍。**
