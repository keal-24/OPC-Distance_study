## 核心对比

```sql
-- OFFSET（读 offset+limit 行，丢掉前 offset 行）
SELECT * FROM tickets ORDER BY created_at DESC LIMIT 20 OFFSET 20000;

-- keyset（定位到游标，读 21 行）
SELECT * FROM tickets
WHERE (created_at < ?) OR (created_at = ? AND id < ?)
ORDER BY created_at DESC, id DESC
LIMIT 21;
```

## 必须自己观察的七件事

**① `OFFSET` 的耗时是线性的**

```text
offset 0     → 0.31ms
offset 99980 → 78.91ms（255 倍）
```

**因为它读了 100000 行，只给你 20 行。**

**② 索引只能把 OFFSET 快 5 倍**

```text
没索引：读 20020 行表数据 → 62ms
有索引：读 20020 个索引项 + 20 行数据 → 12ms
```

**"读 20020 个"这个事实不变。**

**③ 游标必须带 `id`**

```text
同一毫秒插入 30 条（批量导入常见）
只用 created_at → 30 条全跳过或全包含 → 重复/遗漏
(created_at, id) → 唯一，稳定
```

**④ `ORDER BY` 必须双列**

```text
只按 created_at DESC → 同毫秒的顺序不确定（数据库可能返回不同顺序）
加 id DESC → 完全确定
```

**⑤ `LIMIT limit + 1` 是判断 has_more 的最省办法**

```text
不需要 COUNT
不需要额外查询
多读 1 行就够
```

**⑥ keyset 天然免疫"翻页期间插入/删除"**

```text
因为它从"某个位置"往后读，不是"跳过 N 条"
```

**⑦ keyset 不能跳页，这是结构性代价**

```text
要跳到第 5000 页，必须先知道第 4999 页的最后一条
→ 只能一页页翻（比 OFFSET 还慢）
```

**所以要么改 UI，要么保留 OFFSET 但限制深度。**
