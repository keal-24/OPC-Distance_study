## 必须自己观察的七件事

**① 10 万行才会痛**

```text
300 行   → 全表扫 0.1ms，"加索引"看不出差别
30000 行 → 8ms，能感觉到
100000 行 → 30ms，明显
```

**所以今天第一件事是造数据。** 造完你会亲眼看到"5ms 变 200ms"。

**② 必须 `await res.text()`**

```javascript
// ❌ 只测了响应头到达
const res = await fetch(url);

// ✅ 测了完整响应
const res = await fetch(url);
await res.text();
```

**差 10 倍**（2ms vs 12ms）。

**③ 必须预热 3 次 + 跑 30 次取 P95**

```text
第 1 次：TCP 连接建立 + JIT 未编译 + 缓存空
单次测量：下次测可能是 62ms（磁盘缓存状态不同）
```

**没有"跑 30 次取 P95"这个说明，你的数字不可比。**

**④ 时间分布必须用平方，不能均匀**

```javascript
const t = Math.pow(rand(), 2);   // 偏向 0 → 80% 在最近 100 天
```

**均匀分布会让"最近 7 天"只有 1.9% 的数据 → 你低估"按时间筛选"的成本。**

**⑤ 批量插入必须用事务，差 59 倍**

```text
每条一个事务 → 10 万次 fsync → 20 分钟
每 1000 条一个 → 100 次 fsync → 15 秒
```

**⑥ `JSON.stringify` 和 `/health` 不是瓶颈**

```text
JSON.stringify 20 条  0.21ms
/health               4ms（框架开销）
```

**把它们写进"不要优化它"，防止你手痒。**

**⑦ 五个 SCAN 是明天要解决的全部问题**

```text
COUNT(*)                 SCAN
ORDER BY created_at      SCAN + TEMP B-TREE
offset=20000             SCAN + TEMP B-TREE
GROUP BY category        SCAN + TEMP B-TREE
WHERE category           SCAN
LIKE '%裂%'              SCAN（无解，第152节）
```
