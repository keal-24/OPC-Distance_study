## 核心对比

```sql
-- 死路（212ms，函数无法建索引）
SELECT * FROM tickets ORDER BY LENGTH(input) DESC LIMIT 20;

-- 出路（0.4ms）
ALTER TABLE tickets ADD COLUMN input_len INTEGER NOT NULL DEFAULT 0;
CREATE INDEX idx_tickets_len ON tickets(input_len DESC);
SELECT * FROM tickets ORDER BY input_len DESC, id DESC LIMIT 20;
```

## 必须自己观察的七件事

**① 函数排序比"无索引字段排序"慢 2 倍**

```text
ORDER BY need_human（无索引）       → 89ms
ORDER BY LENGTH(input)（函数）      → 212ms
```

**因为函数要对 10 万行各执行一次。**

**② 预计算列快 530 倍**

```text
212ms → 0.4ms
```

**代价：多一列、多一个索引、写入时多算一次、要处理"更新时同步"。**

**③ `CREATE INDEX ... DESC` 的 DESC 不是装饰**

```text
CREATE INDEX idx ON t(x)        → ORDER BY x DESC 可能退化成 TEMP B-TREE
CREATE INDEX idx ON t(x DESC)   → 直接读
```

**显式写 DESC 更保险。**

**④ 小数除法必须写 `.0`**

```sql
(? - created_at) / 3600000 * 0.5      -- ❌ 整数除法，全 0
(? - created_at) / 3600000.0 * 0.5    -- ✅
```

**这是 SQL 里最常见的坑之一。**

**⑤ 热度必须"定时算"，不能"实时算"**

```text
实时算：每行 5 个运算 + log → 320ms
定时算：读索引 → 0.31ms
```

**快 1000 倍。**

**⑥ 所有分页 ORDER BY 最后一列必须是 id**

```sql
ORDER BY hot_score DESC           -- ❌ 同分不稳定
ORDER BY hot_score DESC, id DESC  -- ✅
```

**小数据量时 SQLite 恰好稳定，但数据量大到用临时文件排序时就没了。**

**⑦ `urgency` 直接排序是错的**

```javascript
["high", "medium", "low"].sort()   // → ["high", "low", "medium"]
```

**字典序里 `low` 在 `medium` 前面。必须用 `urgency_rank`。**
