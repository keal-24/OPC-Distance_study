## 两个核心问题

```text
① N+1     → 21 次查询 → 修成 3 次（用 IN 合并）
② COUNT   → 9ms      → 修成 0.01ms（用 counter 表）
```

## 必须自己观察的七件事

**① N+1 的耗时只有 3ms，但它是指数级隐患**

```text
现在：1 个关联 × 20 条 = 21 次 → 12ms
加功能：3 个关联 × 20 条 = 61 次 → 20ms
每页改 100 条：3 × 100 = 301 次 → 60ms
```

**修 N+1 的收益是"未来可预测"，不是"现在的 3ms"。**

**② 修 N+1 要看"查询次数"，不是"耗时"**

```javascript
// 耗时差异可能只有 3ms（因为索引快）
// 但查询次数 21 → 3 是明确的
```

**断言 `q.report().total <= 3`。**

**③ `IN (?)` 有 999 个参数上限**

**你的 `limit ≤ 100` 安全。但"批量导出"会有几千个 id → 必须分片。**

**④ counter 只能用 `value = value + ?`**

```javascript
// ❌ 会丢更新
const v = getCounter("tickets");
setCounter("tickets", v + 1);

// ✅ 原子
db.prepare("UPDATE counters SET value = value + ? WHERE name = ?").run(1, "tickets");
```

**⑤ 任何绕过正常写入路径的操作都会让 counter 漂移**

**你的 `seed-big.js` 手插 10 万行 → counter 还是 0 → 第一次 check 就漂移。**

**这正是坑一。** 解法：`calibrateCounter`。

**⑥ 中间件里的重复查询最容易被忽略**

```text
中间件查一次 user
路由里又查一次 user
→ 2 次同样的 SQL
```

**用 `req.load(key, fn)` 合并。**

**⑦ 不用全局缓存的原因**

```text
全局 Map 存所有用户 → 10 万用户就爆内存
                   → 用户改名后缓存不更新
请求级缓存 → 请求结束就清 → 无泄漏、无过期问题
```
