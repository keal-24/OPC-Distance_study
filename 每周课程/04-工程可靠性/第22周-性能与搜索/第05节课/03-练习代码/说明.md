## 核心对比

```sql
-- 死路（41ms，加任何索引都没用）
SELECT * FROM tickets WHERE input LIKE '%内胆裂%';

-- 出路（0.8ms）
SELECT t.*, rank FROM tickets_fts f
JOIN tickets t ON t.id = f.rowid
WHERE tickets_fts MATCH '"内胆裂"'
ORDER BY rank LIMIT 20;
```

## 必须自己观察的七件事

**① 前缀 `LIKE '裂%'` 是能用索引的**

```text
LIKE '裂%'   → 0.31ms（走索引）
LIKE '%裂%'  → 41ms（全表扫）
```

**所以"用户从第一个字开始搜"的场景（比如按姓名搜），索引就够用。**

**② "无结果"比"有结果"慢**

```text
LIKE '%裂%'      → 41ms（命中 20 条就停）
LIKE '%不存在的%' → 49ms（扫完 10 万行）
```

**而 FTS5 反过来：无结果 0.1ms（倒排索引找不到就是找不到）。**

**③ trigram 要求 ≥3 个字**

```text
"内胆"   （2 字）→ trigram 切不出完整 3-gram → 0 结果
"内胆裂" （3 字）→ 能切 [内胆裂] → 命中
```

**这个限制是硬性的，必须在前端/接口层拦住并给明确提示。**

**④ `MATCH '%x%'` 是错的**

```text
FTS5 的 MATCH 语法里 % 不是通配符
'%内胆裂%' 会被当成"含 % 字符的短语" → 0 结果
```

**正确：`MATCH '内胆裂'`（不加任何通配符）。**

**⑤ 用户输入必须加双引号**

```javascript
// 用户输入 "a AND" → 语法错误
MATCH `"a AND"`    // 变成短语，安全
```

**⑥ FTS 让写入慢 50%，磁盘涨 40%**

```text
单条 INSERT：1.24ms → 1.9ms
库大小：30MB → 43MB
```

**这是"搜索快 50 倍"的代价。**

**⑦ 高亮片段要注意 XSS**

```sql
snippet(tickets_fts, 0, '<b>', '</b>', '…', 20)
```

**`<b>` 是你加的，但原文里的 `<script>` 必须转义。**
