# 第22周 · 性能与搜索 · 第 148—154 节课

## 数据涨十倍之后，它还快吗

---

## 这一周的目标

第 21 周你测出了"模型占 98.8%，你的代码只占 1.2%"。**那一刻你可能想："那我不用管性能了。"**

**错。** 因为那个 1.2% 是"每天 1000 条"时的 1.2%。当数据涨十倍，它会变成 30%。

**具体会这样烂掉：**

```text
现在：表里 3000 行，列表接口 5ms，搜索 20ms
三个月后：表里 30000 行，列表接口 12ms，搜索 400ms
一年后：表里 120000 行，列表接口 80ms，搜索 4 秒  ← 用户开始骂
```

**而这些劣化**不是**均匀发生的。** 它们有明确的触发点：

```text
· 表超过 1 万行，没索引的 ORDER BY 从 5ms 变 200ms
· 表超过 5 万行，LIKE '%关键词%' 从 20ms 变 2 秒
· 分页到第 1000 页，OFFSET 9000 要扫 9000 行
· 每页 20 条 × 每条查一次关联表 = 21 次查询（N+1）
```

**这一周要做七件事：**

1. **找出慢在哪** —— 不是猜，是量；
2. **加对索引** —— 索引不是越多越好，加错反而更慢；
3. **消灭 N+1** —— 一次查询拿完，不要循环里查；
4. **分页正确姿势** —— `OFFSET` 到后面会崩，要换 `keyset`；
5. **能搜到** —— `LIKE '%x%'` 用不上索引，要用 FTS5；
6. **排序不崩** —— 按热度/相关度排序需要额外设计；
7. **留一份性能档案** —— 数据量、耗时、索引清单，三个月后能对比。

## 为什么排在这一周

**因为你现在有数据了。**

```text
第 16 周：任务表，几十行
第 21 周：测试跑了几百条，但都清了
现在：如果你真的跑了三个月，表里该有几千到几万行
```

**没有真实数据量，讲索引是纸上谈兵。** 这一周你要先造数据（10 万行），再优化 —— **这样你才能亲眼看到"5ms 变 2 秒"。**

## 这一周的核心认知

```text
你以为的性能优化：改代码让它更快
真实的性能优化：让数据库少做无用功
```

**90% 的性能问题在数据库层，不在你的 JS 代码里。**

```text
· 加一个索引      → 查询从 200ms 变 2ms（100 倍）
· 优化 JS 循环    → 从 0.3ms 变 0.2ms（1.5 倍）
```

**这一周的七节课，六节在讲数据库。**

## 这一周最反直觉的一点

```text
索引不是越多越好。
```

**每个索引：**

```text
① 让写入变慢（每次 INSERT 要更新所有索引）
② 占磁盘空间
③ 可能让查询优化器选错路径
```

**判断标准：**

```text
这个索引服务于哪个具体查询？
  答不出来 → 删掉它
```

**一个 5 万行的表，3–5 个索引是正常。10 个以上要审视，20 个以上一定有问题。**

## 这一周的技术选择

```text
数据库：SQLite（已用）
  为什么不用 Postgres：迁移成本高，且 SQLite 的索引原理完全一样
  FTS5：SQLite 内置全文搜索，不用装 Elasticsearch

压测：复用第 146 节的 load.js
慢查询分析：SQLite 的 EXPLAIN QUERY PLAN
```

**SQLite 的 `EXPLAIN QUERY PLAN` 输出比 Postgres 更直白：**

```text
SCAN tickets                        ← 全表扫，慢
SEARCH tickets USING INDEX idx_x    ← 走索引，快
USE TEMP B-TREE FOR ORDER BY        ← 排序没走索引，中
```

**看懂这三行，你就掌握了 80% 的优化判断。**

## 这一周的五条铁律

```text
一、先量，再改。
    "我觉得列表慢" 不是依据。"列表 12ms，其中 9ms 是 COUNT(*)" 才是。

二、每次只改一处，改完立刻量。
    改三处一起上，从 200ms 变 3ms，你不知道是哪一处的功劳（也就不知道自己有没有改坏）。

三、索引对着查询建，不是对着字段建。
    "给 category 加索引" ← 错，因为你的查询是 (category, created_at) 组合
    "给 (category, created_at) 建复合索引" ← 对

四、分页超过 100 页就该换方案。
    OFFSET 9000 要扫 9000 行。第 1000 页和第一页不该一样慢。

五、性能档案要写"下次什么时候复查"。
    不写，你就不会复查，然后某天突然变慢。
```

## 这一周最容易白干的五件事

**第一：给所有字段都加索引**

```text
"加了索引会更快" → 给 10 个字段各加一个
→ 写入变慢 3 倍（每次 INSERT 更新 10 个索引）
→ 查询没变快（因为你的查询是组合条件，单列索引用不上）
```

**索引要对着"查询的形状"建，不是对着"字段"建。**

**第二：用 `LIKE '%关键词%'` 做搜索**

```text
前置通配符 → 索引完全用不上 → 全表扫
10 万行 → 400ms
100 万行 → 4 秒
```

**正确做法是 FTS5（第 152 节）。**

**第三：以为"加了缓存"就好了**

```text
缓存能救命，但它掩盖问题：
  真实耗时 4 秒 → 缓存命中率高 → 看起来 20ms
  → 缓存一失效（数据更新），用户又等 4 秒
  → 而且你不知道根因是"没索引"
```

**先优化查询，再加缓存。**

**第四：只优化"你看到的那条查询"**

```text
你优化了列表查询：200ms → 3ms
但列表接口还是 250ms
→ 因为 COUNT(*) 要 200ms（你没想到它）
→ 因为中间件里有 3 次额外的查询（你没注意）
```

**所以第 148 节要先"分解接口耗时"，不是只量 SQL。**

**第五：不写基线**

```text
三个月后客户说"你们变慢了"
你：真的吗？
客户：以前 1 秒，现在 3 秒
你：我没有数据...（无法反驳，也无法证明改好了）
```

**`PERF-BASELINE.md` 就是你的证据。**

## 周末的验收

不要急着进第 23 周。先确认这九条：

- [ ] 我有 10 万行真实结构的数据，能随时重建（`scripts/seed-big.js`）
- [ ] 每个接口的耗时我都量过，且分解到"SQL / 代码 / 序列化"
- [ ] 我至少加了 3 个索引，每个都能说出"服务于哪个查询"
- [ ] 我用 `EXPLAIN QUERY PLAN` 确认过走索引（不是 `SCAN`）
- [ ] 我消灭了至少一处 N+1，查询次数从 N 次降到 2 次
- [ ] 分页改成 keyset，第 1000 页和第一页耗时差 < 2 倍
- [ ] 搜索用 FTS5，10 万行里搜关键词 < 20ms
- [ ] 排序不会因为"按热度排"而全表扫
- [ ] `PERF.md` 写完了，含"下次复查条件"

**另外：**

- [ ] 每节课的 `NOTES.md` 都填了
- [ ] 每节课都有 commit + push
- [ ] 我能用三句话讲清"为什么索引不是越多越好"

> **最后一条才是真标准。** 讲不清这条，你会给每个字段加索引，然后发现写入慢了 3 倍、查询没变快。
>
> **这一周第 148、151 节不能落。** 一个讲"怎么量"，一个讲"分页为什么会崩" —— 这两件事不做，后面全是猜。

## 这一周不用学什么

明确排除，避免你分心：

```text
Redis / Memcached       缓存是第 25 周的事，而且你现在瓶颈不在缓存
Elasticsearch           为 10 万行装 ES 是拿大炮打蚊子。FTS5 够
读写分离 / 分库分表     你有 10 万行，不是 10 亿行
连接池调参              SQLite 是单文件，没有连接池概念
VACUUM / ANALYZE 深入   `PRAGMA optimize` 一行就够
CDN / 静态资源优化      第 32 周讲
Node 性能剖析（--prof） 你的代码只占 1.2%，剖析它没意义
数据库设计范式          你已经有表了，这一周是优化不是重设计
```
