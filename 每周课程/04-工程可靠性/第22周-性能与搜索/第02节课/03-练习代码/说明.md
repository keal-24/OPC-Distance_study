## 必须自己观察的七件事

**① 加索引前先看 EXPLAIN，不然不知道改没改**

```bash
node scripts/explain.js    # 五个 SCAN
# 加索引
node scripts/explain.js    # 四个变 SEARCH，LIKE 还是 SCAN
```

**② `SCAN USING INDEX` 也算好，别死追 `SEARCH`**

```text
ORDER BY ... LIMIT 20 → SCAN USING INDEX 就够（读 20 条就停）
WHERE x = ?           → 需要 SEARCH
```

**③ 给 `input` 加索引，`LIKE` 一定不会变快**

**而且优化器会直接忽略它 —— `EXPLAIN` 里根本看不到。**

**代价是 5MB 磁盘 + 写入多一次。**

**④ 复合索引的列顺序：等值在前，范围/排序在后**

```text
WHERE category = ? ORDER BY created_at  →  (category, created_at)
                                          不是 (created_at, category)
```

**反了就用不上 —— 因为没法"跳到 category 段"。**

**⑤ 最左前缀：复合索引不能跳过第一列**

```text
(category, created_at) 能服务：
  WHERE category = ?
  WHERE category = ? ORDER BY created_at

不能服务：
  ORDER BY created_at        ← 跳过第一列
  WHERE created_at > ?
```

**所以 `(created_at)` 单独的索引还得留。**

**⑥ 多余索引的代价是可量化的**

```text
8 个索引 vs 3 个索引
单条 INSERT 慢 2.5 倍
库大 25MB
查询一点没快（因为没有那些查询）
```

**这就是"索引不是越多越好"的证据。**

**⑦ 基数低的列别建单列索引**

```text
urgency 只有 3 个值
→ 索引把 10 万行分成 3 段
→ 查 urgency='high' 还要读 3.3 万行
→ 优化器直接忽略
```

**判断：`COUNT(DISTINCT col)/COUNT(*) < 0.01` → 别建。**
