# 03-练习代码

**这个文件夹故意留空。**

今天要建：

```text
你的项目/
├── PERF.md                  主档案（九节）
├── PERF-LOG.md              变更记录
├── perf/
│   └── snap-20261117.json   快照（可 diff）
└── scripts/
    ├── perf-report.js       一条命令产出所有数字
    └── archive.js           （可选）归档策略
```

## 一条命令

```bash
NODE_ENV=development node scripts/perf-report.js
NODE_ENV=development node scripts/perf-report.js --json > perf/snap-$(date +%Y%m%d).json
```

## 好档案的四个特征

```text
① 有绝对数字（不是"快了"）
② 有对照（改之前 vs 改之后）
③ 有环境（机器/数据量/版本）
④ 有触发条件（什么时候该复查）
```

## 必须自己观察的七件事

**① "0.4ms" 是个孤立数字**

```text
它既不快也不慢
只有"45ms → 0.4ms"才成立
```

**所以每张表必须有"改之前"这一列。**

**② 缺"环境"的档案会失效**

```text
三个月后你换了机器 / 升了 Node
→ 数字变了
→ 你不知道是"代码变慢"还是"机器变快"
```

**所以档案必须有 Node 版本、SQLite 版本、CPU、内存。**

**③ 缺"复查条件"的档案永远不会再看**

```text
❌ "数据量大了就复查"     → 不触发
✅ "tickets 超过 50 万行"  → 可查
```

**而且要把这个条件放进每日摘要，让你天天看到。**

**④ 存 JSON 才能 diff**

```bash
git diff perf/snap-20261117.json perf/snap-20270217.json
```

**这是"性能档案"的最高形态** —— 你能精确看到"哪个查询变慢了多少"。

**⑤ "已知无解的三处"是最诚实也最有用的部分**

```text
LIKE '%x%'     → 41ms，无解（前置通配符）
OFFSET 深翻页  → 无解（改 keyset，但保留"限制深度"的旧接口）
COUNT(*)      → 无解（改 counter，但有漂移风险）
```

**写了，客户问"能搜 2 个字吗"你能答；不写，客户自己试发现 0 结果，觉得你的搜索是坏的。**

**⑥ "不做什么"防止未来的你手痒**

```text
你会看到 JSON.stringify 0.21ms 然后想优化
→ 看到"不做，因为占 0.3%"，放弃
```

**⑦ "变慢"的记录比"变快"更有信息量**

```text
从 PERF-LOG 里能看出"列表接口的 N+1 反复出现"
→ 说明这个坑容易复发 → 该写进 CONVENTIONS.md 或做成 lint
```
