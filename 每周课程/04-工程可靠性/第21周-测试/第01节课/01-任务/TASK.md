# 第 0 步：先算清"错一次"的代价（20 分钟）

## 0.1 五个真实场景

**往下看，每个场景都要你估一个数字。别跳过。**

```text
场景 A：decideUrgency 把 480 元判成 high（应该是 medium）
  后果：客服优先处理了一条不紧急的 → 真正的紧急工单晚 2 小时
  代价估算：____ 元

场景 B：decideCategory 把"物流破损"判成 quality（应该 logistics）
  后果：工单转给了商品组，商品组说"这是物流的事"，又转回来
  代价估算：____ 元

场景 C：某个接口超时没兜底，用户看到 500
  后果：用户重试 3 次，都失败，打电话投诉
  代价估算：____ 元

场景 D：PII 复制进了 summary，客服把工单截图发到工作群
  后果：客户手机号在群里传了一圈
  代价估算：____ 元

场景 E：统计接口把"按分类"算成了"按紧急度"
  后果：你根据错误的报表决定"quality 类最需要优化"
  代价估算：____ 元
```

## 0.2 参考估算（往下看之前先自己填）

```text
A  480 判成 high → 一条工单晚 2 小时 → 客户可能流失
   单条期望损失 ≈ 5 元（因为大多数延迟没后果）
   
B  分类错 → 内部转单一次 → 5 分钟人力 + 客户多等
   单条 ≈ 8 元
   
C  500 无兜底 → 用户投诉 → 处理 20 分钟 + 可能流失
   单次 ≈ 80 元

D  PII 泄露 → 合规风险 + 客户信任
   单次 ≈ 2000 元起（而且是长尾，一次严重的能到几万）

E  报表错 → 你做错决策 → 影响整个月的优化方向
   单次 ≈ 500 元（一次决策错误）

但注意 —— 这些数字要乘上"发生频率"：
  A 每天可能 10 次 → 50 元/天 → 1500 元/月  ← 总影响最大
  B 每天 3 次     → 24 元/天 → 720 元/月
  C 每月 2 次     → 160 元/月
  D 每季度 1 次   → 667 元/月（但尾部风险极大）
  E 每月 1 次     → 500 元/月
```

## 0.3 你会发现的第一个反直觉

**"单次代价最大"的那个（D，PII）不是最该优先测的。**

```text
因为 D 的发生频率低，而且你已经做了自动修复（第 130 节）
真正每天在流血的是 A 和 B —— 单次 5 元、8 元，但一天十几次
```

**这就是为什么"按错了多贵排序"必须带上频率：**

```text
优先级 = 单次代价 × 发生频率 + 尾部风险
```

**只有"单次代价"会让你把时间花在 PII 上，而真正的日常损失在分类规则上。**

## 2.1 以 `decideUrgency` 为例

**它长这样：**

```javascript
export function decideUrgency(text, amount) {
  const s = String(text ?? "");
  if (/投诉|曝光|律师|起诉/.test(s)) return "high";
  if (Number(amount) >= 500) return "high";
  if (/人身|受伤|着火|漏电/.test(s)) return "high";
  if (Number(amount) > 0) return "medium";
  return "low";
}
```

**五行代码，几个分支？**

```text
① 投诉关键词  → high
② 金额 ≥ 500  → high
③ 人身安全    → high
④ 金额 > 0    → medium
⑤ 都不满足    → low
```

**五个出口。但"测哪些情况"远不止五个。**

## 2.3 六类用例的作用

**① 每个出口至少一条**

**作用：证明"这段代码的每条路都被走过"。** 没这个，你会漏掉某个 `if` 分支里的 typo。

**② 边界值**

**作用：抓住 `>=` 写成 `>` 这种错。**

```javascript
if (Number(amount) >= 500) return "high";   // 正确：499 → medium, 500 → high
if (Number(amount) > 500)  return "high";   // 错误：500 → medium
```

**这个错用常规用例（600 / 100）永远测不出来。**

**③ 类型异常**

**作用：真实世界的数据没有类型保证。**

```javascript
// 你以为是 number，实际可能是
req.query.limit     → 字符串 "20"
数据库里的 NULL     → null
JSON 里的 "600"     → 字符串 "600"
```

**`Number(null) === 0`、`Number("abc") === NaN`，两个都不报错，静默出错。**

**④ 组合情况**

**作用：验证"多条规则同时命中时，取哪个"。**

**这个最容易被漏，因为它需要你想"如果两件事同时发生"。**

**⑤ 真实输入**

**作用：验证你的正则在真实文本上有效。**

```javascript
/投诉|曝光|律师|起诉/.test("你们的客服太差了我一定要投诉")   → true ✅
```

**但如果客户写"投述"（错别字）、"投拆"、"律师函" —— 你的正则就漏了。**

**真实输入会暴露这些。**

**⑥ 优先级冲突**

**作用：把"规则之间的先后顺序"固化成测试。**

```javascript
// 如果哪天你把"金额 ≥ 500"挪到"投诉关键词"前面
// 这条测试会失败 → 你会想"我是有意的还是手滑"
```

**这是"保护一个决定"的测试。** 它的价值不在发现 bug，在防止"顺手改坏"。

# 第 3 步：定"测试不许做什么"（20 分钟）

## 3.1 五条禁令

```markdown
## 测试禁令

### 禁 1：不许依赖真实外部服务
模型、邮件、支付、短信 —— 全用假上游。
违反后果：测试会随机失败（网络抖、限流、模型换版本），
         然后你会"重跑一下试试"，那一刻测试就死了。

### 禁 2：不许依赖数据库里已有的数据
每个测试自己造数据，自己清。
违反后果：测试顺序一变就失败，而 node --test 是并发跑的。

### 禁 3：不许测"框架能做的事"
不测 "Express 能正确路由"、"better-sqlite3 能存字符串"。
违反后果：测试数量涨 3 倍，抓到的 bug 是 0。

### 禁 4：不许一条测试断言三件事
一个 it 里只验一个行为。
违反后果：失败时你看输出，不知道是哪个断言坏了。

### 禁 5：不许用 sleep 等异步
用轮询 + 超时，不用 setTimeout(1000)。
违反后果：慢机器上随机失败，快机器上白等。
```

## 3.2 每条禁令的反例

**禁 1 的反例：**

```javascript
// ❌ 错
it("调模型返回包含分类", async () => {
  const r = await callModel("我买的杯子碎了", prompt);
  assert.match(r.text, /quality/);
});
// 这条会随机失败：模型可能返回 logistics、可能超时、可能被限流
```

```javascript
// ✅ 对：用假上游
it("调模型返回包含分类", async () => {
  const srv = await startFakeUpstream("ok");        // 第 128 节
  try {
    const r = await callModel("我买的杯子碎了", prompt, { baseURL: `http://localhost:${srv.port}/v1` });
    assert.match(r.text, /quality/);
  } finally {
    srv.close();
  }
});
```

**禁 2 的反例：**

```javascript
// ❌ 错：依赖上一个测试创建的 id=1
it("能读到工单", () => {
  const t = findTicketById(1);
  assert.ok(t);
});
```

```javascript
// ✅ 对：自己造
it("能读到工单", () => {
  const id = insertTicket({ ... }).lastInsertRowid;
  const t = findTicketById(id);
  assert.ok(t);
  deleteTicket(id);     // 清掉
});
```

**禁 3 的反例：**

```javascript
// ❌ 无意义
it("JSON.parse 能解析合法 JSON", () => {
  assert.deepEqual(JSON.parse('{"a":1}'), { a: 1 });
});

// ❌ 无意义
it("Express 能处理 GET 请求", async () => {
  const r = await fetch("http://localhost:3000/health");
  assert.equal(r.status, 200);
});
```

**这两条测的是 Node 和 Express，不是你的代码。**

**禁 4 的反例：**

```javascript
// ❌ 一条测三件事
it("工单流程正确", () => {
  const id = insertTicket({...}).lastInsertRowid;
  assert.ok(id > 0);                          // ① 插入成功
  const t = findTicketById(id);
  assert.equal(t.category, "quality");        // ② 分类正确
  assert.equal(t.need_human, 1);              // ③ 转人工正确
});
```

**失败时你只看到"工单流程正确 失败"，不知道是哪一条。**

**禁 5 的反例：**

```javascript
// ❌ 错
it("3 秒后队列里有记录", async () => {
  await enqueue(...);
  await new Promise((r) => setTimeout(r, 3000));
  assert.ok(findPending());
});
```

```javascript
// ✅ 对：轮询
it("队列里最终有记录", async () => {
  await enqueue(...);
  const ok = await waitFor(() => findPending(), { timeout: 3000, interval: 50 });
  assert.ok(ok);
});

async function waitFor(fn, { timeout = 3000, interval = 50 }) {
  const t0 = Date.now();
  while (Date.now() - t0 < timeout) {
    if (await fn()) return true;
    await new Promise((r) => setTimeout(r, interval));
  }
  return false;
}
```

**`waitFor` 这个工具你会天天用。 今天先把它写下来。**

## 3.3 一个必须现在决定的事：测试数据放哪

```text
方案 A：测试用真实的开发库
  → 简单，但测试会污染数据，且测试之间互相影响

方案 B：每个测试用独立的内存库
  → 干净，但要每次跑 migrate（50ms，可接受）

方案 C：所有测试共用一个测试库，每次跑之前清空
  → 折中，但并发跑时会互撞
```

**推荐 B：`DB_FILE=:memory:` + 每次 migrate。**

**代价是每条测试多 50ms。20 条测试 = 1 秒。可接受。**

**收益是"测试之间零干扰"**，这是"能并发跑"的前提。

```javascript
export function decideCategory(text, modelSaid) {

```

```text
③ 模型给了 null → 走文本判断
```

```markdown
# 测试计划

1. 单元测试：所有函数都写，目标覆盖率 90%
2. 集成测试：所有接口都测

```

**错在哪？至少五条。**

**参考答案：**

```text
① "所有函数都写" → 包括 getter 和框架调用，浪费 80% 时间
② "覆盖率 90%" → 覆盖率不衡量"情况被验证"，只衡量"行被执行"

⑥ 没有"故意破坏"的验证 → 你不知道测试是不是摆设
⑦ 没有说"不依赖真实外部服务" → 测试会随机失败
```

**第 ② 条最危险。** 覆盖率是个"看起来专业"的指标，但它会让把时间花在"把没测的行也跑一遍"，而真正的 bug 在"已经跑过但没验证边界"的地方。

# 附：常见问题速查

**Q：我的项目很小，只写三五个测试够吗？**

A：**够，但要选对那三五个。**

```text
第一个：你改得最频繁的那个函数（通常是业务规则）
第二个：错了最贵的那个（通常是权限/金额/PII）
第三个：最复杂的那个（通常是解析/分类）
```

**五个测试覆盖 80% 的风险，五十个测试覆盖 85%。** 边际收益断崖式下降。

**Q：怎么知道"这个函数会不停改"？**

A：**看 git 历史。**

```bash
git log --oneline --follow -- app/services/ticket.js | wc -l
# 20 次 → 会不停改 → 必须测

git log --oneline --follow -- app/lib/db.js | wc -l
# 3 次 → 相对稳定 → 可以少测
```

**这个命令是"该测什么"最客观的依据。**

**Q：`decideCategory` 里"模型给的值优先"这个决定，要不要测？**

A：**要，而且这是最值钱的一条测试。**

```javascript
it("模型给了合法类别时，优先用模型的（哪怕文本像别的）", () => {
  // 文本像 quality，但模型说 logistics
  assert.equal(decideCategory("东西碎了", "logistics"), "logistics");
});
```

**为什么值钱？**

```text
三个月后你觉得"文本判断更可靠，应该优先"
→ 你改了顺序
→ 这条测试失败
→ 你会停下来想"当初为什么这么定"
→ 你想起来了（模型有上下文，正则没有）
→ 你改回去
```

**这条测试保护的不是 bug，是一个决策。**

**Q：匿名箭头函数（`(x) => x * 2`）怎么测？**

A：**测不到就直接写在测试里，或者提取成命名函数。**

```javascript
// 如果它在某个函数内部
function processA(items) {
  return items.map((x) => x * 2);   // ← 这个测不到
}

// 提取出来
export const double = (x) => x * 2;
function processB(items) { return items.map(double); }
```

**"为了可测而提取"，本身就是好设计** —— 它让职责更清晰。

**Q：我的函数依赖数据库，怎么单测？**

A：**两条路：**

```text
① 把纯逻辑抽出来（推荐）
   decideUrgency(text, amount)  ← 纯函数，好测
   saveResult({...})            ← 调 repo，用集成测

② 注入依赖（更重，不推荐现在做）
   makeService({ repo })  → 测试时传假 repo
```

**第 ① 条就够了：** 把"规则"和"存取"分开，规则纯函数化，存取用集成测试。

**这就是第 134 节分层带来的红利。**

**Q：`TEST-PLAN.md` 要不要写"暂不测"的清单？**

A：**要，而且很重要。**

```markdown
## 明确不测（及理由）

| 不测什么 | 为什么 |
|---|---|
| `createRotatingStream` 跨天 | 手工验过（第138节），失败后果可接受 |
| 前端样式 | 用眼睛看更快 |
| Express 路由机制 | 框架自己的测试 |
| `listTickets` 全边界 | 只测"offset 超出返回空数组" |
```

**这份清单的作用：三个月后你回来，不会重新纠结"这个该不该测"。**
