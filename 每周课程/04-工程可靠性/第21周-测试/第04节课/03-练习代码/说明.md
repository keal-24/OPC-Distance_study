```text
├── app/index.js              挂上 debugRouter（条件挂载）

```

## 三层

```text
第一层 输入错误          → 拦得住、提示清楚、不泄露
第二层 依赖失败          → 有兜底、人话、落库、耗时可控
第三层 系统内部错误      → 不崩、不泄露堆栈、有 trace_id
```

## 必须自己观察的七件事

**① "被拦时不调用模型"必须单独断言**

```javascript
const before = up.getCallCount();
await client.call(...);
assert.equal(up.getCallCount(), before, "被拦的请求不该调用模型");
```

**只断言"返回 400"证明不了这件事。** 而它每天让你白花 ¥1（100 次注入 × ¥0.01）。

**② `assert.ok(status >= 400)` 是废断言**

```text
400 → 用户改输入
500 → 你改代码
```

**"出错"这件事本身没有信息量，"出错的方式"才是。**

**③ 超时必须断言耗时**

```javascript
assert.ok(ms < 8000, `超时应该 8 秒内结束，实际 ${ms}ms`);
```

**如果超时没设，请求会挂到 Node 默认超时（可能 30 秒甚至无限）。**
**只有耗时断言能抓住这个。**

**④ 超时文案里不能有技术词**

```javascript
assert.ok(!/timeout|ECONN/i.test(r.json.message));
```

**用户不需要知道 `ECONNRESET`。** 他只需要知道"有人在处理，等多长"。

**⑤ 超时落库是"不丢消息"的唯一保证**

```text
超时 → 模型什么都没返回 → input 是唯一副本
→ 不落库 = 消息永久消失，且不报错不告警
→ 用户投诉时你才知道
```

**⑥ 循环引用会让 `res.json` 抛错，可能无限循环**

```text
res.json(a) 抛 TypeError
→ 进 errorMiddleware
→ 中间件里又 res.json
→ 又抛 → 死循环
```

**所以 `errorMiddleware` 里 `res.json` 必须 try/catch。**

**⑦ 错误路径应该占 1/3 以上**

**低于这个比例，说明你测得太"顺"。**
