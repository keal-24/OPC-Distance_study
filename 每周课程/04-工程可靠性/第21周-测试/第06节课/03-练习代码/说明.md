## 核心公式

```text
QPS = 并发数 / 平均响应时间（秒）

并发 10 / 3 秒 = 3.3 QPS
并发 10 / 0.05 秒 = 200 QPS
```

**这个公式解释了"为什么加并发 QPS 不涨"** —— 因为响应时间也在涨。

## 必须自己观察的七件事

**① 先分解，再压测**

```text
不分解：P95 = 5 秒 → 你不知道该优化什么
分解后：模型 4.8 秒 + 你的代码 0.2 秒 → 优化代码只能省 4%
```

**压测前必须做单请求耗时分解。**

**② `/health` 和真实接口的差距就是"瓶颈的位置"**

```text
/health        2800 QPS  → 框架上限
/api/tickets      3 QPS  → 差距 900 倍全在模型
```

**③ 同步阻塞会让 QPS 断崖下跌**

```text
异步并发 10 → 2100 QPS
同步 50ms 并发 10 → 12 QPS
```

**因为 Node 是单线程：同步操作期间所有请求都在排队。**

**④ 平均延迟会骗你**

```text
99 个 10ms + 1 个 3000ms
平均 = (99×10+3000)/100 = 40ms   ← 看着很好
P99  = 3000ms                     ← 真相
```

**只看 P95 和 P99。**

**⑤ "0 错误"不等于成功**

```text
202 = "收到了，正在处理" → HTTP 成功，业务未完成
```

**压测要看状态码分布，不只看 "0 错误"。**

**⑥ 真实需求往往比你的上限小 1000 倍**

```text
每天 1000 条，8 小时集中 → 0.035 QPS
需要的并发 = 0.035 × 3 = 0.1
拐点并发 10
余量 100 倍
```

**这时候优化性能是浪费时间。** 但你还是要知道上限 —— 客户会问。

**⑦ 报告里的"不做什么"比"做什么"重要**

**因为"性能优化"很有诱惑力，你会去做一堆没用的事：**

```text
· 给 100 行的表加索引
· 优化 JSON 序列化（省 0.3ms）
· 换更快的框架（省 3ms，但模型要 3000ms）
```

**写下"不做什么"，你才有拒绝的依据。**
