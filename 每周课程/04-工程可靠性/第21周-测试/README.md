## 这一周的目标

第 20 周你把代码变"能维护"了。**但"能维护"不等于"敢改"。**

现在你要改一行 `decideUrgency`，会做这几件事：

```text
① 改
② 起服务
③ 打开浏览器
④ 手输一个"花了一千三"看看是不是 high
⑤ 再输一个"三十块"看看是不是 low
⑥ 觉得没问题
⑦ 上线
⑧ 三天后发现：有个客户说"四百九"被判成了 high
```

**第 ④⑤ 步叫"手工测试"。它的问题是：**

```text
· 你只会试你想到的情况
· 你下次改别的地方，这五步要重跑一遍
· 你没有留下任何"我测过"的证据
· 你没法在三周后确认"这个还是好的"
```

**这一周把"手工试几下"换成"一条命令跑完，30 秒知道能不能上线"。**

做到七件事：

1. **知道哪些该测、哪些不该测** —— 不是覆盖率越高越好；
2. **给纯函数写单元测试** —— 业务规则是最值得测的东西；
3. **给接口写集成测试** —— 验证"真实请求进去，正确响应出来";
4. **专测错误路径** —— 正常路径你不容易错，错误路径才是 bug 聚集地；
5. **跑一次端到端** —— 从浏览器点进去，走完一整条；
6. **做一次压力测试** —— 知道自己的上限在哪；
7. **写一份上线前清单** —— 每次发布照着过一遍。

## 为什么排在这一周

**因为你现在有了"可测的结构"。**

```text
第 20 周之前：所有逻辑在 server.js 里，接收 req → 无法单测
第 20 周之后：decideUrgency(text, amount) 是纯函数 → 十行就能测
```

**如果第 20 周没做分层，这一周会变成"给 1800 行的文件写测试"，你会直接放弃。**

这也是为什么这两周必须连在一起。

## 这一周的核心认知

```text
你以为的测试：把所有代码都测一遍，覆盖率 90%
真实有用的测试：只测"会变的东西"和"错了会很贵的东西"
```

**具体说：**

| 该测 | 为什么 | 不该测 | 为什么 |
|---|---|---|---|
| 业务规则（分类、紧急度） | 你会不停改它 | 框架代码（Express 路由） | 框架自己测过了 |
| 边界值（500 元、30 字） | 错在这里最贵 | 第三方库（better-sqlite3） | 有它自己的测试 |
| 错误路径（超时、5xx） | 真实世界天天发生 | 简单的 getter | 测了也不能发现什么 |
| 状态流转 | 漏一种组合就出 bug | UI 样式 | 用眼睛看更快 |

**"覆盖率 90%" 是个误导性指标。** 一个 40 行的 `decideUrgency` 里，5 个断言覆盖 100% 的分支，比"给 500 行代码写 300 个无意义断言"有用得多。

## 这一周最反直觉的一点

```text
测试的目的不是"证明代码对"，是"改代码时敢不敢动"。
```

**判断一个测试有没有用的方法：**

```text
把代码改坏一行（比如把 >= 改成 >）
→ 测试应该失败

如果测试还通过 → 这个测试是摆设
```

**这个动作叫"故意破坏"（mutation testing 的手工版）。** 这一周每个测试写完，你都要做一次。

## 这一周的技术选择

```text
测试框架：node --test（Node 内置，零依赖）
断言：    node:assert（内置）
假上游：  第 128 节的 chaos.js（复用）
HTTP 请求：fetch（内置，Node 18+）
压测：    自己写（40 行，不装 autocannon）
```

**为什么不装 Jest / Vitest / Mocha？**

```text
① node --test 够用（describe/it/assert 都有）
② 零依赖 = 零配置 = 你现在就能开始
③ 它的输出格式是 TAP，能被 CI 直接读
④ 学一个将来不用换的（Jest 和 node:test 的 API 几乎一样）
```

**第 146 节为什么不装 autocannon？**

```text
你想知道的是"我的系统在 50 并发下 P95 是多少"
不是一个专业压测工具的 200 行报告
自己写 40 行，你还能顺便学会"并发怎么压"的机制
```

## 这一周的五条铁律

```text
一、每条测试写完，必须做一次"故意破坏"。
    改坏代码，测试要失败。不失败就是摆设。

二、测试不许依赖真实外部服务。
    模型、邮件、支付全部用假上游。否则测试会随机失败，
    而你会开始"重跑一下试试"——那一刻测试就死了。

三、一个测试只测一件事。
    一个 it 里有五个 assert 且分布在三个函数上 → 失败时你不知道哪坏了。

四、错误路径的测试至少占三分之一。
    正常路径你不容易错，错误路径才是 bug 聚集地。

五、清单要能被机器检查。
    "记得检查数据库备份" 这条永远不会被执行。
    "curl /health 返回 ok:true" 这条能被脚本跑。
```

## 这一周最容易白干的五件事

**第一：追求覆盖率**

```text
你给 20 个文件都写了测试，覆盖率 85%
但 decideUrgency 的 500 边界没测
→ 那个 bug 还是上线了
```

**覆盖率告诉你"哪些行被执行过"，不告诉你"哪些情况被验证过"。**

**第二：测了 getter**

```javascript
it("getTicketById 返回 ticket", () => {
  const t = getTicketById(1);
  assert.ok(t);
});
```

**这个断言永远通过（除非数据库挂了）。它没有验证任何业务逻辑，只验证了"ORM 能用"。**

**第三：依赖真实模型**

```javascript
const res = await callModel("我买的杯子碎了");
assert.match(res.text, /杯子/);     // 模型可能不返回"杯子"
```

**这条测试会在某天随机失败，然后你会"重跑一下"，然后你不再相信测试。**

**第四：测试之间有顺序依赖**

```text
test A 创建一个工单（id=5）
test B 读 id=5
→ node --test 是并发跑的 → B 可能在 A 之前跑 → 失败
```

**每个测试必须能独立运行，且不依赖数据库里已有的数据。**

**第五：清单写了 30 项**

**你会在第 3 次发布时开始跳着看，第 5 次时只看前 5 项。**

**12 项以内，其中 5 项能被脚本跑。**

## 周末的验收

不要急着进第 22 周。先确认这九条：

- [ ] 我有 `TEST-PLAN.md`，十个待测点按"错了多贵"排了序
- [ ] `npm test` 一条命令能跑全部
- [ ] `decideUrgency` 的每个分支都有测试，包括 499/500/501
- [ ] 接口测试用假上游，拔掉网线也能跑通
- [ ] 每条测试我都做过"故意破坏"，确认它会失败
- [ ] 错误路径的测试条数 ≥ 总条数的 1/3
- [ ] 端到端测试跑通了"提交 → 202 → 队列 → 完成"
- [ ] 我知道自己的 QPS 上限和 P95 拐点

**另外：**

- [ ] 每节课的 `NOTES.md` 都填了
- [ ] 每节课都有 commit + push
- [ ] 我能用三句话讲清"为什么覆盖率不是目标"

>

## 这一周不用学什么

明确排除，避免你分心：

```text
Jest / Vitest / Mocha     node --test 够用，而且将来换过去成本极低
Playwright / Cypress      真浏览器端到端，第 27 周前端进阶时再说。
                          这一周的"端到端"是用 fetch 走完整链路，不开浏览器
autocannon / k6 / wrk     自己写 40 行压测，你才会理解"并发"是什么
覆盖率报告（c8 / istanbul） 会用 `node --test --experimental-test-coverage` 看一眼就够
TDD（测试驱动开发）        理念好，但对"已经在跑的项目"不适用。先补测试
契约测试 / Pact            多服务之间的事，你只有一个服务
性能剖析（--prof / clinic） 第 22 周专门讲性能
```
