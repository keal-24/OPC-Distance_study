# 03-练习代码

**这个文件夹故意留空。**

今天要建：

```text
你的项目/
├── test/
│   ├── fixtures.js        公共测试数据（真实输入样本）
│   └── ticket.test.js     decideUrgency / decideCategory / extractAmount / needsHuman
└── package.json           加 test / test:watch / test:cov
```

## 一条命令

```bash
npm test
# 等价于 cross-env NODE_ENV=test node --test test/
```

## `ticket.test.js` 的结构

```text
describe("decideUrgency")      20 条
  ▶ 五个出口                    5
  ▶ 金额边界                    7   ← 最重要
  ▶ 异常输入                    6
  ▶ 多条件同时命中               3

  ▶ 模型给的类别                4

  ▶ 异常输入                    3

```

## 必须自己观察的七件事

**① `node --test` 找不到文件时返回 0 且"全绿"**

```bash
node --test test/     # 目录不存在 → 0 tests → 退出码 0
```

**第一次必须做破坏实验，确认"改代码 → 测试变红"。** 否则你以为在跑，实际什么也没跑。

**② `import assert from "node:assert/strict"`**

不加 `/strict`，`assert.equal("600", 600)` 会通过。**加了之后才是 `===`。**

**③ 边界值要 7 条，比出口的 5 条还多**

```text
出口测试保证"每条路走得通"
边界测试保证"路口的位置对"

bug 90% 出在路口：>= 写成 >，门槛写成 300
```

**④ 两个静默错误**

```javascript
Number(null)  === 0        ← 不报错
Number("abc") === NaN      ← 不报错，NaN >= 500 是 false
```

**两个都给出"合理"的业务判断，但都是错的。**

**⑤ `decideUrgency` 里的"优先级测试"无效**

因为所有 high 分支返回同一个值，调换顺序结果不变。

**只有 `decideCategory`（quality 和 logistics 返回不同值）里的顺序测试才有意义。**

**写测试前先问："这个测试能区分什么？"** 区分不了的，不如不写。

**⑥ 对不精确的东西写不精确的断言**

```javascript
// ❌ 假装精确 → 失败 → 你去"修" extractAmount → 引入更多 bug
assert.equal(extractAmount("一千三百八"), 1380);

// ✅ 断言范围
assert.ok(v >= 1000 && v <= 1380);
```

**⑦ 覆盖率 95% 就够，不要追 100%**

剩下 5% 通常是数据定义、防御性 if、不可能发生的 throw。**为它们写测试是浪费。**
