## 端到端 6 步

```text
① 提交（hang 模式）      → 202 + trace_id
② 队列 pending ≥ 1
③ /review/next 取到     → trace_id 和提交的一致
④ /review/:id/done      → 200
⑤ stats 变化            → pending -1，done +1
⑥ trace_id 能查到       → tickets 表里 route=human
```

## 必须自己观察的七件事

**① `hang` 才是确定性的，含糊输入不是**

```text
含糊输入 → 模型可能编答案 → 返回 200 → 测试失败（但其实是"模型有时能猜对"）
hang     → 上游永不响应 → 必然超时 → 必然转人工
```

**端到端每一步都必须确定性。**

**② 队列空要返回 204，不是 200 + 空对象**

```javascript
// ❌ 200 + { ok:true, data:null }
// 前端要判断 data 是不是 null

// ✅ 204 + 无 body
// 前端只看 status === 204
```

**而且 204 带 body 会违反 HTTP 规范。**

**③ 断言"stats 数字变化"比断言"返回 200"有价值**

```javascript
assert.equal(stats2.pending, stats1.pending - 1);
```

**这才证明"状态真的流转了"。**

**④ `next.trace_id === submitted.trace_id` 这条抓的是"测试互相污染"**

**如果队列里有多条（别的测试留下的），"取一条"可能不是你的。**

**`DB_FILE=:memory:` 是根本解法。**

**⑤ 重复处理大概率不幂等（先测出来）**

```javascript
// 调两次 done
// 断言 done 数量涨了 2  ← 证明不幂等
// 然后修，再测"只涨 1"
```

**"先测出 bug，再修，再测通过" 比"直接写正确的测试"更能证明你在修东西。**

**⑥ 积压测试要调小限额，不要造 201 条**

```bash
# .env.test
QUEUE_BACKLOG_LIMIT=3
```

**造 201 条要 200 次 HTTP 请求 ≈ 4 秒。调小限额只要 5 次。**

**⑦ 手动验收不能省**

**测试验不了"页面能用"。** 四步手动走一遍，5 分钟。
