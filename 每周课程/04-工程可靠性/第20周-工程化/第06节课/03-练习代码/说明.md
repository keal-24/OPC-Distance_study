## 文档五部分

```text
1. 快速开始     3 分钟能调通第一个接口
2. 通用约定     base URL / 认证 / 请求格式 / 响应格式 / 分页 / 时间 / trace_id

```

## 必须自己观察的七件事

**① 期望输出写 `{...}` 等于没写**

```text
前端的第一个动作是"照着文档拼 mock"
看到 {...} → 只能猜 → 猜错 → 联调浪费两小时
```

**必须贴完整一行，字段顺序和实际一致。**

**② "常见失败"必须从日志取，不能猜**

```bash
./scripts/log.sh errors | grep -o '"code":"[A-Z_]*"' | sort | uniq -c | sort -rn
```

**你猜的：参数错、超长。
实际的：70% 是 UPSTREAM_DOWN（key 过期）。**

**按日志取，你会发现真正的问题是"key 总是过期"** —— 那更值得修。

**③ `202` 必须单独说明**

**前端最容易犯的错：把 202 当成失败，然后提示用户"重试"。**

**正确：202 是"正在处理"，走"提示等待"，不能让用户重复提交。**

**④ "用 body.ok 判断，不要用 HTTP 状态码"这条必须写**

因为 `202` 的 `res.ok === true`，但业务上没完成。

**这条不写，前端一定会踩。**

**⑤ 数据字典里要写"这条规则是人定的"**

```markdown
金额门槛 500 是拍的，不是行业标准。
```

**不写 → 三个月后客户问"为什么 480 不紧急"，你只能说"这是规则"，变成争执。
写了 → 你能说"当时定 500，可以改成 300"，变成讨论。**

**⑥ 验证脚本是今天最重要的东西**

```text
没有它：文档写完一周是准的，三周后三个接口对不上，没人再信
有它：  改接口/改文档跑一次，立刻知道有没有偏差
```

**"能否被执行验证"是文档和废纸的分界线。**

**⑦ 跑验证脚本会改数据**

`POST /api/tickets` 每跑一次插一条。

**用 `NODE_ENV=test` + 内存库，或者用明显是测试的数据（`message: "文档验证用例"`），跑完删掉。**
