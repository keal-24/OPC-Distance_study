
## 必须自己观察的七件事

**① "忘了设 NODE_ENV"是最常见的起手错误**

```bash
git pull && npm start     # 忘了 source 环境
```

**如果默认走 development，你的进程就跑在生产库上，只是它不知道自己是生产。**

**所以必须拒绝启动，不能给默认值。**

**② 相对路径 + systemd = 连到别的库**

```text
systemd 的默认 WorkingDirectory 是 /
你在 /var/www/app 下手动启动 → ./data/prod.db = /var/www/app/data/prod.db ✅
systemd 启动               → ./data/prod.db = /data/prod.db ❌
```

**而且不报错 —— 建一个新目录、一个新空库，然后"正常运行"。**

**③ 超时不递增会让 firstByte 永远轮不到**

```bash
TIMEOUT_CONNECT_MS=8000
TIMEOUT_FIRST_BYTE_MS=3000
```

**3 秒先超，8 秒的 connect 看门狗还没到点。结果：所有请求都在 3 秒失败，但你以为是"上游慢"。**

**④ 目录不可写的报错是 `SQLITE_CANTOPEN`**

```text
你去查"SQLite 为什么打不开" → 20 分钟后发现是权限
启动时就检查 fs.accessSync(dir, W_OK) → 2 秒解决
```

**⑤ 危险 SQL 的守卫必须"拦截 + 报警"两层**

```text
DROP / TRUNCATE / 无 WHERE 的 DELETE → 拦（这是灾难）
影响 > 100 行的 UPDATE               → 报警（这可能是正常的批量操作）
```

**只拦不报：合法的批量操作被误伤。
只报不拦：真灾难发生了才看到日志。**

**⑥ 四层确认的价值在"你会看一眼环境"**

```text
缺 --confirm-prod → 拒绝
没 --execute      → dry-run
表 > 1000 行      → 要 --i-know
```

**任何一层都能拦住"我以为我在开发环境"。四层之后，你至少会确认一次。**

**⑦ 数据库指纹比路径可靠**

```text
路径可能看起来对但实际指向别处（软链接、挂载、容器卷）
数据的形状骗不了人：12847 行 / 最早 8 月 = 生产库；3 行 / 全是今天 = 空库
```
