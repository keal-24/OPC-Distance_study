# 第20周 · 工程化 · 第 134—140 节课

## 你休假一周，这套代码还能跑吗

---

## 这一周的目标

第 19 周你把系统做成"不会崩"了。**但你有没有想过：这个系统只有你一个人能维护。**

具体表现：

```text
· 所有逻辑挤在 server.js 里，1800 行，改一处要读三遍
· key 硬编码在代码里，换环境要改代码
· 本地能跑，上线报错"找不到模块"
· 报错时前端收到 500 和一段 HTML 错误页
· 日志里只有 console.log，出事查不到
· 接口改了，前端不知道，上线才发现
· 你想加个功能，先在 1800 行里找"该往哪加"
```

**这一周就是把"能跑"变成"能维护"。** 要做到七件事：

1. **按功能分目录** —— 让你知道新代码该放哪；
2. **配置从代码里搬出去** —— 一个环境一套配置，代码不动；
3. **三套环境互不干扰** —— 开发和生产的数据库绝对不是同一个；
4. **统一错误格式** —— 前端只需要处理一种错误结构；
5. **日志分级与轮转** —— 上节课做了结构化，这节做"怎么管";
6. **接口文档** —— 别人（包括三个月后的你）能照着调；
7. **项目规范** —— 写在文件里的约定，不是"我记得"。

## 为什么排在这一周

**因为再往后加功能，成本会指数上升。**

```text
1800 行的 server.js：
  第 21 周加测试     → 没法单测（所有东西耦合在一起）
  第 22 周做性能优化 → 定位不到慢在哪（都在一个文件里）
  第 23 周加通知     → 又往同一个文件里塞 300 行 → 2100 行
  第 24 周多租户     → 要改 40 处，漏一处就是数据泄露
```

**这一周不做，后面每一周都在还债。** 而且债是复利的 —— 第 24 周的多租户改造，在 1800 行里做和在分层结构里做，工作量差 5 倍。

## 这一周的核心：一条线的移动

```text
现在：请求 → server.js（找路由）→ server.js（鉴权）→ server.js（业务）
              → server.js（调模型）→ server.js（写库）→ 响应

之后：请求 → 路由层（只解析参数）
              → 服务层（业务逻辑，可单测）
              → 仓储层（只碰数据库）
              → 外部层（模型/邮件/支付）
```

**这条线画对了，后面五周全部受益。**

## 这一周最反直觉的一点

```text
你以为的分层：把代码拆成一堆小文件
真实的分层：让"改一个需求"只需要动一个文件
```

**判断标准不是"文件多不多"，是"改一处会不会牵连三处"。**

```text
反例（假分层）：
  utils/ 下有 20 个文件，每个 30 行，但业务逻辑还是散在 routes 里
  → 文件多了，改需求还是到处跑

正例（真分层）：
  三个文件：routes/tickets.js、services/ticket.js、repos/ticket.js
  → 改"分类规则"只动 services/ticket.js 一个文件
```

## 这一周的六条铁律

```text
一、一个文件只做一件事，且文件名要说清是什么事。
    "utils.js" 这种名字等于"我不知道这放什么"。

二、配置只能从环境变量读，代码里不许出现具体值。
    包括数据库路径、端口、key、模型名、超时时间。

三、生产环境的启动必须主动校验。
    连错库、缺 key、debug 开着 —— 任何一个都应该拒绝启动。

四、错误响应里不能有堆栈、SQL、文件路径。
    客户看到的每一句话都应该是人写给人看的。

五、文档必须能被执行验证。
    写"返回 200"，就要有一条命令能验证它返回 200。

六、规范不写进文件等于不存在。
    "我们约定用 camelCase" 这句话，三个月后没人记得。
```

## 这一周最容易白干的五件事

**第一：为了分层而分层**

```text
你看到"三层架构"，于是建了 controller/service/repository/model 四层，
每层一个文件，每个文件 5 行，全都只是转发调用。
→ 改一个字段要动 4 个文件
```

**分层的目的是"隔离变化"，不是"符合架构图"。**

判断方法：**这个文件里的代码，会因为这些原因中的一个而改变吗？**

```text
routes/tickets.js     ← 会因"接口参数变了"而改
services/ticket.js    ← 会因"业务规则变了"而改
repos/ticket.js       ← 会因"表结构变了"而改
```

**三种变化原因是不同的，所以三层是合理的。** 如果你的 service 里只有一行 `return repo.find(id)`，那这层是多余的。

**第二：配置放在 `.env` 但提交进 git**

```text
.env          ← 应该进 .gitignore
.env.example  ← 应该提交（只有 key 名，没有值）
```

**提交了 `.env` 的后果：key 泄露，而且 git 历史里永远删不掉。**

**第三：三套环境用同一个数据库**

```text
"开发的时候连着生产库，方便调试"
→ 你某天跑了个测试脚本，把生产数据删了
```

**这是最常见的生产事故，没有之一。**

**第四：错误处理只做"500 + 一句话"**

```text
❌ { error: "Internal Server Error" }
   前端不知道是"参数错了"还是"服务器炸了"，只能统一弹"操作失败"

✅ { code: "TICKET_NOT_FOUND", message: "工单不存在", trace_id: "tr_xxx" }
   前端能精确提示，你能用 trace_id 定位
```

**第五：文档写完就不管**

```text
写完 API.md 那一周它是准的，三周后它有三个接口对不上
→ 没人再信它 → 等于没有
```

**解法：让文档的一部分能从代码生成，或者写成可执行的测试。**

## 周末的验收

不要急着进第 21 周。先确认这八条：

- [ ] 我的项目目录能说出每个文件夹是干什么的
- [ ] 我的代码里搜不到任何硬编码的 key / 端口 / 路径
- [ ] 我把 `NODE_ENV=production` 指向开发库，服务会拒绝启动
- [ ] 前端收到的所有错误都是同一种结构，且没有堆栈
- [ ] 日志按天切分，7 天前的自动删除，错误单独一份
- [ ] 有人（或三个月后的我）照着 `API.md` 能调通全部接口
- [ ] `CONVENTIONS.md` 里的每条约定都有对应的检查方式
- [ ] 我删掉 `node_modules` 重装，`npm start` 能直接跑起来

**另外：**

- [ ] 每节课的 `NOTES.md` 都填了
- [ ] 每节课都有 commit + push
- [ ] 我能用三句话讲清"为什么分层不是把文件拆小"

> **最后一条才是真标准。** 讲不清这条，你会做出一堆 5 行文件的"架构"，然后发现改一个字段要动四个地方。
>
> **这一周第 136 节不能落。** 它讲的是"生产环境连错库"这种一次性毁掉全部数据的事故。

## 这一周不用学什么

明确排除，避免你分心：

```text
TypeScript            类型能防很多 bug，但对现在的你是"多一层要学的东西"。第 27 周再说
依赖注入容器（awilix 等）  三层手写 require 就够，容器会让你看不清数据怎么流的
领域驱动设计（DDD）    聚合根、值对象、领域事件 —— 你只有一个业务，用不上
微服务                你只有一个服务，拆开只会让你多运维三个进程
Monorepo 工具（turbo 等） 一个仓库一个包，不需要
OpenAPI/Swagger 全套    YAML 写 500 行描述 8 个接口，性价比太低。手写 MD 更快
ESLint 全量规则        能跑 prettier + 5 条规则就够，200 条规则会让你天天修格式
```
