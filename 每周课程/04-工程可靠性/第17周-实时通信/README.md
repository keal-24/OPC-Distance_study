## 这一周的目标

上周你的进度是"前端每 1.5 秒问一次"。100 个人同时看，你的服务器每秒被问 66 次，而且**看到的东西永远晚 1.5 秒**。

这一周换成服务器主动推。要做到六件事：

1. **说清四种实时方案的区别** —— 轮询、长轮询、SSE、WebSocket，各用在哪；
2. **用 SSE 把进度推出去** —— 一条连接，进度一变就送到浏览器；
3. **处理断线** —— 网络抖了、电脑睡醒了、服务重启了，连接自己接回来；
4. **给 AI 输出做打字机效果** —— 这是 SSE 最值钱的用法，客户一眼就买单；
5. **用 WebSocket 做双向** —— 多人同时在同一个页面上看到彼此的改动；
6. **知道多实例时的广播问题** —— 为什么你的 SSE 在第二台机器上"失效"了。

## 为什么排在这一周

上周你已经建起了"API 进程 + worker 进程"的结构。**进度现在写在数据库里，用户靠轮询来拿。**

轮询的问题不是"慢"，是**成本随用户数线性上涨**：

```text
10 个人看进度   → 每秒 6.7 次查询   → 无所谓
1000 个人看进度 → 每秒 666 次查询   → 你开始加缓存、加机器
```

**而这 1000 个人里，绝大多数那 1.5 秒里什么都没变。**

**推送的本质：把"问"变成"变了才发"。** 成本从"用户数"掉回"变化次数"。

## 这一周的两条技术线

```text
SSE（Server-Sent Events）  ← 服务器 → 浏览器，单向，用 HTTP
WebSocket                  ← 双向，需要握手升级
```

**别急着学 WebSocket。** 90% 的"实时"需求是单向的：进度、通知、日志、AI 输出。**SSE 就够了，还比 WebSocket 简单十倍。**

| 需求 | 用哪个 | 为什么 |
|---|---|---|
| 任务进度 | **SSE** | 单向，服务器说，浏览器听 |
| AI 流式输出 | **SSE** | 同上，这就是 ChatGPT 的写法 |
| 站内通知 | **SSE** | 单向 |
| 多人协作光标 | WebSocket | 双向，且频率极高 |
| 聊天室 | WebSocket | 双向 |
| 在线状态 | WebSocket | 双向 + 心跳 |

**这一周的排序：SSE 五节，WebSocket 两节。** 因为客户提的需求八成落在前五节。

## 这一周的四条铁律

```text
一、SSE 的接口不能有压缩、不能被缓冲。
    这两件事会让你"代码全对，但就是不实时"——这是最常见的坑。

二、连接必须能自己断、自己重连。
    不要指望网络一直好。写的时候就要想"断了会怎样"。

三、每一条连接都是一个占着内存的对象。
    1000 条连接 = 1000 个对象 + 1000 个 socket。关页面必须清理。

四、跨进程推送，靠的是数据库或消息总线，不是"变量"。
    worker 在另一个进程里，它内存里的东西 API 看不见。
```

## 这一周最容易白干的三件事

**第一：以为 SSE 是"特殊协议"**

它就是普通 HTTP。`Content-Type: text/event-stream`，然后**一直不结束响应**，往里写字符串。就这么简单。

**第二：在接口里 `res.end()`**

一旦 `end`，连接就断了。**SSE 的接口永远不主动 end**，只在你关连接的时候由客户端断。

**第三：忘了 Nginx**

本机测试一切正常，一上线就"卡住不刷新"。**因为 Nginx 默认会缓冲你的响应。** 第 114 节专门讲这个。
