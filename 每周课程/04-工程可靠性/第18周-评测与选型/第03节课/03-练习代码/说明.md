## 必须自己观察的七件事

**① 第一次跑通的那 2 条，`output_text` 是不是纯 JSON**

带 ` ```json ` 包裹的，说明提示词里"不要 markdown 代码块"这句没生效。**这不是模型的问题，是提示词的位置问题** —— 那句话要放在 system 的末尾。

**② `model_returned` 和 `model_requested` 是否一致**

不一致说明供应商在你的模型名下换了后端。**记下来，这是三个月后解释"分数为什么突变"的唯一线索。**

**③ `usage` 里两个数字有没有 null**

有 null 说明供应商没返回 usage。**你的成本估算会全错**，而且你会发现得特别晚（在对账的时候）。

**④ 同一个模型跑两次，差几条**

这就是你的**噪声底线**。差异率 20% 意味着"涨 1 条"毫无意义。**这个数字必须写进 NOTES，否则第 125 节你会做出错误结论。**

**⑤ 有多少条输出被截断**

`max_tokens: 400` 对 5 字段 JSON 是够的，但如果模型的 `summary` 写了 200 字，就会被截。**截断的条数会直接影响通过率，而它是你调参数就能解决的，不是模型的错。**

**⑥ 单条成本里提示词占多少**

大概率是 80% 以上。**这个比例意味着：把提示词砍一半，成本能降 40%。** 而大部分人从来没看过这个数字。

**⑦ 实验日志第 E01 行的"致命 X 条"**

**它比通过率更重要。** 通过率 63% + 致命 4 条 = 完全不能上线；通过率 63% + 致命 0 条 = 可以带人工兜底上线。
