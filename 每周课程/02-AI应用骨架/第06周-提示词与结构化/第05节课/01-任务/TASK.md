# 第 0 步：这类活为什么最值钱（10 分钟）

## 0.1 一个客户会付钱的需求

**客户原话（你会反复听到）：**

```text
"我店里有 3000 条评价，能帮我看看顾客都在抱怨什么吗？"
"这些客服聊天记录，能不能标出来哪些是投诉、哪些是咨询？"
"我们收了一批简历，能不能先按岗位筛一遍？"
```

**人工做法：**

```text
3000 条 × 每条 20 秒 = 16 小时
按 30 元/小时 = 480 元，还要两天
```

**模型做法：**

```text
3000 次调用 × 每条 0.001 元 ≈ 3 元，跑两小时
```

**但前提是：你得能证明它分对了。**

**不能证明准确率，客户不会付钱；能证明，这就是一个 3000-8000 元的项目。**

## 0.2 为什么"分类"比"生成"好学

| 维度 | 生成（写文章） | 分类（打标签） |
|---|---|---|
| 输出空间 | 无限 | 3-5 个值 |
| 对错 | 主观 | **可以算准确率** |
| 验收 | "我觉得还行" | **85% 就是 85%** |
| 优化方向 | 说不清 | **看错分样本** |

**这就是为什么"分类/提取"是接活的第一站：它能被量化。**

## 0.3 今天的两个任务

```text
任务一：分类（classification）  → 这条评论是正面/中性/负面
任务二：提取（extraction）      → 从评论里抽出主题、关键词、是否提竞品
```

**两个任务合并成一次调用。** 因为调两次要花两份钱、等两份时间。

| 文件 | 位置（都在第 36 节的 `prompt-lab` 里） | 内容 |

| `src/dataset.js` | `src/` | 12 条带人工标注的评论 |

# 第 1 步：造一份带标准答案的测试集（20 分钟）

## 1.1 为什么先造测试集

**因为你会想"先跑几条看看效果"。**

**看完之后你会说"好像挺准的"——然后交付一个 60% 准确率的东西。**

**正确顺序：**

```text
先有标准答案 → 再跑 → 算准确率 → 才知道好不好
```

**这和上一节的"先写检查函数"是同一个道理。**

## 1.2 新建 `src/dataset.js`

**自己敲。12 条，其中四条是"难例"，我在注释里标了：**

```javascript
export const REVIEWS = [

  { id: 7, text: "产品质量没得说，就是包装烂得离谱，客服处理也慢。", label: "负面" },
```

## 1.3 标注规则必须自己先定清楚

**在动手之前，写下你的判定标准（写进 `NOTES.md`）：**

```text
正面：明确表达满意、推荐、复购意愿，或问题已解决且态度认可
负面：明确表达不满、损失、劝阻他人购买
中性：询问、陈述事实、未表达情绪

混合情绪如何定：看"用户的最终态度"，不看有没有出现负面词
反讽如何定：看字面与实际语义的相反方向
只有表情：按表情的情绪定
```

**这四条一写，你会发现第 7 条、第 9 条、第 10 条都是"边界案例"。**

**边界案例才是准确率的真正考验。** 容易的那些不算。

## 1.4 一个残酷的准备

**12 条太少，算出来的准确率不说明问题。** 但作为练习够用。

**真实项目里：**

```text
最少 100 条人工标注      才能看出趋势
300-500 条              才能对客户说"准确率 88%"
```

**你现在这 12 条的作用是：让你学会"怎么算准确率"，而不是"证明模型准"。**

# 第 2 步：写 schema（10 分钟）

**在 `src/schemas.js` 里加：**

```javascript
export const REVIEW_SCHEMA = {
  fields: {
    sentiment: { type: "string", enum: ["正面", "中性", "负面"] },
    topics: { type: "array" },
    keywords: { type: "array" },
    mentionsCompetitor: { type: "boolean" },
    reason: { type: "string" },
  },
  required: ["sentiment", "topics", "keywords", "mentionsCompetitor", "reason"],
};
```

**四个字段的设计意图：**

| 字段 | 类型 | 为什么这么设计 |
|---|---|---|
| `sentiment` | 枚举三选一 | 封闭集合，错了一眼能看出来 |
| `topics` | 数组 | 一条评论可能抱怨"物流"和"客服"两件事 |
| `keywords` | 数组 | 后面用来做词云、做搜索 |
| `mentionsCompetitor` | 布尔 | **客户最爱问"顾客有没有提别家"** |
| `reason` | 字符串 | **可解释性：让你能看出它为什么这么判** |

## 2.1 为什么留 `reason`

**因为它能救你。**

```text
判错了 + 有 reason  → 你能看出它理解错了哪一句 → 改提示词有方向
判错了 + 没 reason  → 你只知道它错了
```

**限制长度：`reason` 不超过 30 字。** 不然它会写一篇小作文，白花钱。

**要写进提示词，不是写进 schema。** schema 只定义类型。

## 2.2 数组类型的校验要注意

**你上一节的 `checkShape` 已经支持 `array` 了（`typeOf` 里判断了 `Array.isArray`）。**

**但它不检查"数组里的元素是不是字符串"。**

**这一段后面练习会让你补上。** 先记住这个缺口：**现在它只能保证"是个数组"，不能保证"是个字符串数组"。**

## 3.2 `reviewV2`：给判定标准 + 边界例子

```javascript
  reviewV2: {
    id: "review-classify",
    version: "v2-rubric",
    system: `你是电商评论分析器。只输出一个 JSON 对象，不输出任何其他文字。

字段定义：
- sentiment：只能是 "正面"、"中性"、"负面" 之一
- topics：字符串数组，从 ["质量","物流","客服","价格","包装","发票","其他"] 中选择，最多 3 个
- keywords：字符串数组，从评论原文中截取 1-3 个关键词，不得自己造词
- mentionsCompetitor：布尔值，评论中提到其他品牌/店铺时为 true
- reason：字符串，不超过 30 字，说明 sentiment 的判定理由

sentiment 判定标准：
- 正面：明确表达满意、推荐、复购意愿；或提出问题但已解决且表达认可
- 负面：明确表达不满、损失、劝阻他人；或问题未解决且表达失望
- 中性：询问、陈述事实、未表达情绪

边界规则（必须遵守）：
1. 反讽按真实语义判，不按字面。例如「等半个月，太高效了」判负面。
2. 同时出现正负评价时，以用户的最终态度为准。例如「产品好但包装烂，客服也慢」判负面。
3. 只有表情符号时，按表情情绪判。😍😍 判正面。
4. 出现负面词但整体称赞时，按整体态度判。例如「便宜得可怕，结果比大牌好用」判正面。
5. 询问类（含「吗」「能否」「是否」且无情绪表达）判中性。

规则：
- 不要输出 markdown 代码块，不要加解释。
- 字段名必须完全一致，不要翻译成中文，不要增加字段。
- 评论过短或无法判断时，sentiment 填 "中性"，reason 写「信息不足」。`,
  },
```

## 3.3 逐块讲清关键设计

### 设计一：`topics` 给了封闭清单

**为什么不在提示词里说"提取主题"：**

```text
"提取主题"      → 每条的主题词都不一样：物流慢/快递/配送/发货速度
给固定 7 个选项 → 全是"物流"，你才能统计"60% 的差评在骂物流"
```

**这就是分类和描述的区别。** 客户要的是统计，不是作文。

### 设计二：`keywords` 要求"从原文截取"

**否则模型会给你"用户体验""产品质量"这种总结词 —— 漂亮，但没用。**

**词云要的是原词，不是它概括的类目。**

### 设计三：边界规则 5 条，条条针对难例

**回看你的数据集：**

| 规则 | 对应哪条评论 |
|---|---|
| 1 反讽 | id 6 |
| 2 最终态度 | id 7、id 10 |
| 3 只有表情 | id 8 |
| 4 负面词但称赞 | id 9 |
| 5 询问判中性 | id 3 |

**这五条不是拍脑袋写的。是从测试集里反推出来的。**

**正确顺序是：**

```text
先跑 v1 → 看错哪几条 → 针对错的写规则 → 再跑
```

**你现在直接看到 v2，是因为我把过程压缩了。实际做项目时必须走一遍"看错样本 → 写规则"。**

### 设计四：`reason` 限 30 字

**不限的话，它会写 100 字，每条评论多花 3 倍 token。**

**3000 条评论，就是 3 倍的钱。** 这不是小事。

# 第 4 步：跑批 + 算准确率（30 分钟）

## 4.1 新建 `experiments/e05-classify.js`

```javascript
import { askJson } from "../src/ask-json.js";
import { PROMPTS } from "../src/prompts.js";
import { REVIEW_SCHEMA } from "../src/schemas.js";
import { REVIEWS } from "../src/dataset.js";

const LABELS = ["正面", "中性", "负面"];

const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

const classifyOne = async (text, system, { retries = 1 } = {}) => {
  const messages = [
    { role: "system", content: system },
    { role: "user", content: `评论：${text}` },
  ];

  const result = await askJson(messages, REVIEW_SCHEMA, {
    temperature: 0.2,
    maxTokens: 500,
    retry: retries,
  });

  return result.data;
};

const evaluate = async (label, system) => {
  const rows = [];
  const matrix = {};
  LABELS.forEach((actual) => {
    matrix[actual] = {};
    LABELS.forEach((predicted) => {
      matrix[actual][predicted] = 0;
    });
  });

  let correct = 0;
  let failed = 0;

  for (const review of REVIEWS) {
    try {
      const data = await classifyOne(review.text, system);
      const predicted = data.sentiment;
      const ok = predicted === review.label;

      if (ok) correct += 1;
      if (matrix[review.label] && matrix[review.label][predicted] !== undefined) {
        matrix[review.label][predicted] += 1;
      }

      rows.push({
        id: review.id,
        actual: review.label,
        predicted,
        ok,
        reason: data.reason,
        topics: (data.topics || []).join("/"),
      });
    } catch (error) {
      failed += 1;
      rows.push({ id: review.id, actual: review.label, predicted: "（失败）", ok: false, reason: error.message });
    }

    await sleep(500);
  }

  console.log(`\n===== ${label} =====`);
  console.table(rows);

  const total = REVIEWS.length;
  const rate = (((correct / total) * 100).toFixed(1));

  console.log(`准确率：${correct}/${total} = ${rate}%　调用失败：${failed}`);

  console.log("\n混淆矩阵（行=人工标注，列=模型判断）：");
  const header = ["实际\\预测", ...LABELS].join(" | ");
  console.log(header);
  LABELS.forEach((actual) => {
    const line = [actual, ...LABELS.map((predicted) => matrix[actual][predicted])].join(" | ");
    console.log(line);
  });

  return { label, correct, total, rate, rows, matrix };
};

const main = async () => {
  const results = [];

  results.push(await evaluate("v1 粗版", PROMPTS.reviewV1.system));
  results.push(await evaluate("v2 带判定标准", PROMPTS.reviewV2.system));

  console.log("\n===== 对比 =====");
  results.forEach((item) => {
    const wrongIds = item.rows.filter((row) => !row.ok).map((row) => row.id);
    console.log(`${item.label}：${item.rate}%　错在第 ${wrongIds.join("、") || "无"} 条`);
  });
};

main().catch((error) => {
  console.error("跑挂了：", error.userMessage || error.message);
  process.exitCode = 1;
});
```

### 先看准确率

### 再看混淆矩阵

```text
实际\预测 | 正面 | 中性 | 负面
正面      |  4  |  0  |  0
中性      |  0  |  3  |  0
负面      |  0  |  1  |  4
```

**读法：**

```text
对角线上的数字 = 判对的
非对角线上的 = 判错的，"行是真相，列是它的判断"
```

**上面这个矩阵告诉你：它把 1 条负面判成了中性。**

### 最后看错分样本

**这是最有价值的一步。** 每条错分都要回答：

```text

③ 是模型能力不足？（写清了它还是做不到）
```

**三种原因的修法完全不同：**

| 原因 | 修法 |
|---|---|
| 标准不清楚 | 改 `NOTES.md` 里的判定规则，可能要重标 |
| 提示词没写 | 加一条边界规则，重跑 |
| 能力不足 | 接受这个错，或换更大的模型 |

**第三种要认。** 不是所有问题都能靠提示词解决。

# 第 5 步：提取任务——比分类更容易出错（20 分钟）

## 5.1 提取和分类的区别

```text
分类：从固定选项里挑一个     → 错了一眼看出来
提取：从原文里抠出内容       → 错得"看起来很像对的"
```

**例子：提取"金额"**

```text
原文：合同总价 48000 元，预付 30%，余款 60 天内结清
正确提取：48000
常见错误：48000 / 14400（算了预付款）/ 48000 和 14400 都塞进去
```

**第二种错误最坑：你收到一个数字，看起来正常，实际上是预付款。**

## 5.2 提取的三条原则

### 原则一：要求"从原文截取"，不许总结

```text
❌ "关键词：用户体验差"
✅ "关键词：漏水"（原文里有）
```

**理由：** 总结词无法回溯。**出问题时你没法核对。**

### 原则二：区间和单位必须结构化

```text
❌ "金额：48000 元左右，可能含税"
✅ "amount": 48000, "currency": "CNY", "taxIncluded": null
```

**`null` 表示"原文没说"，这是有效信息。**

### 原则三：数量不定的字段要限个数

```text
topics 最多 3 个
keywords 最多 3 个
```

**不限的话，它会给你 8 个，你还得写代码截断。**

## 5.3 练习：把"主题"用起来做统计

**在 `e05-classify.js` 末尾加一段统计（用 v2 的结果）：**

```javascript
const topicCount = new Map();

results[1].rows.forEach((row) => {
  (row.topics || "").split("/").filter(Boolean).forEach((topic) => {
    topicCount.set(topic, (topicCount.get(topic) || 0) + 1);
  });
});

console.log("\n主题分布：");
[...topicCount.entries()]
  .sort((a, b) => b[1] - a[1])
  .forEach(([topic, count]) => console.log(`  ${topic}：${count} 条`));
```

**这段输出就是客户要的那张图：**

```text
物流：7 条
质量：4 条
客服：3 条
```

**从"3000 条评论"到"物流是最大问题"，这就是你卖的东西。**

**注意：** 12 条样本的主题分布没有意义，但代码逻辑是对的。**真实项目里换成 3000 条，这张表就值钱了。**

# 第 6 步：五个必须知道的坑（15 分钟）

## 坑 1：模型偏爱"中性"

**不确定的时候，模型倾向选中间那个。**

**后果：你的差评被大量判成中性，客户看到的"负面率"是假的。**

**怎么发现：**

```text
看混淆矩阵，如果"中性"那一列数字特别大 → 中招了
```

**怎么修：**

```text
① 在提示词里写"只有在明确是询问或陈述时才判中性，不确定时按情绪倾向判"
② 或者去掉"中性"这个选项，只分正/负，让它在两个里选
```

**第二种更狠，但更准。取决于业务要不要"中性"这一类。**

## 坑 2：类别不平衡

**真实数据里，好评可能是 90%。**

**如果模型全判"正面"，准确率也有 90%——但完全没用。**

**所以要看的不是准确率，是"负面类的召回率"：**

```text
负面召回率 = 判对的负面数 / 实际负面总数
```

**上面那个混淆矩阵例子里：负面 5 条，判对 4 条 → 召回率 80%。**

**这才是客户关心的数字："我的差评你有没有漏掉"。**

## 坑 3：文本被截断

**评论超过 2000 字，你只塞了前 500 字，后半段的抱怨它看不到。**

**修法：**

```text
① 明确截断并告知："（评论过长，以下为前 500 字）"
② 或者对长文本先摘要再分类（多一次调用）
```

**别忘了第 37 节的教训：切了要告诉它。**

## 坑 4：`topics` 不在枚举里

**你给了 7 个选项，它给你"物流速度慢"。**

**这不是它的错，是它想更精确。**

**两种处理：**

```text
严格：不在枚举里就判失败，重试
宽松：映射到最近的枚举（"物流速度慢" → "物流"）
```

**今天用严格。** 因为统计需要干净的类目。

**但要在提示词里写清"必须从下列 7 个中选，不得新增"。** 你 v2 里已经写了，很好。

## 坑 5：把 `reason` 当证据

**`reason` 是它给出的解释，不是它真实的推理过程。**

**它可能先"感觉"这条是负面，再编一个理由。**

**所以：**

```text
✅ 用 reason 帮你定位问题
❌ 用 reason 作为"它想清楚了"的证据
```

**判断它是否真懂，看准确率，不看理由写得多漂亮。**

# 附：常见问题速查

| 情况 | 原因 | 怎么做 |
|---|---|---|
| 准确率算出来 > 100% | 分母写错 | `correct / 总数`，别除以判对数 |
| 全是"中性" | 模型回避判断 | 加"不确定按情绪倾向判"，或去掉中性类 |
| `topics` 出现新类目 | 枚举约束不够硬 | 提示词写"不得新增"，严格校验 |
| `keywords` 是总结词 | 没要求从原文截取 | 加"必须是原文中出现的词" |
| 跑一半报 429 | 发太快 | 每次之间 `sleep(500)` |
| 每次结果不一样 | `temperature` 高 | 分类任务用 0.1-0.2 |
| `reason` 写了一大段 | 没限字数 | 提示词写"不超过 30 字" |
| 12 条准确率好看，真实数据崩 | 样本太容易 | 加难例，扩到 100 条以上 |
| 混淆矩阵打歪 | 控制台等宽字体问题 | 换成自己拼字符串打印 |
