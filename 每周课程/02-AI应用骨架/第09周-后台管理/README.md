# 第09周 · 后台管理 · 第57—63节课

## 客户要能自己改东西，你才不用当免费客服

---

## 这一周的目标

第 8 周你有了真实用户、真实权限。这一周做一个**后台**，让管理员能自己改数据。

六件事：

1. **后台页面结构** —— 侧栏 + 列表页 + 表单页，不用框架怎么组织；
2. **列表** —— 表格、空状态、加载状态、时间显示；
3. **搜索与筛选** —— 多条件组合、URL 里带状态、输入防抖；
4. **分页** —— offset 翻页的坑、总数怎么算、页码越界；
5. **增删改** —— 表单校验、软删除、乐观锁冲突；
6. **操作日志** —— 谁在什么时候改了什么，从什么改成了什么。

## 为什么排在这一周

**因为这是客户提得最多的需求，而且它决定你能不能只做一个项目。**

```text
没有后台：
客户想改一个价格 → 微信找你 → 你改代码 → 部署 → 回复他
一次 30 分钟，一个月 10 次 = 5 小时

有后台：
客户自己改 → 30 秒
```

**5 小时 vs 30 秒。** 这就是"能不能同时服务 10 个客户"的分界线。

**而且后台能加价：**

```text
"我给你一个后台，你能自己改商品、自己看订单"
→ 报价加 2000-5000
```

## 为什么不用现成的 admin 框架

**明确不用：**

```text
❌ AdminJS / React-Admin / Ant Design Pro —— 这一周要你亲手写一遍
❌ Vue / React —— 第 27 周才讲前端进阶，现在用原生 JS
❌ Element UI 等组件库 —— 一个表格组件 200KB，你只需要 40 行
```

**理由：**

```text
① 现成框架你要先学它，学习成本比手写高
② 客户的需求永远有 20% 是框架不支持的，那时你得改源码
③ 手写过一遍，你才知道"分页为什么这么设计"
```

**这一周只有原生 JS + 手写 CSS + `fetch`。**

## 这一周必须建立的五个认知

### 认知一：后台的每一个接口，都必须能回答"谁在操作"

**因为后台能改数据，而改数据要有痕迹。**

```text
❌ app.patch("/api/admin/users/:id")                 // 不知道是谁改的
✅ app.patch("/api/admin/users/:id", requireAuth, requireRole("admin"), ...)
   + audit.log({ actorId: req.user.id, action: "update", ... })
```

**第 63 节的审计日志，是从第 57 节就开始要求的，不是最后加上去的。**

**为什么：** 出事后（客户说"我的商品被人改了"），你能查出来是谁、什么时候、从什么改成什么。

**没有这个，你只能对客户说"我不知道"。**

### 认知二：分页必须在服务端

**新手写法：**

```javascript
const allUsers = db.prepare("SELECT * FROM users").all();   // 10 万条
res.json({ users: allUsers.slice(offset, offset + 20) });   // 后端切
```

**为什么错：**

```text
① 10 万条记录全读进内存 → 慢、占内存
② 网络传输 10 万条 → 几十 MB
③ 用户能在 F12 里看到你的全部数据
```

**正确：`LIMIT ? OFFSET ?` 交给数据库。**

**但 offset 分页有坑（第 60 节讲），要理解它什么时候不能用。**

### 认知三：URL 是后台的状态容器

**筛选条件、页码、排序，全部放进 URL。**

```text
/admin/users.html?q=alice&role=admin&page=2&sort=created_at
```

**为什么：**

```text
① 刷新页面状态不丢
② 能把链接发给同事（"你看这个用户"）
③ 浏览器前进/后退能用
④ 收藏夹能存
```

**这是"后台好不好用"的第一分水岭。** 用 `sessionStorage` 存筛选条件的后台，刷新一下就回到第一页，很难用。

### 认知四：前端隐藏按钮不是权限，后端才是

**这条第 8 周说过。在后台里它会再犯一次。**

```javascript
// 前端：非管理员不显示删除按钮
if (currentUser.role === "admin") showDeleteButton();
```

**F12 改掉判断，或者直接 curl。**

**所以：每个 `/api/admin/*` 接口都挂 `requireRole("admin")`，一个都不能漏。**

**前端的隐藏只是"别让用户看见他点不了的东西"，不是安全。**

### 认知五：删除要做成"软删除"，除非你想不到后悔

**`DELETE FROM users WHERE id = ?` 是真删。**

**客户点错了，数据没了，你只能从备份恢复（如果有备份）。**

**软删除：**

```sql
UPDATE users SET deleted_at = '...' WHERE id = ?
```

**所有查询加 `AND deleted_at IS NULL`。**

**代价：每个查询都要记得加。** 这个"记得"很容易忘（第 53 节讲过同一个坑）。

**折中方案：**

```text
users / items 表：软删除（误删代价高）
logs 表：真删（本来就是记录，删了不心疼）
```

## 三条铁律

```text
一、所有 /api/admin/* 接口，必须同时挂 requireAuth 和 requireRole("admin")。
   只挂一个，就是漏洞。

二、任何写操作（增/改/删），必须写审计日志。
   记 who / when / what / before / after。

三、列表接口不发全量数据。
   必须带 limit，默认 20，上限 100。
```

## 这一周最容易卡住的六个地方

### 第一处：分页总数用了 `COUNT(*)` 但没加筛选条件

```javascript
const total = db.prepare("SELECT COUNT(*) FROM users").get().total;              // 5000
const rows = db.prepare("SELECT * FROM users WHERE role = ? LIMIT 20").all("admin");  // 3 条
```

**症状：前端显示"共 5000 条，250 页"，但点第 2 页就没数据了。**

**修法：`COUNT` 和 `SELECT` 用完全相同的 `WHERE`。**

**这是分页最经典的 bug。**

### 第二处：`LIMIT ?` 传了字符串

```javascript
db.prepare("SELECT * FROM users LIMIT ? OFFSET ?").all(req.query.limit, req.query.offset);
```

**`req.query.limit` 是字符串 `"20"`。**

**SQLite 会容忍（隐式转换），但 `Number("")` 是 `NaN`，用户不传就是 `LIMIT NaN` → 报错或返回 0 条。**

**必须 `Number()` + 校验 + 兜底默认值。**

### 第三处：搜索关键词没转义 `%` 和 `_`

```javascript
db.prepare("SELECT * FROM users WHERE email LIKE ?").all(`%${q}%`);
```

**用户输入 `%` → 匹配全部（等于没筛）。**

**输入 `_` → 匹配任意单字符。**

**要转义：**

```javascript
const escaped = q.replace(/[%_\\]/g, (char) => `\\${char}`);
```

**然后 `LIKE ? ESCAPE '\'`。**

### 第四处：时间显示成 ISO 字符串

```text
2026-11-16T09:31:12.482Z
```

**用户看不懂。而且这是 UTC，比北京时间早 8 小时。**

**必须格式化：`2026-11-16 17:31`。**

**第 44 节讲过 UTC 的坑，后台里会再踩一次。**

### 第五处：编辑表单提交了未改动的字段

**现象：两个管理员同时编辑同一用户，后保存的覆盖了前一个的修改，而且看不出冲突。**

**这叫"丢失更新"（lost update）。**

**修法：乐观锁（第 61 节）。**

```text
表单里带 updated_at
保存时检查：WHERE id = ? AND updated_at = ?
影响行数为 0 → 说明别人改过了 → 提示"数据已变更，请刷新"
```

### 第六处：软删除后"查不到了"但"唯一约束还在"

**场景：**

```text
用户 alice@example.com 被软删除
她又来注册 → UNIQUE 冲突 → 注册失败
```

**修法（三选一）：**

```text
A. 唯一索引改成部分索引 UNIQUE(email) WHERE deleted_at IS NULL（SQLite 支持）
B. 软删除时把 email 改成 alice@example.com.deleted.1699999999
C. 注册时发现是软删除的，直接恢复它
```

**A 最干净。这一周用 A。**
