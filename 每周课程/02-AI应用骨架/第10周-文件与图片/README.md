# 第10周 · 文件与图片 · 第64—70节课

## 客户传一张 10MB 手机照片，你的页面就卡死了

---

## 这一周的目标

第 9 周你管理数据。这一周管理**文件**。

六件事：

1. **上传文件** —— 两种提交方式、`multipart/form-data` 到底是什么；
2. **限制类型和大小** —— 前端能改，所以服务端必须自己验；
3. **存文件信息** —— 文件放磁盘，元信息放数据库，怎么配套；
4. **压缩图片** —— 10MB 手机照压到 300KB，画质还能看；
5. **缩略图** —— 列表里不加载原图，加载 60 倍小的缩略图；
6. **在线预览** —— PDF 和图片不用下载就能看。

## 为什么排在这一周

**因为这是"看起来简单、做起来全是坑"的典型。**

```text
新手以为：
<input type="file" /> → 用户选 → 上传到服务器 → 存起来 → 完事
```

**实际会遇到：**

```text
手机拍的照片是 12MB，iPhone 的是 HEIC 格式（浏览器不显示）
用户传了一个改了扩展名的 .exe
用户传了 100 个文件，把你的磁盘塞满
文件名里有中文和空格，URL 打不开
用户传了 10000×8000 的图，服务器内存爆掉
同名的两个文件互相覆盖
用户删了记录，磁盘上的文件还在
```

**这一周把这些全处理掉。**

**而且这一周有一个"真的能省钱"的结论：**

> **原图 12MB，压缩后 300KB，缩略图 8KB。**
>
> **列表页加载 20 张图：原图 240MB（必崩），缩略图 160KB。**

**40 倍的差距。**

**明确不用：**


**用什么：**

| 需求 | 工具 | 为什么 |
|---|---|---|
| 解析 multipart | **手写**（第 64 节） | 知道格式才不会被库坑 |

| 图片处理 | `sharp` **或** 纯 JS 降级 | 见下方说明 |
| 缩略图 | 同一个库 | — |
| PDF 预览 | 浏览器原生 `<iframe>` | 0 依赖 |

**关于图片处理库，说清楚：**

```text
sharp：快（C++ 底层），但 npm install 可能失败（需要预编译包）
jimp：纯 JS，一定能装，但慢 5-10 倍
```

**这一周的做法：**

**第 67 节先试 `sharp`，装不上就换 `jimp`。**

**代码结构设计成"可替换"，让你体会"为什么要把第三方库包一层"。**

## 这一周必须建立的五个认知

### 认知一：`multipart/form-data` 不是"一种编码"，是一份协议

**你会手写解析器，因为：**

```text
理解"边界（boundary）怎么切分文件"
理解"为什么文件流不能一次读完"
理解"为什么文件名要单独处理"
```

**这三件事，用库的时候你会忽略，出问题时你会束手无策。**

### 认知二：任何来自客户端的"类型"都不可信

```text
Content-Type: image/jpeg    ← 随便写
文件名：photo.jpg           ← 随便改
扩展名：.jpg                ← 随便改
```

**唯一可信的是文件头部的"魔数"（magic number）。**

**`FF D8 FF` 是 JPEG，`89 50 4E 47` 是 PNG，`25 50 44 46` 是 PDF。**

**第 65 节会写一个真正的魔数检测器，并亲手用"改了扩展名的 exe"去试探它。**

### 认知三：文件放磁盘，元信息放数据库，两者必须配套

**为什么不全放数据库（BLOB）：**

```text
① 数据库备份会变得巨大（12MB 的图 × 1000 张 = 12GB）
② 读 BLOB 会占内存
③ 数据库适合"小、结构化"的数据
```

**为什么不全放磁盘（不用数据库）：**

```text
① 无法按"用户"查文件
② 无法记录"谁在什么时候传的"
③ 文件名冲突、权限判断全要自己做
```

**正确：**

```text
磁盘：文件内容（originals/、thumbs/）
数据库：id、user_id、原文件名、存储名、大小、MIME、尺寸、缩略图路径、创建时间
```

**两者用 `storage_key` 关联。**

### 认知四：压缩不是"越小越好"，是"够用就行"

**一个具体的取舍：**

```text
原图：12MB（4032×3024，手机原片）
方案 A：质量 90，2400px → 1.2MB
方案 B：质量 80，1600px → 380KB
方案 C：质量 60，1200px → 150KB（看得见糊）
```

**详情页展示用 B。列表缩略图用更小的。**

**"够用"的标准：在目标尺寸下看不出模糊。**

**第 67 节会让你自己对比这三种，用眼睛判断。**

### 认知五：删除要删两处，而且要能容忍"一处失败"

**删文件时：**

```text
① 删数据库记录
② 删磁盘文件
```

**顺序和失败处理：**

```text
先删数据库，再删磁盘：
  磁盘删除失败 → 孤儿文件（占空间，不可见）→ 可以定时清理
先删磁盘，再删数据库：
  数据库删除失败 → 记录在，文件没了 → 用户点开报 404
```

**选前者。因为"孤儿文件"可以扫描清理，"死记录"是用户可见的故障。**

**这一周同时做一个"孤儿清理"脚本。**

## 三条铁律

```text
一、任何上传，服务端必须自己校验类型和大小。
   前端的 accept / maxlength 一律当"提示"，不当"限制"。

二、上传的文件永远不要放在 public/ 里。
   一旦放进静态目录，就等于"任何人知道 URL 就能下载"。

三、所有用户提供的文件名，都要重命名后存储。
   原名只存数据库。否则会碰上路径穿越、特殊字符、同名覆盖。
```

## 这一周最容易卡住的六个地方

### 第一处：`req.body` 里拿不到文件

**`express.json()` 只处理 `application/json`。**

**文件上传是 `multipart/form-data`，`express.json()` 会跳过它，`req.body` 是空的。**

**必须用专门的解析器（这一周手写 + busboy）。**

**症状：`req.files` 是 `undefined`，`req.body` 是 `{}`。**

### 第二处：文件存了但内容是空的 / 只有几 KB

**原因：`busboy` 的 `file` 事件里没有消费流。**

```javascript
busboy.on("file", (name, file, info) => {
  // 只记录了 info，没有读 file
  // → 流没人消费 → 数据被丢弃 或 请求卡住
});
```

**必须 `file.pipe(写流)` 或者手动 `file.on("data")`。**

### 第三处：`413 Payload Too Large`

**两层限制，任何一层都可能触发：**

```text
express.json({ limit: "64kb" })       第 50 节设的
服务器/代理的 body 上限（Nginx 默认 1MB）
```

**上传接口要单独放宽，不能全局放宽。**

**第 64 节会示范"只给上传路由设大限制"。**

### 第四处：中文文件名变乱码

**`multipart` 的 `filename` 可能是 RFC 2047 编码的：**

```text
=?UTF-8?B?5L2g5aW9LmpwZw==?=
```

**要解码才能得到 `你好.jpg`。**

**或者 `filename*=UTF-8''%E4%BD%A0%E5%A5%BD.jpg`（RFC 5987）。**

**第 64 节会给一个 `parseFilename` 函数。**

### 第五处：`sharp` 装不上

**`npm install sharp` 报错，通常是：**

```text
① 网络问题（要下预编译二进制）
② Node 版本太新，没有对应的预编译包
③ Windows 缺 Visual C++ 运行库
```

**这一周的做法：**

**`src/image.js` 里 try/catch import，失败就降级到 `jimp`，两个都失败就跳过压缩（只存原图）。**

**这样你的代码在任何环境都能跑，只是"有没有压缩"的区别。**

### 第六处：大图导致内存爆

**`sharp` 处理 10000×8000 的图，内存占用可能 1-2GB。**

**防护：**

```text
① 先读图片头部（几十字节）拿到尺寸
② 尺寸超过 12000×12000 直接拒
③ sharp 设置 limitInputPixels
```

**不防的话，一个用户传一张巨图就能把你的服务打挂。**
