# 第07周 · 成本与流式 · 第43—49节课

## 让它像产品，不让它烧钱

---

## 这一周的目标

第 6 周你解决了"输出对不对"。这一周解决"要花多少、快不快、能不能停"。

六件事：

1. **算清一次调用多少钱** —— 看懂 input/output 分开计价，能把 token 换算成人民币；
2. **把每次调用记下来** —— 记账文件、字段设计、按天聚合，第一次答出"这功能一个月多少钱"；
3. **管住长度** —— `max_tokens`、上下文裁剪、截断的处理，不让一条超长输入吃掉一天预算；
4. **做缓存** —— 命中率、过期时间、什么能缓存什么绝对不能；
5. **做流式** —— 从"转圈 8 秒"到"0.6 秒出第一个字"，含首字延迟的概念；
6. **能中断、能超时** —— 用户点停止要真的停，上游超时要真的断，钱不能白花。

## 为什么排在这一周

第 6 周结束时，你的应用"答得对"，但客户一用就会提三个问题：

```text
"怎么点半天没反应？"          → 没有流式
"这功能一个月要花我多少钱？"   → 你没有记账，答不出来
"用户乱点会不会烧爆？"        → 没有长度限制、没有中断
```

**这三个问题答不上来，你的报价就上不去。**

**反过来，能答上来，你就可以按"年度服务费"卖，而不是按"一个页面 3000 块"卖。**

**这是你从"做网页的"变成"做系统的"的分水岭。**

## 这一周必须用真模型算钱，用假模型调结构

```text
算钱（价格、token 数、成本）  → 必须看真实 usage，假模型给不出真 token
流式（字节怎么来、怎么断）    → 假模型更好用，可控延迟、可控故障
缓存（命中率、TTL）          → 假模型足够，还省钱
```

**所以这一周的假模型要升级：它得真的分块吐字、真的返回 usage、能听指令故障。**

**第 43 节会把这份假模型完整给你，不用自己编。**

**一条必须知道的现实：**

> **不同模型的中转价差可以是 30 倍。** 便宜模型 0.001 元/千 token，贵的 0.03 元/千 token。
>
> **这一周你要建立的不是"某个模型多少钱"（这个每月都变），是"怎么算、怎么记、怎么控"。**
>
> **价格表要能改，不能写死在代码里。**

## 这一周的五个认知

### 认知一：成本是 input 和 output 分开算的，而且差价很大

```text
输入 1000 token 可能 0.001 元
输出 1000 token 可能 0.004 元
```

**为什么输出更贵：** 输出是一个字一个字生成的，每个字都要跑一次完整的前向计算；输入可以并行处理。

**后果：**

```text
"让它详细点说"   → 直接乘 4 倍
"塞 2 万字资料"  → 输入便宜，但会挤掉输出空间
```

**优化方向从此不同：少让它说，比少给它看更省钱。**

### 认知二：不记账，你就是在猜

**"大概几毛钱吧"这种回答，客户一听就知道你没做过生产系统。**

**记账之后你能说出：**

```text
上周 3127 次调用，790 万 token，成本 41.6 元
平均每次 0.0133 元
最贵的单次 0.42 元（有人粘了一篇长文）
```

**这才叫"我管得住这个系统"。**

### 认知三：流式不是"体验优化"，是"能不能用"的问题

**同样 8 秒：**

```text
不流式 → 用户看到转圈 8 秒，20% 的人在第 4 秒就关了
流式   → 0.6 秒出第一个字，用户开始读，读完正好 8 秒
```

**用户感知的不是"总时长"，是"多久有反应"。**

**这个指标叫 TTFT（Time To First Token，首字延迟）。**

### 认知四：缓存能省钱，但缓存错了会出事故

**能缓存的：**

```text
同一段文本的翻译
同一份合同的信息提取
同一批固定问题的回答
```

**绝对不能缓存的：**

```text
带用户隐私的问答（A 用户的答案给 B 用户看到 = 数据泄漏）
实时信息（今天股价、当前库存）
带鉴权的请求（缓存键里没用户 id，必然串号）
```

**判据：两个不同用户，看到同一个答案会不会有问题？会，就不能缓存。**

### 认知五：中断不是"前端不显示了"，是"上游要真的停"

**新手做法：**

```text
用户点停止 → 前端停止渲染 → 后端继续跑完 → 钱照扣
```

**正确做法：**

```text
用户点停止 → 前端 abort → 后端收到连接关闭 → 后端 abort 上游 → 上游停止生成
```

**这条链路任何一环断了，你都在为没人看的内容付钱。**

## 三条铁律

```text
一、价格表必须是配置，不能写死在代码里。
   模型改名、降价、涨价，你要能在 1 分钟内改完。

二、任何对外的模型接口，必须有 max_tokens 上限。
   没有上限的接口，等于把信用卡交给陌生人。

三、带用户数据的内容，缓存键里必须有用户标识。
   少一个字段，就是一次数据泄漏。
```

## 这一周最容易卡住的六个地方

### 第一处：`usage` 是 `undefined`

**不是所有中转都返回 `usage`；流式默认也不返回。**

**处理：**

```text
非流式 → 没有 usage 就用"字符数 / 1.6"估算，并标记 estimated: true
流式   → 请求时加 stream_options: { include_usage: true }，最后一个 chunk 才有 usage
```

**这个字段不处理，你的报表会有一半是空的。**

### 第二处：SSE 被缓冲，前端一个字都看不到

**两个地方会缓冲：**

```text
① 反向代理（Nginx）→ 加 X-Accel-Buffering: no
② Express 压缩中间件 → 对 text/event-stream 关掉 compression
```

**现象很典型：等了 8 秒，所有字一次性出现。** 那就是全被缓冲了。

### 第三处：`fetch` 读流不会"一段一段来"

**`await response.text()` 会等全部收完。**

**必须用 `response.body.getReader()`，或者 `for await (const chunk of response.body)`。**

**这一步不换写法，流式等于没做。**

### 第四处：缓存键漏了参数

**只哈希了 `messages`，没哈希 `model` 和 `temperature`。**

**后果：改了模型，返回的还是旧模型的答案。**

**缓存键必须包含"影响输出的所有输入"。**

### 第五处：`max_tokens` 太小，答案被腰斩

**`finish_reason: "length"` 就是被截断的信号。**

**不处理这个字段，用户会看到半句话，还以为是模型笨。**

### 第六处：点了停止，账单还在涨

**前端 abort 了，后端没监听 `req.on("close")`，上游请求还在跑。**

**这一条最贵。** 第 48 节专门治它。

## 周末的验收

- [ ] 我能算出一次具体调用的钱（不是"大概"）
- [ ] 我的 `usage.jsonl` 里有真实记录，`report.js` 能按天汇总
- [ ] 我知道这个应用的"每次对话成本"是多少
- [ ] 我实测过 `max_tokens` 太小会怎样（看到 `finish_reason: length`）
- [ ] 缓存命中率有数字，成本降幅有数字
- [ ] 流式接口能让第一个字在 1 秒内出现
- [ ] 点停止之后，终端里没有"后来才完成的调用"

> **倒数第二条才是真标准。**
>
> 点停止后如果日志里还有一次完整的调用记录，说明你只停了前端。**这一条不解决，你的产品在真实用户手里会一直漏钱。**
