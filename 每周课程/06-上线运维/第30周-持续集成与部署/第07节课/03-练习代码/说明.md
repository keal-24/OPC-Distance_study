## `pipeline.yml` 的六道关

```text
test       跑单测，不过就停
build      构建镜像，输出 sha 和 tag
deploy     通过 SSH 去服务器拉新镜像，输出 current_sha
smoke      查 /health + 查版本号是不是这次的 sha
rollback   if: failure()，读 .previous_sha 退回上一版
notify     if: always()，把每个 job 的结果发出去
```

**`smoke` 里 `curl` 必须带 `-f`。** 不带 `-f`，HTTP 500 也会被当成成功，`smoke` 永远通过，回滚永远不会触发——这是这一节最贵的坑。

## `rollback` 为什么必须写在同一个 workflow 里

因为回滚需要**知道刚才部署的是哪个版本**。跨 workflow 传 sha，要么靠 `workflow_run`（复杂），要么靠重新查（可能已经变了）。

**放在同一个 workflow，`needs.deploy.outputs.current_sha` 直接就能用。**

## ⚠️ 这个目录里绝不能出现的东西

```text
❌ 真实的 SSH 私钥（一律 ${{ secrets.SSH_KEY }}）
❌ 真实的 API key
❌ 真实的服务器 IP（用 47.98.xx.xx）
❌ 明文密码
```

**⚠️ 关于 `StrictHostKeyChecking=no`：** 它会让 CI 不校验服务器主机密钥，中间人可以冒充你的服务器收走你的部署指令。**正确做法是把 `SSH_KNOWN_HOSTS` 也放进 secrets**，用 `ssh-keyscan` 生成，第一次连的时候人肉核对一次指纹。

## 这一节要留下的证据

| 证据 | 证明什么 |
|---|---|
| 一次全绿的 Actions 运行页 | 流水线是通的 |
| 一次 `smoke: failure` + `rollback: success` | 自动回滚真的会发生 |
| 服务器上 `cat .current_sha` 和 `docker inspect` 的对比 | 回滚后跑的是旧镜像 |
| 一条真实的告警通知截图 | 失败了你会知道 |
