# 第30周 · 持续集成与部署 · 第 204—210 节课

## push 一下，机器替你检查、打包、上线

---

## 这一周的目标

第 29 周你学会了把应用装进镜像，但在服务器上还是**手动** `docker compose up -d`。

这一周把那双手拿开。你要能做到这五件事：

1. **看懂一次自动化是怎么被触发的** —— 一个 yml 文件放在哪、写什么，push 之后它在哪跑；
2. **让机器替你挑毛病** —— 语法检查、代码规范检查，写错了当场变红；
3. **让机器替你跑测试** —— 测试不过就合不进去，不靠自觉；
4. **让机器替你打包** —— 构建镜像、按 commit 编号打 tag、推到镜像仓库；
5. **让机器替你上线，出问题自己退回来** —— 部署 + 冒烟检查 + 失败回滚。

## 为什么排在这一周

第 31 周你会买服务器、配 Nginx、配 HTTPS。那一周要反复部署，**一天可能部署七八次**。

如果你还靠手动，第 31 周会变成这样：

```text
改一行代码
  ↓ 手动 npm test（忘了跑）
  ↓ 手动 git push
  ↓ ssh 登服务器（输一次密码）
  ↓ cd /srv/app && git pull（冲突了，手动解决）
  ↓ docker compose build（3 分钟，盯着看）
  ↓ docker compose up -d
  ↓ 浏览器刷新，500（忘了看日志）
  ↓ ssh 重新登，docker compose logs
  ↓ 发现是 .env 少了一行
  ↓ 改服务器上的 .env
  ↓ 再 restart
```

**一次 20 分钟，一天八次就是两个半小时。**

而且每一步都可能漏：忘了跑测试、pull 冲突解错、镜像 tag 覆盖了没法回滚。

自动化之后是：

```text
改一行代码
  ↓ git push
  ↓ （走开，去泡杯茶）
  ↓ GitHub 上出现一个绿勾
  ↓ 网站已经是新的了
```

**这一周就是把左边那条路换成右边这条。**

## 一个必须先讲清楚的规矩

这一周所有实验都在**你自己新建的练手仓库**里做，不要在课程仓库里跑。

原因有两个，第二个更要命：

```text
一、这一周会大量 push 到 GitHub。课程仓库是学习资料，不该有你的构建日志。

二、这一周要配置 Secrets（密钥）。只要手一抖把密钥 echo 到日志里，
    它就会永久留在 Actions 的运行记录里 —— 就算你删了仓库，别人也可能已经 clone 走了。
```

所以：

```text
练手仓库：ci-lab（第 204 节课自己建，建议设为 Private）
课程仓库：只读，不要 push
```

**另外一个成本规矩：**

GitHub Actions 对**公开仓库**免费不限量。对**私有仓库**，免费账户每月有 2000 分钟额度（Linux 机器按 1 倍计算）。

```text
一次 CI 跑 2 分钟 × 一天 push 10 次 × 30 天 = 600 分钟/月
```

**在学习阶段够用，但别拿它跑死循环。** 这个额度会变，以 GitHub 官网当时的说明为准。

## 这一周的四条铁律

这四条会跟着你一辈子：

```text
一、任何密钥都不许出现在 yml 里。
    只写 ${{ secrets.XXX }}，真值放在仓库设置里。

二、每一个推上去的镜像都必须带 commit 编号的 tag。
    只用 latest，出事那天你没有任何东西可以退回去。

三、CI 失败就是失败，不许用 continue-on-error 把它变绿。
    红了要修，不是要盖住。

四、自动部署的脚本必须是幂等的。
    同一个脚本连跑三遍，结果要和第跑一遍一样。
```

## 这一周最危险的四个坑

**第一：把密钥写进 yml 然后 push。**

仓库一旦是公开的，全世界的爬虫几十秒内就会扫到。**即使你下一分钟就删掉，它已经在别人的数据库里了。** 唯一的补救是立刻去服务商那里吊销重发。

**第二：镜像只用 `latest`。**

出事时你执行 `docker compose up -d`，拉到的还是坏的那个版本。**没有旧 tag，你只能改代码重新构建 —— 而那时候你连问题在哪都还没看清。**

**第三：`StrictHostKeyChecking=no`。**

网上大量教程教你这么写，为了绕过一个报错。它的意思是"**不验证对面是不是真的我的服务器**"。中间人可以冒充你的服务器，拿到你的部署私钥。

**第四：分支保护没开，测试红着也合进去了。**

CI 只是"告诉你红了"，**它本身拦不住任何人**。真正拦住的是仓库设置里的 required checks。

**这四条不是"不能碰"，是"碰之前必须知道代价"。**

## 周末的验收

不要急着进下一周。先确认这七条：

- [ ] 我的 `ci-lab` 仓库里 `.github/workflows/` 下至少有 3 个 yml，都能跑出绿勾
- [ ] 我故意写错过一次，看到过红色 ❌，并且看懂了报错
- [ ] CI 里跑的测试有 3 个以上，本地 `npm test` 和 CI 结果一致
- [ ] 我的镜像在 GHCR 上有一个带 commit sha 的 tag，不只有 `latest`
- [ ] 我做过一次"完全不碰服务器"的部署：只 push，网站就变了
- [ ] 我配过一次失败通知，并且真的收到过那条消息
- [ ] 第 7 节的流水线里，冒烟检查失败后服务回到了上一个版本

**另外：**

- [ ] 每节课的 `NOTES.md` 都填了，没有大片空白
- [ ] 「卡在哪」那一栏写了真实内容（不是"没有卡住"）
- [ ] 我能用三句话讲清 "workflow / job / step / runner 各是什么"

> **最后一条才是真标准。** 讲不出来，说明你只是把别人的 yml 抄了七遍。
>
> **一周七节课，落一节课没关系，但第 4、5、7 节不能落。** 因为"镜像怎么打 tag"、"密钥怎么给"、"失败怎么退"，是自动化能不能长期用的分界线。

## 这一周不用学什么

明确排除，避免你分心：

```text
Jenkins / GitLab CI / Drone      概念一样，换的是语法，用不到
Kubernetes / K8s                 单机 Docker 够你用到几十个客户
Terraform / 基础设施即代码        第 7 阶段的事
自建 Runner（self-hosted）       等免费额度真不够了再说
蓝绿部署 / 金丝雀发布            先有"能回滚"，再谈"不停机"
多环境（dev/staging/prod）       你一个人做产品，先一个环境
代码覆盖率报告                   覆盖率 80% 不等于没 bug
```

**这一周只用 GitHub Actions 一个平台。** 因为你现在只有它，也只需要它。**换平台时，你学的是"流水线有哪几段"，不是某个平台的按钮在哪。**

这一周你会在本地假装有一台服务器（用 `ssh localhost` 或先跳过部署那一步），第 31 周会：

**⚠️ 一处要提前说明，别到时候觉得白学了：**

**第 31 周会故意退回"裸机部署"——`git clone` + `npm ci` + `pm2`，不用容器。**

不是推翻这一周，是补课：

```text
这一周你用容器，很多细节被藏起来了（Node 装在哪、依赖装在哪、进程怎么死的）。
第 31 周手动来一遍，你才知道容器帮你做了什么。
而且第 34 周交付私有化项目时，客户的老服务器常常装不了 Docker。
```

**两条路线的排查层次完全一样**，只是命令换：`docker compose ps` ↔ `pm2 list`。这一周写的 `deploy.sh`、冒烟检查、回滚思路，第 31 周全部沿用。

**所以这一周的部署脚本先写出来，第 31 周把 IP 填进去、把 `docker compose` 换成 `pm2 restart`，就能用。**
