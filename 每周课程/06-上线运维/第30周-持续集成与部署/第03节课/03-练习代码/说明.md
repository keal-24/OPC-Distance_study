## 为什么要有 `src/` 和 `test/` 两个目录

```text
src/    放"会被部署的业务代码"
test/   放"只在开发和 CI 里跑的验证代码"
```

**分开之后，第 4 节的 Dockerfile 才能做到"只把 src/ 打进镜像，test/ 不进"。**

**如果测试和源码混在一起，你以后要么把测试打进生产镜像，要么写一堆 COPY 排除规则。**

## 建目录的命令

```bash
mkdir -p src test
```

**Windows 上 `mkdir` 不支持一次建两个目录。** 用 Git Bash 或者写两次：

```bash
mkdir src
mkdir test
```

## 今天的实验顺序

```text
① 写 src/price.js（业务函数）
② 写 test/price.test.js（一个测试）
③ npm test                        → 1 个绿
④ 补到 5 个测试（正常/空/边界/错误/异步）
⑤ npm test                        → 5 个绿
⑥ 故意改错 calcTotal              → 看 4 个变红
⑦ 改回来
⑧ 写 test.yml，push               → CI 绿
⑨ 开分支 → 改错 → 开 PR           → 看 Merging is blocked
⑩ 修好 → 合并 → 删分支
```

**第 ⑨ 步是本课的重点。** 不要跳过，也不要"我知道会拦就不做了"。

## 一个必须注意的点

**`test/` 目录下不要放"不是测试"的文件。**

```text
❌ test/helper.js          → 会被当成测试文件跑，报"0 个用例"
✅ test-utils/helper.js    → 放在目录外面
```

**`node --test` 会把 `test/` 下的所有 `.js` 都扫一遍。** 扫到没有用例的文件，它可能报错，也可能静默跳过。

**两种情况都会让你困惑。**

## 这一课的检查重点

不是"5 个测试都过"，是"**你被拦住过一次**"。

```text
PR 页面：
  ❌ Some checks were not successful
  🔒 Merging is blocked
```

**只有亲眼看到那个灰色的 Merge 按钮，你才会真的相信"CI 能拦住人"。**
