# 第 0 步：为什么要有这一步（10 分钟）

## 0.1 你现在会什么

```text
https://your-domain.com/health   → {"ok":true,"db":"up"}
数据库挂了 → 503
备份每天 3 点跑
恢复演练做过
```

**问题在于：**

```text
这些都要你主动去问。
你不问，它们什么都不说。
```

## 0.2 你以后会遇到什么

```text
① 凌晨 2 点证书过期，早上 8 点客户发消息"你们网站打不开"
② 数据库连接池耗尽，页面一直转圈，你在睡觉
③ 磁盘满了，进程反复重启，pm2 的日志刷了几百兆
④ 域名解析被人改了，你的站指向了别人的服务器
⑤ 你装了一堆监控，每天 200 封告警邮件，最后你把通知关了
```

**第 ⑤ 条是这一节真正的难点。**

```text
装监控不难。
装到"该响的时候响、不该响的时候不响"，才难。
```

## 0.3 今天要建立的三个概念

```text
① 监控分三层：域名层、HTTP 层、业务层。少一层就有盲区。
② 告警要分级。所有东西都告警 = 什么都不看。
③ 告警必须"能闭环"：收到 → 处理 → 恢复通知 → 记录。
```

# 第 1 步：先想清楚"什么叫挂了"（20 分钟）

## 1.1 三个层次，三种盲区

**大多数人只监控第一层。**

| 层 | 检查什么 | 工具 | 这一层挂了的表现 |
|---|---|---|---|
| **① 域名层** | 域名还能解析吗 | DNS 监控 / `dig` | "找不到服务器" |
| **② HTTP 层** | 能返回 200 吗 | UptimeRobot | 502 / 超时 |
| **③ 业务层** | 核心功能能用吗 | 关键词监控 / 合成监控 | 页面打开了，但登录不了 |

**⚠️ 只监控 ② 会出现这种情况：**

```text
域名解析被改了 → 请求到了别人的服务器 → 别人的服务器返回 200
你的监控显示"正常"
```

**所以域名层要单独监控。**

## 1.2 软 200 在监控里的表现

**上节课讲过 `/health` 的软 200。在监控里它是这样：**

```text
UptimeRobot 访问 https://your-domain.com
→ 返回 200（因为首页是静态 HTML，Nginx 直接从磁盘读）
→ 监控显示 Up
→ 但实际上 Node 进程已经死了，所有接口 502
```

**为什么首页还是 200：**

```text
如果你的前端是打包好的静态文件，由 Nginx 直接返回，
那 Node 挂了，首页照样能打开。
用户点"发送消息"才会失败。
```

**这就是"首页绿、功能全废"。**

## 1.3 三种监控类型，各有各的用处

**以 UptimeRobot 为例（其他工具类似）：**

| 类型 | 检查什么 | 适合 |
|---|---|---|
| **HTTP(s)** | 状态码是不是 2xx/3xx | 最基础，必须有 |
| **Keyword** | 页面里有没有某个关键词 | **解决软 200 的利器** |
| **Port** | 某个端口通不通 | 数据库、SSH |
| **Ping** | ICMP 通不通 | 服务器活着没（但很多云厂商封 ICMP） |
| **Heartbeat** | 你的程序主动"报到" | 后台任务、定时任务 |

**这一节要用的是 HTTP(s) + Keyword。**

## 1.4 监控项清单

**一个最小可用的个人项目，至少监控这四项：**

| # | 监控什么 | 类型 | 间隔 | 为什么 |
|---|---|---|---|---|
| 1 | `https://your-domain.com` | HTTP(s) | 5 分钟 | 网站能不能打开 |
| 2 | `https://your-domain.com/health` | Keyword（找 `"ok":true`） | 5 分钟 | 后端和数据库能不能干活 |
| 3 | 证书到期日 | 证书监控 / 日历 | 每天 | 到期会让整站打不开 |
| 4 | 服务器 CPU / 磁盘 | 云监控 | 5 分钟 | 资源耗尽的前兆 |

**⚠️ 第 3 项很多工具不提供，就用日历（第 223 节）。**

**这一节先把 1、2、4 做掉。**

## 1.5 不要监控的东西

**这一条和"要监控什么"一样重要。**

| 不要监控 | 为什么 |
|---|---|
| 每个 API 接口都单独建一个监控 | 10 个监控 = 10 倍告警噪音 |
| 模型 API 的响应时间 | 它慢是常态，告警没有意义 |
| 内存使用率（没有阈值依据时） | Node 本来就会用满可用内存再 GC |
| "用户在线数" | 这不是故障指标 |
| 每小时访问量下降 | 可能只是半夜 |

**原则：**

> **只监控"用户能感知到的故障"，以及"故障的前兆"。**

# 第 2 步：配 UptimeRobot（25 分钟）

## 2.1 它是什么

**大白话：一台在国外的机器，每隔几分钟访问一次你的网站，打不开就发邮件给你。**

| 项目 | 说明 |
|---|---|
| 免费版 | 50 个监控、5 分钟间隔（**这些数字会变，以官网为准**） |
| 付费版 | 更短间隔（1 分钟）、更多监控、短信 |
| 注册 | 邮箱即可，不用信用卡 |

**⚠️ 它的服务器在国外。**

```text
如果你的站只对国内开放（比如安全组只放行了国内 IP），
UptimeRobot 会一直报"Down"。
这一节后面会讲怎么处理。
```

## 2.2 注册

**操作：**

1. 打开 `https://uptimerobot.com`；
2. 点 `Register`；
3. 填邮箱 + 密码；
4. 去邮箱点验证链接。

**应该看到：**

```text
Your account is ready.
```

**⚠️ 邮箱一定要用你每天都会看的那个。** 这是后面告警的通道。

## 2.3 建第一个监控：首页

**操作：**

1. 登录后点 `+ Add New Monitor`；
2. `Monitor Type` 选 `HTTP(s)`；
3. `Friendly Name` 填：`主站首页`；
4. `URL` 填：`https://your-domain.com`；
5. `Monitoring Interval` 选 `5 minutes`；
6. `Alert Contacts To Notify` 勾上你的邮箱；
7. 点 `Create Monitor`。

**应该看到列表里出现一行：**

```text
主站首页   https://your-domain.com   Up   100.00%   5 min
```

**逐列读：**

| 列 | 意思 |
|---|---|
| 名称 | 你起的名字 |
| URL | 监控的地址 |
| `Up` | 当前状态（Up / Down / Paused） |
| `100.00%` | 过去 24 小时的可用率 |
| `5 min` | 检查间隔 |

**⚠️ 刚建的时候状态可能是 `Paused` 或 `Not checked yet`。**

```text
等 5 分钟，或者手动点右侧的 "Resume" / 刷新。
```

## 2.4 建第二个监控：`/health` + 关键词

**这一步是这节课的重点。**

**操作：**

1. `+ Add New Monitor`；
2. `Monitor Type` 选 **`Keyword`**；
3. `Friendly Name`：`后端健康`；
4. `URL`：`https://your-domain.com/health`；
5. `Keyword Type`：`exists`（存在）；
6. `Keyword`：`"ok":true`；
7. 间隔 `5 minutes`；
8. 告警联系人勾邮箱；
9. 创建。

**应该看到：**

```text
后端健康   https://your-domain.com/health   Up   100.00%   5 min
```

**为什么用 `"ok":true` 而不是 `200`：**

```text
HTTP(s) 类型只看状态码。
但有些框架在出错时也返回 200（错误处理写错了）。
Keyword 类型看内容，能抓到这种情况。
```

**⚠️ 关键词要带引号。**

```text
你的 /health 返回 {"ok":true,"db":"up",...}
关键词写 "ok":true 能精确匹配。
只写 ok 会匹配到任何包含 ok 的地方（比如 error 里也有）。
```

**如果你的 `/health` 返回的字段名不同：**

```text
先 curl 一次，复制真实输出，从里面挑一个"只有在健康时才出现"的字符串。
```

**例如：**

```json
{"status":"healthy","checks":{"db":{"ok":true}}}
```

**关键词可以写：`"status":"healthy"`**

## 2.5 为什么关键词监控能解决"软 200"

**对比一下：**

| 场景 | HTTP(s) 监控 | Keyword 监控 |
|---|---|---|
| Node 挂了，Nginx 返回 502 | Down | Down |
| Node 活着，数据库挂了（`/health` 返回 503） | Down（503 非 2xx） | Down（没有 `"ok":true`） |
| Node 活着，但 `/health` 写错了返回 200 `{ok:false}` | **Up（漏报）** | **Down（抓到了）** |
| 首页是静态文件，Node 挂了 | **Up（漏报）** | 取决于监控哪个 URL |

**第三行是关键：**

```text
如果你的 /health 实现有 bug，状态码没改对，
HTTP(s) 监控会漏，Keyword 监控能补上。
```

**所以两个都建：一个看状态码，一个看内容。**

## 2.6 配告警联系人

**操作：**

1. 右上角头像 → `My Settings`；
2. 找 `Alert Contacts`；
3. 确认邮箱是 `Verified` 状态；
4. 可以再加一个（备用邮箱 / 手机号）。

**应该看到：**

```text
you@example.com    Email    Verified
```

**⚠️ 如果状态是 `Not Verified`：**

```text
告警发不出去。
去邮箱找 UptimeRobot 的验证邮件（可能在垃圾箱）。
```

## 2.7 想收到微信通知怎么办

**UptimeRobot 本身不发微信。**

**两种常见做法：**

| 做法 | 原理 | 难度 |
|---|---|---|
| **企业微信群机器人** | UptimeRobot 用 `Webhook` 类型，把 JSON 发到群机器人的 URL | 中 |
| **Server酱 / 同类服务** | 中间服务转一手，推到微信 | 低（要注册） |

**企业微信群机器人的大致步骤：**

```text
① 在企业微信里建一个群
② 群设置 → 群机器人 → 添加 → 复制 Webhook URL
③ UptimeRobot → Alert Contacts → Add → Webhook
④ 填那个 URL
⑤ 但 UptimeRobot 的 JSON 格式和群机器人要的格式不一样
   → 需要一个转换（云函数 / 中转服务）
```

**⚠️ 第 ⑤ 步是门槛。**

```text
企业微信群机器人要的是 {"msgtype":"text","text":{"content":"..."}}
UptimeRobot 发的是它自己的格式。
直接填 URL 不会成功。
```

**所以这一节不要求你打通微信。** 用一个"你每天必看"的邮箱就够了。

**如果邮箱你也不看，那问题不在工具，在习惯。**

# 第 3 步：故意停服务，验证告警真的会响（25 分钟）

## 3.1 为什么要"故意"停

**因为"配好了"和"真的会响"是两件事。**

```text
配置页面显示 Up，只能说明"它在检查"。
能不能发出告警、你能不能收到，必须真的制造一次故障才知道。
```

**⚠️ 而且要注意时间：**

```text
UptimeRobot 每 5 分钟检查一次。
所以你停服务后，最多要等 5—6 分钟才会收到告警。
这期间网站是真的打不开的。
```

**所以：**

```text
挑一个没人在用的时间做。
如果你已经有客户，提前发个通知，或者干脆用一个测试子域名。
```

## 3.2 停服务

**在服务器上：**

```bash
pm2 stop my-app
```

**应该看到：**

```text
[PM2] Applying action stopProcessId on app [my-app](ids: [ 0 ])
[PM2] [my-app](0) ✓
┌────┬──────────┬─────────────┬─────────┬─────────┬──────────┬────────┬──────┬───────────┬──────────┬──────────┬──────────┐
│ id │ name     │ namespace   │ version │ mode    │ pid      │ uptime │ ↺    │ status    │ cpu      │ mem      │ user     │
├────┼──────────┼─────────────┼─────────┼─────────┼──────────┼────────┼──────┼───────────┼──────────┼──────────┼──────────┤
│ 0  │ my-app   │ default     │ 1.0.0   │ fork    │ 0        │ 0      │ 12   │ stopped   │ 0%       │ 0 b      │ root     │
└────┴──────────┴─────────────┴─────────┴─────────┴──────────┴────────┴──────┴───────────┴──────────┴──────────┴──────────┘
```

**注意 `status` 变成 `stopped`，`pid` 变成 `0`。**

**立刻验证网站挂了：**

```bash
curl -I https://your-domain.com
```

**应该看到：**

```text
HTTP/1.1 502 Bad Gateway
Server: nginx/1.24.0 (Ubuntu)
```

**`502` 是什么：**

```text
Nginx 在，但它要转发的后端（3000）没人接。
"网关错误"。
```

**⚠️ 如果首页还是 200：**

```text
说明你的首页是静态文件，由 Nginx 直接返回。
那就去看 /health：
curl -i https://your-domain.com/health
应该看到 502。
```

## 3.3 记下时间

**记下来（这个时间线待会要用）：**

```text
14:00  执行 pm2 stop
14:00  curl 返回 502
```

## 3.4 等着

**去喝水，或者在手机上刷一会儿。**

**⚠️ 不要一直刷新 UptimeRobot 页面。** 它有自己的检查周期，刷新不会加速。

## 3.5 应该收到的告警

**大约 5—6 分钟后，邮箱会收到一封，标题类似：**

```text
[UptimeRobot] 主站首页 is DOWN
```

**正文类似：**

```text
主站首页 (https://your-domain.com) is DOWN

Reason: HTTP 502 - Bad Gateway
Checked at: 2026-11-16 14:06:12 UTC
Duration: 5 min
```

**逐行读：**

| 行 | 意思 | 你要确认什么 |
|---|---|---|
| `is DOWN` | 挂了 | 状态明确 |
| `Reason: HTTP 502` | **具体原因** | 502 = 后端挂了 |
| `Checked at` | 检查时间（UTC） | 北京时间 = UTC + 8 |
| `Duration` | 已经持续多久 | —— |

**⚠️ `Checked at` 是 UTC 时间。**

```text
14:06 UTC = 22:06 北京时间
如果你对不上，会以为"怎么半夜告警"。
```

**第二封（`/health` 那个）：**

```text
[UptimeRobot] 后端健康 is DOWN
Reason: Keyword not found
```

**`Keyword not found` 是什么：**

```text
它访问了 /health，返回的内容里没有 "ok":true。
因为返回的是 Nginx 的 502 错误页。
```

## 3.6 时间线

**完整的应该是：**

```text
14:00:00  你执行 pm2 stop
14:00:05  curl 确认 502
14:03:xx  UptimeRobot 这一次检查（失败）
14:06:xx  UptimeRobot 下一次检查（仍然失败）→ 发告警
14:06:30  你收到邮件
```

**为什么不是第一次失败就告警：**

```text
有些工具默认"连续 2 次失败才告警"，避免网络抖动误报。
UptimeRobot 可以在监控设置里调 "Alert after X failed checks"。
```

**⚠️ 这也是一个权衡：**

| 设置 | 好处 | 代价 |
|---|---|---|
| 1 次失败就告警 | 发现快 | 网络抖动就响，容易疲劳 |
| 3 次失败才告警 | 少误报 | 5 分钟 × 3 = 15 分钟才发现 |

**建议：先用 2 次。**

## 3.7 恢复服务

```bash
pm2 start my-app
```

**应该看到：**

```text
[PM2] Applying action restartProcessId on app [my-app](ids: [ 0 ])
[PM2] [my-app](0) ✓
...
│ 0  │ my-app   │ default     │ 1.0.0   │ fork    │ 12345    │ 0s     │ 13   │ online    │ 0%       │ 45.2mb   │ root     │
```

**验证：**

```bash
curl -i -s https://your-domain.com/health | head -1
```

**应该看到：**

```text
HTTP/2 200
```

## 3.8 应该收到"恢复通知"

**再过 5—6 分钟，邮箱会收到：**

```text
[UptimeRobot] 主站首页 is UP
```

**正文：**

```text
主站首页 (https://your-domain.com) is UP

Reason: HTTP 200 - OK
Checked at: 2026-11-16 14:12:20 UTC
Duration: 6 min
```

**⚠️ 恢复通知很重要。**

```text
没有恢复通知，你不知道"现在到底好了没有"。
你会一直盯着监控面板，或者反复自己访问测试。
```

**UptimeRobot 的恢复通知默认是开的。** 如果你关掉了，去设置里打开。

# 第 4 步：云监控：CPU、内存、磁盘（20 分钟）

## 4.1 为什么需要它

**UptimeRobot 只能看到"网站打不开"。**

**它看不到：**

```text
CPU 已经 98% 了，网站还能响应，但每个请求都慢 3 秒
磁盘已经 92%，再过两天就写不进去了
内存快满了，随时会被 OOM Killer 杀掉
```

**这些是"故障的前兆"。云监控就是看这个的。**

## 4.2 在云控制台配

**腾讯云（阿里云类似，界面会变，以你看到的为准）：**

```text
控制台 → 云监控 → 告警管理 → 告警策略 → 新建
```

**填：**

| 字段 | 填什么 |
|---|---|
| 策略名称 | `服务器基础告警` |
| 监控对象 | 你的实例 |
| 触发条件 | `CPU 使用率 > 80%`，持续 `5 分钟`，`3` 次 |
| 告警渠道 | 邮件 / 短信 / 微信 |

**然后同样方式加两条：**

```text
内存使用率 > 85%，持续 5 分钟
磁盘使用率 > 85%，持续 5 分钟
```

## 4.3 阈值为什么不能太低

**❌ 错误配置：**

```text
CPU > 50% 就告警
```

**后果：**

```text
你的服务器平时就在 40—60% 之间波动。
每天收到 30 封告警。
一周后你把告警关了。
```

**这就是"告警疲劳"的起点。**

**✅ 正确思路：**

```text
先观察一周，看正常波动范围。
阈值设在"明显不正常"的位置：
  CPU     平常 30—50%  → 阈值 80%
  内存    平常 40—70%  → 阈值 85%
  磁盘    只增不减     → 阈值 85%（这个可以低一点）
```

**⚠️ 磁盘是唯一"只增不减"的指标。**

```text
CPU 会回落，内存会释放，磁盘不会。
磁盘到 90% 之后，可能几个小时内就 100%。
所以磁盘告警可以设 80%，早一点没关系。
```

## 4.4 磁盘告警的两种

**云监控给的是"磁盘使用率"。**

**但还有一种是"磁盘 inode 使用率"：**

```text
磁盘空间还有，但能创建的文件数量用完了。
表现：df -h 显示有空间，但写文件报 "No space left on device"。
查：df -i
```

**这个告警很多云厂商不提供，需要自己写脚本。**

**这一周不做，但要知道有这回事。**

## 4.5 验证云监控告警

**方法（不用真的把 CPU 打满）：**

```text
很多云控制台有"测试告警"按钮，能发一条测试消息。
点一下，确认你能收到。
```

**如果非要真的触发：**

```bash
# ⚠️ 临时把 CPU 打满 60 秒，只在你自己的测试服务器上做
timeout 60 bash -c 'while :; do :; done' &
```

**这会起一个死循环，烧一个核 60 秒。**

**⚠️ 不要在生产服务器上做。** 而且 CPU 告警要"持续 5 分钟"，60 秒触发不了。

**所以：用控制台的"测试"功能。**

## 4.6 记录

**补进 `监控配置.md`：**

```markdown

| 指标 | 阈值 | 持续 | 通知方式 | 验证过吗 |
|---|---|---|---|---|
| CPU | 80% | 5 分钟 | | |
| 内存 | 85% | 5 分钟 | | |
```

# 第 5 步：Sentry：抓到代码层面的报错（25 分钟）

## 5.1 为什么还需要 Sentry

**UptimeRobot 只知道"网站 502 了"。**

**它不知道：**

```text
哪个函数抛的异常
哪一行代码
影响了多少个用户
第一次出现是什么时候
```

**Sentry 就是干这个的：把异常堆栈收集起来，聚合展示。**

## 5.2 免费额度

| 项目 | 免费版 |
|---|---|
| 错误数 | 5000 条/月（会变，以官网为准） |
| 项目数 | 1 个 |
| 保留期 | 30 天 |

**个人项目完全够。**

## 5.3 接入（Node + Express）

**装：**

```bash
npm install @sentry/node
```

**应该看到：**

```text
added 12 packages in 3s
```

**`server.js` 最上面加：**

```js
const Sentry = require('@sentry/node')

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  tracesSampleRate: 0.1,
  environment: process.env.NODE_ENV || 'production',
})
```

**逐行读：**

| 行 | 作用 |
|---|---|
| `Sentry.init` | 初始化 |
| `dsn` | **你的项目地址**（在 Sentry 后台能看到），从环境变量读 |
| `tracesSampleRate: 0.1` | 采样 10% 的请求做性能追踪（省额度） |
| `environment` | 标记环境，方便区分线上/测试 |

**⚠️ `dsn` 不要写死在代码里。**

```text
它虽然叫"公开 DSN"（可以出现在前端），
但写进 Git 之后，别人可以往你的项目里灌假错误，耗光你的额度。
放 `.env`。
```

**在 `.env` 里加：**

```bash
SENTRY_DSN=https://xxxxxxx@xxxx.ingest.sentry.io/xxxxxxx
```

**在 Express 的错误处理里接上（v8 版本）：**

```js
// 所有路由之后
Sentry.setupExpressErrorHandler(app)
```

**旧版本（v7）写法不同：**

```js
app.use(Sentry.Handlers.errorHandler())
```

**⚠️ 版本差异很大，以你装的版本的官方文档为准。**

**⚠️ 顺序非常重要：**

```text
Sentry 的错误处理必须放在所有路由之后。
放在前面，它抓不到任何东西（Express 是按顺序匹配的）。
```

## 5.4 故意制造一个错误

**加一个测试路由（只在开发/测试环境）：**

```js
if (process.env.NODE_ENV !== 'production') {
  app.get('/debug-sentry', () => {
    throw new Error('Sentry 测试错误')
  })
}
```

**重启，访问：**

```bash
curl -i https://your-domain.com/debug-sentry
```

**应该看到：**

```text
HTTP/1.1 500 Internal Server Error
```

**等 10—30 秒，去 Sentry 后台。**

**应该看到一条 issue：**

```text
Error: Sentry 测试错误
  at /srv/app/server.js:42:11
```

**逐行读：**

| 部分 | 意思 |
|---|---|
| `Error: Sentry 测试错误` | 错误信息 |
| `at /srv/app/server.js:42:11` | **文件、行、列** |
| 出现次数 | 这条错误发生了几次 |
| 影响用户数 | 有多少个不同用户遇到 |

**这就是 Sentry 比日志强的地方：它帮你聚合。**

## 5.5 Sentry 和日志的分工

| 需求 | 用什么 |
|---|---|
| "网站挂了吗" | UptimeRobot |
| "为什么挂了"（代码层面） | Sentry |
| "这个请求发生了什么"（逐条） | Nginx / pm2 日志 |
| "数据库慢查询" | 数据库日志 |

**⚠️ 不要指望一个工具干所有事。**

# 第 6 步：告警分级与"告警疲劳"（20 分钟）

## 6.1 什么叫告警疲劳

```text
第一周：收到告警，立刻爬起来查
第二周：收到告警，看一眼，是误报
第三周：收到告警，划掉
第四周：把通知关了
第五周：真出事，没人知道
```

**这就是告警疲劳。** 它不是"你不负责"，是"系统设计得让人无法负责"。

## 6.2 分级：P0 / P1 / P2

| 级别 | 定义 | 响应时间 | 通知方式 |
|---|---|---|---|
| **P0** | 用户完全用不了 | 立刻（半夜也要起） | 电话 / 短信 + 邮件 |
| **P1** | 核心功能坏了，但网站还能开 | 2 小时内 | 邮件 + 即时消息 |
| **P2** | 有隐患，不影响当前使用 | 当天/本周 | 邮件 / 只在面板上看 |
| **P3** | 只是想知道 | 有空再看 | 不通知，只记录 |

**你的项目至少要分清 P0 和 P2。**

## 6.3 把监控项分级

| 监控项 | 级别 | 为什么 |
|---|---|---|
| 首页 502/503 | **P0** | 所有人打不开 |
| `/health` 返回 503 | **P0** | 后端废了 |
| 证书 7 天内到期 | **P0** | 马上会全站打不开 |
| 证书 30 天内到期 | P2 | 还有时间处理 |
| 磁盘 90% | **P1** | 快写不进去了 |
| 磁盘 80% | P2 | 提前知道 |
| CPU 90% 持续 10 分钟 | **P1** | 会变慢，但还能用 |
| CPU 70% | P3 | 不通知 |
| Sentry 出现新错误 | P2 | 看有没有影响用户 |
| 备份失败 | **P1** | 数据没保护了 |
| 备份超过 24 小时没跑 | **P1** | 同上 |

**⚠️ 注意"备份失败"是 P1，不是 P3。**

```text
备份失败不会让网站挂，但会让你在"真出事"时无法恢复。
它是"延迟爆炸"的问题。
```

## 6.4 减少噪音的四个手段

| 手段 | 怎么做 |
|---|---|
| **合并** | 同一个故障只发一条（`/health` 挂了就别再发首页，它们是同一个原因） |
| **延迟** | 连续 2—3 次失败才告警 |
| **静默期** | 同一告警 30 分钟内不重复发 |
| **分级** | P2 只发邮件，不进手机通知 |

**UptimeRobot 免费版对"合并/静默"支持有限，所以更要控制监控数量。**

**原则：**

> **监控项控制在 5 个以内。每加一个，都要问"它挂了我会做什么"。**

## 6.5 一张"该不该告警"的判断表

**每次想加监控，先过这张表：**

| 问题 | 如果答案是"否" |
|---|---|
| 这件事坏了，用户能感知到吗？ | 不要告警 |
| 我收到告警后，有明确的动作吗？ | 不要告警 |
| 它会天天响吗？ | 调阈值或降级 |
| 它和已有监控重复吗？ | 合并 |

**⚠️ 第二行最重要：**

```text
如果一个告警你收到后只会"哦，知道了"，那它不是告警，是噪音。
```

# 第 7 步：故意犯七个错（30 分钟）

## 错误 1：只监控首页，首页是静态的

**操作：**

1. 只建一个 HTTP(s) 监控，URL 是 `https://your-domain.com`；
2. 停掉 Node：

```bash
pm2 stop my-app
```

3. 等 6 分钟。

**会怎样：**

```text
监控显示：Up（100%）
首页 curl：HTTP/2 200
/health curl：HTTP/1.1 502
```

**为什么：**

```text
你的首页是 Nginx 直接从磁盘返回的静态 HTML。
Node 挂了不影响它。
所以"首页能打开"完全不等于"应用能用"。
```

**用户视角：**

```text
打开首页 → 看到界面 → 点"发送" → 转圈 → 报错
```

**怎么修：**

```text
① 加一个 /health 的 Keyword 监控（第 2.4 步）
② 或者监控一个"必须经过 Node"的 URL
```

**⚠️ 起回服务：**

```bash
pm2 start my-app
```

## 错误 2：只监控 IP，不监控域名

**操作：**

1. 建一个监控，URL 填 `http://47.98.xx.xx`（IP）；
2. 域名解析正常；
3. 现在把 A 记录改成一个错的 IP（或者暂停解析）；
4. 等 6 分钟。

**会怎样：**

```text
IP 监控：Up（因为服务器和 IP 都没变）
域名访问：找不到服务器
```

**为什么：**

```text
IP 监控只检查"这台机器 80 端口有没有响应"。
它完全不碰 DNS。
DNS 挂了、域名过期了、被人改了，它一律不知道。
```

**这是最危险的盲区：**

```text
用户访问的是域名，不是 IP。
你监控的和用户用的，不是同一条路。
```

**怎么修：**

```text
监控的 URL 必须和用户访问的一模一样：https://your-domain.com
IP 监控可以作为"辅助"，不能替代。
```

**验证 DNS 层：**

```bash
ping your-domain.com
```

**或者用专门的 DNS 监控服务（有些厂商提供）。**

## 错误 3：告警发到一个你不看的邮箱

**操作：**

1. UptimeRobot 里填一个 `xxx@company.com`（你离职了但还在用的那种）；
2. 或者填一个 `noreply@` 之类；
3. 或者邮箱进了垃圾箱。

**会怎样：**

```text
告警确实发了。
但你不知道。
等于没装监控。
```

**为什么这是最常见的失败：**

```text
技术上一切正常，流程上断了。
```

**怎么查：**

```text
① 演练一次（第 3 步），确认你真的收到
② 收到后，把它标记为"非垃圾邮件"
③ 在手机上装邮箱 App，开启推送
④ 加第二个渠道（第二个邮箱 / 短信）
```

**⚠️ 一个具体的坑：**

```text
UptimeRobot 的发件域名可能被某些邮箱判成垃圾邮件。
第一次一定要去垃圾箱找。
```

## 错误 4：所有东西都设 1 分钟告警

**操作：**

1. 付费版或试用，把 10 个监控的间隔都设成 1 分钟；
2. 把"任何一个监控失败就告警"打开；
3. 不设静默期；
4. 跑一天。

**会怎样：**

**手机：**

```text
09:01 [UptimeRobot] 主站首页 is DOWN
09:01 [UptimeRobot] 后端健康 is DOWN
09:02 [UptimeRobot] 主站首页 is DOWN
09:02 [UptimeRobot] 主站首页 is UP
09:03 [UptimeRobot] 后端健康 is DOWN
...
（一天 200+ 封）
```

**然后：**

```text
你把 App 通知关了。
一周后真出事，你没看到。
```

**为什么：**

```text
网络抖动、DNS 抖动、对方机房抖动，都会造成"偶发一次失败"。
1 分钟间隔 + 1 次失败就告警 = 把抖动当故障。
```

**怎么修：**

```text
① 间隔 5 分钟
② 连续 2—3 次失败才告警
③ 监控项减到 5 个以内
④ 同一告警 30 分钟内不重复
```

## 错误 5：停了 Nginx，但监控显示 Up

**操作：**

1. 你的站前面有一层 CDN（或云厂商的"加速"）；
2. 停掉服务器上的 Nginx：

```bash
sudo systemctl stop nginx
```

3. 访问 `https://your-domain.com`。

**会怎样：**

```text
浏览器：能打开（CDN 缓存了）
监控：Up
服务器上 curl：Connection refused
```

**为什么：**

```text
CDN 把页面缓存了，Nginx 挂了它还能返回旧内容。
监控看到的是 CDN 的缓存，不是你的服务器。
```

**怎么判断：**

```bash
curl -I https://your-domain.com
```

**看响应头：**

```text
x-cache: HIT
age: 3421
```

**`x-cache: HIT` = 命中缓存，`age` = 缓存了多少秒。**

**怎么修：**

```text
① 监控一个不能缓存的 URL（/health 通常不缓存，但要确认响应头）
② 在 /health 的响应里加 Cache-Control: no-store
③ 监控时带一个随机参数：https://your-domain.com/?t=123
```

**在 Nginx 里给 `/health` 关缓存：**

```nginx
location = /health {
    proxy_pass http://127.0.0.1:3000;
    add_header Cache-Control "no-store" always;
}
```

**⚠️ 或者在应用里加：**

```js
app.get('/health', (req, res) => {
  res.set('Cache-Control', 'no-store')
  // ...
})
```

**⚠️ 起回 Nginx：**

```bash
sudo systemctl start nginx
```

## 错误 6：证书到期没有任何监控

**操作：**

1. 你只监控了"网站能不能打开"；
2. 证书在第 90 天过期；
3. 到期当天早上。

**会怎样：**

```text
UptimeRobot：证书过期后，它访问 https 会失败 → Down
你：早上 9 点收到告警
客户：早上 7 点就发现打不开了
```

**为什么监控"来不及"：**

```text
证书过期是"瞬间生效"的。
它不会提前变慢、不会提前 502。
到期那一秒，所有 https 访问全部失败。
```

**所以：**

```text
不能等"坏了再告警"。
必须在"还有时间处理"的时候就告警。
```

**怎么修（三种）：**

| 方式 | 怎么做 |
|---|---|
| 日历 | 到期前 30 天提醒（第 223 节） |
| 证书监控服务 | 有些工具专门监控证书剩余天数 |
| 自己写脚本 | `openssl ... -checkend 2592000`（30 天） |

**`-checkend` 的用法：**

```bash
echo | openssl s_client -connect your-domain.com:443 -servername your-domain.com 2>/dev/null \
  | openssl x509 -noout -checkend 2592000
```

**如果证书在 30 天内会过期，输出：**

```text
Certificate will expire
```

**否则输出：**

```text
Certificate will not expire
```

**`2592000` = 30 天 × 24 × 3600 秒。**

**这个可以放进 cron，每天跑一次，快到期就发邮件。**

## 错误 7：故障恢复了，但没人知道

**操作：**

1. 停服务，收到 DOWN；
2. 起服务；
3. **把恢复通知关掉**（或者你根本没注意）。

**会怎样：**

```text
你只知道"它挂了"。
你不知道"它好了没有"。
```

**结果：**

```text
你半夜爬起来，连上服务器，查了半天，发现早就恢复了。
或者：你以为它还在挂，一直不敢睡。
```

**为什么恢复通知重要：**

```text
告警的价值 = 让你知道"现在需要做什么"
恢复通知 = 告诉你"现在不需要做什么了"
```

**怎么修：**

```text
在 UptimeRobot 的 Alert Contacts 设置里，
确认 "Up" 通知是开着的。
```

**⚠️ 更好的做法：**

```text
告警里带上"已持续多久"。
如果一条告警说"已持续 6 分钟"，你至少知道它不是刚发生的。
```

# 附：常见问题速查

| 现象 | 原因 | 怎么做 |
|---|---|---|
| 监控一直 Down，但浏览器能打开 | 监控服务器在国外，被安全组挡了 | 放行国外 IP，或用国内监控服务 |
| 监控 Up，但用户说打不开 | 只监控了静态首页 | 加 `/health` Keyword 监控 |
| 监控 Up，但 DNS 挂了 | 监控的是 IP | 改成监控域名 |
| 收不到告警邮件 | 邮箱没验证 / 进垃圾箱 | 查 Alert Contacts 状态 |
| 告警一天几十封 | 间隔太短 / 没有重试次数 / 监控太多 | 5 分钟 + 连续 2 次 |
| 恢复后还在报 Down | 缓存 / 检查还没轮到 | 等一个周期，或手动刷新 |
| 停了 Nginx 还显示 Up | CDN 缓存 | 看 `x-cache`，监控不缓存的 URL |
| `/health` 被 CDN 缓存 | 没设 `Cache-Control` | 加 `no-store` |
| 证书过期当天才知道 | 没有提前监控 | 日历 + `-checkend` |
| Sentry 收不到错误 | `dsn` 没配 / handler 位置不对 | 放在所有路由之后 |
| Sentry 额度很快用完 | `tracesSampleRate` 太高 | 降到 0.1 |
| 手机没推送 | 邮箱 App 没开通知 | 开推送，标记为非垃圾 |
| 告警里时间是 UTC，对不上 | 时区 | 北京时间 = UTC + 8 |
| 想加微信通知 | UptimeRobot 不原生支持 | Webhook + 群机器人 + 格式转换 |
| 云监控 CPU 天天告警 | 阈值太低 | 观察一周再定阈值 |
| 磁盘 90% 但 `df -h` 还有空间 | inode 用完了 | `df -i` 查 |
| 备份失败没人知道 | 没监控备份 | 写检查脚本或用 Heartbeat |
| Heartbeat 一直报 Down | 你的程序没按时"报到" | 检查定时任务 |
| 监控面板一片绿，但客户在骂 | 监控项选错了 | 按"用户视角"重新选 |
| 告警响了，你不知道该做什么 | 没有 RUNBOOK | 第 224 节 |
