```text
凌晨两点，客户打电话说"网站打不开"。

你能在多长时间内判断"是哪一层坏了"？
```

**如果你答不上来，这一节就是为你写的。**

# 第 1 步：先定"放哪"（10 分钟）

## 1.1 三个地方，缺一不可

| 位置 | 为什么 | 怎么放 |
|---|---|---|
| **本地** | 你自己随时能看 | `03-练习代码/RUNBOOK.md` |
| **项目仓库** | 换电脑、给别人交接 | 仓库根目录 `RUNBOOK.md`（**不含密码**） |
| **手机离线** | 半夜、在外面、没网 | 导出 PDF / 截图，存到手机相册或备忘录 |

**⚠️ 唯独不能只放在服务器上。**

```text
服务器挂了 → 你 SSH 不上去 → RUNBOOK 在服务器里 → 你看不到
```

**这是最讽刺的一种失败：**

```text
你为了"服务器坏了怎么办"写了一份文档，
然后把它放在了那台服务器上。
```

## 1.2 为什么必须"一页"

**因为紧急情况下，你的认知能力会下降。**

```text
平时：能读 20 页文档，能推理，能查资料
半夜：只想看到"第一步敲什么，看到什么算通过"
```

**一页纸的标准：**

```text
手机上一屏能看完（或者两屏）。
不需要滚动超过 3 次。
不需要点开任何链接。
```

**⚠️ 一页纸不是"内容少"，是"层级清楚"。**

```text
主表：八步排查（十行）
命令卡：按场景分（五组）
联系人：六行
回滚：三行
```

**加起来能塞进一页 A4。**

## 1.3 RUNBOOK 里绝对不能写的东西

| 不能写 | 为什么 | 替代 |
|---|---|---|
| 服务器 root 密码 | 文档会流传 | 密码管理器 |
| 数据库密码 | 同上 | `.env` + 密码管理器 |
| API Key | 同上 | 同上 |
| 客户手机号 | 隐私 | 只写"客户对接人：见合同" |
| 身份证号 / 备案密码 | 合规 | 密码管理器 |

**⚠️ 一个真实的翻车：**

```text
有人把 RUNBOOK 提交到了 GitHub 公开仓库，
里面有数据库密码。
三个月后被扫描器发现，数据库被拖走。
```

**所以：**

```text
RUNBOOK 里写"密码在 1Password 的 xxx 条目"，
不写密码本身。
```

# 第 2 步：八步排查法（30 分钟）

## 2.1 先做第 0 步：确认"是不是只有你打不开"

**⚠️ 这一步不在八步里，但每次都要先做。**

```text
① 用手机 4G 打开（关 WiFi）
② 让客户发一张截图
③ 用在线工具访问（多个地区同时测）
```

**为什么：**

```text
如果是"只有你打不开"，那是你的网络 / 缓存 / hosts 问题，
服务器可能一点事都没有。
```

**判断：**

| 现象 | 结论 |
|---|---|
| 手机 4G 能开，电脑不能 | 你本地网络 / DNS 缓存 |
| 手机也不能开 | 继续八步 |
| 客户说不能开，你能开 | 客户侧问题 / 地区问题 |
| 所有人都不能开 | 继续八步 |

## 2.2 八步表

**顺序是从外往里：DNS → 网络 → 服务器 → 进程 → 应用 → Nginx → 配置 → 转发。**

| 步 | 查什么 | 命令 | 通过了说明 | 不通过怎么办 |
|---|---|---|---|---|
| 1 | DNS 解析 | `ping your-domain.com` | 方括号里的 IP 是你的服务器 | 查解析 / 清缓存 / 查域名到期 |
| 2 | 服务器活着 | `ping 47.98.xx.xx` | 有回复（或至少不报"找不到主机"） | 云控制台看实例状态 |
| 3 | SSH 能进 | `ssh root@47.98.xx.xx` | 登进去了 | 查 22 端口 / 安全组 / 密码 |
| 4 | 进程在跑 | `pm2 list` | status 是 `online` | `pm2 start my-app` |
| 5 | 应用能响应 | `curl -I http://127.0.0.1:3000` | 200 或 3xx | 看 `pm2 logs` |
| 6 | Nginx 在跑 | `systemctl status nginx` | `active (running)` | `systemctl start nginx` |
| 7 | 配置没坏 | `sudo nginx -t` | `syntax is ok` + `test is successful` | 用备份回滚 |
| 8 | 转发正确 | `curl -I http://127.0.0.1` | 200 / 301 | 查 `proxy_pass` / `server_name` |

**⚠️ 顺序不能跳。**

```text
第 1 步就挂了，后面七步一条都不用看。
而大多数人反过来：先看代码，看到第 5 步才发现请求根本没到。
```

## 2.3 每一步的"应该看到"和"判断"

### 第 1 步：DNS

```bash
ping your-domain.com
```

**通过：**

```text
正在 Ping your-domain.com [47.98.xx.xx] 具有 32 字节的数据:
```

**不通过：**

```text
Ping 请求找不到主机 your-domain.com。请检查该名称，然后重试。
```

**判断：**

```text
IP 不对 → 解析被改 / 没生效 / 域名过期
完全找不到主机 → 域名过期 / 解析被删
IP 对但 ping 超时 → 正常（ICMP 被封），继续第 2 步
```

**⚠️ "IP 对但 ping 超时"要继续往下走，不要停在这里。**

### 第 2 步：服务器

```bash
ping 47.98.xx.xx
```

**通过：**

```text
来自 47.98.xx.xx 的回复: 字节=32 时间=28ms TTL=52
```

**或者超时（正常，说明不了什么）。**

**不通过：**

```text
请求超时
```

**判断：**

```text
⚠️ 云服务器安全组通常不放行 ICMP，所以"超时"不能判定服务器挂了。
真正的判断要进第 3 步。
```

**去云控制台看实例状态：**

```text
运行中 → 继续
已停止 → 启动
不存在 → 服务器被释放了（去查续费）
```

### 第 3 步：SSH

```bash
ssh root@47.98.xx.xx
```

**通过：**

```text
Welcome to Ubuntu 22.04.4 LTS (GNU/Linux 5.15.0-119-generic x86_64)
...
root@ubuntu-server:~#
```

**不通过：**

```text
ssh: connect to host 47.98.xx.xx port 22: Connection timed out
```

**或：**

```text
ssh: connect to host 47.98.xx.xx port 22: Connection refused
```

**判断：**

| 报错 | 意思 | 怎么办 |
|---|---|---|
| `Connection timed out` | 22 端口不通 | 安全组 / 防火墙 / 服务器关机 |
| `Connection refused` | 服务器在，但 22 没监听 | SSH 服务挂了（要控制台 VNC） |
| `Permission denied (publickey)` | 密钥不对 | 检查密钥 / 用密码登 |
| `Host key verification failed` | 服务器重装过 | `ssh-keygen -R 47.98.xx.xx` |

**⚠️ 如果 SSH 进不去但网站还能开：**

```text
说明服务器活着、Nginx 活着，只是 22 被挡了。
不要重启服务器（会丢现场）。
先用云控制台的"VNC 登录"进去看。
```

### 第 4 步：进程

```bash
pm2 list
```

**通过：**

```text
│ 0  │ my-app   │ default     │ 1.0.0   │ fork    │ 12345    │ 2h     │ 13   │ online    │ 0%       │ 45.2mb   │ root     │
```

**逐列读这一行：**

| 列 | 值 | 意思 | 正常吗 |
|---|---|---|---|
| `id` | `0` | PM2 内部编号 | 不重要 |
| `name` | `my-app` | **进程名** | 必须和 RUNBOOK 里写的一致 |
| `version` | `1.0.0` | 从 `package.json` 读的 | 不重要 |
| `mode` | `fork` | 单进程模式 | 正常 |
| `pid` | `12345` | 进程号 | **是 0 就说明没在跑** |
| `uptime` | `2h` | 已经跑了 2 小时 | **很小 = 一直在重启** |
| `↺` | `13` | 累计重启 13 次 | 缓慢增长正常，暴涨不正常 |
| `status` | `online` | 在线 | **只看这一列也行** |
| `mem` | `45.2mb` | 内存占用 | 突然几百 MB 要查 |

**不通过：**

```text
│ 0  │ my-app   │ default     │ 1.0.0   │ fork    │ 0        │ 0      │ 15   │ errored   │ 0%       │ 0 b      │ root     │
```

**判断：**

| status | 意思 | 怎么办 |
|---|---|---|
| `online` | 正常 | 继续第 5 步 |
| `errored` | 起不来 | `pm2 logs my-app --lines 50` |
| `stopped` | 被停了 | `pm2 start my-app` |
| `↺` 很大（如 200） | **一直重启** | 看日志，通常是代码错 / 端口被占 |

**⚠️ `↺` 是重启次数。**

```text
如果它每秒都在涨，说明进程起了就崩、崩了又起。
看 error 日志。
```

### 第 5 步：应用

```bash
curl -I http://127.0.0.1:3000
```

**通过：**

```text
HTTP/1.1 200 OK
X-Powered-By: Express
```

**不通过：**

```text
curl: (7) Failed to connect to 127.0.0.1 port 3000: Connection refused
```

**逐字读：**

| 部分 | 意思 |
|---|---|
| `curl: (7)` | 连不上 |
| `Connection refused` | 端口没人监听 |

**判断：**

```text
Connection refused → 进程没起，或起了但监听别的端口
200 但没有 X-Powered-By → 3000 上是别的程序
超时（28）→ 进程活着但卡住了（死循环 / 数据库阻塞）
```

### 第 6 步：Nginx

```bash
systemctl status nginx --no-pager
```

**通过：**

```text
Active: active (running) since Mon 2026-11-16 10:00:12 CST; 5h ago
```

**不通过：**

```text
Active: failed (Result: exit-code) since Mon 2026-11-16 22:31:02 CST; 2min ago
```

**判断：**

```text
failed → 配置坏了 / 端口冲突 / 启动失败
看：journalctl -u nginx -n 50 --no-pager
```

### 第 7 步：配置

```bash
sudo nginx -t
```

**通过：**

```text
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

**不通过：**

```text
nginx: [emerg] unexpected "}" in /etc/nginx/sites-enabled/default:12
nginx: configuration file /etc/nginx/nginx.conf test failed
```

**判断：**

```text
报错行号往往不是错误行号，看前 3—5 行找少写的分号 / 括号。
```

**⚠️ 这一步最容易"看起来正常其实不正常"：**

```text
nginx -t 失败时，正在跑的 Nginx 用的还是旧配置。
所以网站可能还开着，但你的修改没生效。
```

### 第 8 步：转发

```bash
curl -I http://127.0.0.1
```

**通过：**

```text
HTTP/1.1 200 OK
X-Powered-By: Express
```

**不通过：**

| 结果 | 意思 | 怎么办 |
|---|---|---|
| `502 Bad Gateway` | Nginx 到了，后端没通 | 回到第 4、5 步 |
| `404 Not Found` | `server_name` 没匹配 | `curl -H "Host: 域名" 127.0.0.1` |
| `403 Forbidden` | 被 `deny` 挡了 | 查 `allow/deny` |
| 连接被重置 / 444 | 落到兜底块 | 查 `server_name` 拼写 |

## 2.4 把八步做成一张"检查单"

**RUNBOOK 里的核心就是这张表。**

**打印出来贴在显示器边上，或者存在手机相册第一张。**

```text
□ 0  手机 4G 能开吗？（排除自己）
□ 1  ping 域名 → IP 对不对
□ 2  ping IP → 服务器在不在
□ 3  ssh → 进得去吗
□ 4  pm2 list → online 吗
□ 5  curl 127.0.0.1:3000 → 200 吗
□ 6  systemctl status nginx → running 吗
□ 7  nginx -t → ok 吗
□ 8  curl -I 127.0.0.1 → 200 吗
```

**⚠️ 每一步都要"记录结果"，不是"看一眼"。**

```text
因为你会跳步、会记错、会自我说服"这个应该没问题"。
写下来，就没法骗自己。
```

**逐行读这张检查单：为什么是这个顺序，为什么少了任何一行都不行**

| 行 | 查什么 | 挂着说明什么 | 为什么不能跳 |
|---|---|---|---|
| `□ 0` 手机 4G | 换个网络试 | 只有你打不开 | **先排除自己**：你电脑的 DNS 缓存、公司网络、你的浏览器插件，都能造出"网站挂了"的假象 |
| `□ 1` ping 域名 | 域名解析 | DNS 层断了 | 后面的 IP、SSH、Nginx 全用不上——**请求根本没到那台机器** |
| `□ 2` ping IP | 服务器活着 | 机器关了 / 被释放 | 云服务器通常不回 ICMP，**超时不能判定挂了**，要配合控制台看实例状态 |
| `□ 3` ssh | 远程能进 | 22 被挡 / 服务器重装 | **进不去就没法做 4—8 步**。这一行挂了，先想 VNC，不要急着重启 |
| `□ 4` pm2 list | 进程在跑 | 应用崩了 / 被 OOM 杀了 | 这一步才第一次看到"你的程序"。前三行通、这行挂 = 纯应用问题 |
| `□ 5` curl 127.0.0.1:3000 | 应用能响应 | 进程在但代码错 | **关键分界点**：这行通说明应用没问题，问题在 Nginx；这行挂说明不用看 Nginx |
| `□ 6` nginx 状态 | 反向代理活着 | Nginx 停了 | 5 通 6 挂，是最典型的"应用好的，门卫睡着了" |
| `□ 7` nginx -t | 配置语法 | 配置写错 | 配置错了 Nginx **可能还在用旧配置跑**，你以为改了其实没生效 |
| `□ 8` curl -I 127.0.0.1 | 转发规则 | `server_name` / `proxy_pass` 错 | 7 通 8 挂，只剩转发这一层。**502 是连不上后端，404 是 host 不匹配** |

**读法：**

```text
从上往下，第一个打不了勾的那一行，就是故障层。
它上面的都不用管，它下面的都不用看。
```

**这张表最大的价值不是"查到问题"，是"让你不跳过"。**

```text
没这张单子，你会从第 5 步开始查（因为那是你自己写的代码）。
查了两小时，最后发现第 1 步的 DNS 填错了一个数字。
```

# 第 3 步：常用命令卡（20 分钟）

## 3.1 按场景分组，不要按字母排序

**紧急时你是按"我要干什么"找命令，不是按"命令首字母"。**

### 场景 A：网站打不开

```bash
# 1. 从外面看
curl -I https://your-domain.com
ping your-domain.com

# 2. 在服务器上看
pm2 list
curl -I http://127.0.0.1:3000
systemctl status nginx --no-pager
sudo nginx -t
curl -I -H "Host: your-domain.com" http://127.0.0.1
```

### 场景 B：服务起不来

```bash
pm2 logs my-app --lines 100 --nostream
pm2 restart my-app
pm2 list

# 端口被占
sudo ss -tlnp | grep :3000

# 磁盘满了
df -h
sudo du -sh /var/log/* | sort -h | tail -5
```

### 场景 C：证书问题

```bash
sudo certbot certificates
sudo certbot renew --dry-run
sudo certbot renew
sudo systemctl reload nginx

# 看到期日
echo | openssl s_client -connect your-domain.com:443 -servername your-domain.com 2>/dev/null | openssl x509 -noout -dates
```

### 场景 D：数据恢复

```bash
# 看有哪些备份
ls -lht /srv/backups/ | head

# 建测试库
createdb -h 127.0.0.1 -U app restore_test

# 恢复
pg_restore -h 127.0.0.1 -U app -d restore_test --no-owner --clean --if-exists /srv/backups/xxx.dump

# 验数据
psql -h 127.0.0.1 -U app -d restore_test -c "SELECT count(*) FROM messages;"

# 确认无误后，才考虑恢复到正式库（⚠️ 高风险）
```

### 场景 E：查日志

```bash
sudo tail -f /var/log/nginx/access.log
sudo tail -100 /var/log/nginx/error.log
sudo grep " 502 \| 500 " /var/log/nginx/access.log | tail -20
pm2 logs my-app --lines 100 --nostream
journalctl -u nginx -n 50 --no-pager
```

### 场景 F：改配置（标准动作）

```bash
# 永远三步走
sudo cp /etc/nginx/sites-available/default /etc/nginx/sites-available/default.bak-$(date +%F-%H%M)
sudo nano /etc/nginx/sites-available/default
sudo nginx -t && sudo systemctl reload nginx
```

**⚠️ 最后一行不能拆开。**

## 3.2 三条"救命命令"

**这三条不常用，但出事时必须想起来：**

```bash
# 1. 谁把磁盘占满了（包括已删除但被占用的）
sudo du -sh /* 2>/dev/null | sort -h | tail -10
sudo lsof +L1 | head -20

# 2. 端口被谁占了
sudo ss -tlnp | grep :80

# 3. 最近一小时系统发生了什么
journalctl --since "1 hour ago" --no-pager | tail -50
```

# 第 4 步：找谁（15 分钟）

## 4.1 为什么要写"找谁"

**因为有些故障你解决不了。**

```text
域名被注册商 hold 了 → 只能开工单
服务器硬件故障 → 只能迁移
备案被驳回 → 只能重新提交
支付接口异常 → 只能找支付方
```

**半夜遇到这些，你要能立刻找到入口，而不是搜索"腾讯云客服电话"。**

## 4.2 联系人表

**在 RUNBOOK 里写：**

```markdown
## 找谁

| 什么事 | 找谁 | 入口 |
|---|---|---|
| 域名解析 / 过户 / 续费 | 域名注册商 | 控制台 → 工单 |
| 服务器 / 网络 / 安全组 | 云厂商 | 控制台 → 工单（7×24） |
| 备案进度 | 云厂商备案专员 | 备案系统 → 联系客服 |
| 证书签发失败 | Let's Encrypt 社区 / certbot 文档 | community.letsencrypt.org |
| 模型 API 报错 | 模型平台 | 控制台 → 工单 |
| 支付异常 | 支付服务商 | 商户后台 → 客服 |
| 客户侧问题 | 客户对接人 | 见合同 |
| 我自己 | 备用手机 | —— |
```

**⚠️ 最后一行"我自己"不是玩笑。**

```text
如果你的主手机丢了 / 没电了，你需要一个"备用联系方式"。
写在 RUNBOOK 里，或者告诉一个家人。
```

## 4.3 记下"账号是谁的"

**这一条能救命：**

| 资源 | 注册在谁名下 | 登录邮箱 | 谁能找回 |
|---|---|---|---|
| 域名 | | | |
| 服务器 | | | |
| 备案主体 | | | |
| 模型平台 | | | |
| 支付商户号 | | | |

**⚠️ 如果域名注册在客户名下：**

```text
你改不了解析，也续不了费。
所有操作都要客户配合。
这在合同里必须写清。
```

**如果注册在你名下：**

```text
客户要搬走时，你得配合过户。
合同里也要写清。
```

## 4.4 升级路径

**什么情况下"不再自己查，直接找人"：**

```text
□ SSH 完全进不去，且云控制台 VNC 也进不去 → 开工单（可能硬件故障）
□ 服务器被释放 / 实例不存在 → 立刻开工单 + 查备份
□ 域名状态是 serverHold / 客户 disputes → 立刻开工单
□ 备案被注销 → 立刻联系备案专员
□ 怀疑被入侵（陌生进程 / 异常流量）→ 先断网，再开工单
```

**⚠️ "怀疑被入侵"时，第一动作是"保留现场 + 断公网"，不是"杀进程"。**

```text
杀了进程，证据就没了。
先快照磁盘，再处理。
```

# 第 5 步：回滚与恢复优先级（20 分钟）

## 5.1 三个"上一版"

**出问题时，最快的解法往往是"回到上一个好的状态"。**

| 回滚什么 | 怎么回 | 耗时 |
|---|---|---|
| **代码** | `git log` → `git checkout <上一个 tag>` → `pm2 restart` | 2 分钟 |
| **Nginx 配置** | `cp default.bak-xxx default` → `nginx -t && reload` | 1 分钟 |
| **数据** | 从备份 `pg_restore` 到正式库 | **取决于数据量（第 221 节记过耗时）** |

**⚠️ 数据回滚是最贵的。**

```text
代码回滚 2 分钟，用户无感。
数据回滚 40 分钟，且这 40 分钟内的新数据会丢。
```

## 5.2 恢复优先级

**同时出多个问题时，按这个顺序：**

| 优先级 | 问题 | 为什么排这里 |
|---|---|---|
| **P0** | 数据正在被破坏（误删 / 被入侵） | 停服务，保住数据 |
| **P0** | 网站完全打不开 | 所有用户受影响 |
| **P1** | 核心功能坏了（登录 / 支付） | 大部分用户受影响 |
| **P1** | 证书过期 | 全站打不开（等同 P0，但可预测） |
| **P2** | 部分功能异常 | 少数用户受影响 |
| **P2** | 告警噪音 / 日志异常 | 不影响用户 |
| **P3** | 成本超预期 / 文档过期 | 有空再处理 |

**⚠️ 第一条反直觉：**

```text
"数据正在被破坏"时，正确动作是"立刻停服务"，不是"想办法修"。
停服务 10 分钟，比数据丢一半好。
```

## 5.3 停服务的标准动作

**⚠️ 这是高危操作，RUNBOOK 里要写清"什么时候可以停"。**

```bash
# 停应用（网站变成 502，但 Nginx 还在，能看到错误页）
pm2 stop my-app

# 停 Nginx（整个站打不开）
sudo systemctl stop nginx

# 停数据库（最彻底，也最危险）
sudo systemctl stop postgresql
```

**停之前要做的：**

```text
① 在客户群里发一条"系统维护，预计 X 分钟"
② 确认你知道怎么启动回来
③ 确认备份是最新的
```

## 5.4 RUNBOOK 里的"回滚卡"

```text
────────────────────────────────────
【代码回滚】
cd /srv/app
git log --oneline -5
git checkout <上一个正常的 commit>
npm ci --omit=dev
pm2 restart my-app
curl -I http://127.0.0.1:3000
────────────────────────────────────
【配置回滚】
ls -lt /etc/nginx/sites-available/ | head
sudo cp /etc/nginx/sites-available/default.bak-20261116-1430 /etc/nginx/sites-available/default
sudo nginx -t && sudo systemctl reload nginx
────────────────────────────────────
【数据恢复】
（见第 221 节恢复演练记录，耗时约 __ 分钟）
createdb -h 127.0.0.1 -U app restore_test
pg_restore -h 127.0.0.1 -U app -d restore_test --no-owner --clean --if-exists <备份文件>
psql -h 127.0.0.1 -U app -d restore_test -c "SELECT count(*) FROM messages;"
────────────────────────────────────
```

# 第 8 步：故意犯六个错（25 分钟）

## 错误 1：RUNBOOK 只存在服务器上

**操作：**

1. 把 `RUNBOOK.md` 写在 `/srv/app/RUNBOOK.md`；
2. 本地不留，仓库不提交；
3. 然后停掉 Nginx，或者干脆让服务器不可达（改安全组）。

**会怎样：**

```text
你想看 RUNBOOK → 要 SSH → SSH 进不去 → 看不了
```

**为什么这是最容易犯的错：**

```text
"文档放在项目里"听起来很合理。
但项目在服务器上。
```

**怎么修：**

```text
① 本地一份（03-练习代码/）
② 仓库一份（项目根目录，不含密码）
③ 手机一份（PDF / 截图）
```

**⚠️ 手机那份要能离线看。**

```text
存成图片或 PDF，不要存成一个需要联网打开的链接。
```

## 错误 2：只写"检查服务状态"

**操作：**

**RUNBOOK 里写：**

```text
第 3 步：检查服务是否正常
第 4 步：检查 Nginx 配置
第 5 步：检查数据库
```

**会怎样：**

**半夜你看到这三行，脑子里会冒出一串问题：**

```text
"检查服务"是 systemctl 还是 pm2？
"检查配置"是 nginx -t 吗？还是要看文件？
"检查数据库"用什么命令？psql 还是 systemctl？
```

**结果：**

```text
你花了 5 分钟想命令，而不是 5 秒执行。
```

**怎么修：**

```text
每一条都写成"可复制的一条命令 + 通过的样子"。
```

**对比：**

| ❌ 空话 | ✅ 可执行 |
|---|---|
| 检查服务状态 | `pm2 list` → 看 status 是不是 `online` |
| 检查 Nginx | `sudo nginx -t` → 看是不是 `test is successful` |
| 检查数据库 | `psql -h 127.0.0.1 -U app -d appdb -c "SELECT 1;"` |
| 检查磁盘 | `df -h` → 看 `Use%` 是不是 > 85% |

**然后遇到这个：**

```text
RUNBOOK 第 4 节写"找谁"，每一行都有"入口"。
```

| ❌ | ✅ |
|---|---|

**操作：**

**你不知道"上一个版本"是哪个。**

```text
是 a1b2c3d 的前一个？
还是上一次发布的 tag？
```

## 错误 5：把密码写进 RUNBOOK 并提交到 Git

**操作：**

**RUNBOOK 里写：**

```markdown
## 数据库

- 主机：127.0.0.1
- 用户：app
- 密码：Abc123456!
```

**然后：**

```bash
git add RUNBOOK.md
git commit -m "加运维手册"
git push
```

**会怎样：**

**短期：没事。**

**长期：**

```text
① 仓库如果是公开的 → 全世界都能看到
② 仓库如果是私有的，但协作者换了 → 前同事还能看到
③ 有人 clone 过 → 密码永远在历史里
④ 扫描器会盯着 GitHub 的公开仓库，几分钟内就能抓到
```

**为什么"删掉再提交"没用：**

```text
git 的历史里还有。
要清历史得用 git filter-repo，很麻烦，还可能影响别人。
```

**怎么修：**

```text
① 立刻改密码（这是第一动作，不是"删文件"）
② 从 RUNBOOK 里删掉，改成"密码在密码管理器的 xxx 条目"
③ 如果已经推到公开仓库，假设它已经泄露
```

**⚠️ 顺序不能反：**

```text
先改密码，再清理文档。
因为清理文档不能"收回"已经泄露的东西。
```


**会怎样：**

```text

```

**为什么这很危险：**

```text
你不会怀疑 RUNBOOK，你会怀疑"服务器是不是坏了"。
然后开始瞎查。
```

**怎么修：**

```text
① RUNBOOK 顶部写"最后更新日期"
② 每次改架构 / 改路径 / 改进程名，顺手改 RUNBOOK
③ 每季度做一次演练（第 6 步）
④ 演练时"只用 RUNBOOK"，不用记忆
```

**⚠️ 一个简单的检查方法：**

```text
把 RUNBOOK 发给一个不了解你项目的人，
让他照着做一遍。
他卡住的地方，就是 RUNBOOK 的 bug。
```

# 附：常见问题速查

| 现象 | 原因 | 怎么做 |
|---|---|---|
| 网站打不开，但 ping 有 IP | 后端 / Nginx | 走第 4—8 步 |
| 浏览器"找不到服务器" | DNS | 查解析 / 域名到期 |
| `502 Bad Gateway` | 后端没起 | `pm2 list` → `pm2 start` |
| `404` | `server_name` 不匹配 | `curl -H "Host: 域名" 127.0.0.1` |
| 连接超时 | 安全组 / 服务器关机 | 云控制台看实例 |
| `Connection refused` | 端口没监听 | `ss -tlnp \| grep :端口` |
| SSH 进不去但网站能开 | 22 被挡 / SSH 服务挂 | 用 VNC，别重启 |
| `nginx -t` 失败但网站能开 | 用的是旧配置 | 修配置，别看网站 |
| 证书红色警告 | 过期 / 域名不匹配 | `certbot certificates` |
| 磁盘 100% | 日志 / 备份 | `df -h` → `du -sh /*` |
| `rm` 日志不释放空间 | 进程占着句柄 | `truncate -s 0` 或 reload |
| `pm2` 一直重启 | 代码错 / 端口占 | `pm2 logs --lines 100` |
| 域名 `serverHold` | 未实名 / 风控 | 开工单 + 实名 |
| 服务器实例不存在 | 到期被释放 | 立刻开工单 + 查异地备份 |
| 数据误删 | 人为 / 代码 bug | **先停服务**，再恢复 |
| 恢复后数据还是不对 | 备份时间点不对 | 看文件名时间戳 |
| 客户说打不开，你能开 | 客户侧 / 地区 | 让客户发截图 + 用 4G 测 |
| 改了配置没生效 | 没 reload / 没建软链接 | `nginx -t && reload` |
| RUNBOOK 里的命令报错 | 路径 / 进程名变了 | 演练，改 RUNBOOK |
| 半夜找不到文档 | 只放在服务器 / 电脑 | 手机存一份离线 |
| 怀疑被入侵 | 陌生进程 / 异常流量 | 先快照 + 断公网，再开工单 |
| 不知道找谁 | 没写联系人表 | 现在补，写到"点哪里" |
