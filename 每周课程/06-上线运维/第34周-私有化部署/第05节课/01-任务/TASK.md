```text
① 交付半年后，客户被上级安全检查，查出"存在厂商维护账号"，写进整改单。
```

**前两条是法律风险，后三条是交付质量问题。**

```text
③ 售后通道：交接后你要维护，但不是靠"偷偷留个账号"，而是靠一个客户知情、可审计、可随时关闭的流程。
```

**第三个概念是这节课的核心。** 不是"不留访问"，是"访问要见光"。

# 第 1 步：先认清"后门"长什么样（20 分钟）

## 1.1 六种后门，你可能已经留了三个

| 类型 | 具体形式 | 客户知不知道 | 危险程度 |
|---|---|---|---|
| 账号后门 | 你自己建的 `support` 账号 | 不知道 | 高 |
| 密钥后门 | 你的 SSH 公钥还在 `authorized_keys` | 不知道 | **极高** |
| 密码后门 | 所有密码都是你设的，客户没改过 | 客户有，但没改 | 高 |
| 定时任务后门 | 你留了一个 cron 每天回连 | 不知道 | **极高** |
| 数据后门 | 备份文件里带着你的密钥 | 不知道 | 中 |
| 文档后门 | 运维手册里写着你的手机号和账号 | 知道 | 低，但不专业 |

**"极高"的两条，是安全审计一查就出来的。**

## 1.2 为什么"留个账号方便维护"是错的

**你的理由：**

```text
客户 IT 不懂技术，出问题我进不去，怎么维护？
```

**客户的视角：**

```text
任何能在我们不知情的情况下进入系统的人，都是风险。
不管他是谁，不管他是不是好心。
```

**审计的视角：**

```text
等保要求：账号唯一、实名、可审计、离岗即删。
"厂商维护账号"是典型的不符合项。
```

**出事之后的视角：**

```text
数据泄露 → 追责 → 查到有一个不在册的账号 → 问：这个账号谁的？
→ 你的名字。
```

**四条视角，只有第一条是"方便"，后三条都是"责任"。**

## 1.3 正确的做法：临时访问，全程留痕

```text
不是"永远能进"，是"需要时能进，进的时候客户知道，进完就关"。
```

**三种合规的访问方式：**

| 方式 | 怎么做 | 留痕 |
|---|---|---|
| 客户开临时账号 | 客户建账号给你，用完删除 | 客户有建号和删号记录 |
| 客户在场操作 | 你口述，客户 IT 敲 | 客户自己的 shell 历史 |
| 堡垒机 | 客户堡垒机分配临时权限 | 堡垒机录屏 + 审计日志 |

**这三种，共同点是：客户知道，且能随时收回。**

## 1.4 逐行读：一次审计会看什么

**审计员登进机器，会敲这些命令：**

```bash
last -20
```

**应该看到：**

```text
root     pts/0        10.20.30.55      Mon Mar 10 09:12   still logged in
root     pts/1        10.20.30.88      Fri Mar  7 16:40 - 18:22  (01:42)
support  pts/0        47.98.xx.xx      Thu Mar  6 14:10 - 15:30  (01:20)
root     tty1                          Wed Mar  5 08:00 - 08:05  (00:05)
```

**逐行读：**

| 行 | 审计员看到什么 | 危险信号 |
|---|---|---|
| `root pts/0 10.20.30.55` | 内网地址登录 | 正常 |
| `support pts/0 47.98.xx.xx` | **一个叫 support 的账号，从公网 IP 登录** | **重大发现** |
| `root tty1` | 本地控制台 | 正常，可能是装机时 |

**`47.98.xx.xx` 是公网地址。** 内网系统出现公网登录记录，等于"有人从外面进来过"。

**再看账号：**

```bash
cat /etc/passwd | grep -v nologin | grep -v false
```

**应该看到：**

```text
root:x:0:0:root:/root:/bin/bash
support:x:1001:1001::/home/support:/bin/bash
ollama:x:998:998::/usr/share/ollama:/bin/false
```

**逐字段读：**

```text
support  :x          :1001 :1001 ::/home/support :/bin/bash
用户名    密码占位符    UID   GID   描述  家目录        登录 shell
```

**`support` 这个账号有 `/bin/bash`，说明它能登录。**

**`ollama` 是 `/bin/false`，说明它不能登录，只能跑服务。这是对的。**

**这就是审计报告里会出现的一行：**

```text
【中危】存在非实名账号 support，具备交互式登录权限，无法追溯到具体人员。
```

**这一行，会写进整改单，然后客户会来找你。**

# 第 2 步：交接清单，15 项一项不能少（30 分钟）

## 2.1 清单全貌

| 序号 | 项目 | 交接内容 | 谁保管 |
|---|---|---|---|
| 1 | 服务器 root 密码 | 新密码，密封交接 | 客户 IT |
| 2 | 客户管理员账号 | 新建 `admin`，实名 | 客户业务负责人 |
| 3 | 数据库超级用户 | 改密码，只给客户 DBA | 客户 DBA |
| 4 | 数据库应用账号 | 只读/读写分权，密码在 `.env` | 客户 IT |
| 5 | 应用管理员账号 | 移交 + 强制改密 | 客户业务 |
| 6 | SSH 密钥 | **删除你的公钥**，装客户的 | 客户 IT |
| 7 | HTTPS 证书 | 证书文件 + 私钥 + 到期日 | 客户 IT |
| 8 | 备份位置 | 路径 + 保留策略 + 恢复方法 | 客户 IT |
| 9 | 日志位置 | 路径 + 轮转策略 + 保留期 | 客户 IT |
| 10 | 开机自启 | 服务清单 + 验证方法 | 客户 IT |
| 11 | 端口清单 | 开了哪些、为什么 | 客户网络 |
| 12 | 定时任务 | 备份、清理、续期 | 客户 IT |
| 13 | 第三方账号 | 模型 API、短信、邮件 | 客户或注销 |
| 14 | 文档 | 四件套 + 本次交接单 | 客户 IT |
| 15 | 联系人 | 你的公司、电话、响应时间 | 客户 IT |

**15 项，每一项都要有"交接给谁"和"怎么验证"。**

## 2.2 第 1 项：root 密码怎么交

**❌ 错误做法：**

```text
微信发一句：root 密码是 Abc123456
```

**为什么错：**

```text
① 微信记录永久保存，谁都能翻
② 客户可能不改
③ 出了事，聊天记录证明"密码是你设的、你发的"
④ 密码可能同时被你用在别处
```

**✅ 正确做法：**

```text
① 现场让客户 IT 自己敲新密码（你不看）
② 或者写进密封信封，双方在封口签字
③ 交接单上写"已于 X 时 X 分完成密码变更，由甲方操作"
```

**为什么让客户自己敲：**

```text
从这一刻起，"只有客户知道 root 密码"这句话是真的。
你签的交接单才有意义。
```

**如果只能远程交接：**

```text
用密码管理器（如 Bitwarden）发一次性链接，设置 24 小时过期、阅后即焚。
不要用微信、邮件、短信。
```

## 2.3 第 6 项：SSH 密钥，这是最容易漏的

**先看现在有谁的钥匙：**

```bash
cat /root/.ssh/authorized_keys
```

**应该看到：**

```text
ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC... your-laptop
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... support@company
```

**逐字段读：**

```text
ssh-rsa                          密钥类型
AAAAB3Nza...                     公钥内容（很长）
your-laptop                      注释，通常是生成时的 用户名@主机名
```

**两条都要处理：**

| 行 | 是谁的 | 怎么处理 |
|---|---|---|
| `your-laptop` | 你的笔记本 | **删掉** |
| `support@company` | 你公司的运维机 | **删掉** |

**删之前，先让客户装好自己的钥匙。**

**客户生成密钥（在客户 IT 的电脑上）：**

```bash
ssh-keygen -t ed25519 -C "zhang@hospital-it"
```

**应该看到：**

```text
Generating public/private ed25519 key pair.
Enter file in which to save the key (/home/zhang/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):
Enter same passphrase again:
Your identification has been saved in /home/zhang/.ssh/id_ed25519
Your public key has been saved in /home/zhang/.ssh/id_ed25519.pub
The key fingerprint is:
SHA256:9f2c1a4e7b3d5f8a0c2e4b6d8f0a2c4e6b8d0f2a zhang@hospital-it
```

**逐行读：**

| 行 | 意思 | 建议 |
|---|---|---|
| `Enter file in which to save` | 存哪 | 直接回车用默认 |
| `Enter passphrase` | 给私钥加密码 | **建议设**，私钥丢了还有一层保护 |
| `key fingerprint` | 指纹 | 记下来，核对用 |

**把公钥内容发给客户前，先看一眼：**

```bash
cat ~/.ssh/id_ed25519.pub
```

**应该看到：**

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... zhang@hospital-it
```

**客户 IT 把这一行加到服务器：**

```bash
echo "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... zhang@hospital-it" >> /root/.ssh/authorized_keys
```

**然后验证客户能登（让客户自己开一个新窗口试）：**

```bash
ssh root@10.20.30.40
```

**应该能直接进去，不要密码。**

**⚠️ 顺序很重要：**

```text
先加客户的钥匙 → 验证客户能进 → 再删你的钥匙
顺序反了，你可能把自己锁在外面，客户也进不去。
```

**删你的钥匙：**

```bash
sed -i '/your-laptop/d' /root/.ssh/authorized_keys
sed -i '/support@company/d' /root/.ssh/authorized_keys
```

**验证：**

```bash
cat /root/.ssh/authorized_keys
```

**应该只剩客户那一行。**

**`sed -i` 是什么：**

```text
-i  直接改文件（不加 -i 只打印到屏幕）
/pattern/d  删除包含 pattern 的行
```

**⚠️ 改之前先备份：**

```bash
cp /root/.ssh/authorized_keys /root/.ssh/authorized_keys.bak
```

**但备份文件本身也是风险，交接完要删：**

```bash
shred -u /root/.ssh/authorized_keys.bak
```

**`shred -u` 是什么：**

```text
先覆写文件内容，再删除。
普通 rm 只删目录项，数据块可能还在磁盘上。
对密钥这种敏感文件，用 shred。
```

**注意：在 SSD 和某些文件系统上，shred 也不能保证彻底擦除。** 所以最好的办法是**一开始就别把私钥放在服务器上**。

## 2.4 第 2 项：建客户的管理员账号

**为什么不用 root 干日常：**

```text
root 是"系统管理员"，能做任何事。
业务管理员只需要"在应用里管用户、看数据"。
用 root 干业务的事，等于给每个人发万能钥匙。
```

**应用层的管理员账号，在应用里建：**

```text
登录应用 → 用户管理 → 新建用户
邮箱：zhang@hospital.local
角色：admin
```

**然后让客户自己改密码：**

```text
首次登录强制改密，你在旁边看着，不要记。
```

**验证客户能进：**

```text
让客户用自己的账号登录，能进后台，能看到用户列表。
```

**然后禁用你的管理员账号：**

```sql
UPDATE users SET status = 'disabled' WHERE email = 'admin@customer.local';
```

**应该看到：**

```text
UPDATE 1
```

**为什么要保留记录而不是删除：**

```text
审计要求"账号变更有记录"。
直接 DELETE 掉，日志里看不出发生过什么。
设成 disabled，操作记录还在。
```

## 2.5 第 3 项：数据库账号

**看现在有哪些数据库账号：**

```bash
docker compose exec postgres psql -U chatapp -d chatapp -c "\du"
```

**应该看到：**

```text
                             List of roles
 Role name |                         Attributes                         | Member of
-----------+------------------------------------------------------------+-----------
 chatapp   | Superuser, Create role, Create DB, Replication, Bypass RLS | {}
 postgres  | Superuser, Create role, Create DB                          | {}
```

**逐列读：**

| 列 | 意思 | 问题 |
|---|---|---|
| `Role name` | 账号名 | |
| `Attributes: Superuser` | **超级用户** | 应用账号不该是超级用户 |
| `Create role / Create DB` | 能建账号、建库 | 应用账号不该有 |
| `Bypass RLS` | 绕过行级安全 | 多租户场景下很危险 |

**`chatapp` 是应用账号，却是 Superuser。这是第 33 周讲过的"权限过大"问题，在私有化交付里必须修。**

**修：**

```sql
-- 建一个只读写业务表的账号
CREATE ROLE chatapp_app LOGIN PASSWORD '客户自己设的密码';
GRANT CONNECT ON DATABASE chatapp TO chatapp_app;
GRANT USAGE ON SCHEMA public TO chatapp_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO chatapp_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO chatapp_app;
```

**应该看到：**

```text
CREATE ROLE
GRANT
GRANT
GRANT
GRANT
```

**逐行读：**

| 语句 | 给什么权限 |
|---|---|
| `CREATE ROLE ... LOGIN PASSWORD` | 建一个能登录的账号 |
| `GRANT CONNECT` | 能连这个库 |
| `GRANT USAGE ON SCHEMA` | 能看到这个 schema |
| `GRANT SELECT/INSERT/UPDATE/DELETE ON ALL TABLES` | 能读写数据，**不能改表结构** |
| `GRANT USAGE ON ALL SEQUENCES` | 能用自增序列 |

**没有给的权限：**

```text
CREATE / DROP / ALTER     不能改表结构
SUPERUSER                 不是超级用户
CREATEROLE / CREATEDB     不能建账号建库
```

**然后改应用连接串：**

```bash
# .env 里
DB_USER=chatapp_app
DB_PASSWORD=客户设的密码
```

**验证：**

```bash
docker compose exec app node -e "
const {Pool}=require('pg');
const p=new Pool({connectionString:process.env.DATABASE_URL});
p.query('SELECT count(*) FROM users').then(r=>{console.log(r.rows);process.exit(0)}).catch(e=>{console.error(e.message);process.exit(1)});
"
```

**应该看到：**

```text
[ { count: '12' } ]
```

**再验证它不能改表结构：**

```bash
docker compose exec postgres psql -U chatapp_app -d chatapp -c "DROP TABLE users;"
```

**应该看到：**

```text
ERROR:  must be owner of table users
```

**这个报错就是权限生效的证据。** 记进交接记录。

## 2.6 第 7 项：证书和私钥

**找证书在哪：**

```bash
ls -l /opt/app/nginx/certs/
```

**应该看到：**

```text
-rw-r--r-- 1 root root 3854 Mar 10 09:00 fullchain.pem
-rw------- 1 root root 3272 Mar 10 09:00 privkey.pem
```

**`privkey.pem` 是 `-rw-------`，只有 root 能读。这是对的。**

**交接要写清：**

```text
证书文件：/opt/app/nginx/certs/fullchain.pem
私钥文件：/opt/app/nginx/certs/privkey.pem
签发机构：XXX
签发日期：2026-03-10
到期日期：2027-03-10
续期方式：内网 CA 签发 / 手动更新（无外网不能用 certbot）
```

**为什么内网不能 `certbot`：**

```text
certbot 要连 Let's Encrypt 验证域名所有权。
内网域名外网访问不到，验证不了。
所以私有化项目通常用：
① 客户自己的内网 CA
② 商业证书，手动导入（一年一换，要写进运维手册）
③ 干脆用 HTTP（内网可接受，但要客户书面确认）
```

**⚠️ 证书到期是私有化项目最常见的"一年后突然挂掉"。**

```text
把到期日写进交接单，同时写进你自己的日历。
```

## 3.5 查脚本里的明文密码

```bash
grep -rn -E "password|passwd|PASSWORD" /opt/app/scripts/ 2>/dev/null
```

**应该看到（不好）：**

```text
/opt/app/scripts/backup.sh:8:PGPASSWORD=Abc123456 pg_dump -U chatapp chatapp > ...
```

**逐段读：**

```text
backup.sh:8        第 8 行
PGPASSWORD=...     环境变量方式传密码
问题：密码明文写在脚本里，任何能读脚本的人都能看到
```

**修：**

**方案一：用 `.pgpass`**

```bash
cat > /root/.pgpass <<'EOF'
postgres:5432:chatapp:chatapp_app:客户设的密码
EOF
chmod 600 /root/.pgpass
```

**格式：**

```text
主机:端口:数据库:用户名:密码
```

**然后脚本里不用写密码：**

```bash
pg_dump -h postgres -U chatapp_app chatapp > backup.sql
```

**⚠️ 但容器里的 pg_dump 读不到宿主机的 `/root/.pgpass`。**

**方案二（更实用）：用容器内的环境变量**

```bash
docker compose exec -T postgres pg_dump -U "$DB_USER" "$DB_NAME" > backup.sql
```

**`docker compose exec` 会把容器的环境变量带进去，`POSTGRES_PASSWORD` 已经在容器里了，`pg_dump` 用本地 socket 连接，不需要密码。**

**这个方案最干净：密码只存在 `.env` 和容器环境里，脚本里一个都没有。**

# 第 4 步：设计一条见得光的售后通道（20 分钟）

## 4.1 问题：交干净了，售后怎么办

**你的担心是真的：**

```text
客户 IT 不懂 Docker，服务挂了不会重启。
你没有任何账号，怎么帮他？
```

**答案不是"留后门"，是"设计一个流程"。**

## 4.2 三种合规通道

| 通道 | 适用 | 怎么开 | 怎么关 |
|---|---|---|---|
| 客户开临时账号 | 需要登服务器排查 | 客户 IT 执行 `useradd`，设 24 小时有效期 | 客户删账号，或 `chage -E` 到期 |
| 客户陪同操作 | 简单问题 | 视频会议 + 客户共享屏幕 | 会议结束即关闭 |
| 堡垒机临时授权 | 有堡垒机的客户 | 客户在堡垒机里授权 2 小时 | 到期自动回收 |

**共同点：客户知情、有记录、能随时收回。**

## 4.3 临时账号的标准流程

**写进《售后支持说明》：**

```text
一、远程支持流程

1. 甲方通过电话/邮件提出支持请求，说明现象。
2. 乙方判断需要登录服务器时，向甲方提出书面申请（邮件即可），
   写明：目的、需要的权限、预计时长。
3. 甲方在服务器上创建临时账号：
     useradd -m -e $(date -d "+1 day" +%Y-%m-%d) support_tmp
     passwd support_tmp
   并把临时密码通过约定方式告知乙方。
4. 乙方在授权时段内操作，操作内容记录在工单中。
5. 支持完成后，乙方通知甲方，甲方执行：
     userdel -r support_tmp
6. 甲方在交接记录中登记本次支持的时间和账号。
```

**为什么用 `-e` 设过期日：**

```bash
useradd -m -e $(date -d "+1 day" +%Y-%m-%d) support_tmp
```

```text
-e 是账号过期日。到了那天，账号自动失效，不需要有人记得删。
这是"技术上保证能收回"，不是"靠人记得"。
```

**验证：**

```bash
chage -l support_tmp
```

**应该看到：**

```text
Last password change                                    : Mar 10, 2026
Password expires                                        : never
Password inactive                                       : never
Account expires                                         : Mar 11, 2026
Minimum number of days between password change          : 0
Maximum number of days between password change          : 99999
Number of days of warning before password expires       : 7
```

**逐行读：**

| 行 | 意思 |
|---|---|
| `Account expires: Mar 11, 2026` | **账号在 3 月 11 日失效** |
| `Password expires: never` | 密码本身不过期（无所谓，账号会过期） |

**注意：`Account expires` 只管"能不能登录"，不管"已经登录的会话"。**

```text
如果对方还开着 SSH 会话，账号过期不会踢他下线。
要立刻断开，用：
pkill -u support_tmp
```

## 4.4 工单要记什么

**每次支持都留一条记录：**

| 字段 | 内容 |
|---|---|
| 时间 | 2026-03-10 15:20—15:50 |
| 提出人 | 客户张工 |
| 现象 | 系统打不开，页面 502 |
| 原因 | 服务器重启后 ollama 容器未启动（restart 策略漏配） |
| 操作 | `docker compose up -d ollama`，补 `restart: unless-stopped` |
| 结果 | 恢复 |
| 账号 | `support_tmp`，已通知客户删除 |

**这条记录有三个作用：**

```text
① 客户知道你来过、做了什么
② 你知道三个月前发生过什么
③ 出了争议，这是证据
```

## 4.5 响应时间怎么写

**不要写"7×24"，写你能做到的：**

| 级别 | 定义 | 响应 | 解决 |
|---|---|---|---|
| 紧急 | 系统完全不可用 | 4 小时（工作日 9—18 点） | 8 小时 |
| 一般 | 部分功能异常 | 1 个工作日 | 3 个工作日 |
| 咨询 | 使用问题 | 2 个工作日 | — |

**必须加的那一句：**

```text
因甲方网络限制、审批流程或配合人员不在岗导致无法及时接入的，
响应时间相应顺延。
```

**为什么必须加：**

```text
客户规定"远程接入要提前一天申请"。
你 4 小时内根本进不去，但合同写了 4 小时响应。
不加这一句，你每次都违约。
```

```text
第一句：现在这台机器上，只有你们的人能登录。我的钥匙已经删了，root 密码是你们自己设的。
第二句：以后需要我进来，你们给我开临时账号，用完删掉，我这边有工单记录。
第三句：这份交接单签了，账号和密码的责任就转到你们这边，我这边负责系统和代码。
```

**为什么要把第三句说出来：**

```text
责任转移这件事，必须当面说清。
不说，客户以为"签了字你还要负责所有事"。
```

# 第 6 步：密码到底怎么给（15 分钟）

## 6.1 四种方式对比

| 方式 | 安全性 | 可追溯 | 建议 |
|---|---|---|---|
| 微信/QQ 发文字 | 差 | 有记录但永久保存 | ❌ 不用 |
| 邮件发文字 | 差 | 有记录 | ❌ 不用 |
| 电话口述 | 中 | 无 | 应急可用 |
| 现场客户自己设 | **高** | 交接单签字 | ✅ 首选 |
| 密码管理器一次性链接 | 高 | 有访问记录 | ✅ 远程首选 |
| 密封信封 | 中高 | 封口签字 | ✅ 纸质交付可用 |

## 6.2 现场让客户自己设密码

**流程：**

```text
① 你把键盘让给客户
② 客户敲 passwd
③ 屏幕不显示输入，你在旁边不看
④ 客户确认能重新登录
⑤ 你在交接单上写"密码已由甲方于 15:30 重置，乙方不知晓"
```

**`passwd` 的输出：**

```text
Changing password for user root.
New password:
Retype new password:
passwd: all authentication tokens updated successfully.
```

**逐行读：**

| 行 | 意思 |
|---|---|
| `New password:` | 输入新密码，**屏幕不显示任何字符** |
| `Retype new password:` | 再输一遍 |
| `all authentication tokens updated` | 改成功了 |

**"屏幕没反应"是正常的。** Linux 故意不显示，防止别人看到长度。

## 6.3 密封信封（纸质交付）

**适用：客户要求纸质留档、或者要交给多个人。**

```text
准备：
① 一张纸，写上账号和新密码
② 装进信封
③ 封口处双方签字
④ 信封正面写：系统名称 + 账号 + 启用日期 + "启封请登记"
⑤ 交接单上记：信封编号、封口签字人、存放位置
```

**为什么这么做：**

```text
密码不在任何电子渠道留痕。
谁启封的、什么时候启封的，有登记。
出问题时能追到"谁可能知道密码"。
```

## 6.4 密码管理器一次性链接

**适用：远程交付、密码需要当场看。**

**以 Bitwarden Send 为例（其他同类工具类似）：**

```text
① 创建一个 Send，类型选"文本"
② 内容填账号密码
③ 设置：24 小时后过期、最多访问 1 次
④ 生成链接，发给客户
⑤ 客户打开看完，链接自动失效
```

**为什么比微信好：**

```text
① 有访问记录（谁、什么时候、从哪个 IP 看的）
② 看完即焚，不会永久留在聊天记录里
③ 可以设密码保护，二次验证
```

**注意：**

```text
这些工具的界面和功能会变，以你用的那个版本为准。
核心是三点：过期、限次、有记录。
```

# 第 7 步：离场前 20 分钟自查（10 分钟）

## 7.1 十条自查

| 序号 | 检查 | 命令 | 通过标准 |
|---|---|---|---|
| 1 | SSH 公钥 | `cat /root/.ssh/authorized_keys` | 只有客户的 |
| 2 | 普通账号 | `awk -F: '$3>=1000&&$3<65534' /etc/passwd` | 只有客户实名的 |
| 3 | 定时任务 | `crontab -l` | 只有备份 |
| 4 | 登录记录 | `last -10` | 只有客户 IP |
| 5 | 临时文件 | `ls /root /tmp` | 没有数据导出文件 |
| 6 | 脚本密码 | `grep -rn PASSWORD /opt/app/scripts` | 没有明文 |
| 7 | Git 凭证 | `ls -la ~/.git-credentials` | 不存在 |
| 8 | 应用账号 | 应用后台用户列表 | 你的账号已禁用 |
| 9 | 数据库角色 | `\du` | 没有多余角色 |
| 10 | 对外连接 | `ss -tnp` | 没有指向公网的 ESTAB |

## 7.2 第 10 条怎么做

```bash
ss -tnp state established
```

**应该看到：**

```text
Recv-Q Send-Q Local Address:Port  Peer Address:Port  Process
0      0      10.20.30.40:22      10.20.30.55:51234  users:(("sshd",pid=2841,fd=4))
0      0      172.18.0.3:54321    172.18.0.4:11434  users:(("node",pid=12,fd=21))
```

**逐行读：**

| 行 | 判断 |
|---|---|
| `10.20.30.40:22 ← 10.20.30.55` | 客户 SSH 登录，正常 |
| `172.18.0.3 → 172.18.0.4:11434` | 容器间调用模型，正常 |
| **没有 `47.98.x.x:443`** | **正确，没有出网** |

**如果看到公网地址：**

```text
立刻查是哪个进程：
ss -tnp state established | grep -v "10\.\|172\.\|127\."
```

**任何一条到公网的连接，都要能解释清楚。解释不了就是后门。**

```text
② 改了配置导致起不来，说是你装的问题
③ 忘了密码，问你能不能找回来（你不能，也不该能）
```

# 第 8 步：故意犯 6 个错（35 分钟）

## 错误 1：先删自己的钥匙，再加客户的

**操作：**

```bash
> /root/.ssh/authorized_keys      # 清空
```

**然后想起来还没加客户的公钥。**

**会怎样：**

```bash
ssh root@10.20.30.40
```

```text
root@10.20.30.40: Permission denied (publickey).
```

**再试密码登录：**

```text
root@10.20.30.40: Permission denied (publickey).
```

**为什么连密码都不让用：**

```text
如果 sshd_config 里设了 PasswordAuthentication no（第 212 节课教的），
就只能用密钥。密钥没了，密码也不让用，就彻底进不去。
```

**怎么修：**

```text
① 让客户去机房，用物理控制台登录（如果有）
② 或者客户有云平台的 VNC 控制台
③ 都没有的话，只能重装系统 —— 这是最坏结果
```

**正确顺序：**

```text
① 加客户公钥
② 让客户开新窗口验证能登
③ 确认客户登进去了
④ 再删自己的
⑤ 自己再试一次，确认进不去（这一步是验证"真的删掉了"）
```

**第 ⑤ 步很重要：**

```text
你不试，就不知道有没有删干净。
试了进不去，才是真的交出去了。
```

## 错误 2：删了唯一的管理员账号

**操作：**

你在应用里把自己的 `admin@customer.local` 删了，还没建客户的。

**会怎样：**

```text
登录页面 → 输入客户账号 → 提示"用户不存在"
用 admin 登录 → 提示"用户不存在"
```

**数据库里看：**

```bash
docker compose exec postgres psql -U chatapp -d chatapp -c "SELECT email, role, status FROM users;"
```

**应该看到：**

```text
        email         | role  | status
----------------------+-------+---------
 li@hospital.local    | user  | active
 wang@hospital.local  | user  | active
(2 rows)
```

**一个 admin 都没有。**

**为什么：**

```text
你把唯一的 admin 删了，剩下两个都是普通用户。
普通用户没有"管理用户"的权限，谁也建不了新账号。
```

**怎么修（还有数据库权限的情况下）：**

```sql
UPDATE users SET role = 'admin' WHERE email = 'li@hospital.local';
```

**应该看到：**

```text
UPDATE 1
```

**然后让 li 登录，建其他人的账号。**

**正确做法：**

```text
① 先建客户 admin
② 让客户登录验证
③ 再禁用你的 admin（不是删除）
④ 禁用后自己试一次登录，确认进不去
```

**为什么"禁用"不"删除"：**

```text
① 审计要看到"账号变更记录"
② 万一客户 admin 出问题，还能临时恢复
③ 删除是不可逆的，禁用是可逆的
```

## 错误 3：客户改了数据库密码，`.env` 没改

**操作：**

交接会上客户自己 `ALTER USER` 改了密码，你没改应用配置。

**会怎样：**

```bash
docker compose restart app
docker compose logs app --tail 20
```

```text
Error: password authentication failed for user "chatapp_app"
    at /app/node_modules/pg/lib/client.js:526:15
    at process.processTicksAndRejections (node:internal/process/task_queues:95:5)
```

**为什么：**

```text
应用用 .env 里的 DATABASE_URL 连库。
客户改了数据库里的密码，.env 里还是旧的，两边对不上。
```

**怎么修：**

```bash
# 改 .env
vi /opt/app/.env
# 改 DB_PASSWORD

docker compose up -d app
```

**`up -d` 而不是 `restart`：**

```text
restart 只是重启容器，环境变量还是旧的。
up -d 会重新读取 compose 和 .env，重建容器。
改环境变量必须用 up -d。
```

**正确顺序：**

```text
① 客户在数据库里改密码
② 你在 .env 里改同样的密码
③ docker compose up -d app
④ 验证应用能连上
⑤ 在交接单上记录"密码变更时间"
```

**⚠️ 两个人同时改密码，最容易出错。**

```text
让一个人操作，另一个人看着。
改完立刻验证，不要等到明天。
```

## 错误 4：交接单没写证书到期日

**操作：**

交接单上写"HTTPS 证书已交接"，没写什么时候到期。

**会怎样：**

**一年后：**

```text
客户：网站打不开了，浏览器提示"证书已过期"。
你：证书到期了，要换。
客户：这个不是你们负责吗？
你：交接单上写了证书已经交给你们了。
客户：但你没说会过期啊。
```

**为什么：**

```text
内网证书不能自动续期（没外网，certbot 用不了）。
必须人工换。
一年后没人记得，必然过期。
```

**怎么修：**

**交接单上加三行：**

```text
证书到期日：2027-03-10
续期方式：联系 XXX 重新签发，或使用甲方内网 CA
续期责任：甲方
```

**并且：**

```text
① 把到期日写进你自己的日历（提前 30 天提醒）
② 在《运维手册》第一页写一条"每年 3 月检查证书"
③ 如果年费包含证书，写清"每年提供一次证书更新"
```

**为什么你自己也要记：**

```text
即使合同写了是客户的责任，证书过期时客户第一个电话还是打给你。
提前 30 天提醒一句，比事后解释一小时便宜。
```

## 错误 5：留了一个"心跳"定时任务

**操作：**

为了方便监控，你加了：

```bash
*/10 * * * * curl -s "http://47.98.xx.xx/api/beat?host=$(hostname)&ver=1.2.0" >/dev/null
```

**会怎样：**

**三个月后客户做流量审计：**

```text
客户：我们发现这台服务器每隔 10 分钟向一个外部 IP 发请求。
你：那是我加的心跳，用来监控服务活着。
客户：也就是说，我们的服务器一直在向你们公司上报数据？
你：只上报主机名和版本号……
客户：这属于数据外传，要写进整改单。
```

**为什么这很严重：**

```text
① 客户的网络策略可能是"禁止任何出网连接"，你违反了
② 就算只发主机名，也是"未授权的对外通信"
③ 审计报告上会写"存在未申报的外联通道"
④ 这会让整个项目的信任度归零
```

**怎么修：**

```bash
crontab -e
# 删掉那一行
```

**如果要监控，用合规的方式：**

| 方式 | 做法 | 合规性 |
|---|---|---|
| 客户自己的监控 | 客户用 Zabbix/Prometheus 监控本机 | ✅ 数据不出内网 |
| 客户主动上报 | 客户 IT 每周发一次状态截图 | ✅ |
| 内网监控服务器 | 在客户内网部署一台监控机 | ✅ |
| 厂商外联心跳 | 你的服务器接收客户数据 | ❌ |

**核心区别：谁发起连接、数据往哪走。**

```text
客户→你：客户主动发，数据出网，但客户知情。
你→客户：你连进去，需要客户开权限。
客户内网内部：数据不出网，最安全。
```

## 错误 6：微信发密码，客户没改

**操作：**

```text
微信：张工，root 密码是 Abc@123456，数据库密码一样。
张工：收到，谢谢。
```

**会怎样：**

**半年后出事：**

```text
审计：root 密码从未修改，且通过微信传输，存在泄露风险。
客户：这是厂商交付时设的。
你：我发过密码，你们没改。
客户：你没说要改。
```

**为什么这是你的责任：**

```text
① 密码是你设的，也是你发的
② 你没有在交接单上写"密码已由甲方重置"
③ 微信记录证明"密码由乙方掌握"
```

**怎么修：**

**当场补救：**

```text
① 立刻让客户改密码（远程指导或到场）
② 补一份交接记录，写清"X 年 X 月 X 日已重置"
③ 如果密码在别处也用过，全部改掉
```

**下次怎么做：**

```text
① 密码不由你设 —— 装机时就让客户设，或者装完立刻让客户改
② 不用微信发 —— 现场让客户自己敲，或密码管理器一次性链接
③ 交接单写明 —— "密码已于 X 时由甲方重置，乙方不知晓"
```

**一句话记住：**

```text
只要你还能登录客户的系统，你就还是"有可能泄露数据的人"。
交接的本质，是把这个可能性去掉。
```

# 附：常见问题速查

| 现象 | 原因 | 怎么做 |
|---|---|---|
| `Permission denied (publickey)` | 没有可用密钥 | 用控制台登录，加回公钥 |
| 客户改了密码应用连不上 | `.env` 没同步 | 改 `.env` 后 `up -d app` |
| `Account expires` 到了还能登 | 已有会话不会断 | `pkill -u 账号` |
| 删了管理员进不去后台 | 没有其他 admin | 数据库里 `UPDATE users SET role` |
| 审计说"存在厂商账号" | 没删干净 | 按十条自查逐项处理 |
| 审计说"存在外联" | 有心跳/cron | 删 cron，改用客户内网监控 |
| 证书过期 | 内网不能自动续 | 手动换，提前写进日历 |
| 客户问"你们还能进吗" | 交接没做干净 | 现场演示"我登不进去" |
| 客户忘了密码 | 正常 | 走临时账号流程，不要"帮他找回" |
| 交接单客户不签 | 觉得没必要 | 说明这是审计要的，不是你不信任他 |
| 客户要求"永久维护账号" | 图省事 | 拒绝，改临时账号 + 工单 |
| 客户 IT 离职，没人会操作 | 培训不足 | 第 238 节课的培训要点要补 |
