# 第 1 步：四件套分别给谁看（15 分钟）

## 1.1 一张表说清

| 文档 | 读者 | 什么时候看 | 多长 | 成功标准 |
|---|---|---|---|---|
| 安装手册 | 客户的实施人员 / 你自己 | 重装、迁移、扩容 | 15—30 页 | 照着做能装出来 |
| 运维手册 | 客户 IT 值班人员 | 每天 / 出故障时 | 10—20 页 | 能自己重启、能描述故障 |
| 验收单 | 客户负责人 + 你 | 验收会 | 2—4 页 | 逐条勾，双方签字 |
| 培训要点 | 客户 IT + 业务骨干 | 培训那 30 分钟 | 3—5 页 | 听完能操作 |

**四个读者，四种写法。**

## 1.2 最常见的错误：四份写成一份

**很多人交一本 80 页的《系统交付文档》，里面什么都有。**

**结果：**

```text
安装的人找不到安装步骤（夹在第 4 章第 3 节）
运维的人找不到重启命令（夹在第 7 章）
验收的人找不到勾选项（散在各处）
```

**正确做法：**

```text
四份独立文档，每份都能单独使用。
互相引用可以，但不能"必须看另一份才懂"。
```

## 1.3 文档的"版本-日期-适用版本"三件套

**每份文档第一页必须有：**

```text
文档版本：v1.0
编写日期：2026-03-12
适用系统版本：v1.2.0
编写人：XXX
```

**为什么必须有"适用系统版本"：**

```text
系统升级到 1.3.0 之后，1.2.0 的安装手册可能就不对了（比如多了一个环境变量）。
没有这个字段，你分不清手里这份文档是哪一版的。
```

**每次系统升级，四份文档都要检查一遍是否需要更新。**

| 升级类型 | 文档要不要改 |
|---|---|
| 只修 bug | 不用 |
| 加环境变量 | 安装手册 + 运维手册 |
| 加功能 | 四份都要（验收单加项） |
| 改表结构 | 运维手册（备份恢复部分） |

## 1.4 逐行读：一份好文档和一个坏文档

**❌ 坏：**

```text
3.2 启动服务
使用 docker compose 启动所有服务。
```

**问题：**

```text
① 在哪执行？没有 cd
② 用什么账号？没说
③ 起了之后怎么知道成功？没说
④ 报错怎么办？没说
```

**✅ 好：**

```text
3.2 启动服务

操作：
1. 用 root 登录服务器。
2. 进入部署目录：
   cd /opt/app
3. 启动：
   docker compose up -d
4. 等待约 30 秒，检查状态：
   docker compose ps

应该看到：
NAME             IMAGE             STATUS
chatapp-app      chat-app:1.2.0    Up (healthy)
chatapp-db       postgres:16.3     Up (healthy)
chatapp-nginx    nginx:1.25.3      Up

如果看到 Exit 或 Restarting：
   docker compose logs app --tail 50
   把输出发给技术支持。
```

**逐项对比：**

| 要素 | 坏文档 | 好文档 |
|---|---|---|
| 在哪做 | 没写 | `cd /opt/app` |
| 谁做 | 没写 | root |
| 做什么 | 一句话 | 编号步骤 |
| 成功什么样 | 没写 | 贴了真实输出 |
| 失败怎么办 | 没写 | 给了下一步命令 |

**这五个要素，是"可执行文档"的标准。**

## 2.5 第 6 章：配置系统（最容易卡住的一章）

```markdown
## 6. 配置系统

### 6.1 创建管理员密码

系统首次启动需要设置管理员账号。

操作：
1. 编辑配置文件：
   cd /opt/app
   vi .env
2. 找到这几行，把值改成你的密码：

   DB_PASSWORD=请填写数据库密码
   SESSION_SECRET=请填写32位随机字符串
   ADMIN_PASSWORD=请填写管理员初始密码

3. 生成随机字符串（任选一种）：

   openssl rand -base64 24

   如果提示 openssl 不存在：
   head -c 24 /dev/urandom | base64

   应该看到类似：
   k7Qm2XvT9pLzR4sN8wYcB6dF

4. 保存退出（vi：按 Esc，输入 :wq 回车；nano：Ctrl+O 回车，Ctrl+X）

5. 确认权限：
   ls -l .env

   应该看到：
   -rw------- 1 root root 356 Mar 12 10:00 .env

   chmod 600 .env
```

**为什么这一章要写这么细：**

```text
这是客户最容易卡住、也最容易搞错的地方。
密码权限不对，等于把数据库交给所有登录用户。
```

## 2.6 第 7 章：启动与验证

```markdown
## 7. 启动与验证

### 7.1 启动

cd /opt/app
docker compose up -d

应该看到：
[+] Running 4/4
 ✔ Network app_backend       Created
 ✔ Container chatapp-db      Healthy
 ✔ Container chatapp-app     Started
 ✔ Container chatapp-nginx   Started

### 7.2 验证（五项，全过才算成功）

第一项：容器状态
docker compose ps

应该看到三个都是 Up，其中两个带 (healthy)。

第二项：健康接口
curl -s http://127.0.0.1/health

应该看到：
{"status":"ok","db":"ok","version":"1.2.0"}

第三项：页面访问
在浏览器打开 http://服务器IP/

应该看到登录页面。
如果打不开，按《运维手册》第 5 节排查。

第四项：登录
用 .env 里的 ADMIN_PASSWORD 登录。

第五项：提问
在对话框输入"你好"，应该 10 秒内有回答。
```

**五项验证，覆盖了"进程 - 接口 - 页面 - 登录 - 功能"。**

**只写"启动成功"是不够的。**

**逐行读 `docker compose ps` 那张输出：**

| 行 | 容器 | 状态 | 说明什么 | 不这样说明什么 |
|---|---|---|---|---|
| `chatapp-app` | 你的应用 | `Up (healthy)` | 进程活着，且健康检查通过 | `Up` 但没有 `(healthy)` → 健康检查还没过或没配 |
| `chatapp-db` | 数据库 | `Up (healthy)` | 数据库能接受连接 | `Up (unhealthy)` → 库起了但不能用（密码错、卷权限错） |
| `chatapp-nginx` | 反向代理 | `Up` | 端口在监听 | 这里没 `(healthy)` 是正常的，nginx 镜像没配健康检查 |
| `Exit 1` 任意一个 | — | 已退出 | **启动就崩了** | 看 `docker compose logs <服务名>` |
| `Restarting` 任意一个 | — | 反复重启 | 配置错或依赖没起来 | **这比 Exit 更隐蔽**，它会一直占着 CPU 刷日志 |

**读法：**

```text
① 先看有没有 Exit / Restarting —— 有的话后面全不用看
② 再看三个是不是都在 Up
③ 最后看两个 (healthy) 有没有出现
④ 少一个 (healthy)，就用 curl /health 确认到底是哪一层不行
```

**为什么 `Up` 不等于可用：**

```text
Up 只代表"容器里的主进程还活着"。
你的 Node 进程可以活得好好的，但数据库连不上，每个请求都 500。
所以安装手册必须写"下一步：curl /health"，而不是"看到 Up 就完事"。
```

## 2.7 第 9 章：卸载（客户很在意）

```markdown
## 9. 卸载

⚠️ 卸载会删除所有数据，操作前必须备份。

### 9.1 备份（必须做）

/opt/app/scripts/backup.sh

确认备份文件存在：
ls -lh /opt/app/backup/

### 9.2 停止并删除容器

cd /opt/app
docker compose down

### 9.3 删除数据（不可恢复）

⚠️ 以下命令会永久删除数据，执行前请再次确认已备份。

rm -rf /opt/app

### 9.4 卸载 Docker（可选）

systemctl stop docker
systemctl disable docker
rm -rf /var/lib/docker
```

**为什么客户在意"卸载"：**

```text
能装不能卸的系统，客户不敢用。
"删一个目录就干净了"是单机 compose 方案的一大卖点。
```

**⚠️ 所有的 `rm -rf` 前面都要有警告和"先备份"。**

## 3.3 故障树：一张图走到底

```text
系统打不开
│
├─ 能 ping 通服务器吗？
│   ├─ 不能 → 服务器关机 / 网络断 / IP 变了
│   │          → 联系甲方网络管理员
│   └─ 能 → 继续
│
├─ SSH 能进吗？(ssh root@IP)
│   ├─ 不能 → 22 端口被封 / 密码错 / 磁盘满导致 sshd 挂
│   │          → 用控制台登录，df -h
│   └─ 能 → 继续
│
├─ Docker 活着吗？(systemctl status docker)
│   ├─ 挂了 → systemctl start docker
│   └─ 活着 → 继续
│
├─ 容器在跑吗？(docker compose ps)
│   ├─ 有 Exit → docker compose logs <服务> --tail 50
│   ├─ 有 Restarting → 同上，多半是配置错
│   └─ 都 Up → 继续
│
├─ 本机能访问吗？(curl localhost/health)
│   ├─ 不通 → 应用问题，看 logs app
│   └─ 通 → 继续
│
├─ 本机能访问页面吗？(curl -I localhost/)
│   ├─ 502 → nginx 转发失败，看 nginx 配置里的 upstream
│   ├─ 404 → server_name 不匹配
│   └─ 200 → 继续
│
└─ 别的机器能访问吗？
    ├─ 不能 → 防火墙 / 网段限制
    └─ 能 → 浏览器缓存 / 用户电脑 DNS
```

## 3.4 日常操作：四条命令

**用表格写，不要用段落。**

| 操作 | 命令 | 什么时候用 |
|---|---|---|
| 看状态 | `docker compose ps` | 每天上班第一件事 |
| 重启应用 | `docker compose restart app` | 页面 500，改配置后 |
| 重启全部 | `docker compose down && docker compose up -d` | 大改动后 |
| 看日志 | `docker compose logs app --tail 100` | 任何异常 |

**⚠️ `down` 的注意事项必须写：**

```text
docker compose down 只删容器和网络，不删数据（数据在 ./data/）。
但不要加 -v，加了会删卷。
```

**为什么这句话必须写：**

```text
客户 IT 在网上搜到 docker compose down -v，一敲，数据没了。
```

```markdown

如果没有今天的目录，看日志：
tail -30 /opt/app/logs/backup.log

⚠️ 必须在测试库上做，不要动生产库。

1. 建测试库：
   docker compose exec postgres psql -U chatapp -d postgres -c "CREATE DATABASE restore_test;"
2. 恢复最新备份：
```


## 6.3 文档转 PDF

**为什么交 PDF 不交 Word：**

| 格式 | 优点 | 缺点 |
|---|---|---|
| Markdown | 好维护 | 客户打不开 |
| Word | 客户能改 | 排版会乱，版本失控 |
| **PDF** | **排版固定，不可改，能打印** | 不好改 |

**做法：**

```text
① Markdown 写原稿（你自己维护）
② 用工具转 PDF（VS Code 插件、pandoc、在线工具都行）
③ 文件名带版本号：安装手册-v1.0.pdf
④ 同时留 Markdown 原件在你自己的仓库里
```

**为什么文件名要带版本：**

```text
客户电脑里会有 v1.0 和 v1.1 两份。
不带版本号，他不知道哪份是新的。
```

**转 PDF 时检查三件事：**

```text
① 代码块有没有被截断（长命令要换行）
② 表格有没有超出页面
③ 中文字体有没有变成方块
```

## 7.1 项目复盘表

**交付完一周内，自己坐下来填这张表。**

| 项目 | 内容 |
|---|---|
| 合同额 | 68000 |

**"超支最多的环节"通常在这三个里：**

```text
① 环境适配（国产系统、ARM、数据库）
② 数据导入（格式乱、量大、只能导一次）
③ 验收扯皮（标准不清、签字人不在）
```

**这三个，正好对应第 232 节课的 12 个问题。**

```text
12 个问题问得越细，这三个环节越省时间。
```

## 7.2 一个真实的复盘（示例）

```text
项目：某医院，合同 68000
计划工时：17 天
实际工时：24 天

超支明细：
  国产数据库适配   计划 2 天 → 实际 6 天（达梦分页、主键、时间函数全要改）
  数据导入         计划 1 天 → 实际 3 天（客户给的 CSV 编码是 GBK，还有重复）
  验收             计划 1 天 → 实际 3 天（签字人要等院办会）

毛利：68000 − 24×1500 − 3000 = 29000（计划是 38600）
毛利率：42.6%（计划 56.8%）

结论：
  1. 国产库项目报价要乘 1.5
  2. 数据导入要单独报价，按数据量算
  3. 验收周期要写进合同，且要有"逾期视为通过"
```

**这张表比任何总结都有用。** 它告诉你下次该报多少钱。

## 7.3 收款节点要主动跟

| 节点 | 比例 | 你要做什么 |

| 质保期满 | 10% | 到期前一个月提醒客户 |

**验收单原件很重要。**

```text
很多客户付款流程要求"验收单原件"。
```

```text
验收后 6 个月或 12 个月，客户不会主动提醒你。
```

## 7.4 年费和续费的起点

**交付后第 10 个月，做三件事：**

```text
① 发一封"系统运行情况小结"（附上这一年的支持记录）
② 提醒证书到期日
③ 提出下一年的运维方案和报价
```

**为什么是第 10 个月：**

```text
太早，客户觉得你急着收钱。
太晚，客户已经找了别家。
第 10 个月，正好在合同到期前，有话可说。
```

**这封邮件模板：**

```text
X 主任，您好：

- 累计支持 12 次，其中紧急 1 次（3 月 15 日重启故障），已恢复

XX
```

**这封邮件的效果：**

```text
客户看到的是"有人在管这件事"，而不是"来收钱的"。
```

# 第 8 步：故意犯 6 个错（35 分钟）

## 错误 1：文档里没写"在哪个目录执行"

**操作：**

安装手册里写：

```text
3. 启动服务
docker compose up -d
```

**会怎样：**

客户在 `/root` 下执行：

```text
no configuration file provided: not found
```

**为什么：**

```text
docker compose 默认在当前目录找 docker-compose.yml。
客户在 /root，文件在 /opt/app，找不到。
```

**怎么修：**

```text
① 手册里补一句"cd /opt/app"
② 或者用 -f 指定文件：
   docker compose -f /opt/app/docker-compose.yml up -d
③ 更好：写成一个脚本，客户只需要执行脚本
```

**"可执行文档"的检验方法：**

```text
找一个没参与过这个项目的人，让他照着文档做一遍。
他卡在哪，就是文档缺哪。
```

**这个测试叫"新人测试"，成本一小时，能发现一半的问题。**

## 错误 2：安装手册没写密码规则，客户设了 123456

**操作：**

手册里写"请设置数据库密码"，没写要求。

**会怎样：**

客户设了 `123456`。

**安全扫描报告：**

```text
【高危】数据库账号使用弱口令
账号：chatapp
建议：使用 12 位以上，包含大小写字母、数字、符号
```

**为什么：**

```text
"请设置密码"这句话，对不懂安全的人等于"随便设一个"。
```

**怎么修：**

**手册里给明确规则和示例：**

```text
密码要求：
- 至少 16 位
- 包含大写字母、小写字母、数字、符号
- 不包含姓名、单位名、年份

生成方法（任选一种）：
  openssl rand -base64 24
  head -c 24 /dev/urandom | base64

示例（不要直接用这个）：
  k7Qm2XvT9pLzR4sN8wYcB6dF
```

**并且加一条检查：**

```bash
# 装完后检查密码长度
grep ^DB_PASSWORD= /opt/app/.env | awk -F= '{print length($2)}'
```

**应该看到：**

```text
32
```

**小于 16 就要改。**

## 错误 3：验收单写"系统运行正常"

**操作：**

```text
| 1 | 系统运行正常 | ☐通过 ☐不通过 |
```

**会怎样：**

**验收会：**

```text
客户：这个"正常"怎么判断？
你：就是能正常用。
客户：我觉得有点慢，算正常吗？
你：……
```

**为什么：**

```text
"正常"是主观词。
没有测量方法，就没有判断标准。
```

**怎么修：**

**每条都要有"验收方法"和"可量化标准"：**

```text
| 序号 | 验收项 | 验收方法 | 标准 | 结果 |
|---|---|---|---|---|
| 1 | 首页可打开 | 浏览器访问 http://IP/ | 3 秒内出现登录页 | ☐通过 ☐不通过 |
| 2 | 提问有回答 | 输入"你好" | 60 秒内出现回答 | ☐通过 ☐不通过 |
| 3 | 回答与文档相关 | 抽 5 个问题 | 至少 4 个相关 | ☐通过 ☐不通过 |
```

**三个要素：**

```text
动作（怎么测）+ 标准（多少算过）+ 结果（勾选）
```

## 错误 5：培训只讲不练

**操作：**

你在会议室讲了 40 分钟，客户听了，点头，散了。

**会怎样：**

**一周后：**

```text
客户：系统打不开了，你快看看。
你：你重启一下试试，docker compose restart app。
客户：在哪里敲？
```

**为什么：**

```text
听一遍的记忆留存率约 5%。
动手做一遍约 75%。
```

**怎么修：**

**培训必须留出"客户动手"的时间：**

```text
① 让客户自己打开终端
② 你念命令，他敲
③ 敲错了不要抢键盘，让他自己改
④ 每人至少做一遍"重启 + 看日志 + 找备份"
⑤ 做完在签到表上打勾
```

**验收单第 22 条就是为这个设计的：**

```text
"客户可独立重启服务 —— 客户现场操作一次"
这一条不过，说明培训没做到位。
```

**为什么不能你替他敲：**

```text
你替他敲，他永远学不会。
而且他会觉得"这个很难，我不敢动"。
```

## 错误 6：文档版本和系统版本对不上

**操作：**

系统升级到 1.3.0，新增了一个必填环境变量 `FEATURE_FLAG`。
安装手册还是 1.2.0 的版本。

**会怎样：**

**半年后客户重装：**

```bash
docker compose up -d
```

```text
Error: FEATURE_FLAG is required
    at config.js:12:11
```

**为什么：**

```text
1.3.0 的代码要求 FEATURE_FLAG 必须有值。
1.2.0 的安装手册里没有这一项。
```

**怎么修：**

**短期：**

```bash
echo "FEATURE_FLAG=on" >> /opt/app/.env
docker compose up -d
```

**长期：**

```text
① 每次升级，检查四份文档是否需要更新
② 文档头部写"适用系统版本"
③ 交付包里文档和安装包版本必须一致
④ 在 upgrade.sh 里加一步"打印需要人工确认的配置变更"
```

**检查方法：**

```bash
# 对比 .env.example 和实际 .env
diff /opt/offline/offline-package/config/.env.example /opt/app/.env
```

**逐行读 `diff` 的输出：**

| 输出形状 | 意思 | 你要做什么 |
|---|---|---|
| `< NEW_FLAG=on` | 只在新模板里有 | 加到实际 `.env` 里（否则新功能缺配置） |
| `> OLD_FLAG=xxx` | 只在老 `.env` 里有 | **不要急着删**，先确认新版本还认不认它 |
| `---` / `+++` | 文件分隔线 | 不处理 |
| `1234c1234` | 第 1234 行"改动"（change） | 逐字看，可能是值变了 |
| `1234a1235` | 新增（append） | 大概率要补 |
| `1234d1233` | 删除（delete） | **最危险的一类**，删掉可能导致启动失败 |

**读法：**

```text
< 号开头 = 左边（新模板）有、右边（实际 .env）没有  → 你要补进去
> 号开头 = 右边（实际 .env）有、左边没有           → 先问"这个还需不需要"
```

**为什么这一步必须手工做，不能脚本自动覆盖：**

```text
直接 cp .env.example .env → 你客户自己填的数据库密码、密钥全没了
脚本自动合并                → 碰上"要删的项"它会乱删
```

**升级时这一步必须做。** 第 237 节课讲过。

**一条规则：**

```text
系统版本变了，文档版本必须跟着变。
哪怕只改了一行，也要升版本号。
```
