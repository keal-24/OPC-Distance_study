# 第 1 步：先看一张坏表（15 分钟）

## 1.1 大多数人做的检查表长这样

```markdown
## 安全检查表

- [x] 密钥安全
- [x] 输入校验
- [x] 权限控制
- [x] 防注入
- [x] 上传安全
- [x] 日志安全
```

**六项全打了勾。看起来很棒。**

**问题在哪：**

```text
① "密钥安全"指什么？查了历史吗？服务器上的文件权限是多少？
② 谁检查的？什么时候？
③ 如果审计的人问"你怎么验证的"，你怎么答？
④ 三个月后你自己看这张表，能靠它复查吗？
```

**答案是：全答不上来。这张表是装饰品。**

## 1.2 一张好表的五个要素

每一项必须包含：

| 要素 | 例子 |
|---|---|
| **检查什么**（具体到能执行） | ".env 不在 Git 历史里" |
| **怎么验**（给命令） | `git log --all --oneline -- .env` |
| **通过标准**（什么算通过） | 输出为空 |
| **结论**（三选一） | 通过 / 不通过 / 不适用 |
| **证据**（贴输出或截图位置） | 贴输出 |

**只有五样都有，这一项才算"检查过"。**

## 1.3 一个例子，两种写法

**坏写法：**

```markdown
- [x] 密钥没泄露
```

**好写法：**

```markdown
### 1. 密钥不在 Git 历史里

**怎么验：**

```bash
git log --all --oneline -- .env
git log --all -p | grep -E "sk-[a-zA-Z0-9]{20,}|ghp_[a-zA-Z0-9]{20,}"
```

**通过标准：** 两条命令输出都为空。

**结论：** ✅ 通过

**证据：**

```text
（无输出）
```

**检查人 / 日期：** 我 / 2026-11-16
```

**差别在哪：**

```text
坏写法：你只能信我
好写法：任何人都能重跑一遍验证我
```

> **这就是"专业"和"业余"的分界。** 业余的说"我检查过了"，专业的给一张别人能复现的表。

### 2. `.env` 不在工作区被跟踪

```bash

```

**通过标准：** 无输出。

**再确认 `.gitignore` 里有它：**

```bash

```

**应该看到：**

```text

```bash

| 行 | 意思 |
|---|---|
| `.env` | 忽略根目录的这个文件 |
| `.env.local` | 忽略本机覆盖版 |
| `.env.*` | 忽略 `.env.production` 之类 |
| `!.env.example` | **例外**：这个要提交，它是模板 |

**没有 `!.env.example` 会出现什么：** 你以后想提交一个示例文件，被 `.gitignore` 拦住了，得加 `-f`，很容易忘。

### 3. 服务器上 `.env` 权限是 600

```bash
ls -l /srv/app/.env
```

**通过标准：** 权限列是 `-rw-------`。

**如果是 `-rw-r--r--`：**

```bash
chmod 600 /srv/app/.env
```

**一起检查这几个：**

```bash
ls -l /srv/app/.env /srv/app/data/*.db /srv/app/backups/ 2>/dev/null
```

**通过标准：** `.env` 和 `*.db` 都是 `600`，`backups/` 目录是 `700`。

**逐位读 `-rw-------` 这十位：**

| 位置 | 字符 | 意思 |
|---|---|---|
| 第 1 位 | `-` | 普通文件（`d` 才是目录） |
| 第 2—4 位 | `rw-` | **属主**可读、可写、不可执行 |
| 第 5—7 位 | `---` | **同组用户**什么都不能做 |
| 第 8—10 位 | `---` | **其他人**什么都不能做 |

**对比 `-rw-r--r--`（默认的 644）：**

| 位置 | 字符 | 意思 |
|---|---|---|
| 第 2—4 位 | `rw-` | 属主可读写 |
| 第 5—7 位 | `r--` | **同组可读** ← 这就是洞 |
| 第 8—10 位 | `r--` | **所有人可读** ← 这就是事故 |

**为什么数据库文件也要 600：** 里面有用户的全部数据。**不需要"能执行"，也不需要"别人能读"。**

**为什么 `backups/` 要 700：** 目录的 `x` 位是"能进去"，`r` 位是"能列出文件名"。`700` 意味着只有你能进、能列、能写，**别人连目录里有什么文件都看不到**。

## B 组：输入与权限（5 项）

### 5. 每个写接口都有服务端校验

```bash
grep -rn "app\.\(post\|put\|patch\|delete\)" server.js
```

**通过标准：** 每一条后面都能看到 `validate` / `check` / `schema.parse` 之类的调用。

**如果看到这样的：**

```js
app.post("/api/chat", requireLogin, async (req, res) => {
  const { messages } = req.body;        // ❌ 直接用了
```

**就是没校验。**

**怎么验真的挡住了：**

```bash
# 发一个空的
curl -i -X POST http://127.0.0.1:3000/api/chat \
  -H "Content-Type: application/json" \
  -H "Cookie: sid=..." \
  -d '{}'
```

**通过标准：** `HTTP/1.1 400`，body 里有明确错误码。

**不通过的样子：**

```text
HTTP/1.1 500 Internal Server Error
```

**500 比 200 更糟。** 因为 500 说明代码崩了，通常还会在日志里留一段带文件路径的栈。

**一条批量验的命令：**

```bash
for body in '{}' '{"messages":"not-an-array"}' '{"messages":[]}' '{"messages":[{"role":"x"}]}'; do
  echo "--- $body"
  curl -s -o /dev/null -w "%{http_code}\n" -X POST http://127.0.0.1:3000/api/chat \
    -H "Content-Type: application/json" -H "Cookie: sid=..." -d "$body"
done
```

**通过标准：** 全是 `400`，一个 `500` 都没有。

### 6. 越权：改 id 看不到别人的数据

```bash
# 用 A 的 cookie 读 B 的资源
curl -i http://127.0.0.1:3000/api/messages/2 -H "Cookie: sid=<A的>"
```

**通过标准：** `404`。

**关键：必须是 404，不是 403。**

```text
403 → 这个 id 存在，但不是你的（泄露了"存在性"）
404 → 可能不存在，也可能不是你的（不泄露任何东西）
```

**批量扫一遍：**

```bash
for id in 1 2 3 4 5 100 999; do
  code=$(curl -s -o /dev/null -w "%{http_code}" \
    http://127.0.0.1:3000/api/messages/$id -H "Cookie: sid=<A的>")
  echo "$id -> $code"
done
```

**通过标准：** 只有属于 A 的那几个是 `200`，其余全 `404`。

**逐行读一次真实的扫描输出：**

| 行 | 输出 | 结论 | 为什么 |
|---|---|---|---|
| `1 -> 200` | 200 | ✅ 正常 | id=1 是 A 自己的，看得到是对的 |
| `2 -> 404` | 404 | ✅ 正常 | id=2 是 B 的，返回"不存在"，不泄露任何信息 |
| `3 -> 404` | 404 | ✅ 正常 | 同上 |
| `4 -> 200` | 200 | ❌ **有洞** | 如果 4 不是 A 的，这个 200 就是越权成功 |
| `100 -> 404` | 404 | ✅ 正常 | 不存在，和"不是我的"给同一个回答 |
| `999 -> 404` | 404 | ✅ 正常 | 同上 |
| 全部 `200` | 200×7 | ❌ **最严重** | 接口完全没检查归属，是"游客模式" |
| 全部 `403` | 403×7 | ⚠️ 藏着洞 | 403 说明"存在但不是你的"，等于告诉了攻击者哪些 id 真实存在 |

**读法：**

```text
① 先数有几个 200，和你实际拥有的数据条数对上没有
② 再看 404 和 403 有没有混着出现（混着出现 = 半修）
③ 最后看有没有 500（500 说明查询本身炸了，可能压根没走 user_id 分支）
```

**"全部 403"为什么也是问题：**

```text
攻击者发 1..1000，收到 403 的那些 id 是真实存在的。
然后他拿真 id 去想别的办法（社工、撞库、找别的接口）。
而你什么都没泄露，本来可以让他一无所获。
```

**如果所有 id 都返回 200：** 你的接口根本没检查归属，是"游客模式"。

### 7. 写操作也带 `user_id`

```bash
grep -rn "UPDATE\|DELETE" server.js db.js | grep -v "user_id"
```

**通过标准：** 输出为空，或者每一条你都人工确认过"这条不涉及用户数据"。

**典型的漏法：**

```js
// ❌ 只看 id
await db.run("DELETE FROM messages WHERE id = ?", [id]);

// ✅ 两个条件
await db.run("DELETE FROM messages WHERE id = ? AND user_id = ?", [id, uid]);

**验的方式：**

# 用 A 的 cookie 删 B 的消息
curl -i -X DELETE http://127.0.0.1:3000/api/messages/2 -H "Cookie: sid=<A的>"
```

**通过标准：** `404`，**并且 B 的消息还在**：

```bash
sqlite3 data/app.db "SELECT COUNT(*) FROM messages WHERE id = 2;"
```

### 8. 列表接口不返回别人的数据

```bash
curl -s http://127.0.0.1:3000/api/messages -H "Cookie: sid=<A的>" | \
  python -c "import sys,json; d=json.load(sys.stdin); print(len(d.get('items',d)))"

**通过标准：** 条数等于 A 自己的消息数。

**这条最容易漏**，因为它不报错、不异常，只是多返回了几条。

**四种容易漏的形态：**

```text

④ 统计        GET /api/stats（返回总数时泄露了别人的数据量）

### 9. 身份只来自服务端会话

```bash
grep -rn "req\.body\.user_id\|req\.query\.user_id\|req\.body\.userId" server.js
```

**通过标准：** 输出为空。

**如果有：** 这是最严重的一类洞。攻击者只要在请求里塞 `user_id=1`，就能以别人的身份操作。

**正确写法：**

```js
// 中间件统一注入
app.use((req, res, next) => {
  const sid = req.cookies?.sid;
  const user = sessions.get(sid);      // 只从会话查
  req.user = user || null;
  next();
});

// 用的时候
const uid = req.user.id;               // ✅ 永远从这里取
```

**为什么这条最容易被写错：** 因为"让前端传 user_id"在开发时很方便 —— 不用登录就能测。

**这个方便是要还的。**

### 11. 不能参数化的地方走白名单

```bash
grep -rn "ORDER BY\|LIMIT" server.js | grep '\${'
```

**通过标准：** 每一处都走映射表。

```js
const SORT = {
  newest: "created_at DESC",
  oldest: "created_at ASC",
};
const order = SORT[req.query.sort] || SORT.newest;   // ✅ 白名单
// 不要：`ORDER BY ${req.query.sort}`             ❌
```

**为什么 `ORDER BY ?` 不行：** 占位符只能替代**值**，不能替代**标识符**（表名、列名、排序方向）。

**验一下：**

```bash
curl -s "http://127.0.0.1:3000/api/messages?sort=xxx" -H "Cookie: sid=..." | head -c 100
```

**通过标准：** 正常返回（走了默认排序），不是 500。

### 13. 上传四道关都在

```bash
curl -s -o /dev/null -w "%{http_code}\n" -F "file=@evil.html" \
  http://127.0.0.1:3000/api/avatar -H "Cookie: sid=..."
```

**通过标准：** `400`，body 里有明确的拒绝原因。

**四项都要验：**

| 验什么 | 命令 | 通过标准 |
|---|---|---|
| 扩展名白名单 | 传 `evil.html` | 400 |
| 伪造类型 | `curl -F "file=@evil.html;type=image/png"` | 400（魔数拦住了） |
| 大小限制 | 传 50MB 文件 | 413，且信息里有上限 |
| 直链不可访问 | 访问 `/uploads/xxx` | 404 |

**最后一条最容易漏验：**

```bash
curl -i http://你的域名/uploads/anything.jpg
```

**通过标准：** `404`。

**如果返回 `200`：** 文件还在 web 根里，第 229 节白做了。

## D 组：日志、依赖、运维（4 项）

### 14. 日志里没有敏感信息

```bash
grep -cE "1[3-9][0-9]{9}" /var/log/nginx/access.log /srv/app/logs/*.log 2>/dev/null
```

**通过标准：** 全是 `0`（或者数字明显异常时人工抽查一行）。

**抽一行看看实际内容：**

```bash
sudo tail -3 /var/log/nginx/access.log
```

**要确认两件事：**

```text
① 没有 ?phone= / ?idcard= / ?token=
② 应用日志里没有完整手机号
```

**再看你的访问日志格式用的是哪个变量：**

```bash
sudo grep -n "log_format\|access_log" /etc/nginx/nginx.conf /etc/nginx/sites-enabled/*
```

**通过标准：** 用的是 `$uri`，不是 `$request`。

---

### 15. 依赖审计干净或不修的都有记录

```bash
npm audit --audit-level=high
```

**通过标准：** `found 0 vulnerabilities`，或者报出来的每一条都在 `deps-audit.md` 里。

**顺便锁死版本：**

```bash
ls -l package-lock.json
```

**通过标准：** 文件存在，且在 Git 里：

```bash
git ls-files | grep package-lock.json
```

**为什么：** 没有 lock 文件，服务器上 `npm install` 每次装的版本可能不一样。**今天能跑，明天挂**，就是这么来的。

（你的 CI 应该用 `npm ci`，它要求 lock 文件存在。）

---

### 16. 数据库端口不对公网开

```bash
# 在服务器上
ss -lntp | grep -E "3306|5432"
```

**通过标准：** 本地地址是 `127.0.0.1:3306`，不是 `0.0.0.0:3306`。

**从你的电脑验（这一步才是真的）：**

```bash
# 在你本地 Windows 上跑
nc -zv 47.98.xx.xx 3306
```

**通过标准：** `Connection refused` 或超时。

**如果连上了：** 立刻改，不要等到明天。开放 3306 的机器一般几小时内就会被扫到。

**再确认 Nginx 只转发你那一个端口：**

```bash
grep -n "proxy_pass" /etc/nginx/sites-enabled/*
```

**通过标准：** 只有 `127.0.0.1:3000` 这一条。**所有 `proxy_pass` 都该是 `127.0.0.1`。**

---

### 17. HTTPS 全站，且自动续期正常

```bash
curl -sI http://你的域名 | head -3
```

**通过标准：** `301` 或 `308`，`Location` 是 `https://`。

```bash
curl -sI https://你的域名 | head -3
```

**通过标准：** `200`。

**续期演练：**

```bash
sudo certbot renew --dry-run
```

**通过标准：** 输出里有 `Congratulations, all simulated renewals succeeded`。

**为什么这一项必须验：** 证书过期那天的现象是"网站打不开，浏览器报不安全"，而你不会每天看它。**90 天后突然挂，是最典型的死法。**

---

### 18. 备份存在，且恢复演练过

```bash
ls -lh /srv/backups/ | tail -5
```

**通过标准：** 最近一个备份的时间在 24 小时内，大小不是 0。

**更硬的通过标准：你做过一次恢复。**

```bash
# 真的恢复一次（在测试目录里，别在正式库上）
sqlite3 /tmp/restore-test.db < backups/latest.sql
sqlite3 /tmp/restore-test.db "SELECT COUNT(*) FROM users;"
```

**通过标准：** 行数和正式库接近。

**没测过恢复的备份等于没备份。** 这一句话在这一周出现第二次了。

---

### 19. 敏感接口有频率限制

```bash
for i in $(seq 1 20); do
  curl -s -o /dev/null -w "%{http_code} " -X POST http://127.0.0.1:3000/api/login \
    -H "Content-Type: application/json" -d '{"phone":"13800138000","password":"wrong"}'
done
echo
```

**通过标准：** 前几次是 `401`，后面变成 `429`。

**如果 20 次全是 401：** 没有限流，登录接口可以被无限次试密码。

**最该限流的三个接口：**

```text
① 登录 / 验证码发送      ← 暴力破解 + 短信轰炸，直接烧钱
② 调用模型的接口          ← 刷你的 token 账单
③ 上传                    ← 塞满磁盘
```

ls -l SECURITY-CHECKLIST.md RUNBOOK.md

客户看完能回答：我的数据安全吗？出问题你会怎么处理？多久能恢复？
```

# 第 4 步：写修复清单（15 分钟）

## 4.1 没通过的项怎么处理

**建 `修复清单.md`：**

```markdown
# 修复清单

| # | 问题 | 风险 | 临时措施 | 彻底修法 | 截止 | 状态 |
|---|---|---|---|---|---|---|
| 8 | 列表接口返回了别人的数据 | 高：能看全部用户对话 | 先下线这个接口 | 查询加 `user_id` | 2026-11-17 | 进行中 |

```

**四列必须有：风险、临时措施、彻底修法、截止日。**

**为什么要有"临时措施"：**

```text
彻底修可能要三天。这三天你的网站还在公网上跑。
临时措施（先下线、先加白名单、先关端口）能让你活过这三天。
```

## 4.2 风险的三个等级

```text
高：能被远程利用，且后果是"数据泄露 / 被人控制"
    → 今天修，或者今天就下线这个功能

中：需要特定条件才能利用（要有账号、要特定配置）
    → 本周内修

低：理论上存在，实际很难触发
    → 记下来，下个迭代修
```

**不要把所有问题都标"高"。** 全标高的结果是一个都不修。

## 4.3 修完要回来改结论

**这是最容易被跳过的一步。**

```text
① 修完
② 重跑那条命令
③ 把表里的 ❌ 改成 ✅
④ 把证据换成新的输出
⑤ 更新汇总数字和日期
```

**没改结论 = 表在骗人。**

# 第 5 步：故意犯五个错（25 分钟）

## 错误 1：把"检查过"当成"通过"

**操作：**

```markdown
| 6 | 越权 | 改 id 看不到别人的数据 | ✅ 通过 | 我检查过了 |
```

**会怎样：** 表看起来很漂亮。

**为什么错：**

```text
"我检查过了"不是证据。
三个月后你自己都不记得当时怎么检查的。
审计的人问"你怎么验的"，你答不上来。
```

**怎么修：**

```markdown
| 6 | 越权 | 改 id 看不到别人的数据 | ✅ 通过 | 见下方输出 |
```

```text
for id in 1 2 3 4 5 100 999; do
  code=$(curl -s -o /dev/null -w "%{http_code}" ...)
  echo "$id -> $code"
done

1 -> 200
2 -> 404
3 -> 404
4 -> 404
5 -> 404
100 -> 404
999 -> 404
```

**"证据"那一列必须是能贴出来的东西：命令输出、截图、文件路径。**

## 错误 2：20 项全打勾

**操作：** 一项一项往上打 ✅，五分钟填完。

**会怎样：** 汇总表显示 20/20。

**为什么错：**

```text
① 五分钟填完 = 你没真跑任何一条命令
② 真实的系统不可能 20 项全过
③ 客户看到"全部通过"会问："那你们做过渗透测试吗？"
```

**怎么修：**

```text
每填一项，必须先跑那条命令，把输出贴上去。
跑完 20 条，至少需要 50 分钟。
少于 50 分钟的表，一定是假的。
```

## 错误 3：把"不适用"当偷懒的出口

**操作：**

```markdown
| 13 | 上传安全 | ⭕ 不适用 |
| 19 | 频率限制 | ⭕ 不适用 |
| 20 | 说明文件 | ⭕ 不适用 |
```

**会怎样：** 汇总看起来"没有不通过"。

**为什么错：**

```text
你的项目明明有上传功能（头像）。
你的项目明明有登录接口，需要限流。
"不适用"被你用成了"我不想做"。
```

**怎么修：** 每个"不适用"必须写一句理由，而且理由是**关于功能的**，不是关于你的意愿：

```markdown
| 13 | 上传安全 | ⭕ 不适用 | v1.0.0 只支持纯文本对话，无上传入口 |
```

**自查方法：**

```bash
# 你真的没有上传功能吗
grep -rn "multer\|formidable\|multipart" server.js package.json
```

**有输出 = 你有上传功能，"不适用"就是假的。**

## 错误 4：修完不改表

**操作：**

```text
① 表里第 8 项标了 ❌
② 你去改了代码，加上了 user_id
③ commit，push
④ 表里还是 ❌
```

**会怎样：** 一个月后你翻这张表，以为还有个洞，又去查一遍。

**为什么错：** 表的意义是"当前状态",不是"曾经的状态"。

**怎么修：**

```text
① 修完立刻重跑命令
② 把 ❌ 改成 ✅
③ 换掉证据
④ 更新汇总数字
⑤ 更新日期（这一项重新检查的日期）
```

**更好的做法：把检查做成脚本。**

```bash
# security-check.sh
#!/usr/bin/env bash
echo "=== 1. 密钥不在历史 ==="
git log --all --oneline -- .env || true
echo "=== 2. .env 未被跟踪 ==="
git ls-files | grep -E "^\.env$" || echo "OK"
# ...
```

**每次改完跑一遍，把输出贴进表里。** 这样表和代码永不错位。

## 错误 5：只检查代码，不检查服务器

**操作：**

```text
表里 20 项全在本地跑完了，全是 ✅。
```

**会怎样：** 上线之后发现：

```text
① 服务器上的 .env 是 644（你本地是 600）
② 服务器上 3306 对公网开着（你本地没这个概念）
③ 服务器上的证书 7 天后过期
④ 服务器上的代码是两周前的版本
```

**为什么错：**

```text
本地和服务器是两套环境。
你检查的是"代码有没有洞"，漏了"服务器配错"。
```

**怎么修：**

```text
20 项里，明确标出哪几项必须在服务器上跑：
  3   服务器 .env 权限
  16  数据库端口
  17  HTTPS 与续期
  18  备份与恢复
  14  Nginx 日志格式

这五项在家里跑没有意义。
```

**最后一条最容易漏：**

```bash
# 在服务器上
cd /srv/app && git log --oneline -1
```

**和本地对比：**

```bash
git log --oneline -1
```

**两个哈希不一样 = 服务器跑的不是最新代码。**

# 附：常见问题速查

| 现象 | 原因 | 怎么做 |
|---|---|---|
| `git log --all -- .env` 有输出 | 历史里真有 | 先吊销密钥，再换，最后才清历史 |
| `git ls-files \| grep .env` 有输出 | `.env` 被跟踪了 | `git rm --cached .env`，补 `.gitignore` |
| 越权测试返回 403 而不是 404 | 泄露了 id 存在 | 改成"查不到就 404" |
| 所有 id 都返回 200 | 接口没做归属检查 | 查询加 `AND user_id = ?` |
