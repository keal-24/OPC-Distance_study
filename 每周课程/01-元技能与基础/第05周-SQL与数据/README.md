# 第05周 · SQL与数据 · 第29—35节课

## 从 JSON 文件到真正的数据库

---

## 这一周的目标

第 19 节课你用 JSON 文件存数据。我实测过：**同时发 23 条消息，最后只剩 2 条。**

**23 条进去，2 条出来，丢了 21 条。文件没有报错，接口也返回了 200。**

这一周解决这个问题，并把数据能力补齐。七节课之后你要能做到六件事：

1. **说清数据库和文件到底差在哪** —— 不是"更高级"，是"能在并发下保证数据正确"；
2. **会设计表** —— 给你一段需求，你能推出要几张表、每张表哪些列、每列什么类型；
3. **会增删改查** —— 包括 NULL 的坑、分页、动态条件、中文排序的真实限制；
4. **会 JOIN** —— 一对多、多对多、反连接；
5. **会安全地写** —— 事务、索引、软删除、`changes` 检查；
6. **会保护数据** —— 备份、验证、以及**真的做过一次恢复演练**。

## 一个前提：这一周不装任何数据库软件

**不用装 MySQL、PostgreSQL、不用装 Navicat。**

Node 22 内置了 `node:sqlite`，一行 `import` 就能用：

```javascript
import { DatabaseSync } from "node:sqlite";
const db = new DatabaseSync("shop.db");
```

**为什么这样选：**

| 传统教程的做法 | 我们的做法 |
|---|---|
| 装 MySQL Server | 不用装 |
| 配端口、账号、密码、字符集 | 不用配 |
| 装图形客户端 | 不用装 |
| 卡在"连不上数据库"三天 | 不会 |

**这不是偷懒，是取舍。** 学 SQL 的难点在"想清楚要什么数据"，不在"配环境"。**环境配三天的人，通常第三天就放弃了。**

**代价：SQLite 有边界，而且这些边界我全部在课件里实测并写清了替代方案。**

| SQLite 的限制 | 课件里的处理 | 在第几节 |
|---|---|---|
| 不能改列类型（`ALTER COLUMN` 不存在） | 教"建新表 + 搬数据 + 改名"的重建法 | 第 30 节 |
| 排不了中文拼音（只有三种 collation） | 实测 `PRAGMA collation_list`，给出三种替代方案 | 第 32 节 |
| `INSERT OR REPLACE` 会改掉 id | 实测 id 从 8 变 10，讲清它是"删了再插" | 第 31 节 |
| WAL 模式下直接复制 `.db` 会得到空库 | 实测报错 `no such table`，教正确的备份命令 | 第 35 节 |
| 没有行级安全（RLS）、没有真正的服务端 | **第 24 周换 PostgreSQL 时解决，理由写在那周的 README 里** | 第 24 周 |

**最后一行很重要，现在就说清楚。**

### 什么时候必须换掉 SQLite（这一段决定了后面两周能不能接上）

**SQLite 不是"玩具"，很多真产品在用。但它有三条硬边界，越过了就必须换：**

```text
① 多个进程/多台机器同时写
   SQLite 是单文件，写锁是文件锁。部署到服务器上多开一个进程就开始抢锁。
   → 典型信号：EADDRINUSE 之后改用 cluster，或上了 Docker 多副本

② 需要数据库层的权限隔离
   SQLite 没有 RLS（行级安全），只能在代码里过滤。
   代码里过滤 = 漏一行 SQL 就漏数据。
   → 典型信号：一个库要同时服务多个客户（多租户）

③ 需要容器化部署，且不想管卷
   容器重启 = 容器内文件全丢。挂卷能解决，但备份/迁移/扩容都变麻烦。
   → 典型信号：第 29 周上 Docker
```

**第 24 周（多租户）同时踩中了第②条和第③条，所以那一周换 PostgreSQL，并且文章里明确写了为什么换、怎么换。**

**换库的真实成本只有四处**（第 24 周 README 里有完整对照表）：

| | SQLite（本周） | PostgreSQL（第 24 周） |
|---|---|---|
| 驱动 | `node:sqlite` 内置 | `npm install pg` |
| 占位符 | `?` | `$1`、`$2` |
| 类型 | `TEXT`、`INTEGER` | `uuid`、`jsonb`、`timestamptz` |
| 主键默认值 | 手工写 | `gen_random_uuid()` |

**你现在学的东西一条都不会作废。** SQL 语句结构、JOIN 逻辑、事务语义、索引原理、软删除、`changes` 检查——全部原样搬到 PostgreSQL。

**唯一要改的是占位符：`?` 变成 `$1`。** 读代码时在脑子里换一下就行。

**这一周不要提前学 PostgreSQL。** 先把 SQL 本身学透，换引擎是换方言，不是重学语言。

## 这一周的四条铁律

```text
一、金额用整数分，时间用 ISO 字符串。

二、拼 SQL 只能拼结构，值永远走 ? 参数。

三、UPDATE / DELETE 之后必须看 changes。changes === 0 要当错误。

四、循环写入必须包事务。没演练过的备份等于没有备份。
```

**逐条说清为什么：**

**铁律一** —— `0.1 + 0.2 !== 0.3`，浮点数存钱一定出错。所以 `price_cents INTEGER`。时间用 ISO 字符串（`2026-11-17T01:20:00.000Z`），因为它是唯一能字符串排序等于时间排序的格式，而且 SQLite 没有 `datetime` 类型。

**铁律二** —— 拼 SQL 有两种情况，必须分清：

```text
拼结构（表名、列名、ORDER BY 字段） → 可以拼，但必须走白名单
拼值（用户输入）                    → 永远走 ? 参数，一次都不例外
```

**铁律三** —— `UPDATE ... WHERE id = 1` 改了 0 行，说明 id 不存在或已被删。**它不报错。** 你不看 `changes`，就会以为成功了。

**铁律四** —— 没包事务的循环插入，2000 条要 4972ms；包了事务只要 4ms。**差了 1243 倍，因为每次插入都单独落盘。**

## 这一周实测到的六个"反直觉"结论

**这些不是理论，是在本机跑出来的。每一条课件里都附了原始输出，你可以自己复现。**

| 结论 | 实测数据 | 反直觉在哪 |
|---|---|---|
| **事务让批量插入快 1243 倍** | 无事务 2000 条 = 4972ms，有事务 = 4ms | 事务通常被当成"安全措施"，没想到它还是性能手段 |
| **索引只快 3.6 倍** | 2 万行，无索引 25ms，有索引 7ms | 网上都说"快几百倍"，因为那些例子是磁盘上百万行 |
| **WAL 模式下复制 `.db` 会得到空库** | 报错 `no such table: t` | 文件明明存在、大小也对，数据却在 `-wal` 里 |
| **`INSERT OR REPLACE` 会改掉 id** | id 从 8 变成 10 | 名字叫 REPLACE，实际是 DELETE + INSERT |
| **`NOT IN (1,2,NULL)` 返回空结果** | 加一个 `NULL`，结果从 36 条变成 0 条 | SQL 的三值逻辑：`x != NULL` 是 `NULL`，不是 `true` |
| **SQLite 排不了中文拼音** | 只有 `BINARY` / `NOCASE` / `RTRIM` 三种 collation | 换成 `utf8mb4` 的 MySQL 也不一定能，得靠 `pinyin` 列 |

**第二条特别值得记住。** 因为它教会你一件事：**任何"快 N 倍"的数字，先问"在什么数据量下、什么硬件上"。** 25ms 和 7ms 对人来说都是瞬间，但 2.5 秒和 0.7 秒就是"能用"和"不能用"的区别。

## 这一周最危险的两条命令

**第一：`UPDATE` / `DELETE` 不带 `WHERE`**

```sql
UPDATE accounts SET balance = 0      ← 忘了 WHERE
changes: 2000                        ← 2000 行全被改了
```

**它不报错。`changes` 还会如实告诉你"影响了 2000 行"，但它不认为这是错的——SQL 没有"你可能是想只改一行"这种常识。**

**第 34 节教你三道保险，让这种事在代码层面就发生不了：**

```text
第一道：WHERE 为空就直接抛错
第二道：先 SELECT 一遍，把要改的行打印出来
第三道：包事务 + 检查 changes 是否等于预期
```

**第二：软删除后忘记过滤**

```sql
SELECT * FROM accounts               ← 忘了 WHERE is_deleted = 0
```

**已注销的用户会出现在列表里。** 这个 bug 能活很久，因为：

```text
① 它不报错
② 它只在"有已删除数据"时才表现出来
③ 测试时数据都是新建的，没人删过，所以永远测不出来
```

**第 34 节会让你亲手造这个 bug，再修好它。**

**不要急着进第 2 阶段。先确认这七条：**

- [ ] 我的 `bookstore.db` 有六张表（`authors` / `publishers` / `books` / `customers` / `orders` / `order_items`），且外键真的生效（插一条 `customer_id = 9999` 的订单会失败）
- [ ] 我撞过五个 NULL 坑，并记下了真实数字（不是"知道有坑"，是"我的查询返回了 0 条"）
- [ ] 我写出了 `buildProductQuery`，喂它 `?status='; DROP TABLE--` 这种垃圾参数不崩、不注入
- [ ] `chat-app` 已经迁到 SQLite，重启服务后会话和消息还在
- [ ] 我实测过事务的性能差距，数字记在笔记里
- [ ] 我做过一次 `UPDATE` 不带 `WHERE` 的实验（在 `safe-lab` 里），看到 2000 行被改
- [ ] **我真的删过一次数据，然后恢复回来了**

**最后一条是硬指标，不许打勾了事。**

**验收方式：**

```text
① 备份 → 记下某个表的条数（比如 36 条）
② 真的删掉（DELETE FROM ...，不是软删除）
③ 确认现在查是 0 条
④ 用备份恢复
⑤ 再查，必须是 36 条
```

**必须出现"0 条"这个中间状态。** 跳过第③步的人，通常是在"恢复"时把原来的库又拷回来了，看起来成功了，实际上一旦真出事就完蛋。

**这一周只用手写 SQL + `node:sqlite`。**

**为什么全程不用 ORM（这条容易被误解，说清楚）：**

**不是因为 ORM 不好，是因为它还不到出场的时候。**

```text

```

**顺序必须是：先会手写 SQL → 再学 ORM 帮你省事。**

**反过来的人（先学 ORM）遇到 ORM 搞不定的问题，就完全没有办法了。** 而且第 24 周换 PostgreSQL 时，手写 SQL 的人只改占位符，用 ORM 的人要重新调映射配置。

**`03-练习代码` 是空的，这是故意的。** 课件里的代码是标准答案，你必须自己敲一遍。

**数据库文件放哪：**


**`.db` 不进 Git 的原因：** 它是二进制，Git 存不了差异，稍微改一点整个文件重存，仓库会迅速膨胀。**备份靠备份文件，不靠 Git。**

## 一句话总结这一周

> **数据库不是"更好用的文件"，是"在你写错的时候仍然能保证数据正确"的一层东西。**

**这句话的意思是：**

```text
文件：你写什么就是什么，写错了也是什么
数据库：约束、事务、类型，会在你写错的时候拦住你
```

**所以这一周真正学的不是 SQL 语法，是"让数据库替你兜底"的思路**——能交给约束的不要靠代码判断，能包在一个事务里的不要分两步做。
