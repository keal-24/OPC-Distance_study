## 为什么这节课必须自己敲

这节课有四个"看起来对但其实错"的地方：

**① `INNER JOIN` 悄悄丢行**

你查"所有作者和他的书"，结果那个没写过书的作者不见了。**不报错，只是少一行。**

**② `LEFT JOIN` 后在 `WHERE` 筛右表**

你以为写的是左连接，**实际退化成了内连接**。行数变少，不报错。

**③ `COUNT(*)` 在 `LEFT JOIN` 下数错**

"这个标签有 0 本书"，用 `COUNT(*)` 会显示 1。**所有 0 都变 1，报表全错。**

**④ N+1 在小数据上测不出来**

5 条数据时 N+1 只要 1ms，你觉得没问题。**10000 条时会变成秒级。**

**这四个都是"不报错但结果错"，比报错危险得多。**

## 必须自己造的四个边界

`seed.mjs` 里埋了四个：

1. 一个没写过书的作者 → 测 INNER 丢行
2. 一个没下过单的客户 → 同上
3. 一本没有任何标签的书（兄弟）→ 测 GROUP_CONCAT 返回 null
4. 一本只有一个标签的书（彷徨）→ 测单标签情况

**不要觉得这些是"多余的数据"。没有它们，你的 JOIN 查询永远测不出问题。**

## 大作业：迁移 chat-app

**这是本阶段唯一一个"真实迁移"任务。**

要求：

- 用事务包住（失败全回滚）
- 用 `lastInsertRowid` 建立新旧 id 映射
- 清洗脏数据（`role` 只能是 user/assistant）
- 迁移后写 `verify.mjs` 自动对比
- **旧 `chat.json` 留着不删**

**最后一条是铁律：迁移完先并行跑几天，确认没问题再删旧数据。**
