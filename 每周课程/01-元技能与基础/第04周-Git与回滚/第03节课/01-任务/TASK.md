# 第 2 步：`git log` 的六种用法（25 分钟）

## 2.1 基本用法

```text
git log
```

**会进入一个"分页器"，显示完整信息：**

```text
commit b6a0d70f3e8c9a1b2c3d4e5f6a7b8c9d0e1f2a3 (HEAD -> main)
Author: 测试 <test@example.com>
Date:   Mon Nov 16 11:29:53 2026 +0800

    修复 multiply 用成了加法的问题

commit ...
```

**每一项包含：**

| 部分 | 内容 |
|---|---|
| `commit b6a0d70...` | 完整哈希 + 当前分支指向 |
| `Author:` | 作者和邮箱 |
| `Date:` | 提交时间 |
| 空行之后 | 提交信息 |

**`(HEAD -> main)` 是什么：**
告诉你"HEAD 指向 main，main 指向这个提交"。**这就是第 22 节课的三层指针。**

**怎么退出：**
按 `q`。

**这个一定要记住。** 很多人第一次 `git log` 之后以为终端卡死了。

## 2.2 `--oneline`：只看一行

```text
git log --oneline
```

**输出：**

```text
b6a0d70 修复 multiply 用成了加法的问题
196590b 更新 README：补充用法说明
76450c4 添加 multiply 函数
...
```

**每一项是：短哈希 + 提交信息的第一行。**

**注意"第一行"：** 如果你的提交信息有多行，这里只显示第一行。

**这就是第 23 节课说的"第一行要让 `--oneline` 看得懂"。**

## 2.3 `--stat`：看每次改了哪些文件

```text
git log --stat --oneline
```

**输出会变长：**

```text
b6a0d70 修复 multiply 用成了加法的问题
 calc.js | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

196590b 更新 README：补充用法说明
 README.md | 8 ++++++++
 1 file changed, 8 insertions(+)
```

**读法：**

```text
calc.js | 2 +-          改了这个文件，2 行变化（1 加 1 删）
README.md | 8 ++++++++  改了 8 行，全是新增
```

**`+` 和 `-` 的数量就是"加了几行、删了几行"。**

**这个用法最实用：** 快速看"每次提交影响了哪些文件"，不用读具体代码。

**只看最近 3 次：**

```text
git log --stat --oneline -3
```

**`-3` 是什么：** 只显示最近 3 条。

## 2.4 `-p`：看具体改了什么

```text
git log -p --oneline -1
```

**`-p` 是什么：** patch，显示每行改动。
**`-1` 是什么：** 只看最近 1 条。

**输出：**

```text
b6a0d70 修复 multiply 用成了加法的问题
diff --git a/calc.js b/calc.js
index 83db48f..4de8fd7 100644
--- a/calc.js
+++ b/calc.js
@@ -1,3 +1,3 @@
 function multiply(a, b) {
-  return a + b;
+  return a * b;
 }
```

**逐行读 diff：**

| 行 | 意思 |
|---|---|
| `diff --git a/calc.js b/calc.js` | 在比较 calc.js 的两个版本 |
| `index 83db48f..4de8fd7 100644` | 改前哈希..改后哈希 + 文件权限 |
| `--- a/calc.js` | 旧版本 |
| `+++ b/calc.js` | 新版本 |
| `@@ -1,3 +1,3 @@` | 旧版本从第 1 行起 3 行，新版本从第 1 行起 3 行 |
| ` function multiply(a, b) {` | 空格开头 = 没变 |
| `-  return a + b;` | `-` 开头 = 删掉的 |
| `+  return a * b;` | `+` 开头 = 新加的 |

**`@@` 那一行怎么读：**

```text
@@ -1,3 +1,3 @@
   │  │ │  │ │
   │  │ │  │ └─ 新版本共 3 行
   │  │ │  └─── 新版本从第 1 行开始
   │  │ └────── 旧版本共 3 行
   │  └──────── 旧版本从第 1 行开始
   └─────────── 减号 = 旧版本（a 版本）
```

**用一句话记：**

```text
-旧,行数 +新,行数
```

**`-` 永远对应 `---` 那个旧文件，`+` 永远对应 `+++` 那个新文件。**

**这个一定要会读。** 因为**所有 diff 工具（GitHub、VS Code、PR 界面）都用同样的格式。**

### 一个问题：为什么有时候是 `-1,3` 有时候是 `-1`？

**如果行数是 1，Git 会省略 `,1`。**

**我实际跑出来的输出（只改第 2 行、只改第 9 行）：**

```text
@@ -2 +2 @@ line1
-line2
+line2改
@@ -9 +9 @@ line8
-line9
+line9改
```

**对比：**

```text
@@ -5 +5 @@         ← 旧版本第 5 行，新版本第 5 行，各 1 行
@@ -5,7 +5,9 @@     ← 旧版本从 5 起 7 行，新版本从 5 起 9 行
```

**看到 `-5` 不要以为是"少了什么"，它只是 `-5,1` 的简写。**

### `@@` 后面为什么还跟着一段文字

**仔细看上面那段输出：`@@ -2 +2 @@ line1`**

**最后的 `line1` 是什么：** 是这段改动**上一行的内容**，用来帮你定位"这是文件里的哪一块"。

**Git 的规则：** 它会自动抓取改动块前面的**第一行像"函数定义或段落开头"的文字**，附在 `@@` 后面。

**在 JavaScript 文件里，它通常抓的是函数声明：**

```text
@@ -1,3 +1,3 @@ function multiply(a, b) {
```

**在文本文件里，它抓的可能是随便一行内容。** 上面那个例子抓的是 `line1`，因为这个文本文件没有函数。

**这个附注有什么用：**

- 你在一大堆 diff 里找"哪个函数被改了"，不用翻回去看上下文；
- 在 GitHub 的 PR 界面里，`@@` 后面的内容会显示成灰色的提示，就是同一个东西。

**注意：这段文字只是"提示"，不参与比较。** 你不需要读懂它，只要知道它告诉你"改动大概在哪一块"。

### 一个文件里有多个改动块怎么看

**如果一次提交改了两个不相邻的地方，而且中间隔得够远，diff 里会有两个 `@@`：**

```text
@@ -1,3 +1,3 @@
 function multiply(a, b) {
-  return a + b;
+  return a * b;
 }
@@ -12,4 +12,5 @@
 function divide(a, b) {
+  if (b === 0) return null;
   return a / b;
 }
```

**两个 `@@` = 两处改动。** 中间没显示的行（第 4—11 行）是**没变的部分，Git 省略了**。

**为什么要省略：** 一个 800 行的文件只改了 2 行，全打出来根本没法看。

**一个必须知道的细节：改动离得近会合并成一个块**

**我实测过：在 10 行的文件里同时改第 2 行和第 9 行，结果只有一个 `@@`：**

```text
@@ -1,10 +1,10 @@
```

**不是两个 `@@`，是整个文件都算一个改动块。**

**为什么：** 因为默认上下文是 3 行。第 2 行旁边 3 行是第 1—5 行，第 9 行旁边 3 行是第 6—10 行，**这两个范围连在一起了，所以合并成一块。**

**规律：**

| 两处改动的距离 | diff 里是几块 |
|---|---|
| 相隔 ≤ 6 行 | **1 块**（上下文重叠了） |
| 相隔 > 6 行 | 2 块 |

**这个"6"是怎么来的：** 上下各 3 行，加起来 6 行。

**知道这个有什么用：** 你看到"哇这次改了整个文件"，其实可能只改了两行，只是它们离得近。**用 `-U0` 就能看真相。**

### 怎么看到更多上下文行

**默认 `@@` 前后各显示 3 行。** 想看更多：

```text
git log -p -U10 --oneline -1
```

**`-U10` = 上下文 10 行（`U` 是 unified 的缩写）。**

**什么时候需要：** 你看 diff 时搞不清"这段代码在哪个函数里"，就要多几行上下文。

**反过来，只想看改了哪几行、不要上下文：**

```text
git log -p -U0 --oneline -1
```

**我实测的 `-U0` 效果（同一个"改第 2 行和第 9 行"的提交）：**

```text
@@ -2 +2 @@ line1
-line2
+line2改
@@ -9 +9 @@ line8
-line9
+line9改
```

**注意：用 `-U0` 之后，两处改动**分开**显示了！**

**因为上下文是 0 行，它们不再重叠，所以变成两块。**

**这就是 `-U0` 的真正用途：看清"到底改了几个地方"。**

**什么时候用 `-U0`：**

| 场景 | 用 `-U0` |
|---|---|
| 想知道"这次到底动了几行" | 是 |
| 代码审查时快速扫一遍 | 是 |
| 想理解改动在什么上下文里 | 否，用默认或 `-U5` |
| 想确认"没顺手改别的" | 是 |

**`-U0` 的用处：** 快速数出“这次到底动了几行”。

### 一个必须警惕的坑：`\ No newline at end of file`

**有时候 diff 末尾会出现这一行：**

```text
+  return a * b;
\ No newline at end of file
```

**它是什么意思：** 这个文件的**最后一行没有换行符**。

**为什么会这样：** 有些编辑器保存时会自动加换行，有些不加。如果两边不一致，Git 会提示这一行。

**它算不算问题：**

| 情况 | 要不要管 |
|---|---|
| 只是提示，代码能跑 | 不用管 |
| 整个文件显示“全改了”但内容看着一样 | **要管** —— 可能是换行符（CRLF/LF）不一致 |

**第二种情况很常见：** 有人用 Windows 编辑，有人用 Mac 编辑，换行符不同，Git 会认为整个文件都改了。**但内容其实一个字没变。**

**怎么确认：** 用 `git diff --ignore-all-space` 再看一次。如果这次没差异了，就是空白字符的问题。

```text
git diff --ignore-all-space
```

## 2.5 筛选：按时间、按作者、按文件

### 按时间

```text
git log --oneline --since="1 hour ago"
git log --oneline --since="2026-11-01"
git log --oneline --until="2026-11-15"
git log --oneline --since="1 week ago" --until="yesterday"
```

**时间表达法很灵活：**

```text
"1 hour ago"
"2 days ago"
"1 week ago"
"2026-11-16"
"yesterday"
"last monday"
```

### 按作者

```text
git log --oneline --author="你的名字"
```

**在团队里这个最常用：** "我上周做了什么"。

### 按文件

```text
git log --oneline -- calc.js
```

**注意 `--` 这个分隔符。**

**为什么需要它：**
因为 Git 要区分"这是分支名/文件名"。

```text
git log --oneline -- calc.js      只显示改了 calc.js 的提交
git log --oneline calc.js         会被理解成"查看 calc.js 这个分支"
```

**规则：跟文件名时，一律加 `--`。**

**试试看：**

```text
git log --oneline -- calc.js
```

**应该只看到 4 条**（提交 2、3、4、6 都改了 `calc.js`，提交 1 和 5 没改）。

```text
git log --oneline -- README.md
```

**应该只看到 2 条**（提交 1 和 5）。

## 2.6 组合筛选

```text
git log --oneline --since="1 week ago" --author="你的名字" -- calc.js
```

**这条命令的意思是：**

```text
最近一周 + 我提交的 + 改过 calc.js 的
```

**这就是"历史调查"的典型用法。**

## 2.7 六种用法总结

| 用法 | 看什么 | 什么时候用 |
|---|---|---|
| `git log` | 完整信息 | 需要看作者、时间 |
| `--oneline` | 一行一条 | 快速扫一遍 |
| `--stat` | 改了哪些文件 | 找"哪次动了这个文件" |
| `-p` | 具体改动 | 看"具体改了什么" |
| `--since` / `--author` | 筛选 | 缩小范围 |
| `-- 文件` | 单文件历史 | 追某个文件 |

**组合起来就是：**

```text
git log --oneline --stat --since="1 week ago" -- calc.js
```

**"最近一周谁改过 calc.js，改了几行"。**

# 第 3 步：`git show` 和 `git diff`（25 分钟）

## 3.1 `git show`：看某一次提交

```text
git show HEAD
```

**显示最近一次提交的完整信息 + 具体改动。**

**看指定提交：**

```text
git show 76450c4
```

**（用你自己的哈希）**

**只看统计：**

```text
git show --stat 76450c4
```

**看某次提交里某个文件：**

```text
git show 76450c4:calc.js
```

**注意那个冒号。**

**`<提交>:<文件路径>` 是什么：**
"取出那个提交里那个文件的内容"。

**这个用法非常有用：**

```text
想看"上一次提交时这个文件长什么样"
想看"一个月前这个配置是什么"
```

**注意路径写法：**

```text
git show HEAD:calc.js                 仓库根目录的 calc.js
git show HEAD:src/app.js              子目录里的
git show HEAD:./calc.js               相对当前目录（某些版本支持）
```

**完整路径最保险。**

## 3.2 `git diff`：看两个状态之间的差异

**`diff` 有四种常见用法，容易搞混。**

### 用法一：工作区 vs 暂存区

```text
git diff
```

**意思：我改了但还没 add 的东西。**

**做实验：**

1. 改一下 `calc.js`（随便加个空格）；
2. 运行 `git diff`；
3. 你会看到改动。

**这时候 `git status` 显示 `modified: calc.js`。**

### 用法二：暂存区 vs 上次提交

```text
git diff --staged
```

**意思：我 add 了但还没 commit 的东西。**

**做实验：**

1. 接着上面，`git add calc.js`；
2. 运行 `git diff` → **没有输出**（因为工作区已经和暂存区一样了）；
3. 运行 `git diff --staged` → **看到改动**。

**这两个的区别就是"暂存区"这一层。**

### 用法三：工作区 vs 某次提交

```text
git diff HEAD
```

**意思：我现在的工作区，和上次提交比，差了什么。**

**注意：它包含了"已 add"和"未 add"的所有改动。**

**对比：**

```text
git diff            只显示未 add 的
git diff --staged   只显示已 add 的
git diff HEAD       显示全部（未 add + 已 add）
```

**这个对比非常重要。** 很多人搞不清为什么 `git diff` 看不到自己刚 add 的改动。

### 用法四：两个提交之间

```text
git diff 76450c4 b6a0d70
```

**意思：从提交 A 到提交 B，改了什么。**

**也可以对比分支：**

```text
git diff main feature
```

**意思：feature 分支相对 main 改了什么。**

**这个在合并前很有用：**

```text
git diff main feature --stat
```

**先看统计，再决定要不要细看。**

## 3.3 `--stat` 和 `--name-only`

**不想读每一行，只看统计：**

```text
git diff --stat
git diff --staged --stat
```

**只想看文件名：**

```text
git diff --name-only
git diff --name-status
```

**`--name-status` 会带状态标记：**

```text
M       calc.js
A       newfile.js
D       deleted.js
```

| 标记 | 意思 |
|---|---|
| `M` | Modified，修改 |
| `A` | Added，新增 |
| `D` | Deleted，删除 |
| `R` | Renamed，重命名 |

**这个在"提交前检查"时特别有用**（第 23 节课的那四个检查）。

## 3.4 一个救命用法：`--check`

```text
git diff --check
```

**检查"有没有空白字符错误"（比如行尾多余空格、Tab 和空格混用）。**

**有问题的行会被列出来：**

```text
calc.js:5: trailing whitespace.
+  return a + b; 
```

**为什么重要：**
因为它会让 diff 里出现"看起来没改动但实际改了"的行。**这会掩盖真正的改动。**

**什么时候用：**
提交前跑一下。**很多项目在 CI 里强制检查这个。**

# 第 4 步：`git blame`——谁改的（20 分钟）

## 4.1 最基本的用法

```text
git blame calc.js
```

**输出（我在测试仓库里实际跑出来的）：**

```text
196590b4 (测 2026-11-16 11:29:53 +0800 1) line1
b6a0d70f (测 2026-11-16 11:29:54 +0800 2) line2 改了
196590b4 (测 2026-11-16 11:29:53 +0800 3) line3
```

**逐列读：**

| 列 | 内容 |
|---|---|
| `196590b4` | 这次改动来自哪个提交（短哈希） |
| `(测 ...)` | 谁改的、什么时候 |
| `1)` | 这是文件的第几行 |
| `line1` | 那一行的内容 |

**关键理解：**

```text
blame 显示的是"最后修改这一行的那次提交"
不是"创建这个文件的那次提交"
```

**注意第 2 行是 `b6a0d70f`（较新的提交），第 1、3 行是 `196590b4`（较早的提交）。**

**因为只有第 2 行被改过。**

### 输出里的两个特殊符号

**符号一：哈希前面有个 `^`**

**当某个提交是"第一次提交"（没有父提交）时，Git 会在哈希前加 `^`：**

```text
^916f25f (测 2026-11-16 11:20:11 +0800 1) const CONFIG = {
```

**`^` 的意思是"这是初始提交"。**

**看到 `^` 说明这行从仓库建立那天就有，**没有人"改"过它，是有人"创建"了它。

**符号二：某个字段显示不全时的 `...`**

**如果文件名太长，`blame` 会在末尾显示 `...`。**

**这不影响判断，只是显示宽度限制。**

### 文件中途改过名会怎样

**这是个很容易困惑的情况。**

假设：

```text
第 1 次提交：创建 utils.js，写了 calculate()
第 2 次提交：把 utils.js 重命名为 helper.js
第 3 次提交：在 helper.js 里改了 calculate()
```

**现在对 `helper.js` 跑 `blame`：**

- 改过的那行 → 显示第 3 次提交；
- 没改的那些行 → 显示第 2 次提交（重命名那次），**而不是第 1 次提交**。

**为什么：** 因为重命名在 Git 看来是"删一个文件 + 加一个文件"，那些没变的行在"新文件"里算是第 2 次提交时才出现的。

**怎么看到真正的创建历史：**

```text
git blame -C -C helper.js
```

**但这里有个坑：`-C` 写一次没用，必须写两次。我实测过。**

### 实测：`-C` 和 `-C -C` 的差别

**测试设置：**

```text
甲方：创建 a.js，里面写了 calcFee 函数（8 行代码）
乙方：把 calcFee 那段代码整段复制到新建的 b.js
```

**现在对 `b.js` 跑 blame，三种参数的结果完全不同：**

**① 不加参数（默认）：**

```text
bb5c83f8 (乙 ... 1) const RATE = 0.1;
bb5c83f8 (乙 ... 2) const BASE = 100;
bb5c83f8 (乙 ... 3)
bb5c83f8 (乙 ... 4) function calcFee(amount) {
bb5c83f8 (乙 ... 5)   const fee = amount * RATE;
...
```

**全部 8 行都是"乙"。**

**② 加一个 `-C`：**

```text
bb5c83f8 (乙 ... 1) const RATE = 0.1;
bb5c83f8 (乙 ... 2) const BASE = 100;
...
```

**没有任何变化，还是全"乙"。**

**这一点非常重要：`-C` 单独用几乎没用。**

**③ 加两个 `-C -C`：**

```text
^8ee610b a.js (甲 ... 1) const RATE = 0.1;
^8ee610b a.js (甲 ... 2) const BASE = 100;
^8ee610b a.js (甲 ... 3)
^8ee610b a.js (甲 ... 4) function calcFee(amount) {
^8ee610b a.js (甲 ... 5)   const fee = amount * RATE;
...
```

**全部 8 行追溯到了"甲"，而且还告诉你了 `a.js`！**

**注意输出里多了个 `a.js`** —— 这个位置的字段本来是空的，当 Git 发现代码来自另一个文件时，会在这里显示那个文件名。

**④ 加三个 `-C -C -C`：** 结果和两个一样。

**所以结论是：**

| 参数 | 效果 | 什么时候用 |
|---|---|---|
| 不加 | 只看当前文件的改动 | 默认 |
| `-C` | 几乎没用 | 别用 |
| `-C -C` | **能找到"从别的文件复制过来"的代码** | **这才是要的** |
| `-C -C -C` | 更激进（跨所有提交找），更慢 | 前一个还找不到时 |

**记住：要写两个 `-C`，写一个等于没写。**

### 三种 `-C` 的官方含义

**为什么一个不管用、两个才管用，原因是它们搜索的范围不一样：**

| 参数 | 搜索范围 |
|---|---|
| `-C` | 只在**同一次提交里被改名的文件**内找 |
| `-C -C` | 在**当前提交涉及的整个文件树**里找（包括新建的文件） |
| `-C -C -C` | 在**整个仓库的所有提交**里找 |

**为什么 `-C` 一个不够：** 因为在我们的测试里，`b.js` 是**新建**的文件，不是改名的。Git 需要一个 `-C` 的"跳过改名检测"能力，但只在改名范围内搜，找不到新文件里的复制。

**加上第二个 `-C` 才扩大到"整个文件树"，这时才发现"这 8 行和 a.js 里的一模一样"。**

**这解释了为什么很多人说"`-C` 没用"** —— 他们只写了一个。

## 4.2 `blame` 是用来干什么的

**不是用来"抓谁写的烂代码"。**

**三个真实用途：**

**用途一：找到一个 bug 的来龙去脉**

```text
看到一行奇怪的代码 → blame → 找到那次提交
→ git show 那个提交 → 看提交信息
→ 原来是为了修复某个特定问题才这么写的
```

**用途二：判断代码能不能改**

```text
这段代码看起来很怪
blame 发现是三个月前某次紧急修复加的
→ 先问清楚再改，可能是为了绕开某个坑
```

**用途三：找相关的人问问题**

```text
这行代码看不懂 → blame → 知道是谁改的 → 去问他
```

**注意：blame 在团队里是敏感操作。**

**如果你的团队文化是"blame 用来追责"，那这个团队有问题。**

**正确的用法是"理解历史"，不是"找人负责"。**

## 4.3 常用参数

### 只看某个范围的行

```text
git blame -L 10,20 calc.js
```

**只看第 10 到 20 行。**

**`-L` 是什么：** line range。

**这个在长文件里很有用。**

### 忽略空白改动

```text
git blame -w calc.js
```

**`-w` 是什么：** ignore whitespace。

**为什么需要：**
如果有人只是重新格式化了文件（改了缩进），`-w` 能让你看到"真正的逻辑改动是谁做的"，而不是"格式化的人"。

### 看到某次提交之前的状态

```text
git blame <某个提交> -- calc.js
```

**意思是：在那个提交的时间点，每一行是谁改的。**

## 4.4 `blame` 最大的陷阱：一次格式化毁了整个历史

**这是真实工作中最常见的抱怨，几乎每个团队都遇到过。**

**但这里有个细节，很多教程讲错了。我实际测过，结果和你想的可能不一样。**

### 实测：只改缩进 vs 激进格式化

**测试用的文件（两个函数）：**

```text
function f(x){
if(x){return 'a'}
return "b"
}
function g(y){
if(y){return 'c'}
return "d"
}
```

**由甲创建。然后我做两种格式化，分别看 blame 结果。**

### 情况一：只改缩进（2 空格 → 4 空格 / 加缩进）

**实际输出（我跑出来的）：**

```text
^f5331a9 (甲 ... 1) function multiply(a, b) {
8143a702 (丁 ... 2)     return a * b; // 乘法
^f5331a9 (甲 ... 3) }
^f5331a9 (甲 ... 5) function divide(a, b) {
8143a702 (丁 ... 6)     return a / b;
^f5331a9 (甲 ... 7) }
```

**注意：并不是所有行都变成了"丁"。**

- 第 1、3、5、7 行（`function ... {` 和 `}`）**还是"甲"** —— 因为这些行的内容一个字没变，只是**前面没有缩进**，所以格式化没动它们；
- 第 2、6 行（`return ...`）变成了"丁" —— 因为**这两行的缩进真的变了**。

**结论：只改缩进时，受影响的是"有缩进的行"，不是全部行。**

### 情况二：激进格式化（加空格 + 引号转换 + 加分号）

**这次我把文件整体按 Prettier 风格重写了一遍。**

**实际输出：**

```text
2af2ab9b (丙 ... 1) function f(x) {
2af2ab9b (丙 ... 2)   if (x) { return "a"; }
2af2ab9b (丙 ... 3)   return "b";
^cfbf6d6 (甲 ... 4) }
2af2ab9b (丙 ... 5) function g(y) {
2af2ab9b (丙 ... 6)   if (y) { return "c"; }
2af2ab9b (丙 ... 7)   return "d";
^cfbf6d6 (甲 ... 8) }
```

**8 行里有 6 行变成了"丙"。** 只有第 4、8 行那两个单独的 `}` 还是"甲"。

**这就是真实情况：格式化越激进，被"覆盖"的行越多。**

### 关键：`-w` 只解决空白，不解决其他

**在同一份"激进格式化"的文件上，我跑了 `git blame -w`：**

```text
^cfbf6d6 (甲 ... 1) function f(x) {
2af2ab9b (丙 ... 2)   if (x) { return "a"; }
2af2ab9b (丙 ... 3)   return "b";
^cfbf6d6 (甲 ... 4) }
^cfbf6d6 (甲 ... 5) function g(y) {
2af2ab9b (丙 ... 6)   if (y) { return "c"; }
2af2ab9b (丙 ... 7)   return "d";
^cfbf6d6 (甲 ... 8) }
```

**结果：第 1、5 行回来了（它们的差异只是 `x){` 和 `x) {` 这种空格），但第 2、3、6、7 行还是"丙"。**

**为什么？** 因为这几行除了空格，**还多了分号和双引号**（`'a'` → `"a";`）。**`-w` 只忽略空白，不管引号和分号。**

**所以：**

| 格式化类型 | `-w` 能不能穿透 |
|---|---|
| 只改缩进 | **能** |
| 加空格（`x){` → `x) {`） | **能** |
| 单引号转双引号 | **不能** |
| 加分号 | **不能** |
| 换行位置变了 | **不能** |

**这是很多人对 `-w` 的误解：以为它无视一切格式差异。它只无视空白。**

### 真正能穿透一切的是 `--ignore-rev`

**在同一份文件上，我用 `--ignore-rev` 跳过那次格式化提交：**

```text
git blame --ignore-rev HEAD a.js
```

**实际输出：**

```text
^cfbf6d6 (甲 ... 1) function f(x) {
^cfbf6d6 (甲 ... 2)   if (x) { return "a"; }
^cfbf6d6 (甲 ... 3)   return "b";
^cfbf6d6 (甲 ... 4) }
^cfbf6d6 (甲 ... 5) function g(y) {
^cfbf6d6 (甲 ... 6)   if (y) { return "c"; }
^cfbf6d6 (甲 ... 7)   return "d";
^cfbf6d6 (甲 ... 8) }
```

**全部 8 行都回到了"甲"。** 完全穿透。

**这就是 `--ignore-rev` 的价值：它不看差异大小，直接把那次提交"当作没发生"。**

### 三种手段的选择顺序

```text
第一步：先试 git blame -w
        → 如果格式化只是改缩进/空格，这就够了

第二步：不够的话用 git blame --ignore-rev <哈希>
        → 不管格式化多激进，都能穿透

第三步：多个格式化提交，写进 .git-blame-ignore-revs
        → 一次配置，永久生效
```

**先试 `-w`，因为它最省事。不行再上 `--ignore-rev`。**

### 配置 `.git-blame-ignore-revs`（一次配好，永久生效）

**建文件：**

```text
# 格式化提交，不影响代码逻辑
d1a2b3c4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0
```

**每行一个完整哈希（40 位，不能用短哈希）。`#` 开头是注释。**

**告诉 Git 用这个文件：**

```text
git config blame.ignoreRevsFile .git-blame-ignore-revs
```

**这个配置文件要提交进仓库**，让团队所有人共用。

**注意：这个 `git config` 是本地配置，每个人都要执行一次。** 如果想让团队自动生效，要在仓库里放一个说明，或者写进项目的初始化脚本。

### 从流程上避免（最根本）

**这是最该做的：把格式化单独提交，并在提交信息里标注。**

```text
git commit -m "style: 全项目统一 4 空格缩进（无逻辑改动）"
```

**为什么这很重要：**

| 做法 | 后果 |
|---|---|
| 格式化和改代码混在一次提交 | blame 完全失效，无法追溯 |
| 格式化单独提交 + 加进忽略列表 | blame 正常，格式化也不影响 |

**这就是"提交要小而专"的真正原因。** 第 23 节课讲过"一次提交只做一件事"，这里你能看到它的实际价值。

### 自己动手验证

**操作（在 `history-lab` 里做）：**

1. 打开 `calc.js`，按 `Shift + Alt + F`（VS Code 格式化文档）。

   **这会触发一次格式化。** 如果文件已经是标准格式，可能什么都没变 —— 那先故意把缩进改乱再格式化。

2. 提交：

```text
git commit -am "style: 统一缩进（无逻辑改动）"
```

3. 跑 `git blame calc.js`，看有多少行变成了你。

4. 跑 `git blame -w calc.js`，看回来了多少行。

5. 如果还有没回来的，跑：

```text
git blame --ignore-rev HEAD calc.js
```

**你要亲眼看到这三步的差别。** 因为以后在团队里遇到"blame 全是同一个人"，你就知道该按这个顺序试。

## 4.5 一个替代方案：`git log -p -- 文件`

**如果你想看"这个文件完整的历史"，而不是"每行是谁改的"，用这个：**

```text
git log -p -- calc.js
```

**它会按时间倒序显示这个文件的每一次改动。**

**输出开头大概长这样：**

```text
commit b6a0d70f3e8c9a1b2d4e5f6a7b8c9d0e1f2a3b4c
Author: 测 <t@e.com>
Date:   Mon Nov 16 11:29:54 2026 +0800

    修复 multiply 用成了加法的问题

diff --git a/calc.js b/calc.js
index 83db48f..4de8fd7 100644
--- a/calc.js
+++ b/calc.js
@@ -1,3 +1,3 @@
 function multiply(a, b) {
-  return a + b;
+  return a * b;
 }

commit 916f25f...
```

**每一块的结构：**

| 部分 | 内容 |
|---|---|
| `commit <哈希>` | 这次提交的完整哈希 |
| `Author: 名字 <邮箱>` | 谁提交的 |
| `Date: ...` | 什么时候 |
| 空行后的缩进文字 | 提交信息 |
| `diff --git ...` | 从这里开始是这个文件的具体改动 |

**这个输出的好处：** 你能一次看到"这个文件被谁、为什么、怎么改的"完整脉络。

**不好的地方：** 文件改过 50 次，就会输出 50 块，很长。

**怎么截断：**

```text
git log -p -- calc.js -5
```

**`-5` = 只看最近 5 次。**

**对比：**

| 命令 | 回答什么问题 | 输出量 |
|---|---|---|
| `git blame` | 这一行是谁改的 | 文件行数 |
| `git log -p -- 文件` | 这个文件改过哪些次、每次改了什么 | 提交次数 × 改动量 |
| `git log --oneline -- 文件` | 这个文件改过几次（只要标题） | 提交次数 |

**三个配合用最有效：**

```text
① git log --oneline -- 文件      先看改过几次，有没有可疑的
② git log -p -- 文件 -3          看最近 3 次的详情
③ git blame 文件                 定位到具体某行
④ git show <哈希>                看那次提交的完整内容和信息
```

**这个四步顺序要记住。** 从"粗"到"细"，不要一上来就 `blame` 一个 500 行的文件。

# 第 5 步：`-S` 搜索——这段代码什么时候出现的（15 分钟）

## 5.1 问题场景

**你在代码里看到一段奇怪的逻辑：**

```javascript
if (value === "0") {
  value = 0;
}
```

**你想知道：这是谁、什么时候、为什么加的？**

**`git log -- 文件` 会显示所有改动，但太多。**

**你需要"只找包含这段文字的提交"。**

## 5.2 `-S` 的用法

```text
git log --oneline -S "line2 改了"
```

**输出（实测）：**

```text
b6a0d70 修改 b.txt 第二行
```

**只返回了一条：那次"加入或删除"这段文字的提交。**

**`-S` 是什么：**
"pickaxe"（镐）。**它查找"某段文字的出现次数发生变化"的提交。**

**什么叫"出现次数变化"：**

```text
某个提交让它从 0 次变成 1 次 → 命中了（新增）
某个提交让它从 1 次变成 0 次 → 命中了（删除）
某个提交让它从 1 次变成 2 次 → 命中了
某个提交只是把这一行挪了位置（次数不变）→ 不命中
```

**所以 `-S` 找的是"内容的增删"，不是"位置移动"。**

## 5.3 `-G` 和 `-S` 的区别

```text
git log --oneline -G "a \* b"
```

**`-G` 是什么：** 用正则匹配**改动的行**。

**`-S` vs `-G`：**

| | `-S` | `-G` |
|---|---|---|
| 匹配什么 | 字符串出现次数的变化 | 改动行里是否匹配正则 |
| 适合 | 找"这段代码是哪次加的" | 找"哪些改动涉及这种模式" |

**大多数情况用 `-S` 就够。** 需要正则时用 `-G`。

## 5.4 一个更实用的用法：找"删掉的代码"

```text
git log --oneline -S "return a + b" -- calc.js
```

**这会找到所有"加入或删除 `return a + b`"的提交。**

**在你的练习仓库里，应该会找到两条：**

```text
提交 4（添加 multiply，写成了 a + b）
提交 6（修复成 a * b，删掉了 a + b）
```

**这就是"这个 bug 的生命周期"：哪次引入的、哪次修掉的。**

**这个用法在排查"功能什么时候消失的"时特别有用：**

```text
用户说"以前有个导出按钮，现在没了"
→ git log --oneline -S "导出" -- src/
→ 找到删掉它的那次提交
→ git show 那次提交，看提交信息说了什么
```

## 5.5 组合起来：完整的"考古"流程

**假设有一个 bug，你要查清它的来龙去脉。**

```text
第一步：定位可疑代码
  读代码，找到那几行

第二步：看这几行是谁改的
  git blame -L 10,20 文件名

第三步：看那次提交的完整内容
  git show <哈希>

第四步：看提交信息说了什么
  （在 git show 的输出里）

第五步：如果信息不清楚，看这个文件的历史
  git log -p -- 文件名

第六步：如果还是不清楚，找相关的人
  （提交信息里有作者）
```

**这个流程能解决 90% 的"这段代码为什么是这样"的问题。**

# 第 6 步：故意犯五个错（15 分钟）

## 错误 1：`git log` 之后以为卡死了

**操作：**

```text
git log
```

**屏幕停住了，底部显示 `:`。**

**这不是卡死，是分页器。**

**怎么退出：** 按 `q`。

**其它分页操作：**

```text
空格      下一页
b         上一页
↑ ↓       逐行滚动
/关键词    搜索
q         退出
```

**`:` 是什么：** 分页器在等你输入命令。

**如果你看到 `(END)`，也是同一回事。**

**不想进分页器：**

```text
git --no-pager log
```

**或者：**

```text
git log --oneline | cat
```

**更简单：**

```text
git config --global core.pager ""
```

**这一行会彻底关掉分页器。**

**但建议留着：** 因为长输出时有分页器更好读。**养成按 `q` 的习惯就行。**

## 错误 2：`git diff` 看不到刚 add 的改动

**操作：**

1. 改 `calc.js`；
2. `git add calc.js`；
3. `git diff`。

**输出是空的。**

**为什么：** `git diff` 只比较"工作区 vs 暂存区"。你 add 之后两边一样了。

**用 `git diff --staged` 才能看到。**

**这个坑几乎每个新手都踩过。**

**记这一句：**

```text
git diff           未 add 的
git diff --staged  已 add 的
git diff HEAD      全部
```

## 错误 3：`git log -- 文件名` 忘了 `--`

**操作：**

```text
git log --oneline calc.js
```

**会看到什么：**

```text
fatal: ambiguous argument 'calc.js': unknown revision or path not in the working tree.
Use '--' to separate paths from revisions, like this:
'git <command> [<revision>...] -- [<file>...]'
```

**Git 直接告诉你答案了：用 `--` 分隔。**

**为什么：**
Git 不知道 `calc.js` 是分支名还是文件名。**加 `--` 明确说"后面是路径"。**

**规则：**

```text
git log --oneline -- calc.js     ✅
git diff main -- calc.js         ✅
git show HEAD -- calc.js         ✅
```

## 错误 4：`git show 哈希:文件` 路径写错

**操作：**

```text
git show HEAD:./calc.js
```

**可能报错：**

```text
fatal: path './calc.js' exists on disk, but not in 'HEAD'
```

**为什么：**
Git 里的路径是"从仓库根目录算的"，不是"从当前目录算的"。

**正确写法：**

```text
git show HEAD:calc.js
```

**如果文件在子目录：**

```text
git show HEAD:src/app.js
```

**注意：不要写 `./`，也不要用反斜杠。**

## 错误 5：以为 `blame` 显示的是"创建者"

**操作：**

**在你的 `calc.js` 上跑 `blame`，然后看第一行 `function add(a, b) {`。**

**它显示的提交应该是"添加 add 函数"那次。**

**现在把文件整个重写一遍（改缩进、改函数名大小写），然后提交。**

**再跑 `blame`。**

**你会发现：所有行都变成"最后一次提交"了。**

**为什么：**
因为每个行都被改了。**blame 只看"最后一次修改这一行"的提交。**

**这说明：**
`blame` 在文件被大规模格式化/重写后就失效了。**这时要用 `git log -p -- 文件` 看完整历史。**

## 五个错误总结

```text
log 停住              → 按 q 退出
diff 看不到 add 的     → 用 --staged
log -- 忘 --          → 加 -- 分隔
show 哈希:路径 写错    → 从仓库根目录写，不加 ./
blame 当"创建者"      → 它只显示最后一次修改
```

# 附：常见问题速查

| 情况 | 原因 | 怎么做 |
|---|---|---|
| `git log` 停住 | 进了分页器 | 按 `q` |
| `git diff` 看不到改动 | 已 `add` | 用 `--staged` |
| `ambiguous argument` | 路径没加 `--` | `git log -- 文件` |
| `path exists on disk, but not in 'HEAD'` | 路径写法错 | 从仓库根目录写，不加 `./` |
| improve blame 全是同一提交 | 文件被格式化/重写 | 用 `git log -p -- 文件` |
| `git show` 输出太长 | 大提交 | 加 `--stat` 或指定文件 |
| 想看某文件的历史版本 | 不知道怎么写 | `git show HEAD~3:路径/文件` |
| 中文路径报错 | 编码问题 | 加双引号，或用 Git Bash |
| `-S` 搜不到 | 只改了位置没改内容 | 改用 `git log -p` 人工看 |
| 不知道该看哪个提交 | 历史太长 | 用 `--since` + `--author` + `-- 文件` 三重筛选 |
| `--name-status` 的字母看不懂 | 不认识标记 | M=改 A=加 D=删 R=改名 |
| `git diff --check` 报空白错误 | 行尾多余空格 | 编辑器设置"保存时删行尾空格" |
