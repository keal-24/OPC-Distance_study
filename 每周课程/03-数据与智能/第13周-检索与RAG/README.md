# 第13周 · 检索与RAG · 第85—91节课

## 让 AI 答得出"我们公司"的问题

---

## 这一周的目标

这一周不是"学 RAG 这个技术"。是**做出一个你敢交给客户的资料问答系统，并且能说清它哪里不行**。七节课结束时，你要能做到这五件事：

1. **把大堆文字切成"值得检索"的块** —— 不是按页切，是按语义切，并知道切坏了长什么样；
2. **建一套能排序、能高亮、能截断的关键词检索** —— 并且知道它在什么情况下必然是零；
3. **从零手写余弦相似度** —— 不引库，能手算，能解释为什么是余弦不是欧氏距离；
4. **把两边的弱点拼起来** —— 关键词补向量的否定词，向量补关键词的同义词；
5. **用数字证明改动更好** —— 一套能重复跑的评测，和一份"能对客户说出口"的结论。

---

## 为什么排在这一周

第 12 周你手上有了干净的文字。第 14 周你要让模型动手做事。

**这一周是把"有资料"变成"能回答"的那一步。**

它排在第三阶段的中间，是因为前面两周的所有工作，都到这一周才第一次被验证：

| 你以为的问题 | 真正的问题在哪一周 |
|---|---|
| "搜'报销'搜不到'费用核销'" | W13（同义词）—— 但前提是 W11 采到了那篇制度 |
| "答出来的数字是错的" | W13（引用核查）—— 但前提是 W12 没在解析时丢列 |
| "同一个问题两个答案" | W11（去重增量）—— 同一份文件被采了两次 |
| "检索结果里全是页脚广告" | W12（清洗）—— 导航文字全进了库 |

**这就是为什么第 13 周放在最后：它是前面两周的检验场。**

**不学这一周的后果很具体：** 你会做出一个"能对话但答不到点上"的机器人，然后开始怀疑是模型不够好，花几周换模型、调提示词，最后发现是检索的问题。

七节课的代码全在同一个项目 `rag-app` 里。后面几节不新建项目，只往里加文件。

| 节课 | 主题 | 核心产出（都在 `第NN节课/03-练习代码/rag-app/` 下） |

| 第 88 节 | 向量检索概念 | `tools\cosine.js` + `tools\vector-lab.js` + `out\vector-lab.md` |

| 第 91 节 | 完成资料问答 | `search-hybrid.js` + `eval-cases.js` + `eval.js` + `out\compare.md` |

**七个产出是连着的，而且是有因果的：**

```text
第 85 节切坏 → 第 86 节建索引建在碎块上 → 第 87 节怎么调都搜不到
第 89 节向量不归一化 → 第 91 节混合排序全乱
第 91 节没有评测集 → 你永远不知道混合到底有没有用
```

**所以跳节的代价很大。** 唯一可以跳过的是第 88 节（纯概念、手算），但**跳过它的后果是第 89–91 节你会一直困惑"为什么分数是这个数"**。

## 这一周有两个"假东西"

这一周有两个地方需要花钱：**embedding 接口**和**问答模型**。所以两处都做了假实现。

### 假 embedding（第 89 节）

```text
算法：字符 2-gram → 哈希到 256 维 → 归一化
能做到：字面相近的文本，向量也相近
做不到：意思相近但字面不同（这正是真模型的能力）
```

**它存在的理由不是"省钱"，是"让你愿意做那些该做的验证"。**

```text
用真接口：
  想验证"存 BLOB 还是 JSON" → 调一次接口 → 花钱
  想验证"1 万块排序要多久" → 调 1 万次 → 一大笔钱
  → 你会因为心疼钱而跳过这些验证
  → 而这些验证恰恰是最重要的

用假向量：
  所有管道、存储、排序、性能问题，零成本验证完
  最后换成真接口，只改一行 .env
```

**它的局限必须说清楚：** 用假向量跑评测，你会得到"向量检索没什么用"的错误结论。**因为假向量只做字面匹配，而向量的全部价值都在字面之外。**

### 假问答模型（第 90 节）

`MOCK_LLM=true` 时返回三段预设答案，**每一段都是故意有问题的**：

| 预设 | 故意包含的问题 |
|---|---|
| `default` | 有引用，但引用块里没有那个结论（幻觉 + 假引用） |
| `badcite` | 引用了不存在的编号 `[9]` |
| `noscite` | 有实质内容但完全没有引用 |

**这三段就是你的核查代码要抓的靶子。** 先人工找出错误，再让代码去抓 —— 顺序不能反。

## 这一周最容易卡住的六个地方

### 一、`no such module: fts5`

**原因：** 你的 SQLite 编译时没带 FTS5。`better-sqlite3` 官方预编译包是带的，某些镜像不是。

**解法：** `npm uninstall better-sqlite3` 再 `npm install better-sqlite3`。还不行就看第 86 节的降级方案（`node:sqlite`，Node 22.5+ 自带，也支持 FTS5）。

### 二、`fts5: syntax error near "-"`

**原因：** 用户输入里有 `-` `"` `*` `(` `)` `:` 这些 FTS5 的语法字符，直接扔进 `MATCH` 就是语法错误。

**解法：** 所有用户输入都必须先清洗。第 87 节的 `buildMatchQuery()` 就是干这个的。**这不是安全问题，是稳定性问题 —— 一个正常用户输入"报销-流程"就能把接口打 500。**

### 三、`bm25` 排序排反了

**原因：** `bm25()` 返回负数，**越负越相关**。而余弦是**越大越相关**。

**解法：** 记住这两个方向是反的。`ORDER BY bm25(...)` 是升序，`sort((a,b) => b.score - a.score)` 是降序。**在同一个项目里两套都写，一定会搞混一次。**

### 四、`维度不一致：查询 1536 维，块 1 是 256 维`

**原因：** 你换了 embedding 模型，但库里的向量还是老模型算的。

**解法：** `node build-vectors.js --force` 全量重算。**特别注意：绝对不要写"截断到较短长度"这种容错**，那会静默算出毫无意义的结果。

### 五、单条调用和批量调用的向量不一样

**原因：** embedding 接口**不保证返回顺序和输入顺序一致**。

**解法：** 必须 `.sort((a, b) => a.index - b.index)`。这个错极其难发现 —— 你的检索"能返回结果"，只是排在前面的偶尔是错的。

### 六、混合后所有关键词结果都排到后面

**原因：** 你把 bm25 的分数和余弦的分数直接比大小了。bm25 是负数，永远排在后面。

**解法：** 用 RRF，只看名次不看分数。**而且拒答判断不能用 RRF 分数** —— RRF 分数只取决于名次，只要凑够 5 条，第 1 名永远约等于 `1/61`，跟相关不相关无关。

## 这一周的五条铁律

```text
一、先假后真。
    所有要花钱的步骤，先在假实现上把管道验证完。
    换成真接口只改一行 .env，代码不动。

二、建索引和查询必须用同一个分词规则。
    规则不一致，索引就白建了，而且不会有任何报错。

三、排序用 RRF，拒答用原始余弦。
    两件事必须分开。混在一起会做出一个"阈值永远调不出来"的系统。

四、引用区块必须由代码生成，不能让模型写。
    让模型写引用 = 它可以编引用。让代码写 = 引用一定是真的那块。

五、10 块的库上测出来的命中率，不能当承诺。
    前 5 条覆盖了半个库，命中率必然高。
    能承诺的是"三种方案的相对排序"，不是"我们能到 90%"。
```

## 周末的验收

```text
- [ ] 我能对 300 页的手册说出"为什么不能整本塞进 prompt"，并给出两个数字
- [ ] 我切出来的块大小在 400–800 字之间，且我故意切开过一个句子看到后果
- [ ] 我知道 unicode61 对中文做了什么，为什么我要自己插空格
- [ ] 我能默写余弦相似度的公式，手算过一遍，和代码结果一致
- [ ] 我知道 bm25 是越负越相关，余弦是越大越相关
- [ ] 我测出了"关键词在同义词上是 0 命中"，并贴了三个证据
- [ ] 我的库里每个块都有向量，BLOB 长度全部等于 维度×4
- [ ] 我的答案里每个引用都能在依据区块里找到对应原文
- [ ] 我的核查抓住过至少一次"编造"，贴了原句和依据的对照
- [ ] 无关问题会被拒答，而不是硬答
- [ ] 我对三种检索跑了同一批问题，有命中率 / Top-1 / MRR 三个数字
- [ ] 我能说清混合检索在我自己的数据上好了多少，以及它没解决什么
```

> **第 7 节和第 11 节不能落。**
>
> 第 7 节（关键词检索）落了，你不知道关键词的边界在哪 —— 你会以为"搜不到"是 bug，然后花时间调一个原理上不可能实现的东西。
>
> 第 11 节（评测）落了，你这一周做的所有事都没有证据。**你会有六个"感觉不错"的东西，和零个"能对客户说出口"的结论。**

**另外三条，是这一周真正的分水岭：**

```text
- [ ] 我逐句对照过答案和依据，找出过模型编造的那一句
- [ ] 我知道"向量检索不解决否定词"，并且能说出为什么
- [ ] 我不用假向量的评测结果下任何结论
```

## 这一周不用学什么

明确划掉，别在这上面花时间：

```text
LangChain / LlamaIndex            本课程一律不用。手写 200 行，比学框架快
向量数据库（Pinecone / Milvus）    第 6 阶段（上线运维）讲选型时才提
faiss / hnswlib                   几万块以内用不上，暴力扫描就够
专门的 rerank 模型                 需要额外接口和费用，第 18 周（评测与选型）会提
多跳推理 / 图谱 RAG                这一周不做。它是另一个量级的问题
混合的权重学习（learned fusion）    RRF 等权够用，调参留到有真实数据之后
中文分词库（jieba / nodejieba）     不装。第 86 节讲清了"逐字插空格"的取舍
```

**关于"不用 LangChain"多说一句：**

这不是保守。这一周你要理解的是**"检索为什么能工作"**，而框架会把这件事藏起来。等你手写过一遍、知道每一步在干什么，再用框架就是省事；反过来，你只会调参数。

## 下一步

第 14 周：**智能体与工具**。

这一周你做到的是"**你**决定调哪个检索，**模型**只负责组织语言"。

```text
这一周的流程：
  用户问 → 你检索 → 你拼 prompt → 模型答
  ↑ 关键决定全部由你的代码做
```

下一周的流程会变：

```text
用户问 → 模型决定"我要查什么" → 你执行 → 模型看结果 → 再决定下一步
          ↑ 关键决定交给模型了
```

**这就是从"聊天"到"智能体"的转变。** 而第 92 节会讲清一件事：**大多数需求不该用智能体，一步能做完的别上循环。**

**衔接点在这一周的第 90 节课：** 引用核查。下周你要让模型自己调工具，那时候"模型说的和实际做的对不对得上"会变成同一个问题，只是从"引用"变成了"工具调用"。
