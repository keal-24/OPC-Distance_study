# 第 1 步：向量是什么（20 分钟）

## 1.1 做什么 / 为什么

**做什么：** 用一组三维向量，把它画在脑子里，然后扩展到 256 维。

**为什么从三维开始：**

因为**三维以内的东西你能想象。** 256 维想象不了，但你可以用三维的直觉去理解它。

```text
三维  → 能画出来，能想象
256 维 → 画不出来，但每一维做的事情和三维完全一样
```

**维度不是"玄学"，它只是"有多少个数字"。**

## 1.2 一个三维的例子

假设我们把"一段文字的意思"表示成三个数字：`[正式程度, 金额相关, 流程相关]`。

**这是一个人为造的、极度简化的"向量"。真实模型算出来的不是这三个东西，但这个例子能让你看清机制。**

| 文字 | 正式程度 | 金额相关 | 流程相关 | 向量 |
|---|---|---|---|---|
| 住宿费标准 | 8 | 7 | 2 | `[8, 7, 2]` |
| 住的能报吗 | 2 | 6 | 3 | `[2, 6, 3]` |
| 报销流程 | 7 | 5 | 9 | `[7, 5, 9]` |
| 今天的天气 | 3 | 0 | 0 | `[3, 0, 0]` |

**用这三个数，就能看出一些东西：**

```text
住宿费标准 [8,7,2]  vs  住的能报吗 [2,6,3]
  → 第 2 维（金额）都高，第 3 维（流程）都低 → 像

住宿费标准 [8,7,2]  vs  报销流程 [7,5,9]
  → 第 3 维差很远（2 vs 9）→ 没那么像

住宿费标准 [8,7,2]  vs  今天的天气 [3,0,0]
  → 完全不同 → 不像
```

**注意"住的能报吗"和"住宿费标准"在第一个维度上差很多（2 vs 8，不正式 vs 正式）。**

**这就是向量的价值：它允许某些维度差很多，只要整体方向接近，就算像。**

**关键词检索做不到这一点 —— 它在任何一块上对不上就归零。**

## 1.3 真实向量长什么样

真实模型给的向量长这样（示意，不是真实值）：

```text
// 真实 embedding 大概长这样：1536 个浮点数，每个在 -1 到 1 之间
[-0.0234, 0.0891, -0.1176, 0.0442, 0.0038, -0.0912, ... 共 1536 个]
```

**三个必须知道的特征：**

| 特征 | 说明 | 后果 |
|---|---|---|
| **维度高** | 1536 或 1024 或 768 或 256，看模型 | 存储和计算成本都跟着涨 |
| **每个数是小数** | `-0.0234` 这种，不是整数 | 不能用"相等"比较，只能算距离 |
| **你自己看不懂每一维** | 第 37 维代表什么？没人知道 | 不能手工调，也不能解释"为什么像" |

**第三条最反直觉，也最重要：**

```text
人造的三维向量：每一维有明确含义（正式程度、金额、流程）
真实 embedding：每一维的含义是模型自己学出来的，没人能命名
```

**所以你永远不能问"为什么这两句话相似"，只能问"相似度是多少"。** 这在后面给客户做解释时会是麻烦事。

# 第 2 步：手算余弦相似度（30 分钟）

## 2.1 做什么 / 为什么

**做什么：** 先在一张纸上手算一遍，再写成 20 行代码，对比两个结果。

**为什么必须手算：**

因为**你以后会看到"相似度 0.83"这样的数字，如果不知道它是怎么来的，你就无法判断它可不可信。**

```text
0.83 是什么意思？
  比 0.7 好多少？
  0.5 算不算相关？
  为什么不是 83%？
```

**手算一遍，这些问题全部有答案。**

## 2.2 余弦相似度的公式

```text
                A · B
cos(θ) = ───────────────────
           |A| × |B|
```

**三部分，都很简单：**

| 符号 | 名字 | 怎么算 | 例子（A=[8,7,2], B=[2,6,3]） |
|---|---|---|---|
| `A · B` | 点积 | 对应位相乘再相加 | `8×2 + 7×6 + 2×3 = 16+42+6 = 64` |
| `\|A\|` | 模长（长度） | 每项平方求和再开根号 | `√(64+49+4) = √117 ≈ 10.817` |
| `\|B\|` | 模长 | 同上 | `√(4+36+9) = √49 = 7` |

```text
          64           64
cos = ────────── = ────────── ≈ 0.8438
      10.817 × 7     75.72
```

**0.8438。这就是"住宿费标准"和"住的能报吗"的相似度。**

**现在手算另外三个，你会看到差异：**

| 组合 | 点积 | \|A\| | \|B\| | cos |
|---|---|---|---|---|
| 住宿费标准 vs 报销流程 | `8×7+7×5+2×9=56+35+18=109` | 10.817 | `√(49+25+81)=√155≈12.450` | `109/134.67≈0.8095` |
| 住宿费标准 vs 今天的天气 | `8×3+7×0+2×0=24` | 10.817 | `√9=3` | `24/32.45≈0.7396` |
| 住的能报吗 vs 今天的天气 | `2×3+6×0+3×0=6` | `√(4+36+9)=7` | 3 | `6/21≈0.2857` |

**注意第二个：`住宿费标准 vs 今天的天气` 是 0.7396。**

**这个数字很高！但这两句话意思完全无关。**

**为什么？** 因为"今天的天气"的向量是 `[3,0,0]`，它只在第一个维度上有值。而"住宿费标准"的第一个维度是 8。**两个向量都指向"第一维"这个方向，所以夹角小。**

**这就是余弦相似度的一个真实弱点：它只看"方向"，不看"长度"。**

```text
[3,0,0] 和 [8,7,2] 夹角不大，因为 [3,0,0] 的方向是"纯第一维"
如果换成 [0.3, 0, 0]（同方向，长度十分之一），相似度完全一样
```

**在真实 embedding 里这个问题没那么严重**（因为每一维都有值，方向分布很散），**但它确实存在。** 记住这一点，第 91 节做阈值判断时你会用到。

## 2.3 操作：写 cosine.js

新建 `tools\cosine.js`：

```javascript
// cosine.js —— 余弦相似度，零依赖
// 只做一件事：给两个等长数组，返回 [-1, 1] 之间的相似度

function dot(a, b) {
  let s = 0;
  for (let i = 0; i < a.length; i += 1) {
    s += a[i] * b[i];
  }
  return s;
}

function norm(a) {
  let s = 0;
  for (let i = 0; i < a.length; i += 1) {
    s += a[i] * a[i];
  }
  return Math.sqrt(s);
}

function cosine(a, b) {
  if (a.length !== b.length) {
    throw new Error("维度不一致：" + a.length + " vs " + b.length);
  }
  const na = norm(a);
  const nb = norm(b);
  if (na === 0 || nb === 0) {
    // 零向量没有方向，相似度无意义。返回 0 而不是 NaN。
    return 0;
  }
  return dot(a, b) / (na * nb);
}

module.exports = { cosine, dot, norm };
```

**三个设计决定，都要能说出理由：**

| 决定 | 理由 |
|---|---|
| 维度不一致就抛异常 | 静默返回 0 会让你以为是"不相关"，其实是数据有问题 |
| 零向量返回 0 而不是 NaN | `NaN` 会污染整个排序（任何比较都是 false） |
| 不在这里做归一化 | **归一化是建库时的事**，不是查询时的事。见第 4 步 |

**第二条特别重要：**

```text
[1, 2] 和 [0, 0]
  → NaN 会传染：NaN > 0.5 是 false，NaN < 0.5 也是 false
  → 你的排序函数里所有比较都失败，结果顺序变成"随机"
  → 而这个错不会报异常
```

**这是数值计算里最典型的一类坑：不是崩，是静默错。**

**现在看这张表的排序，找出它的三个问题：**

| 排名 | 组合 | 相似度 | 问题 |
|---|---|---|---|
| 1 | 住宿费标准 vs 住的能报吗 | 0.8438 | ✓ 对，这是我们要的 |
| 2 | 住宿费标准 vs 报销流程 | 0.8095 | 也说得过去（都跟钱有关） |

**三个结论：**

```text
① 相似度不是"百分比"。0.8438 不能说成"84% 相关"
② 单靠数值大小排序会出错。0.7396 和 0.8438 差得不多，
   但一个是"对的"、一个是"完全错的"
③ 人造的三维向量太少，分辨不出来。真实 embedding 有 1536 维，
   能把"天气"和"住宿"推得很远
```

**第 ③ 条是关键：为什么真实模型需要那么高的维度？**

```text
维度少 → 向量空间小 → 不同的东西容易挤在一起（都落在相似的几个方向上）
维度多 → 空间极稀疏 → 不同的东西容易分开
```

**但要付代价：** 1536 维的向量，每个 float 4 字节 = 6KB。1 万个块 = 60MB。**算一次相似度要 1536 次乘加。**

**这就是为什么第 89 节要讲"存 BLOB 还是 JSON"和"什么时候该上索引"。**

| 现象 | 原因 | 怎么办 |

| 结果和手算差很多 | 维度顺序错了 | 检查 `[正式, 金额, 流程]` 的顺序 |

## 2.6 为什么是"余弦"而不是"欧氏距离"

**三个选择，说明为什么选余弦：**

| 方法 | 公式直觉 | 问题 |
|---|---|---|
| 欧氏距离 | 两个点之间的直线距离 | **和向量长度强相关**。同一段文字被模型算出一个"长度 2 倍"的向量，距离就变 2 倍 |
| 点积 | 对应位相乘相加 | **长向量占优**。长文本的向量模长通常更大，点积天然偏好长文本 |
| 余弦 | 点积除以两个模长 | **只看方向，不看长度** |

**为什么"只看方向"是对的：**

```text
"住宿费标准" 和 "住宿费标准（加粗）"
  → 意思完全一样
  → 模型给的向量方向几乎一样，但模长可能不同
  → 余弦 ≈ 1.0（对）
  → 欧氏距离可能 0.3（看起来"不像"）
```

**一句话：余弦相似度回答的是"这两个东西指的是同一类东西吗"，不是"它们有多长"。**

**代价：** 它丢掉了"长度/强度"信息。这就是为什么 `[3,0,0]` 和 `[8,7,2]` 相似度不低 —— 长度信息被丢掉了。

## 3.2 关键认知：高维空间里随机向量几乎正交

```text
2 维：随机取两个方向，夹角平均 45°，余弦平均 0.64
3 维：平均余弦约 0.5
256 维：平均余弦约 0.06
1536 维：平均余弦约 0.026
```

**维度越高，随机两个向量越"互相垂直"（余弦接近 0）。**

**这件事的实用意义：**

```text
在一个 1536 维的空间里，10 万个向量，随机两个的相似度大约 0.03
真正相关的两个，相似度是 0.7 以上

→ 所以"0.7"这个数字是有意义的：它远高于随机基线
→ 所以在高维空间里，用固定阈值（比如 0.6）是可行的
```

**这解释了为什么第 87 节的 `bm25` 不能用绝对阈值，而向量检索可以：**

```text
bm25 分数：没有统一基线，换库就变
余弦相似度：有统一基线（随机 ≈ 0），换库也在同一尺度上
```

**这是向量检索在工程上更容易使用的一个重要原因。**

## 3.3 操作：加第二、第三部分

在 `vector-lab.js` 末尾追加：

```javascript
// ============ 第二部分：高维随机向量几乎正交 ============
console.log("");
console.log("=== 第二部分：随机向量的平均相似度随维度变化 ===");
console.log("");

function randomVec(dim, seed) {
  // 用简单的线性同余做种子，保证每次运行结果一致
  let s = seed;
  const next = () => {
    s = (s * 1103515245 + 12345) & 0x7fffffff;
    return s / 0x7fffffff;
  };
  const v = new Array(dim);
  for (let i = 0; i < dim; i += 1) {
    v[i] = next() * 2 - 1;
  }
  return v;
}

for (const dim of [2, 3, 8, 32, 256, 1536]) {
  let sum = 0;

  for (let k = 0; k < round; k += 1) {

  }

console.log("");
console.log("  结论：维度越高，随机两个向量越正交（|cos| 越接近 0）");

// ============ 第三部分：归一化之后，余弦 = 点积 ============
console.log("");
console.log("=== 第三部分：归一化 ===");
console.log("");

function normalize(v) {
  const n = norm(v);
  if (n === 0) return v.slice();
  const out = new Array(v.length);
  for (let i = 0; i < v.length; i += 1) out[i] = v[i] / n;
  return out;
}

const a = V["住宿费标准"];
const b = V["住的能报吗"];

const cosRaw = cosine(a, b);
const aN = normalize(a);
const bN = normalize(b);
const dotNorm = dot(aN, bN);
const cosNorm = cosine(aN, bN);

console.log("  原始余弦          = " + cosRaw.toFixed(10));
console.log("  归一化之后再点积  = " + dotNorm.toFixed(10));
console.log("  归一化之后再余弦  = " + cosNorm.toFixed(10));
console.log("");
console.log("  归一化后 |a| = " + norm(aN).toFixed(10));
console.log("  归一化后 |b| = " + norm(bN).toFixed(10));
console.log("");
```

| 结果 | 数字 | 工程意义 |

| 维度 256 的随机基线 | 0.0514 | **相似度 0.05 就是"没关系"。你看到 0.3 就有意义了** |

# 第 4 步：一个重要的问题 —— 为什么"意思像"能被算成"距离近"（20 分钟）

## 4.1 做什么 / 为什么

**做什么：** 不写代码，想清楚一个问题。

**为什么必须想清楚：**

因为**客户会问这个问题，而且他自己也没想明白。**

```text
客户问："你说向量能理解意思，它凭什么理解？"
你答："embedding 模型算出来的"
客户问："那它怎么知道'住宿'和'酒店'是一个意思？"
你答不上来。
```

**答不上来的后果不是丢面子，是客户不信任你的方案。**

## 4.2 核心机制：不是"理解"，是"共现"

**模型的训练方式是：给它海量文本，把中间挖掉的词猜出来。**

```text
训练样本（真实文本）：
  "员工出差期间的【住宿】费用，按标准据实报销"
  "酒店【住宿】发票需附行程单"
  "出差【住酒店】的费用可以报销"

模型学到的东西：
  "住宿" 和 "酒店" 在相似的上下文里出现
  → 它们的向量被拉近
```

**注意：模型不知道"住宿"是什么意思。它只知道"这两个词经常出现在相似的位置"。**

**这就是 1940 年代语言学的那句话的数学版：**

```text
You shall know a word by the company it keeps.
（看一个词交什么朋友，就知道它是什么词）
```

**所以向量相似度的本质是：**

```text
不是"意思相同"  → 是"使用场景重叠"
不是"我理解你"  → 是"你们经常出现在同类句子里"
```

## 4.3 这带来的三个真实限制

| 限制 | 例子 | 后果 |
|---|---|---|
| **专业术语在通用语料里没出现过** | 客户的内部产品代号 "TX-3 型" | 向量是随机的，检索不可靠 |
| **否定词被忽略** | "不能报销" vs "可以报销" | 向量非常接近，**同时也会出现关键词检索的问题** |
| **反义词被拉近** | "合规" vs "违规" | 经常出现在同一段话里，向量接近 |

**第二条特别重要，它是今天最值得记住的一件事：**

```text
向量检索能解决"同义词"问题
但它解决不了"否定词"问题

关键词检索：能区分字面，但同义词全挂
向量检索：能理解同义，但否定词会混

→ 两者的弱点不重叠 → 这就是第 91 节"混合检索"的理由
```

**这就是第 91 节课的伏笔，现在先记住这句话。**

## 4.4 那为什么不用"真正的理解"

**因为"真正的理解"不存在可用的实现。**

```text
你以为的选项：
  A. 关键词匹配（笨，但可控）
  B. 向量检索（"理解意思"）
  C. 真正的理解（不存在）

实际上的选项：
  A. 关键词匹配（字面）
  B. 向量检索（统计共现）
  C. 大模型直接读全文（贵、慢、有上限）

没有"理解"这个选项。向量检索也是一种统计方法，只是它的统计对象更抽象。
```

**这个认知很重要，因为：**

```text
如果你以为"向量检索 = 理解"
  → 你会过度信任它
  → 你不会做评测
  → 客户投诉时你无法解释

如果你知道"向量检索 = 一种统计方法，有明确失效边界"
  → 你会准备基线
  → 你会做混合
  → 你能跟客户说清"哪类问题能答、哪类不能"
```

## 4.5 所以第 87 节的 4/8 意味着什么

**你现在可以给客户一个诚实的回答了：**

```text
✗ "关键词检索太笨了，我们上向量检索" —— 客户听不懂
✓ "关键词检索在字面查询上是 100%，
   在同义词和否定条件上是 0%，
   原因不是实现问题，是它只认字面。
   向量检索能在同义词上补上，但它有另一个弱点（否定词）。
   两边都不擅长的部分，我们做混合，然后给你一份新的评测数据。"
```

**这段话里每个词都有依据。这就是第 87 节那份基线数据的价值。**

## 4.6 如果不是这样

**这一节没有代码，所以没有"报错"。** 但你可能会有三种误解，逐一排除：

| 误解 | 纠正 |
|---|---|
| "向量检索比关键词检索强" | 它们在**不同的地方**强。同义词强、否定词弱 |
| "相似度 0.8 就是 80% 正确" | 它是一个夹角余弦，不是概率。**不能说成百分比** |
| "维度越高越好" | 高维带来更强的分辨力，也带来更高的存储和计算成本。**够用就行** |

# 第 5 步：故意犯三个错（15 分钟）

## 错误 1：用"相等"比较向量

```javascript
// 错误写法
function findSimilar(target, all) {
  return all.filter((v) => v.vector === target);   // 永远匹配不上
}
```

**现象：** 永远返回空数组。

**原因：** 两个浮点数组永远不 `===`（引用不同）。就算内容一样，也是两个不同的对象。

**真正的伤害：** 你会以为是"没有相似内容"，实际上是"比较方法错了"。

**这也说明一件事：** 向量检索里没有"相等"这个概念，只有"多近"。**你的所有查询都是 top-k，不是精确查找。**

## 错误 2：忘记处理零向量，让 `NaN` 传遍全场

```javascript
// 错误写法
function cosine(a, b) {
  return dot(a, b) / (norm(a) * norm(b));   // 零向量时是 0/0 = NaN
}
```

**现象：**

```text
cosine([1,2,3], [0,0,0]) = NaN
[NaN, 0.8, 0.5].sort((x,y) => y - x)   →  顺序完全错乱
NaN > 0.8  →  false
NaN < 0.8  →  false
```

**真正的伤害：**

```text
排序函数里所有涉及 NaN 的比较都返回 false
→ Array.sort 的行为变成"未定义顺序"
→ 你的 top-3 是随机的
→ 而且不报错
```

**怎么查：** 在任何相似度计算的地方加一行断言：

```javascript
if (Number.isNaN(s)) throw new Error("相似度算出了 NaN");
```

**宁可崩，也不要静默返回随机顺序。**

## 错误 3：以为归一化可以在查询时做

```javascript
// 错误写法：查询时归一化，库里存原始向量
function search(q) {
  const qn = normalize(embed(q));
  return chunks
    .map((c) => ({ ...c, score: cosine(qn, c.vector) }))   // ← c.vector 没归一化
    .sort((x, y) => y.score - x.score);
}
```

**现象：** 结果**是对的**（因为 `cosine` 内部会各算各的模长）。

**那错在哪？**

```text
错在性能：每个块都要算两次 Math.sqrt
1 万个块 → 2 万次开根号
如果库里存的已经是归一化向量 → 0 次
```

**更重要的是第二层错：**

```text
// 有人会为了"优化"改成点积
.map((c) => ({ ...c, score: dot(qn, c.vector) }))   // ← 想省一次开根号
```

**这时候结果就错了。** 因为 `c.vector` 没归一化，点积会偏向"模长大的块"。

**真正的伤害：** 你会得到一堆"长文本排前面"的结果，看起来像"检索质量下降"，实际上是数学错了。

**正确做法：** **建库时就归一化，存归一化后的向量。查询时也只归一化查询向量，然后直接用点积。**

```text
建库：v_norm = v / |v|，存 v_norm
查询：q_norm = q / |q|，score = dot(q_norm, v_norm)
→ 结果正确，且最快
```

## 三个错误总结

| 错误 | 现象 | 真正的伤害 | 一眼识别 |
|---|---|---|---|
| 用 `===` 比较向量 | 永远空结果 | 你以为"没有相似内容" | 有没有 `cosine` 或 `dot` |
| 零向量 → `NaN` | 排序随机 | 不报错，结果不可信 | 加 `isNaN` 断言 |
| 查询时才归一化 | 结果对，但慢；改了会错 | 性能损失或数学错 | 看库里存的是什么 |

**这三个错误的共同点：它们都不是"算法错了"，是"实现细节错了"。**

**向量检索的公式只有三行，但把它用对，需要上面这些细节全部正确。**
