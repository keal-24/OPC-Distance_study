## 为什么这些文件必须你自己敲

`run-once.js` 里那段 `try / catch` 的结构，抄一遍不会觉得有什么。但你自己敲完、再故意把关掉服务器跑一次，你会第一次真正体会到：

- **为什么 `step` 要是一个变量，跟着流程往前走** —— 因为失败时不更新它，你永远只看到 `start`；
- **为什么 `catch` 里要传 `fetched`** —— 不然你会看到"失败了，但抓到 0 条"，其实是抓到 30 条、死在写库那一步；
- **为什么 `err.cause` 要单独取** —— 因为 `fetch failed` 这五个字，什么都说明不了。

**这三件事，都是"看起来对"和"真的对"之间的差别。**

## 怎么建

1. `cd` 到本节课的 `03-练习代码\`；
2. `xcopy /E /I /Y "..\第06节课\03-练习代码\collector" collector`；
3. `cd collector`，`del` 掉第 76 节的实验文件，`npm install node-cron`；
4. **先另开一个终端起 `node mock-server.js`**，全程别关；
5. 按课件顺序建文件，一个一个跑，**每跑一个都核对屏幕输出**；
6. 第 3 步制造失败时，务必把临时改的代码改回来再往下走。

**顺序不能乱：** `runs.sql` → `db.js` → `show-tables.js` → `run-once.js`（成功）→ `run-once.js`（三种失败）→ `show-runs.js` → `cron.js` → `report-runs.js`。

**跳了第 3 步，"失败留痕"这个能力你就没验证过** —— 而这恰恰是整节课唯一真正重要的东西。

## 检验自己有没有真学会

做完后，**不看课件**回答：

1. 如果我明天加一个"发送通知"的步骤，`step` 该怎么改？为什么不能直接复用 `save`？
2. 你的 `runs` 表跑了三个月，有 6 万行。你想查"最近 30 天每天的成功率"，SQL 怎么写？
3. `finished_at` 是 null 的行，代表几种情况？分别意味着什么？
4. `cron.js` 用 `spawn`，如果子进程跑不完就被下一次触发覆盖了（比如每 1 分钟触发一次，但每次要跑 90 秒），会发生什么？你该怎么防？
5. 客户说"数据是昨天的"。你会按什么顺序查？说出你的前三条 SQL。
6. 为什么"运行记录的价值，90% 在失败那一次"？

**第 5 个问题是真正的验收。** 前五个是知识，第五个是你能不能靠这套东西吃饭。
