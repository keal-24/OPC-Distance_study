# 第15周 · 多模态 · 第99—105节课

## 让程序会看、会听、会说

---

## 这一周的目标

这一周不是"把四个多模态接口调通"。是**能判断一个多模态需求该不该做、该怎么做、做完能不能用**。七节课结束时，你要能做到这五件事：

1. **把图片塞进请求** —— 知道 base64 和 data URL 各是什么，知道为什么本地文件必须转；
2. **把图变成结构化数据** —— 发票、截图、表格三类图各一套提示词，并且知道哪些字段绝不能信模型；
3. **判断一个"生成图片"的需求该不该用生图** —— 文字、品牌色、logo 这类要精确的，一律用代码叠；
4. **处理音频的两个方向** —— 长音频必须分段且时间戳要加偏移；语音合成必须缓存；
5. **给四种能力建一套统一的错误出口** —— 六类错误、哪些能重试、给用户看什么话。

---

## 为什么排在这一周

第 14 周你让模型学会了"调工具"。但工具操作的对象，一直是**文字**。

**这一周打开的是"非文字的世界"。**

它被排在第三阶段的最后，是因为它是这三种能力里**最像"能直接卖"的一种**：

| 客户说的话 | 需要什么 |
|---|---|
| "我有一堆发票，帮我录进系统" | 图片识别 + 结构化提取（第 100 节） |
| "这个功能老是报错，一堆英文看不懂" | 错误分类 + 用户话术（第 104 节） |
| "能不能做成我发微信语音，它回我" | 转写 + 合成（第 102、103 节） |
| "帮我做一批商品图" | **这个要用代码，不是生图**（第 101 节） |

**最后一条是这一周最反直觉、也最值钱的判断。**

**不学这一周的后果很具体：** 你会在一个"让 AI 写字"的需求上花 20 张图的成本和一下午时间，最后被客户一句"这个字位置不对"打回原点。

七节课的代码全在同一个项目 `mm-app` 里。后面几节不新建项目，只往里加文件。

| 节课 | 主题 | 核心产出（都在 `第NN节课/03-练习代码/mm-app/` 下） |

| 第 100 节 | 图片内容提取 | `lib/extract.js` + `routes/extract.js` + `public/extract.html` + `extractions` 表 |
| 第 101 节 | 生成图片需求 | `lib/imagine.js` + `scripts/imagine-lab.js` + `out/imagine-lab.md` |
| 第 102 节 | 语音转文字 | `lib/audio-info.js` + `lib/transcribe.js` + `out/error-table.md` |
| 第 103 节 | 文字转语音 | `lib/tts-split.js` + `lib/tts-cache.js` + `lib/speak.js` + `out/tts-log.md` |
| 第 104 节 | 多模态错误处理 | `lib/errors.js` + `lib/retry.js` + `lib/error-middleware.js` + `out/error-matrix.md` |
| 第 105 节 | 完成图文助手 | `lib/session.js` + `lib/assistant.js` + `routes/assistant.js` + `public/assistant.html` |

**七个产出是连着的：**

```text
第 99 节的 vision.js → 第 100 节在它基础上做提取 → 第 105 节的追问也用它
第 100 节的 extract.js → 第 105 节的并行里一半是它
第 102 节的时间偏移  → 第 105 节的多段播报是同一类问题
第 103 节的缓存      → 第 105 节的"语音按需"才省得下来
第 104 节的 errors.js → 第 105 节所有接口都靠它出口
```

**跳节的代价：**

```text
跳第 104 节 → 第 105 节你做出来的东西，出错时用户只看到"请求失败"
跳第 100 节 → 第 105 节"看到图并给出字段"这件事就没了，只剩描述
跳第 102/103 → 第 105 节的"念给我听"做不了
```

**唯一能跳的是第 101 节（生图）**，因为它和后面的链路无关。**但它是这一周判断力训练的核心**，跳了你会一直以为"生成图片"就是"调个接口"。

## 这一周有三个"假东西"，各有各的用途

这一周要花钱的地方有四处：视觉、生图、转写、合成。所以四处都做了假实现 —— **但三处的目的完全不同。**

### 一、假视觉（第 99 节）

```text
返回预设的描述和字段 JSON
能做到：跑通整条链路，验证页面、存储、错误处理
做不到：验证任何识别准确率
```

**用途：省下调试管道时的钱。** 因为管道问题（路径错、字段名错、页面不刷新）和"识别准不准"完全无关，你不该为了调前者去付后者的钱。

### 二、假生图（第 101 节）

```text
用提示词的哈希决定颜色，生成一张纯色 PNG
能做到：验证参数、端点、返回解析、存盘
做不到：验证"这个需求该不该生图"
```

**它必须"每张颜色不同"，因为你要能确认"发出去的是不是我以为的那条提示词"。**

**但它永远成功 —— 所以第 4、5 组"不该生图"的实验，在 MOCK 下毫无意义。** 那两组必须用真模型跑一次，你才会亲眼看到"年终大促"四个字被写成什么样。

### 三、假转写（第 102 节）— 这个最特殊

```text
不是返回空，而是返回一段【故意带同音字错误】的文本：
  "在座的" 应该是 "在做的"
  "华东区" 可能是 "华南区"（无法判断）
  "下个月十号" 可能是 "10 号"
```

**为什么假实现要"故意有错"：**

```text
返回完美文本 → 你练不到任何东西
返回带错的文本 → 你能练：怎么逐句对照、怎么标不确定、怎么跟客户说
```

**这是"假数据要模拟真实缺陷"的原则。** 和第 101 节"假图颜色各异"是同一个道理：**假数据必须带可识别的特征。**

### 四、假合成（第 103 节）

```text
生成一段能播的 WAV（不同段用不同频率）
能做到：验证分段、缓存、播放清单
做不到：验证语音自然度
```

## 这一周最容易卡住的六个地方

### 一、`Unexpected token 'I', "ID3..." is not valid JSON`

**原因：** 你在 TTS 的地方用了 `res.json()`。**音频返回的是二进制流，不是 JSON。**

**解法：** `res.arrayBuffer()` 然后 `Buffer.from(...)`。**并且先看 `Content-Type` 再决定怎么读** —— 因为服务"成功"时也可能返回 JSON（错误信息）。

### 二、`Content-Type: multipart/form-data` 手写导致 `file field is required`

**原因：** `multipart/form-data` 必须带 `boundary` 参数，手写会覆盖掉 fetch 自动生成的那个。

**解法：** **只给 `Authorization`，不要设 `Content-Type`。** 这个错误信息完全不指向真正原因，你会去检查 `FormData` 的每一行，全是错的。

### 三、分段转写后时间戳来回跳

**原因：** 每段的 `start` 是相对于**这一段自己**的。第 3 段的 `start: 30.0` 是"第 3 段内部第 30 秒"，不是"全文件第 30 秒"。

**解法：** 累加偏移。`cursorSec += pieceSec`。**而且 `pieceSec` 要用"这段的真实时长"，不是"你请求的上限"。**

### 四、TTS 账单爆炸（2841 次调用 / 36 段文本）

**原因：** 没有缓存，或缓存键只放了 `text`。

**解法：** 缓存键必须包含所有"影响音频字节"的参数：`text` + `model` + `voice` + `speed` + `format` + **`baseUrl`**。

**最后一个是重点：** 换了服务商，同名模型的声音完全不同，缓存键里不带上就会听到旧服务商的声音。

### 五、`PayloadTooLargeError` 但提示说"请压缩到 5MB 以内"

**原因：** `express.json()` 默认 limit 是 **100kb**。

**解法：** `express.json({ limit: "20mb" })`。

**这个坑最阴险：错误信息的方向是对的（"太大"），但阈值是错的（100KB 而不是 5MB）。用户会一直压，压到 50KB 还是失败。**

### 六、`CONTENT_FILTER` 是 HTTP 200

**原因：** 内容审核拒绝在多数服务里返回 200 + `finish_reason: "content_filter"`。

**解法：** **不能只判断 `res.ok`。** 必须检查 `finish_reason`，并且给它一个独立的错误码（不可重试）。

**因为"审核拒绝"和"返回为空"的处理完全不同：** 前者说"请换一张"，后者说"请重试"。**混在一起会让用户无限重试一张永远过不了的图。**

## 这一周的五条铁律

```text
一、所有本地文件都要转 base64 + data URL。
    因为模型服务器访问不到你的硬盘。图片、音频都一样。

二、所有要花钱的步骤，先在假实现上把管道验证完。
    换成真接口只改一行 .env。而且假数据必须"带可识别的特征"。

三、生图不擅长"精确"，代码擅长"精确"。
    文字、品牌色、logo、二维码 —— 全部用代码叠，不要指望模型。

四、错误必须分类，而且必须区分"能不能重试"。
    对"内容审核拒绝"重试五次，是白花钱 + 让用户白等。

五、缓存键要包含所有影响输出的参数，包括服务商地址。
    少一个，就会出现"缓存命中但结果是错的"，而且不报错。
```

## 周末的验收

```text
- [ ] 我能说清 base64 和 data URL 各是什么，为什么本地文件必须转
- [ ] 我上传过一张图，看到了真正发出去的消息 JSON 和 base64 前缀
- [ ] 我能说出"让生图写四个汉字"会失败的原因，以及正确做法
- [ ] 我做了一份"该不该生图"的判断表，至少 10 行
- [ ] 我能从 WAV 头里读出采样率和 byteRate，并算出时长
- [ ] 我手算过 96044 = 44 + 3 × 16000 × 2，和脚本输出一致
- [ ] 我的分段转写让时间戳单调递增（不是每段从 0 开始）
- [ ] TTS 缓存命中率我量出来了，并且知道它省了多少钱
- [ ] 我的缓存键里有 baseUrl（换服务商不会命中旧音频）
- [ ] 六种错误我都能说出 name / status / message 三处指纹
- [ ] 我知道 CONTENT_FILTER 是 200，也知道为什么它最危险
- [ ] 我的重试逻辑对不可重试的错误只调用 1 次、耗时 < 50ms
- [ ] 返回给前端的 JSON 里没有 detail，日志里有
- [ ] 图文助手追问第二轮能正确理解"那日期呢"
- [ ] 我能说出并行省了 1.8 秒、语音按需省了 2.2 秒，以及各自该谁决定
```

> **第 3、4 条和第 11、12 条不能落。**
>
> 第 3、4 条（生图判断）落了，你会在"生成海报"这类需求上反复踩坑，而且每次都以为是"提示词没写好"。
>
> 第 11、12 条（错误分类）落了，你做出来的东西出错时只会说"请求失败"，用户只能一遍遍重试 —— **而你会觉得"功能已经做完了"**。

## 这一周不用学什么

明确划掉，别在这上面花时间：

```text
流式 TTS / 实时语音对话        这是另一套技术（分块输出 + 流式解码），第 17 周讲实时通信时才提
声音克隆 / 声音训练            不是接口能做的事，也不该做
视频生成                       成本和量级完全不同，本课程不涉及
图片局部重绘 / inpainting      需要专门工具，不是通用生图接口能做的
ffmpeg / sharp                 需要编译或大依赖。本课用"只支持 WAV 分段"绕开
浏览器录音 / MediaRecorder      第 27 周（前端进阶）会讲
OCR 引擎自建（tesseract 之外的） 第 82 节已经讲过"本地 vs 多模态"的取舍
```

**关于"不做流式"多说一句：**

这不是偷懒。流式 TTS 需要三个条件同时成立：**接口支持分块输出 + 播放器支持流式解码 + 前端能做缓冲管理**。这三件事都不在这一周的范围里，硬做只会让你得到一个"偶尔断音"的东西。

**今天做的是"点击 → 等 1–3 秒 → 播放"。这个体验在"朗读一段制度"这种场景完全够用。**
