```text
saas-lab/
├── src/
│   ├── pay/
│   │   └── provider.js        适配层：sign / verifySignature / createPayment / queryPayment
│   ├── orders/

├── migrations/
│   └── 013_anomalies.sql      payment_anomalies 表
└── scripts/
    ├── mock-gateway.js        本地假网关（独立进程，端口 4000）
    ├── fake-callback.js       假签名回调（应该被拒）
    ├── tamper-callback.js     真签名 + 假金额（应该被拒）
    └── query-pending.js       主动查单（救回调丢失的订单）
```

## 必须四个进程同时在跑

```text
1. npm run dev                   你的服务，3000
2. node scripts/mock-gateway.js  mock 网关，4000
3. 浏览器                        打开 pay_url 点支付
4. 命令行                        跑各种测试脚本
```

**少一个都测不出来。** 尤其是第 2 个——**它是这节课一半的价值所在**，因为它能造出真实平台不给你造的场景。

## 四个必须亲手做的实验

**一、假签名**

```text
node scripts/fake-callback.js
期望：401 SIGN_INVALID，订单还是 pending
```

**二、真签名 + 1 分钱**

```text
node scripts/tamper-callback.js
期望：400 AMOUNT_MISMATCH，订单还是 pending
```

**三、重放 20 次**

```text
curl -X POST http://localhost:4000/mock/repay/MOCK<单号>?times=20
期望：plan_expires_at 只加 30 天
```

**四、回调丢失**

```text
curl -X POST http://localhost:4000/mock/lose-notify/MOCK<单号>
node scripts/query-pending.js
期望：查单把它救回来
```

**第四个实验最能说明问题。** 你会看到：网关那边显示"已支付"，你的库显示"待支付"，**两边的数据不一致，而客户只知道自己付了钱。**

## 一个容易忽略的细节

**`update orders set payment_no = ...` 要加 `and payment_no is null`。**

```js
// ❌ 会覆盖回调写进去的值
update orders set payment_no = $1 where tenant_id = $2 and id = $3

// ✅ 幂等，不覆盖
update orders set payment_no = $1
where tenant_id = $2 and id = $3 and payment_no is null
```

**这两个值通常一样，所以覆盖了也看不出来。**

**但"通常一样"不是"一定一样"。** 而且这个习惯要养成：**所有"写一个可能已经写过的字段"，都加 `is null` 条件。**
