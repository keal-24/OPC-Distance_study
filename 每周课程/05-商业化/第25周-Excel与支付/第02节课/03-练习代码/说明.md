## 这一节的两个"必须自己想到"

**一、为什么是"先全量校验、再批量入库"**

如果你写成这样：

```js
for (const rec of records) {
  const r = validateRow(rec);
  if (r.errors.length) { failed++; continue; }
  await client.query('insert ...');     // 边校验边插
}
```

**功能上看起来对，但它有一个致命问题：整个操作在一个事务里。**

第三条数据报错、你 `continue` 了，没问题。但如果某一条插入时数据库抛错（比如约束冲突），整个事务回滚——**前面已经插进去的好数据全没了。**

**改法：先把所有行校验完，拿到确定的 `good` 列表，再一次性 `unnest` 插入。**

**这样"哪条不合法"和"数据库能不能插"完全解耦。**

**二、为什么必须 `on conflict do nothing`**

你的代码已经查过"订单号是否已存在"，看起来不需要冲突处理。

**但两个管理员同时传同一份文件呢：**

```text
请求 A：查重 → B001 不存在
请求 B：查重 → B001 不存在
请求 A：insert B001 → 成功
请求 B：insert B001 → 撞唯一约束 → 抛错 → 整个事务回滚 → 全部失败
```

**结果：B 的整批数据一条都没进去，而 A 的全进去了。**

**有了 `on conflict do nothing`，B 的那一条被跳过，其余照常插入，`returning` 只返回真实插入的行数。**

**这才是正确的行为。**

## 三个必须做的实验

```text
1. 全错文件（make-bad.js）
   → 必须不崩，返回 8 条失败，库里 0 条

2. 一半对一半错
   → ok: 4, failed: 4，库里多了 4 条

3. 同一份文件再传一次
   → ok: 0，那 4 条变成 ORDER_NO_EXISTS
```

**第 3 个实验是这一节的核心。** 如果第二次还是 `ok: 4`，说明你的 `on conflict` 或者查重有问题，客户重复上传就会重复入库。
