## 三个数字

```text
200ms    加载提示的延迟
15 秒    请求超时
3 秒     客户能等的"有反馈"的时间
```

**这三个数字不是随便定的，是"人的感知阈值"。**

## 一个反直觉的技巧

**"加载中"要延迟 200ms 才显示。**

```text
接口 30ms   → 不显示骨架屏，直接出数据（否则会闪一下）
接口 800ms  → 200ms 时显示骨架屏
```

**这个技巧叫 "delayed loading indicator"，所有做得好的产品都这么做。**

**不做的后果：** 客户每次刷新都看到"列表消失 → 骨架屏 → 列表出现"，**虽然只闪 30ms，但感觉像卡了一下。**

## 一个必须解决的问题：请求竞态

```text
① 点"待支付" → 请求 A（慢，2 秒）
② 改点"已支付" → 请求 B（快，0.3 秒）
③ 0.3 秒后显示"已支付"的数据 ✅
④ 2 秒后请求 A 返回 → 界面变成"待支付"的数据 ❌
```

**客户看到的是"我点了已支付，怎么显示待支付"。**

**解法就是三行：**

```js
const seq = ++requestSeq;
const data = await fetcher();
if (seq !== requestSeq) return;   // 不是最新请求，丢弃
```

**这三行在筛选、搜索、翻页里 100% 会遇到。** **记住它。**

## 三个必须做的实验

**一、断网（F12 → Network → Offline）**

```text
期望："网络好像断了，检查一下 WiFi 或流量" + [重试]
不是："Failed to fetch"
```

**二、Slow 3G**

```text
期望：有进度提示，等 3—5 秒，数据出现
```

**三、15 秒超时**

```text
期望："请求超时，网络可能不太好" + [重试]
不是：一直转圈
```

**"一直转圈"是最糟的——客户不知道还要等多久，也不知道该不该放弃。**
