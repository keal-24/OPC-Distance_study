## 这一节最重要的一句话

```text
先算差异，再决定写不写。
```

**直接 `for` 循环 upsert 一遍，跑完你什么都不知道：**

```text
本地 300 个，平台 305 个 → 那 5 个在哪？不知道
某次 API 失败被你 catch 住了 → 少了 5 个，没人知道
有人改邮箱 → 被当成新人，多了一条
```

**"对账式同步"把这三件事都变成**看得见的数字**：**

```text
willInsert: 0
willUpdate: 1（张伟：员工001 → 改过的名字）
willDeactivate: 1（李四离职了）
```

## 一个真实的坑

**`unnest` 只能展开一维数组。**

```sql
-- ❌ 想传"每个用户一个部门数组"
from unnest($8::text[][])
```

**报错：`malformed array literal` 或维度不匹配。**

**解法：用逗号拼字符串，插入时 `string_to_array` 拆回来。**

```js
const depts = plan.toInsert.map((r) => (r.departmentIds || []).join(','));
```

```sql
coalesce(string_to_array(nullif(t.depts_str, ''), ','), '{}'::text[])
```

**这个技巧在"要把数组塞进批量插入"时反复用到。**

## 三个必须做的验证

**一、三页拉完 137 人**

```text
[contacts] 第 1 页：50 条，累计 50，has_more=true
[contacts] 第 2 页：50 条，累计 100，has_more=true
[contacts] 第 3 页：37 条，累计 137，has_more=false
```

**注意最后一页是 37，不是 50。** **如果平台数据造的是"正好 150 人"，你永远测不出"最后一页不满"的 bug。**

**二、第二次预览全是 0**

**这是幂等性的证明。** **如果第二次还有 `willInsert`，说明你的唯一键匹配不上。**

**三、改一个名字，预览能看到"从什么改成什么"**

```json
{ "name": ["员工001", "改过的名字"] }
```

**这个"变更详情"是对账报告最值钱的部分——** **客户（或者你自己）能一眼看出"这次同步会改什么"，然后决定要不要执行。**
