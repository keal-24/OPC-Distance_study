## 这一周的目标

把第 25 周那套"收外部数据、保证幂等、对得上账"的能力，用到平台对接上：

```text
第 25 周                     第 26 周
────────────────────────────────────────────
Excel 导入    →  平台推来的事件
支付回调      →  平台的回调（URL 验证 + 加密）
对账          →  拉取通讯录/审批/文档核对
幂等          →  同一个 event_id 来两次
```

**这一周结束，你要能做到这五件事：**

1. **说清飞书 / 企业微信 / 钉钉怎么选**，不靠感觉；
2. **自己管 `access_token`** —— 缓存、续期、并发不打架；
3. **接住平台推来的事件** —— 3 秒内应答，重的不在回调里做；
4. **写一个通用的 Webhook 四件套** —— 验签、幂等、重试、留档，套到任何平台都行；
5. **做出一个卡片机器人** —— 客户在群里点按钮就能操作你的系统。

## 为什么排在这一周

**中国 B 端交付，一半以上的入口在这些平台里。**

客户不会天天打开你的网站，但他天天开着飞书/企微。**你的系统不在他工作的地方，他就不会用。**

更现实的一点：

```text
你在群里推一条"今日有 3 个待审批"
→ 客户点一下按钮批准
→ 全程不打开你的系统
```

**这一条比任何 UI 优化都值钱。** 因为它的成本是"客户不用改变习惯"。

## 一个必须先讲清楚的前提

**这一周不强依赖真实企业凭证。**

```text
真实飞书自建应用  要企业管理员审核、要配 IP 白名单、要开通权限
真实企微自建应用  要企业微信管理员、要有可信域名
```

**你在学习阶段拿不到，也不该为这个卡住。**

**所以这一周做两件事：**

```text
① 一个本地假平台（scripts/mock-platform.js）
   它模仿真实平台的四件事：发 token、推事件（带 5 秒超时）、验签、卡片按钮回调

② 一层适配（src/platform/adapter.js）
   接真实平台时，只改这一个文件
```

**如果你有真实凭证**，那就更好了——`adapter.js` 里给出了飞书和企微的替换写法，直接换。

**假平台最大的价值：** 真实平台不会给你造"回调超时 6 秒""同一个事件推三次""token 提前 5 分钟过期"这些场景，**假平台随便造。**

## 这一周的四条铁律

```text
一、平台的接口一律不可信、不可靠、不可预测。
   会超时、会重复、会乱序、会在半夜改权限。

二、回调必须 3 秒内应答（飞书是 3 秒，企微是 5 秒）。
   重活全部丢到后台，回调只做"记账 + 应答"。

三、token 必须缓存在服务端，绝不能每个请求换一次。
   平台的换 token 接口有频率限制，超了直接封。

四、所有平台事件都要落库，落库要有 event_id 唯一约束。
   平台重推是常态，不去重就一定会重复处理。
```

## 这一周最容易出事的三个地方

**第一：在回调里做耗时操作**

```js
app.post('/webhook/feishu', async (req, res) => {
  await db.query('insert ...');               // 10ms
  const user = await fetchUserInfo(...);      // 300ms
  await sendMessage(...);                     // 500ms
  await callLLM(...);                         // 8000ms  ← 这里就超时了
  res.json({});                               // 平台早就放弃了
});
```

**平台看到超时，会重推。**

**重推你又一次调大模型 → 又超时 → 再重推。**

**最后你收到 3 条一样的消息，客户看到 3 条一样的回复。**

**第二：每个请求换一次 token**

```js
async function sendMessage(...) {
  const token = await getAccessToken();   // 每个请求都换
  ...
}
```

**飞书的 `tenant_access_token` 有效期 2 小时，但换 token 接口有频率限制。**

**并发 10 个请求各换一次，你会被限流；被限流后 token 拿不到，整个应用瘫痪。**

**第三：只处理"成功"分支**

**平台推来的事件里，`event_type` 有几十种。你只处理了 3 种，剩下 27 种会怎样？**

**如果你返回 200，平台认为你处理了，数据就丢了。**

**如果你返回 500，平台一直重试，你一直 500，最后你的接口被标记为不健康。**

**正确做法：收到不认识的事件，记一条 `ignored` 日志，返回 200。**

## 周末的验收

不要急着进下一周。先确认这五条：

- [ ] 我能说出飞书、企微、钉钉各自适合什么客户，以及为什么
- [ ] 我的 `access_token` 缓存在内存里，10 个并发只换 1 次
- [ ] 回调接口在 3 秒内返回，重活全在后台
- [ ] 同一个 `event_id` 推 3 次，业务只执行 1 次
- [ ] 一个卡片消息能发出去，点按钮能收到回调

**另外：**

- [ ] 每节课的 `NOTES.md` 都填了
- [ ] `npm test` 里的隔离测试还是全绿
- [ ] 新加的表都有 RLS

> **第四条才是真标准。** 平台重推是常态，不是异常——**把它当异常处理的人，一定会在某天收到客户"为什么我收到两条一样通知"的投诉**。
>
> **一周七节课，落一节课没关系，但第 178、179 节不能落。** 事件接收和幂等做不好，后面的卡片、拉数据全是空中楼阁。
