## 一句话原则

> **`success` 只代表"客户走完了支付动作"，钱到账没有只有回调知道。**

**所以：**

```text
wx.requestPayment success → 显示"确认中" → 轮询后端
真正的"已支付" → 只能由"带签名的回调"或者"主动查单"决定
```

**这一条和第 174 节（支付回调）完全一样，因为它们是同一个问题的两个变种。**

## 五个必须后端做的事

```text
算金额、调统一下单、二次签名、验签回调、判断已支付
```

**判断标准：任何用到密钥的操作，都必须在服务端。**

**没有例外。**

## 四个错误

| 错误 | 后果 |
|---|---|
| 不验签 | 任何人 POST 一条就能白拿会员 |
| 不在 `where` 里判状态 | 重放三次加三次时间 |
| 用请求里的金额 | 账对不上 |
| 孤儿支付返回 404 | 微信重试 8 次，日志刷满 |

**四个都撞一次。**

## 一个必须知道的结构

**回调里的 `where`：**

```sql
where tenant_id = $1 and id = $2 and status in ('pending', 'expired')
```

**没有 `'paid'`。**

**所以重复回调的 `rowCount = 0`，走"不需要变更"分支。**

**这就是幂等。** **和第 173 节的 `markPaid`、第 180 节的卡片回调，是同一个写法。**

**你已经写了三次了。** **这个模式要在养成本能。**

## mock 和真实的三处差异

```text
签名算法   MD5     →  RSA（私钥签名）
密钥形式   字符串  →  apiclient_key.pem 文件
回调解密   明文    →  AEAD_AES_256_GCM（要 APIv3 密钥）
```

**换真环境时只改这三处，其他代码一行不用动。**
