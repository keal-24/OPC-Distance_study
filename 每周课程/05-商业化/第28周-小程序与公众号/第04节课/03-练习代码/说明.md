## 三句话

```text
code 换 openid
openid 换你的 user_id（要先用邀请码证明"你是谁"）
前端只拿 token
```

**中间那一步是这一节的重点。** **第 190 节那版直接跳过了它，任何人打开就是管理员。**

**记住这三句，这节课就懂了。**

## 三条红线

**一、`session_key` 永不下发。**

**它能解密这个用户的所有敏感数据。** **一旦到了前端，被反编译就全泄露。**

**二、`openid` 不是用户 id。**

**它是"用户 + 小程序"的组合。** **换一个小程序就变了，你的客户数据会全丢。**

**三、生产环境不能开 mock。**

**`WECHAT_MOCK=1` 时任何人都能伪造登录。**

**加一行启动检查：**

```js
if (process.env.NODE_ENV === 'production' && process.env.WECHAT_MOCK === '1') {
  console.error('!!! 生产环境不能开 WECHAT_MOCK');
  process.exit(1);
}
```

## 这一节真正的新东西：把"自动绑定"换成邀请码

**第 190 节那版代码是"登录就给租户第一个账号的权限"，任何打开小程序的人都是管理员。** 这一节把它彻底换掉。

三个文件是这一节的主角：

```text
src/db/system-pool.js        绕过 RLS 的系统连接（没有它，登录接口根本跑不起来）
src/routes/wechat.js         登录 + 绑定两个接口
miniprogram/pages/bind/      输邀请码的页面
```

**为什么需要 `system-pool.js`，一句话：**

**登录的唯一职责是"从零确定这个人是谁"。它必须读 `wechat_users`、必须写 `wechat_users`——而这两张表有 `force RLS`，需要 `app.tenant_id` 才能读写。** **要拿到 `app.tenant_id` 又得先知道这个 openid 绑在哪家公司。** **死循环。**

**所以这条路必须绕过 RLS，而绕过 RLS 意味着"这段代码能看到所有客户的数据"。** **这就是代价，它比"多写一个文件"重得多。**

## 三种绑定方式，为什么选邀请码

```text
① 邀请码（不需要资质，最通用）→ 选它
② 手机号（需要企业主体）
③ 邮箱密码登录（体验差但能用）
```

**选 ①，因为它是唯一"不需要任何资质、也不牺牲安全"的方案。**

**② 其实体验最好**（客户不用记码），但个人小程序拿不到手机号。**如果你的小程序是企业主体，优先做 ②，把 ① 留作备用。**

## 跑之前先确认这个顺序

```text
1. 建表（wechat_users + invite_codes）
2. 建 system-pool.js，.env 加 SYSTEM_DATABASE_URL
3. 改登录路由（两个接口）
4. 改小程序端 login + 加 bind 页
5. 网页版加生成邀请码的接口
6. 按第 3.5 节跑六种情况
```

**第 2 步不能跳。** **跳过它直接写路由，你会看到一个非常费解的报错：** **登录时明明数据库里有这个人，接口却当他不存在，然后插入撞唯一约束报 500。** **那不是并发问题，是 RLS 把你的 `select` 变成了 0 行。**

## `loginPromise` 并发合并

**和第 177 节的 token 单飞是同一个思路：**

```js
if (loginPromise) return loginPromise;    // 已经有人在换了，等它
loginPromise = (async () => { ... })().finally(() => { loginPromise = null; });
```

**不做的后果：**

```text
小程序启动 → 3 个请求同时 401 → 3 次 wx.login → 3 次 code2session
→ 触发微信 45011（登录太频繁）
```

**客户会看到"登录太频繁，请稍后再试"——** **而他什么都没做，只是打开了小程序。**
