# 第 0 步：先看一眼你现在的东西（10 分钟）

## 0.1 你的 `chat-app` 长什么样

第 3 周第 21 节课你做的对话应用，数据结构大概是：

```text
conversations
├── id
├── title
└── created_at

messages
├── id
├── conversation_id
├── role
├── content
└── created_at
```

**看出来了吗：这两张表里没有一个字段在回答"这条数据属于谁"。**

不是缺 `user_id`——就算你第 8 周学会了登录、加了 `user_id`，也还不够。

## 0.2 `user_id` 为什么不够

假设客户 A 是家公司，里面有三个人在用：老王、小李、小张。

```text
老王   user_id = 11
小李   user_id = 12
小张   user_id = 13
```

现在客户 B 也来了，也有三个人：

```text
小赵   user_id = 14
小钱   user_id = 15
小孙   user_id = 16
```

你要做的是：**老王能看到小李的对话**（同一个公司），**但看不到小赵的**（不同公司）。

只看 `user_id`，你根本分不清 11 和 14 有什么关系。你只能再加一张表维护"谁和谁是一伙的"，然后每条查询都去 join 它。

**这就是为什么要有租户（tenant）这一层。**

```text
租户 = 一个客户单位
     = 一家公司 / 一个团队 / 一个工作室

一个租户里可以有 1 个人，也可以有 20 个人。
```

**加上租户之后，数据结构变成三层：**

```text
租户（客户 B）
└── 用户（小赵、小钱、小孙）
    └── 数据（对话、消息、文件）
```

**这一周要干的，就是把"租户"这一层插进你所有的表里。**

## 0.3 三个客户会对你提什么要求

别想"以后做大再说"。你现在接活，第三个月就会遇到这种局面。

```text
客户 A：一家 8 人的设计公司，用你的对话工具整理客户沟通记录
        要求：我们同事之间能看到彼此的记录，外人不许看

客户 B：一家律所，5 个人
        要求：我们的对话涉及案情，绝对不能和别的公司混在一起
              最好能给我们看一份"你们怎么保证不混"的说明

客户 C：一家制造业工厂的 IT 部门
        要求：数据必须存在我们自己的服务器上，不能出内网
```

**三个客户，三种完全不同的处理方式。**

- A 和 B 可以用同一套系统，靠 `tenant_id` 隔开；
- C 的需求**做不到**用同一套共享系统满足，这类客户要么单独部署，要么不接。

**这节课剩下的部分，就是教你怎么判断哪些客户能接、接了之后怎么不把自己拖死。**

# 第 1 步：三条路摆出来（25 分钟）

## 1.1 方案 A：每个客户一套

```text
客户 A → 服务器 A + 数据库 A + 代码 A
客户 B → 服务器 B + 数据库 B + 代码 B
客户 C → 服务器 C + 数据库 C + 代码 C
```

**听起来最安全，事实也确实最安全。** 客户 A 的服务器上没有客户 B 的一个字节。

**一个人做会怎样：**

| 事情 | 一个客户 | 五个客户 |
|---|---|---|
| 发一次版本 | 部署 1 次 | 部署 5 次 |
| 修一个 bug | 改 1 遍、测 1 遍、发 1 次 | 改 1 遍，**发 5 次，测 5 次** |
| 数据库加一列 | 跑 1 次迁移 | 跑 5 次，还得记谁跑过谁没跑 |
| 半夜挂了 | 爬起来 1 次 | 爬起来不确定是哪台挂了 |
| 每月成本 | 1 台服务器 | 5 台 |
| 客户要统计总用量 | 做不到，得手工加 | 做不到 |

**五个客户是分界线。** 三个客户你还能靠意志力撑，五个客户开始你的周末就没了。

**而且这套方案有个隐性成本：客户版本会漂。**

```text
客户 A 说"我们这个按钮能不能换个位置" → 你改了 A
客户 B 说"别改，我们习惯现在的"        → 你不改 B
三个月后 A 和 B 的代码不一样了
半年后你不敢给 A 升级，因为你不知道会坏什么
```

**这就是"一套代码五份拷贝"的真实结局：不是维护五个客户，是维护五个产品。**

## 1.2 方案 B：一套代码，一个客户一个库

```text
代码（一份）
├── 客户 A → 数据库 A
├── 客户 B → 数据库 B
└── 客户 C → 数据库 C
```

**代码只有一份，升级只发一次。** 数据物理隔离，客户 B 的律所会满意。

**问题在连接层：**

```js
// 每次请求都要判断该连哪个库
const pool = pools[tenantId];        // 谁来维护这个 pools？
```

**你要自己管的事：**

```text
① 每个库一个连接池，100 个客户就是 100 个池子，内存吃不消
② 建客户 = 建库 + 建表 + 跑迁移 + 加连接池（要写一套自动化的东西）
③ 加一列 = 100 个库各跑一次，跑失败一半你怎么回滚
④ 跨客户统计（今天总共多少条消息）= 100 次查询再手工加
⑤ 备份 = 100 个库各备一次
```

**这套方案适合"客户数少但数据敏感度高"的场景，比如 10 家医院。**

**一个人 + 想做标准化产品，这套方案的成本比方案 A 还高**——因为方案 A 至少不用写自动化建库程序。

## 1.3 方案 C：一套代码，一个库，靠 `tenant_id` 隔

```text
代码（一份）
数据库（一个）
├── 所有客户的数据都在同一批表里
└── 每行数据带一个 tenant_id，标明属于谁
```

**一个客户的 8 个人和另一个客户的 5 个人，共用同一张 users 表，只是 tenant_id 不同。**

**好处一眼能看出来：**

| 事情 | 怎么做 |
|---|---|
| 加一个客户 | 插一行 `tenants`，几毫秒 |
| 加一列 | 跑一次迁移，全体生效 |
| 发版本 | 部署一次 |
| 统计总用量 | 一条 `SELECT sum()` |
| 备份 | 备一个库 |
| 每月成本 | 一台服务器，客户越多越划算 |

**代价只有一个，但这个代价很重：**

```text
只要有一条 SQL 忘了写 tenant_id，客户就能看到别人的数据。
不会报错。不会告警。功能一切正常。
```

**这不是"小心一点"能解决的问题。** 一个中型项目几千条 SQL，你不可能每条都记住。所以这一周第 165 节要做的事是：**让漏写这件事在代码层面不可能发生**，而不是靠自觉。

## 1.4 还有第四个选项：在方案 C 上加一层枷锁

PostgreSQL 有个功能叫行级安全（Row Level Security，简称 RLS）。

**它在数据库这一层再拦一道：**

```text
应用层写错 → 数据库发现 tenant_id 不匹配 → 直接返回 0 行
```

**相当于锁了两道门。** 第一道是你的代码（第 165 节），第二道是数据库（第 165 节的后半段）。

**这一周走方案 C + RLS。** 不是因为它最先进，是因为它是一人公司唯一算得过来的账。

## 1.5 一句话决策表

以后再有客户来问，照这张表判断：

| 客户情况 | 走哪条路 |
|---|---|
| 普通中小企业，1—50 人，能接受数据在云端 | **方案 C**（这一周做的） |
| 有明确的合规要求（医疗、金融），但规模小 | 方案 C + 签数据处理协议；做不到就走方案 B |
| 要求数据必须在自己的服务器 / 内网 | **方案 A 的单客户版本**（第 34 周私有化部署） |
| 要求"我们的代码不能和别人一样" | 报价 ×3，走方案 A。这种客户通常也付不起 |
| 客户数超过 200，某个大客户占你收入 40% | 那个大客户单独一套，剩下的继续方案 C |

**注意最后一行，这是最容易做错的决定。**

**收入集中的大客户一定要单独一套。** 不是技术原因，是商业原因：他哪天要你改一个只有他需要的功能，你不会为了他把所有客户的产品逻辑搞乱。

# 第 2 步：把账算给自己看（15 分钟）

**不要凭感觉选。** 拿纸算一遍，数字比直觉可靠。

## 2.1 假设：5 个客户，每个客户每月付 2000 元

**方案 A（五套独立）：**

```text
服务器        5 台 × 100 元/月        =  500 元/月
每月维护     5 套 × 2 小时部署          = 10 小时/月
每次改功能   5 套 × 1.5 小时测试回归    =  7.5 小时/次
客户要新功能 只能在其中一套上做，其他四套排队
```

**一个月按 4 次改动算：**

```text
10 + 7.5 × 4 = 40 小时/月   ← 光是维护，不含开发新功能
```

**40 小时是一个人的全部工作时间。** 也就是说：**你有 5 个客户之后，就没时间开发任何新东西了。**

**方案 C（一套共享）：**

```text
服务器        1 台 × 200 元/月（配置高一点）  = 200 元/月
每月维护     1 套 × 2 小时部署                =  2 小时/月
每次改功能   1 套 × 1.5 小时测试              = 1.5 小时/次
```

```text
2 + 1.5 × 4 = 8 小时/月
```

**40 小时 vs 8 小时。** 差出来的 32 小时，才是你能拿去接第六个客户、或者开发新产品的时间。

## 2.2 但方案 C 有一笔隐藏成本

```text
第一次做对隔离       20—30 小时（就是这一周）
之后每条新接口       多写一行 WHERE
出一次数据泄露       客户流失 + 赔偿 + 口碑
```

**这笔成本只付一次。** 方案 A 的 40 小时是每个月都付。

**所以结论很清楚：**

> **方案 C 前期贵、后期便宜；方案 A 前期便宜、后期把你买断。**

**你现在（第一个客户还没签）正是付前期成本最便宜的时候。** 等有 3 个客户再改，你要停机导数据，还要跟客户解释为什么停机。

## 2.3 什么时候可以推翻这个决定

留个记录在这里，以后回头看：

```text
① 某个客户明确要求独立部署，并且愿意付 3 倍价钱 → 给他单独一套，代码用同一个 Git 仓库，不进主线
② 客户数过 200，共享库的慢查询开始互相影响 → 那时候再考虑分库，不是现在
③ 你自己判断失误，方案 C 支撑不住 → 那也是"分库"，不是"重写"，因为 tenant_id 已经在了
```

**注意第三条：只要 tenant_id 在，从共享库换成独立库是有路的。反过来则没有。**

**这就是为什么这一周值得花 20 小时。**

# 第 4 步：连上数据库（15 分钟）

## 4.1 写连接池

**`src/db/pool.js`：**

```js
const { Pool } = require('pg');
require('dotenv').config();

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 5000,
});

pool.on('error', (err) => {
  console.error('[db] 空闲连接出错：', err.message);
});

module.exports = pool;
```

**这四个参数各管什么，一次讲清：**

| 参数 | 意思 | 为什么是这个值 |
|---|---|---|
| `connectionString` | 从哪连 | 只从环境变量来，不在代码里写密码 |
| `max: 10` | 最多同时开 10 条连接 | 一人公司的小应用用不到更多，开多了数据库扛不住 |
| `idleTimeoutMillis` | 空闲 30 秒就关掉 | 免得一直占着数据库的连接数 |
| `connectionTimeoutMillis` | 5 秒连不上就报错 | **没有这个，数据库挂了你的请求会一直挂着不返回** |

**最后那个 `pool.on('error')` 不是可有可无的。**

**如果数据库那边把你的连接踢了（重启、超时、网络断），没有这个监听，Node 会抛一个没人接的异常，整个进程退出。**

**表现就是：数据库闪了一下，你的网站就死了。**

## 4.2 写一个自检脚本

**`scripts/ping.js`：**

```js
const pool = require('../src/db/pool');

(async () => {
  try {
    const { rows } = await pool.query(
      'select current_database() as db, current_user as usr, version() as ver'
    );
    console.log('连上了');
    console.log('库名：', rows[0].db);
    console.log('用户：', rows[0].usr);
    console.log('版本：', rows[0].ver.split(',')[0]);
  } catch (err) {
    console.error('连不上：', err.message);
    process.exitCode = 1;
  } finally {
    await pool.end();
  }
})();
```

**注意最后那个 `await pool.end()`。** 连接池不关，Node 进程不会退出，你会卡在命令行里只能按 Ctrl+C。

**运行：**

```text
npm run ping
```

**跑通之后你会看到类似：**

```text
连上了
库名： saas_lab
用户： postgres
版本： PostgreSQL 16.3
```

**这里有个自检点：库名必须是 `saas_lab`。**

输出的是别的名字，说明 `.env` 里的库名写错了，或者这个库根本不存在。**现在不改，后面建表会建到别的库里，你会找不到自己的表。**

# 第 5 步：故意让它连不上（10 分钟）

**这一步是这节课最重要的三分钟。**

**已经连上了，说明代码对。但你要看清楚"连不上"长什么样**，不然以后客户说"打不开"，你不知道从哪查。

## 5.1 改错一个字

**打开 `.env`，把密码改一个字符**（比如原来的 `abc123` 改成 `abc124`），保存。

**再跑：**

```text
npm run ping
```

**你会看到：**

```text
连不上： password authentication failed for user "postgres"
```

**这句报错的意思是：用户名对了，密码不对。**

## 5.2 再改错一次：改库名

**把 `.env` 最后的 `saas_lab` 改成 `saas_labx`，保存，再跑。**

**你会看到：**

```text
连不上： database "saas_labx" does not exist
```

**这句是说：密码对了，但库不存在。**

## 5.3 再改一次：改主机地址

**把主机改成 `127.0.0.1:5999`（一个没有服务在听的端口），保存，再跑。**

**你会看到：**

```text
连不上： connect ECONNREFUSED 127.0.0.1:5999
```

**这三条报错，覆盖了 90% 的"数据库连不上"：**

| 报错 | 真正的原因 | 怎么修 |
|---|---|---|
| `password authentication failed for user "x"` | 密码错，或用户名错 | 对一遍 `.env`，注意特殊符号要不要转义 |
| `database "x" does not exist` | 库名错，或库没建 | 改库名，或者去建库 |
| `connect ECONNREFUSED 主机:端口` | 服务没起，或端口错 | 确认数据库服务在跑，确认端口 |
| `getaddrinfo ENOTFOUND 主机` | 主机名写错 / 没有网络 | 检查连接串里的域名 |
| `timeout expired` | 连得上但被防火墙拦了 | 云数据库要加白名单 IP |

**最后改回来，再跑一次，确认恢复：**

```text
npm run ping
```

**看到"连上了"才继续。**

**这个动作以后每次接新环境都要做一遍。** 客户给你一个数据库，你第一件事不是写代码，是跑一次连接测试——**连不上和代码写错，是两件完全不同的事，别混在一起排查。**

# 第 6 步：列出你要改的表（15 分钟）

**现在还没到写 SQL 的时候（那是第 163 节）。这一节先做一件看起来没用的事：把清单写下来。**

**为什么先写清单：** 改表是一次性动作，漏一张表，那张表就是泄露入口。**清单写全了再动手，比边写边想快一倍。**

**翻回第 19 节课的 `chat-app`，把它的表结构抄到笔记里：**

```text
conversations   id, title, created_at
messages        id, conversation_id, role, content, created_at
```

**再看第 9 周的后台、第 10 周的文件上传，把里面的表也抄过来：**

```text
users            id, email, password_hash, created_at
files            id, name, path, size, created_at
```

## 6.2 每张表判断一次：加 tenant_id，还是靠外键

**规则只有一条：**

```text
这张表的数据，是不是"直接"属于某个租户？
  是 → 加 tenant_id
  不是（它属于另一张表的一行）→ 通过那张表归属
```

**照着填：**

| 表 | 加 `tenant_id` 吗 | 理由 |
|---|---|---|
| `tenants` | 不加 | 它自己就是租户 |
| `users` | **加** | 用户属于某个公司。注意：同一个人可能属于两家公司，这件事第 164 节处理 |
| `conversations` | **加** | 对话属于某个公司 |
| `messages` | **加** | 它属于 `conversations`，跳两层也能查到租户，但多一列更保险 |
| `files` | **加** | 文件路径里只有 id，查的时候没有 join 机会 |

**`messages` 这一行要特别说一下，因为这里有个真实的选择：**

```text
不加 tenant_id：省一列，但每次查消息都要 join conversations 才知道是谁的
               ——而"忘了 join"正是最容易出的事

加 tenant_id：  多一列，但查消息时条件直接写
               WHERE tenant_id = $1 AND conversation_id = $2
               ——漏不掉
```

**这一周的做法：`messages` 也加。**

**理由不是性能，是安全。** 多一列的成本是存储，少一列的成本是一次数据泄露。

**这条判断以后你会反复用到：涉及安全的地方，"冗余一点"永远比"优雅一点"便宜。**

## 6.3 把清单写进笔记

**打开 `02-笔记/NOTES.md`，在第三节写下你自己的清单。**

**写的时候要带上"这张表有没有唯一约束"** ——第 163 节会用到。

比如：

```text
users        加 tenant_id   有唯一约束：email
orders       加 tenant_id   有唯一约束：订单号
files        加 tenant_id   无唯一约束
messages     加 tenant_id   无唯一约束
```

**看见 `email` 那行了么？**

```text
UNIQUE(email)  →  客户 B 永远注册不了和客户 A 同名的邮箱
```

**这是个必炸的坑，第 163 节第一件事就是修它。**

# 附：常见问题速查

| 报错 / 现象 | 真正的原因 | 怎么修 |
|---|---|---|
| `password authentication failed for user "postgres"` | 密码错 / 用户名错 / 密码里有特殊符号没转义 | 对一遍 `.env`；`@` 写成 `%40`，`:` 写成 `%3A` |
| `database "saas_lab" does not exist` | 库名错，或库还没建 | `CREATE DATABASE saas_lab;` 或者改连接串 |
| `connect ECONNREFUSED 127.0.0.1:5432` | 数据库服务没启动 | Windows 服务里启动 PostgreSQL，或看云控制台状态 |
| `getaddrinfo ENOTFOUND xxx` | 主机名错，或断网 | 检查域名拼写，`ping` 一下 |
| `timeout expired` | 云数据库白名单没加你的 IP | 控制台 → 网络 / 白名单 → 加 IP |
| `npm run ping` 跑完卡住不退出 | 忘了 `await pool.end()` | 加上这一句 |
| `Cannot find module 'pg'` | 没装依赖，或者不在 `saas-lab` 目录里跑 | `cd` 到项目目录，重新 `npm install` |
| 免费云库第一次查询要等 5 秒 | 免费实例休眠了，正在唤醒 | 正常现象，不是代码问题 |
| `error: role "xxx" does not exist` | 用户名写错 | 云控制台里看真实的用户名，通常不是 `postgres` |
| 提交后 GitHub 上看不到 `.env` 但我本地有 | `.gitignore` 生效了 | 正常，就该这样 |
