# 第24周 · 多租户 · 第162—168节课

## 第二个客户来了不用重写

---

## 这一周的目标

把前 23 周做的"一个人的应用"改造成**一套代码服务多个客户**的架构。

这一周结束，你要能做到这六件事：

1. **说清三种隔离方案的区别** —— 独立部署、独立库、共享库，为什么一人公司只能选第三种；
2. **给每张业务表加 `tenant_id`** —— 包括唯一约束和索引怎么配合改；
3. **让 `tenant_id` 只从服务端来** —— 客户端传什么都不算数；
4. **把查询封死在一个入口** —— 不靠"写代码时小心一点"；
5. **给 RLS 单独留一条系统连接** —— 并且说清为什么"登录"这个动作不可能有租户上下文；
6. **自己当黑客攻一次** —— 用客户 A 的登录态去拿客户 B 的数据，全部失败才算过。

## 为什么排在这一周

前面 23 周，你做的东西都默认**只有一个人用**。

第 3 周的 `chat-app`、第 9 周的后台管理、第 10 周的文件上传，这些代码里没有任何地方在问"这条数据属于谁"。

**第一个客户用起来不会有任何问题。第二个客户注册进来，你的代码就开始把两家公司的数据混在一起。**

到那时候改，改的是每一张表、每一条 SQL、每一个接口，还要停机导数据。改不动的结果就是给每个客户单独部署一套——五个客户五套代码，你一个人维护，光改一个错别字要改五遍。

**这是整个 36 周里唯一一个"做错了只能重写"的决定。** 所以它排在你开始接活之前。

```text
第 5 周  你学会建表
第 9 周  你学会做后台
第 24 周 你学会让表分得清是谁的
第 25 周 才开始谈收钱
```

**先能隔离，再谈收费。** 反过来的顺序会让你在收到第一笔钱的时候不敢让第二个人注册。

## 这一周的技术前提

**数据库用 PostgreSQL，通过 `DATABASE_URL` 连。**

第 5 周你用的是 **Node 自带的 SQLite**（`node:sqlite` 的 `DatabaseSync`）。**这一周要换到 PostgreSQL**，先说明为什么。

### 为什么必须换

**三个理由，第三个是硬性的：**

```text
① SQLite 是单文件数据库，没有"服务端"
   多进程同时写会锁表，部署到服务器上是灾难

② 第 29 周要跑 Docker，容器里的 SQLite 文件每次重建都丢
   除非你挂卷，而挂卷的结果是"备份和迁移都变得很麻烦"

③ 第 165 节要用行级安全（RLS）
   SQLite 根本没有这个功能，没有替代品
```

**第三条最要紧。** 第 24 周的核心是"让一条 SQL 想漏都漏不掉"——**第一层是仓储层（代码），第二层是 RLS（数据库）。**

**SQLite 只支持第一层。少一层，你这周的整套验证都是不完整的。**

### 怎么换：只改四个地方

**SQLite 的写法你能直接看懂，改动集中在四处：**

| | SQLite（第 5 周） | PostgreSQL（这一周） |
|---|---|---|
| 驱动 | `node:sqlite` 内置 | `npm install pg` |
| 占位符 | `?` 或 `:name` | **`$1`、`$2`** |
| 类型 | `TEXT`、`INTEGER` | **`uuid`、`jsonb`、`timestamptz`** |
| 主键默认值 | 手工生成 | **`gen_random_uuid()`** |

**还有一处语法差异，只在第 164 节之后才会遇到：**

```sql
-- SQLite
select set_config(...)   -- ❌ 不存在

-- PostgreSQL
select set_config('app.tenant_id', $1, true)   -- ✅ RLS 要用
```

**所以如果你坚持用 SQLite 学完这一周，第 165 节的 RLS 那一半只能跳过。** **那不是"少学一点"，是"少学了一半的防护"。**

### 装 PostgreSQL 的两条路

```text
本地装    Windows 装 PostgreSQL 官方安装包（自带 pgAdmin）
          装完建一个库：CREATE DATABASE saas_lab;

云端免费  Neon / Supabase / Railway 都提供免费 PostgreSQL
          注册后复制 Connection String，粘贴到 .env
```

**云端方案要注意：免费实例会休眠**，十几分钟没人访问后第一次查询要等几秒。**这是正常现象，不是你的代码有问题**（第 162 节的自检会专门让你踩一次）。

### 一个会毁掉这一周的细节：超级用户绕过 RLS

**第 162 节会让你先用 `postgres` 连接——因为只有它有权建表。**

**但 `postgres` 是超级用户，而 PostgreSQL 的规则是：超级用户和带 `BYPASSRLS` 的角色永远绕过行级安全，不管你有没有写 `force row level security`。**

**后果：** **第 165 节你写完四张表的 RLS 策略、跑验证脚本，会看到"不设上下文能读到 2 条消息"——** **明明应该 0 条。** **然后你会回去反复检查那五行 SQL，查不出来，因为问题不在 SQL。**

**所以第 165 节 5.3 有一整节专门讲这件事，会让你建两个角色：**

```text
app_user     日常业务用它，无 super / 无 bypassrls  → RLS 生效
app_system   只在"还不知道租户"时用它，有 bypassrls → 绕过 RLS
```

**并且 `.env` 要从 `postgres` 换成 `app_user`。**

**这是这一周唯一一个"不改就学不到核心"的动作。** **提前知道，第 165 节会顺很多。**

**如果你第 5 周已经把 SQLite 那套学透了**，这一周的 SQL 你照样看得懂——**只是占位符从 `?` 变成 `$1`，读的时候在脑子里换一下。**

**连接串放 `.env`**，这一周的代码读的是：

```text
DATABASE_URL=postgres://用户名:密码@主机:5432/saas_lab
```

**`.env` 不进 Git。** 第 4 周学过，这里再说一遍，因为这一周会新建一个项目目录，很容易忘了复制 `.gitignore`。

## 这一周的五条铁律

这四条比命令重要。命令可以查，判断错了没有救。

```text
一、tenant_id 只从服务端会话推导，永远不从请求参数读。
    只要有一个接口从 req.body 读 tenant_id，整套隔离就是假的。

二、任何 SQL 里出现业务表，就必须出现 tenant_id 条件。
    写不出来说明这条查询本来就不该存在。

三、唯一约束必须带 tenant_id。
    UNIQUE(email) 会让第二个客户永远注册不了同一个邮箱。

四、越权一律返回 404，不返回 403。
    403 等于告诉攻击者"这个 ID 存在，只是你没权限"。

五、绕过 RLS 的连接只能有一条，而且只给"还不知道租户"的地方用。
   登录、注册、auth 反查、支付回调、跨租户定时任务 —— 只有这五类。
   其他地方用一次，隔离就多一个洞。
```

## 这一周最容易出事的三个地方

**第一：更新和删除漏写租户条件**

查询（`SELECT`）漏了租户条件，你会看到别人的数据，很明显，测试时容易发现。

`UPDATE` 和 `DELETE` 漏了租户条件，**没有任何报错，功能看起来完全正常**，只是你把别人的数据改了或删了。

**这一类错误上线三个月都不会被发现，直到客户打电话问"我的数据怎么少了"。**

**第二：文件下载和导出接口**

文件是存在磁盘或对象存储里的，路径里往往只有一个 `id`。

```text
GET /files/8f3a...          ← 这个 id 是谁的？代码里没问
```

**数据接口查得再严，文件接口漏一个，等于全漏。**

**第三：AI 生成的"顺手版本"**

你让 AI 加一个接口，它会写：

```js
app.get('/api/orders/:id', async (req, res) => {
  const { rows } = await db.query('SELECT * FROM orders WHERE id = $1', [req.params.id]);
  res.json(rows[0]);
});
```

**这段代码语法没错、能跑通、功能正常，但它没有任何租户过滤。**

AI 不知道你在做多租户，除非你在提示词里写死。第 162 节会给你一段可以直接用的提示词前缀。
