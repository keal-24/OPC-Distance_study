# AI 应用开发 · 147 天完整路线（一人公司全栈）

> 写给纯小白。每天 60–120 分钟。
> 唯一不变的要求：**每天一次 commit。** 147 天后你的 GitHub 就是你的履历。

**起点：2026-11-15（Day 1）→ 终点：2027-04-11（Day 147）**

---

# 这份计划为什么从 70 天变成 147 天

原来 70 天只教"怎么把 AI 用起来"。你要的是**一个人能把真实项目从头到尾做完、交付出去、还能收到钱**。

这两件事的差距不在 AI 那部分（那部分 70 天够），在于：

| 原来没有的 | 为什么必须有 |
|---|---|
| 登录、账号、权限 | 没有它就没有"我的数据"，任何真实项目都做不了 |
| 流式输出 | 没有它，AI 应用在用户眼里就是"卡死的网页" |
| 支付、对账、回调 | 客户说"我要收费"，你答不会，这单就没了 |
| Excel 导入导出 | 中国企业的数据都在 Excel 里，不能导入客户就用不起来 |
| 多租户 | 第二个客户来了，做错只能重写 |
| 企业微信 / 飞书集成 | 中国 B 端交付，一半以上的入口在这些平台里 |
| 定时任务、Webhook、异步任务 | 每个真实项目都会用到，缺了就有功能实现不了 |
| 前端工程化、组件化 | 页面超过 3 个就开始乱了 |
| 测试、错误监控、日志 | 线上出问题你得知道出了什么、在哪 |
| 部署、域名、Nginx、HTTPS、备份 | 这是"能上线"和"只能自己电脑上看"的分界 |
| 安全（注入、越权、密钥、上传） | 一次数据泄露，信誉就没了 |
| 合规（数据出境、隐私、等保） | 这条能直接决定一个单接不接 |
| 商务（合同、报价、验收、交接） | 会做不会卖，等于不会做 |

**这不是把 70 天摊薄，是在后面接了 77 天的新内容。** 前 14 周（Day 1–98）是 AI 与全栈主线，后 7 周（Day 99–147）是产品化、基础设施、安全与商务。

---

## 先记住一句话

**AI 应用的代码，90% 和传统 web 没区别。区别在那 10%：模型是不确定的。**

传统代码错了会报错，AI 错了会给你一段看起来很对的话。所以 AI 开发的"修"，本质上是**用数据证明改完更好了**，而不是改 bug。这条贯穿 147 天。

## 五个能力，反复轮着练

| 能力 | 具体 | 不会的后果 |
|---|---|---|
| **做出来** | 从零到能跑 | 只能接需求转包 |
| **估工** | 一个需求几天、贵在哪 | 被报价牵着走，做一半发现亏 |
| **验货** | 真做完了吗、有没有糊弄 | 付钱拿到跑不起来的东西 |
| **拆解** | 大需求切成能派的活 | 只能整包外包，带不了人 |
| **止损** | 什么时候该砍、该换 | 沉没成本滚到烂尾 |

## 用 AI 工具开发，你每天到底干什么

Codex、Claude Code、Cursor 这类工具能写掉大部分代码。这不降低要求，是把要求挪了位置：从"能写"挪到"能判断"。

你每天只做四件事：

1. **读**：AI 写完，你要能逐行讲清它在干什么
2. **改**：亲手改一处，看结果怎么变
3. **验**：按验收标准真跑一遍
4. **排**：每天故意弄坏一次，练定位

第 3、4 条是重点。**"能排查"只从这个动作长出来，看书看不出来。**

# 阶段一 · Week 1–2（Day 1–14）地基与第一次对话

**目标**：从一个空文件夹，做出一个真会回话、记得住上下文、并且能上线给人看的机器人。

**为什么先做界面**：因为你要看得见反馈。看不见进展的学习，三天就放弃。

> 这一阶段每天的详细任务单已写好，见 `w01-地基\week01\day001.md` 到 `w01-地基\week02\day014.md`。
> 下面只列要点，详细内容以任务单为准。

### Week 1 · Day 1–7 · 前端与后端入门

| 天 | 主题 | 产出 |
|---|---|---|
| 1 | 第一个网页 | 浏览器里出现你自己的字；GitHub 上有仓库 |
| 2 | 对话框布局 | 一个像聊天软件的页面，`flex: 1` 让输入框贴底 |
| 3 | 开发者工具 | 会用 F12 查问题：Elements / Console / Network |
| 4 | JS 四件事 | 变量、函数、if、数组，全部在 Console 里跑通 |
| 5 | 消息上屏 | 点发送 → 造气泡 → 插入 → 清空 |
| 6 | 第一个后端 | express 起服务，`/hello` 返回 JSON |
| 7 | GET / POST | 会发 POST，懂状态码，制造过 404 |

**Week 1 老板视角**
"做个官网"不是一件事。三个问题砍掉一半溢价：几个页面、要不要后台、内容谁提供。

### Week 2 · Day 8–14 · 连起来、存起来、上线

| 天 | 主题 | 产出 |
|---|---|---|
| 8 | 前后端连通 | fetch 调后端，字出门转一圈变气泡；解决 CORS |
| 9 | 数据库 | Supabase 建表，刷新后消息还在 |
| 10 | 接真模型 | 真的 AI 回答出现；接上历史，能记住前文 |
| 11 | system 提示词 | 换个角色设定，回答风格明显变 |
| 12 | 提示词结构 | 拆成"角色/任务/约束/输出格式"四段 |
| 13 | 会话隔离 | 多对话互不干扰，靠 `conversation_id` |
| 14 | 第一次上线 | 别人能用你的链接对话；代码里搜不到 key 明文 |

**Week 2 老板视角**
一个能对话的 demo，任何人两天就能搭出来。**它的价值不在"能回话"，在"回得准不准、贵不贵、快不快"。**

# 阶段二 · Week 3–5（Day 15–35）对话质量、成本、流式、账号

**目标**：从"能回话"到"回得稳、算得清、像产品"。

**这一阶段新增了三块原来没有的**：流式输出（W4）、登录与账号（W5）、以及提示词版本化。

### Week 3 · Day 15–21 · 提示词深入

| 天 | 主题 | 具体做什么 | 验收 |
|---|---|---|---|
| 15 | 边界与拒答 | 明确写"不知道就说不知道，不要编" | 问范围外的问题，它不编 |
| 16 | 少样本（few-shot） | 给两三个输入输出示例 | 格式和风格明显更稳 |
| 17 | 提示词版本化 | 把 system 存成独立文件 + 版本号，进 Git | 能回滚到上一版；能对比两版效果 |
| 18 | 提示词注入防护 | 用户输入"忽略之前所有指令"时怎么办 | 恶意输入被挡住，不改变行为 |
| 19 | token 是什么 | 数一次请求的输入输出 token | 能说出这次调用花了多少、多少钱 |
| 20 | 上下文窗口 | 故意灌长文本，看它什么时候开始忘 | 记录"从第几条历史开始丢信息" |
| 21 | 裁剪策略 | 只保留最近 N 条 + 一条摘要 | 长对话里它还记得关键信息 |

**Week 3 老板视角**
**提示词是可维护资产，不是聊天记录。** 它应该跟代码一起进 Git，有版本、能回滚。问一句"你们的提示词存在哪"，就知道专业程度。

### Week 4 · Day 22–28 · 结构化、成本、流式

| 天 | 主题 | 具体做什么 | 验收 |
|---|---|---|---|
| 22 | 为什么要结构化 | 让它输出 JSON 而不是一段话 | 前端能直接解析，不用正则抠 |
| 23 | JSON schema | 约束字段、类型、枚举 | 输出字段稳定，不会时有时无 |
| 24 | 解析失败怎么办 | 加校验 + 重试一次 | 故意让它出错，你的代码不崩 |
| 25 | 模型分级 | 简单任务用小模型，复杂用大模型 | 成本降下来，效果没明显掉 |
| 26 | 缓存 | 相同问题不重复调用 | 重复提问不计费、秒回 |
| 27 | **流式输出（SSE）** | 后端边生成边发，前端边收边显示 | 字一个一个往外蹦，不是等 8 秒后整段出现 |
| 28 | 流式 + Nginx | 关掉缓冲，加心跳 | 部署到服务器后流式还正常 |

> **Day 27–28 是这一阶段最重要的一天半。**
>
> 不做流式，你的 AI 应用在客户眼里就是"点了没反应的网页"。**这是 AI 产品的基本配置，不是高级功能。**

### Week 5 · Day 29–35 · 账号体系与登录

| 天 | 主题 | 具体做什么 | 验收 |
|---|---|---|---|
| 29 | 为什么要登录 | 没有身份就没有"我的数据" | 能说清"未登录"和"已登录"有什么区别 |
| 30 | 手机号 + 验证码 | 发送验证码 → 校验 → 建用户 | 能注册、能登录 |
| 31 | 验证码安全 | 限频（60 秒一次）、过期（5 分钟）、一次性 | 连点 5 次只发一条短信 |
| 32 | JWT 是什么 | 登录成功后发一个令牌，之后带着它 | 请求里带 token 能识别出是谁 |
| 33 | 会话保持 | token 存哪、过期怎么办、退出登录 | 刷新页面还是登录状态 |
| 34 | 数据归属 | 每条数据带 `user_id`，只查自己的 | A 登录看不到 B 的消息 |
| 35 | 微信扫码登录（了解） | 知道流程和需要的资质 | 能说清为什么它需要企业认证 |

**Week 5 老板视角**
**"能不能微信登录"这个问题，决定你要不要花 300 元办企业认证、花两周等审核。** 谈单时先问客户的目标用户是 C 端还是 B 端内部员工——答案不同，登录方案和成本差十倍。

# 阶段三 · Week 6–9（Day 36–63）工具、检索、Agent

**目标**：从"会说话"到"会做事、懂你的资料"。
**这是 AI 应用和聊天玩具的分界线。**

### Week 6 · Day 36–42 · 工具调用

| 天 | 主题 | 具体做什么 |
|---|---|---|
| 36 | 工具调用是什么 | 你告诉模型"有这些函数"，它决定调哪个、传什么参数 |
| 37 | 定义第一个工具 | 写一个 `query_db`，给出名称、说明、参数 schema |
| 38 | 解析调用意图 | 从模型返回里取出工具名和参数 |
| 39 | 执行并回填 | 真的执行，把结果作为一条消息再发回去 |
| 40 | 多轮工具 | 让它能连续调两次工具再回答 |
| 41 | 多工具选择 | 给三个工具，测它选得对不对 |
| 42 | 工具失败 | 工具报错时，让它知道失败并重试或换路 |

**Week 6 末验收**：你问一个需要查数据的问题，它能自己调工具、拿到结果、再回答。

### Week 7 · Day 43–49 · 检索（RAG）

| 天 | 主题 | 具体做什么 |
|---|---|---|
| 43 | RAG 解决什么 | 模型不知道你的私有资料，把相关资料找出来塞给它 |
| 44 | 切分 | 把文档切成合适的块（太大召回差，太小丢上下文） |
| 45 | 向量化 | 用 embedding 把每块转成向量存起来 |
| 46 | 检索 | 问题也转向量，找最相近的几块 |
| 47 | 重排 | 粗排 20 条，再精排取前 3 条 |
| 48 | 拼进提示词 | 检索结果作为"参考资料"放进去，要求它据此回答 |
| 49 | 引用与拒答 | 要求标明来自哪份资料；资料里没有就说没有 |

**Week 7 末验收**：用你自己的知识库（比如 `B:\知识库\凯旋知识库`）做一个问答助手，问一个只有你笔记里才有的细节，它能答对并指出出处。

> **这一段是整条路线最值钱的技能。** 它直接对应"让 AI 懂我们公司的东西"，几乎所有企业需求都在这一层。

### Week 8 · Day 50–56 · Agent 循环

| 天 | 主题 | 具体做什么 |
|---|---|---|
| 50 | Agent 是什么 | 模型自己决定下一步做什么，循环到任务完成 |
| 51 | 最小循环 | 思考 → 调用 → 观察 → 再思考，直到它说"完成" |
| 52 | 终止条件 | 步数上限、时间上限、重复动作检测 |
| 53 | 失败恢复 | 工具报错后不是崩，是换策略 |
| 54 | 成本控制 | 一次任务最多花多少钱，超了就停 |
| 55 | 可观测 | 把每一步的思考、调用、结果记下来 |
| 56 | 整合 | 把工具 + 检索 + 循环拼成能完成真实任务的助手 |

**Week 8 末验收**：给它一个三步以上的真实任务（比如"查一下我上周笔记里关于 X 的结论，整理成三条发我"），它能自己完成。

### Week 9 · Day 57–63 · 异步任务与超时

| 天 | 主题 | 具体做什么 | 为什么必须有 |
|---|---|---|---|
| 57 | 为什么会有超时 | HTTP 请求有时限，长任务必然超时 | 不知道这个，你会以为"代码偶尔抽风" |
| 58 | 同步 vs 异步 | 什么时候等、什么时候先返回任务 ID | 判断标准：超过 10 秒就不该同步等 |
| 59 | 任务表设计 | `jobs` 表：状态、结果、时间 | 能查到一个任务跑到哪了 |
| 60 | 提交任务 | 接口立刻返回 `jobId`，后台开跑 | 提交后 1 秒内拿到回应 |
| 61 | 轮询进度 | 前端每 2 秒查一次状态 | 页面能看到进度条动 |
| 62 | 超时与重试 | 给所有外部请求加 `AbortController` | 模型卡住时你的服务不会一起卡死 |
| 63 | 失败处理 | 任务失败要能重跑、要能告警 | 失败时你知道，不是客户先发现 |

> **Day 62 特别重要。** `fetch` 默认没有超时——**你现在 day10 的代码里就有这个隐患**：模型接口卡住时，你的请求会永远挂着。

**Week 6–9 老板视角**
**这一层的报价能翻三倍，不是因为技术难，是因为能落地的方案少。** 但也是最容易翻车的地方：能跑通 demo 和能稳定用，中间差十倍工作量。判断一个 AI 团队靠不靠谱，问一句"你们的 Agent 怎么防止死循环、一次任务成本上限多少"。

# 阶段四 · Week 10–12（Day 64–84）评测、可靠性、工程化

**目标**：从"感觉变好了"到"证明变好了"，以及"代码结构撑得住继续加功能"。

### Week 10 · Day 64–70 · 建立评测

| 天 | 主题 | 具体做什么 |
|---|---|---|
| 64 | 为什么必须评测 | 没评测，改提示词就是碰运气，改好一处坏三处 |
| 65 | 攒评测集 | 从真实使用中收集 30–50 个问题，写清"什么算好答案" |
| 66 | 分类型 | 简单问答、需要检索、需要工具、边界情况、恶意输入 |
| 67 | 自动打分 | 先用规则（关键词命中、格式正确），再用模型当裁判 |
| 68 | 跑分脚本 | 一条命令跑完整个集子，输出通过率 |
| 69 | 记录基线 | 把你现在的分数存下来，这是刻度 |
| 70 | 第一次对比 | 改一句提示词，跑两次，看分数是升是降 |

**Week 10 末验收**：你能说出一个具体数字："这次改动让通过率从 68% 到 79%"，而不是"我觉得好多了"。

### Week 11 · Day 71–77 · 可靠与降级

| 天 | 主题 | 具体做什么 |
|---|---|---|
| 71 | 模型挂了怎么办 | 超时、重试（指数退避）、换备用模型 |
| 72 | 降级策略 | 主模型不可用时用什么兜底 |
| 73 | 限流 | 按用户 / 按 IP 限速，超了返 429 |
| 74 | 幂等 | 同一个请求重复提交只生效一次 |
| 75 | 错误分类 | 哪些错误该让用户重试，哪些该直接告诉他不行 |
| 76 | 日志 | 结构化日志：谁、什么时候、做了什么、结果如何 |
| 77 | 错误监控 | 接 Sentry 或类似服务，报错自动上报带堆栈 |

### Week 12 · Day 78–84 · 工程化：代码结构撑得住

**为什么要有一整周**：你现在 `server.js` 150 行，一个 `/echo` 干五件事。再加流式、加登录、加支付，**它会变成 1000 行，你自己都读不懂。**

| 天 | 主题 | 具体做什么 | 验收 |
|---|---|---|---|

# 147 天后你到什么程度

**会**：

- 独立做出一个能上线的 AI 应用，有登录、有流式、有数据存储
- 让 AI 懂客户的私有资料，能调工具做事

**不会**：

- 训练模型、微调、推理优化、算法研究
