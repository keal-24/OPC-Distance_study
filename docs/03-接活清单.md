# 第一级 · 不做就交付不了（P0）

## 1. 登录与账号体系

**为什么必须**：任何真实项目都要知道"这是谁"。没有登录，就没有"我的数据"这个概念。

**中国场景下的三种登录，各有各的用法：**

| 方式 | 用户成本 | 你需要的 | 适用 |
|---|---|---|---|
| **微信扫码登录** | 最低，扫一下就完 | 微信开放平台账号（**要企业认证，300 元/年**） | 面向 C 端、或客户员工都有微信 |
| **手机号 + 短信验证码** | 低，但要等短信 | 短信服务商（阿里云/腾讯云） | **最通用，B 端首选** |
| **账号密码** | 高，要记 | 自己实现 | 只在客户明确要求时用 |

**最小可用方案**：手机号 + 验证码。因为：
- 不要企业认证，个人也能申请短信服务
- 用户不用记密码
- 天然带"实名"属性

**坑，三个：**

1. **验证码要走后端，不能前端直连短信服务**（否则 key 泄露，别人拿你的号发垃圾短信，一夜几千块）
2. **必须限频**：同一手机号 60 秒一次，同一 IP 每小时 20 次。**不限频等于给攻击者一个免费短信发送器**
3. **验证码要存过期时间**（5 分钟），用完立刻删

> **成本参考**：短信约 0.04 元/条。一个用户注册 + 偶尔登录，一年成本几毛钱。**但要限频，失控时能烧掉几千。**

## 2. 多租户：一个客户一个库，还是共用？

**这是整个架构里最重要的一个决定，而且做错了只能重写。**

**场景**：你给 A 公司做了系统，B 公司也想要。

| 方案 | 怎么存 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **独立部署** | 每个客户一套服务器 + 一个数据库 | 数据物理隔离，客户最放心，能卖高价 | **你运维成本 × N**，客户升级要一个个做 | 客户少、单价高（10 万+） |
| **共享库 + `tenant_id`** | 一张表，每行标记属于哪个客户 | 一套代码一套运维，加客户零成本 | 代码里**每个查询都必须带 `tenant_id`**，漏一处就是数据泄露 | 客户多、单价低（SaaS） |

**我的判断：一人公司优先做"共享库 + tenant_id"。**

理由很实际：**你没有运维团队，独立部署 5 个客户就能把你拖死。**

**共享库最大的风险**：忘了加 `tenant_id` 过滤。

```javascript
// 致命错误：A 客户能查到 B 客户的数据
const { data } = await supabase.from("messages").select("*")

// 正确：永远带上租户条件
const { data } = await supabase.from("messages").select("*").eq("tenant_id", req.tenantId)
```

> **怎么防**：把查询封装成一个函数，**只有这个函数能查库**，所有路由都走它。这样只需要在一处保证带上 `tenant_id`。
>
> **不要到处写裸查询。** 漏一次，客户数据串了，你的信誉就没了。

**现在就要做的动作**：即使你今天只有一个客户，**也给表加上 `tenant_id` 字段**，默认值填个固定值。以后加客户不用改表结构。

## 3. 支付与对账

**为什么必须**：客户说"我要收费"，你答"不会接支付"，这单就没了。

**关键认知：接支付 90% 的坑不在"发起支付"，在"回调"。**

流程是这样：

```
用户点支付 → 你调微信下单接口 → 拿到支付链接/二维码
    ↓
用户在微信里付钱
    ↓
微信服务器 → 主动请求你的 /notify 接口（这叫回调）
    ↓
你收到回调 → 改订单状态为"已支付" → 给用户加额度
```

**四个必须处理的坑：**

| 坑 | 后果 | 怎么办 |
|---|---|---|
| **回调会重复发** | 用户充 100，给他加了两次额度 | **幂等**：处理前先查订单状态，已处理过就直接返回成功 |
| **回调可以伪造** | 别人假装微信给你发回调，白拿额度 | **必须验签**（微信给的那套签名算法） |
| **自己的接口可能挂** | 微信发回调你没收，订单永远"未支付" | 微信会重试，但**你也要做主动查单**（定时查询未完成订单） |
| **金额单位是分不是元** | 收 100 元写成 `100`，实际收 1 元 | 微信所有金额**单位是"分"**，100 元要写 `10000` |

> **"重复回调"是支付第一大 bug**，几乎所有第一次接支付的人都踩过。
>
> **判断方法**：如果客户说"我这里显示付了钱，但额度只加了一次/加了两次"，就是这个。

**个人能接吗**：微信支付和支付宝都需要**企业主体**。你现在如果是个体户或公司就能接，纯个人不行。**这是个现实门槛，谈单前要确认。**

## 4. Excel 导入导出

**为什么必须**：**中国企业的数据基本都在 Excel 里。**

客户说"我们有三万条客户记录"，你问"能给我个什么格式"，答案 99% 是 Excel。

**导入**（把 Excel 变成数据库记录）：
- 解析用 `xlsx` 这个 npm 包
- **必须做的三件事**：表头校验（列名对不对）、逐行校验（必填、格式、重复）、**报告错误行号**
- **必须支持"部分成功"**：不要 30000 行里第 29999 行错就全部回滚，用户会崩溃。**导入成功的先存，失败的列出来让他改**

**导出**（把数据变成 Excel）：
- 同样用 `xlsx`
- **大数据量要分段**：3 万行以上，一次性生成会内存爆炸，要流式写
- **中文文件名要编码**：`Content-Disposition` 里的中文要 `encodeURIComponent`，否则下载下来是乱码名

> **这个功能看起来土，但它决定客户能不能用起来。**
>
> 客户不会手动录 30000 条数据。**你不能导入，他就用不了**——不管你 AI 做得多好。

## 5. 流式输出（SSE）

**为什么必须**：**AI 应用没有流式，客户第一反应是"卡住了"。**

对比：

| 方式 | 用户体验 |
|---|---|
| 一次性返回 | 点发送 → **等 8 秒，屏幕一动不动** → 突然出现整段回答 |
| 流式 | 点发送 → 0.5 秒后开始一个字一个字往外蹦 |

**8 秒空白，用户会以为坏了，会再点一次，会刷新页面。**

**技术方案：SSE（Server-Sent Events）**

- 不是 WebSocket，比 WebSocket 简单得多
- **单向**（服务器 → 浏览器），正好符合"流式返回"
- 用普通 HTTP，不用额外协议

**后端关键点**：

```javascript
res.setHeader("Content-Type", "text/event-stream")
res.setHeader("Cache-Control", "no-cache")
res.setHeader("Connection", "keep-alive")

// 每收到一块就立刻发给浏览器
res.write(`data: ${JSON.stringify({ delta: chunk })}\n\n`)
```

**两个必踩的坑：**

1. **Nginx 默认会缓冲**，导致你写了 10 块，浏览器一次性收到。要关掉：
   ```nginx
   proxy_buffering off;
   proxy_cache off;
   ```
2. **必须发心跳**：长时间没数据，中间的代理会断开连接。每 15 秒发一个空注释 `: ping\n\n`

> **这个功能是"专业感"最直接的来源。** 客户看到字一个个蹦出来，会觉得"这东西是真 AI"。同样的模型，不做流式就像个卡死的网页。

## 6. 异步任务与超时

**为什么必须**：有些活要跑几分钟（批量处理 1000 条数据、生成报告、跑一次检索）。

**在 HTTP 请求里干这些，一定超时。**

**分级处理：**

| 耗时 | 做法 |
|---|---|
| < 10 秒 | 同步等，正常返回 |
| 10 秒 – 1 分钟 | 流式返回（SSE），让用户看到进度 |
| > 1 分钟 | **提交任务 → 立刻返回任务 ID → 前端轮询或 SSE 查进度** |

**最小可用方案**（不用上消息队列）：

1. 建一张 `jobs` 表：`id` `status`(pending/running/done/failed) `result` `created_at`
2. 接口收到请求 → 插一条 `pending` → **立刻返回 `{ jobId }`**
3. 后台异步开始跑（`setImmediate` 或单独一个循环扫表）
4. 前端拿 `jobId` 每 2 秒查一次状态

> **别一上来就用 Redis + BullMQ。** 一人公司的小项目，**数据库当队列完全够用**，还少一个要运维的东西。
>
> **什么时候才需要真队列**：并发任务超过几十个、或者需要多台服务器分担时。

**顺带必须做的：给所有外部请求加超时。**

```javascript
const controller = new AbortController()
setTimeout(() => controller.abort(), 30000)
fetch(url, { signal: controller.signal })
```

> **`fetch` 默认没有超时。** 模型接口卡住时，你的请求会永远挂着，用户的浏览器也永远转圈。**这是个真实的隐患，你现在代码里就有。**

# 第二级 · 强烈建议（P1）

## 7. 企业微信 / 飞书 / 钉钉集成

**为什么重要**：**中国 B 端交付，一半以上的入口在这些平台里。**

客户说的"给我们做个 AI 助手"，真实需求往往是"在我们企业微信里能用"。

| 平台 | 你需要做什么 | 难点 |
|---|---|---|
| **企业微信** | 建自建应用，配 `corp_id` + `secret`，实现接收消息回调 | 回调地址要公网可访问 + 验签 + **5 秒内必须响应**（超时会重试） |
| **飞书** | 建自建应用，事件订阅 | 和企微类似，文档更清楚 |
| **钉钉** | 建机器人 | 相对简单 |

**关键认知：这些平台的"回调"和你接支付的"回调"是同一类问题** —— 都要验签、都要幂等、都要快速响应。

> **你有飞书连接器**（我看到你的环境里已经连着），**这条路对你最短**。飞书文档质量比企微好，先从飞书入手。

**一个必须知道的限制**：企业微信要求**回调接口 5 秒内响应**。**AI 生成要 8 秒，一定超时。**

**解法**：收到消息先回一个"正在思考"，然后用"主动发消息"接口把答案推过去。**这个模式必须掌握，不然企微集成做不了。**

## 8. 定时任务

**为什么必须**：客户一定会要"每天早上 9 点给我发昨天的数据报表"。

**三种做法：**

| 做法 | 怎么做 | 适合 |
|---|---|---|
| **Linux cron** | 服务器上 `crontab -e` | 单机，最简单 |
| **node-cron** | 代码里 `cron.schedule('0 9 * * *', fn)` | 和你的程序一起跑 |
| **云函数定时触发** | 腾讯云/阿里云的定时触发器 | 无服务器 |

**必须处理的问题：**

- **重复执行**：如果程序跑在两台机器上，会执行两次。**用数据库加锁或标记**
- **失败了没人知道**：定时任务静默失败，客户三天后才发现没收到报表。**必须加告警**
- **时区**：服务器是 UTC，你写 "9 点"可能是北京时间 17 点。**统一用 `Asia/Shanghai`**

## 9. Webhook 接收（通用能力）

**为什么必须**：所有第三方服务都是"有事了来通知你"，形式就是 Webhook。

**统一要做的四件事，不管对接谁：**

1. **验签**（确认真是对方发的）
2. **幂等**（同一条事件重复发，只处理一次）
3. **快速响应**（先回 200，再异步处理）
4. **记录原始请求**（出问题时能查）

> **把这四件事写成一个通用函数**，以后接任何平台的 Webhook 都套用。**这是能省几十小时的一个封装。**

## 10. 文件上传与对象存储

**关键点：**

- 前端上传文件 → **不要走后端中转**（大文件会撑爆内存），走"预签名 URL"直传对象存储
- 后端只负责"生成上传凭证"和"记录文件信息"
- 上传前**必须限制类型和大小**（否则用户传个 2GB 视频，你的流量费爆炸）
- **文件名不能直接用用户给的**（可能含 `../` 路径穿越攻击），要生成随机名

> **Supabase Storage 你已经有了**，直接能用，不用另开服务。

## 11. 自动部署（GitHub Actions）

**为什么值得**：你现在每次部署是"SSH 上去 → git pull → pm2 restart"。**一天部署三次就是三遍手动作业，每次都可能出错。**

**配一次 GitHub Actions，以后 `git push` 就自动部署。**

```yaml
name: deploy
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: appleboy/ssh-action@master
        with:
          host: ${{ secrets.HOST }}
          username: root
          key: ${{ secrets.SSH_KEY }}
          script: |
            cd /root/app
            git pull
            npm install
            pm2 restart my-app
```

> **一人公司特别需要这个。** 你没有运维，**能自动化的都必须自动化**，否则你的时间全被杂事吃掉。

## 12. 冒烟测试脚本

**注意：这和 Week 8 的"评测"不是一回事。**

- **评测**：判断 AI 回答得好不好
- **冒烟测试**：判断"系统还活着吗"

**最小可用的做法**：一个脚本，跑一遍核心流程，全过了才算部署成功。

```javascript
// smoke.js —— 部署后跑一下，30 秒内知道有没有崩
const tests = [
  ["健康检查", () => fetch("http://localhost:3000/health")],
  ["能发消息", () => fetch("http://localhost:3000/echo", { method: "POST", ... })],
  ["能读历史", () => fetch("http://localhost:3000/messages")],
]
// 任何一条失败就报警
```

> **为什么值得花一小时写这个**：因为部署完之后，你**永远不确定**是不是真的好了。有这个脚本，30 秒给出答案。

# 第三级 · 按需（P2）

## 13. 微信小程序

**什么时候需要**：客户明确说"要在微信里点开就能用"。

**关键判断：先问客户"是要手机上能用，还是要应用商店能搜到？"**

- 只要手机上能用 → **PWA 就够了**（Day 14 会做，加两个文件的事）
- 要在微信里传播、要微信支付、要用微信登录 → 才需要小程序

**成本差十倍。** 这个判断能救你很多时间。

## 14. 图表与报表

客户要"看数据"，你需要：

- **ECharts**（图表，国内最常用，中文文档全）
- **导出 PDF**：`puppeteer` 把网页转 PDF（最省事，样式所见即所得）

## 15. 邮件与短信通知

- 邮件：`nodemailer` + 腾讯企业邮/阿里云邮件推送
- 短信：阿里云/腾讯云 SMS SDK

**必须先做的：限频和模板审核**（短信内容要提前报备审核，不能随便发）

## 16. TypeScript

**我的判断：你现在不需要专门学。**

理由：你已经会 JS，TS 只是加了类型标注。**一人公司用纯 JS 完全能交付，而且更快。**

**但你必须能读 TS**，因为：
- 找开源模板时，大部分是 TS
- 很多 SDK 的文档示例是 TS

**读到什么程度够**：看到 `const x: string` 知道是"x 是字符串"，看到 `function f(a: number): void` 知道参数和返回类型。**就这些。**

## 17. 数据库迁移

**问题**：你的表现在有 4 列，下个月要加 3 列，**线上已经有数据了**。

**不能做的**：手动去后台点"加一列"。因为你在测试环境加完，忘了在生产环境加，就出 500。

**正确做法**：把每次表结构变更写成文件，按顺序执行。

- Supabase 有 migration 功能（`supabase migration new xxx`）
- 简单项目：一个 `migrations/` 目录，文件名带日期，**记录执行过哪些**

> **现在不做也行，但要知道有这么个东西。** 等你改了第三次表结构、忘了某次改了啥的时候，你就会需要它。

## 18. 缓存 / Redis

**我的判断：你现在不需要。**

理由：一人公司的小项目，**数据库查询够快**，加 Redis 只会多一个要运维、会挂、要备份的东西。

**什么时候才需要**：QPS 上千、或者有明显的重复计算（比如每天算一次全站统计）。

**但有一个"缓存"你现在就该做**：**缓存相同的 AI 请求**。

同一个问题问两次，第二次直接用上次的答案。**这是最直接的省钱手段**，尤其客户测试阶段会反复问同一句话。

# 第四级 · 不是技术，但会卡死你

## 19. 合规：三条必须搞清的

### ① 数据出境（**这条最重要**）

**你在用 OpenAI 格式的接口，如果模型实际在境外服务器上，客户的业务数据就"出境"了。**

**这是真实的法律风险，不是吓唬人。**

| 情况 | 风险 |
|---|---|
| 客户是国内企业，数据是客户信息/个人信息，模型在境外 | **需要走数据出境合规流程，小项目基本做不了** |
| 客户数据是公开信息、或经过脱敏 | 风险低 |
| 用国内模型（通义、豆包、DeepSeek、文心） | 无出境问题 |

> **谈单时必须问清**："这些数据里有客户个人信息吗？"
>
> **如果答案是有，你又用境外模型，这个项目你接不了** —— 或者必须换国内模型。
>
> **这一条决定了你的技术选型，必须在报价之前问。** 谈完再改，成本翻倍。

### ② 隐私政策与用户协议

**只要收集任何用户信息（手机号、聊天内容），就需要。**

最省事的做法：找个模板改一下，放在网站上，注册页让用户勾选"我已阅读并同意"。

### ③ 等保（网络安全等级保护）

**客户是国企、政府、医院、学校时，会问"你们过等保了吗"。**

- 等保二级：小项目可能会被要求，大概几万块 + 几个月
- **一人公司基本做不了**

**判断**：如果客户是这个背景，你要提前问"需不需要过等保"。**需要的话，这个单你可能要放弃，或者找有资质的公司合作。**

## 20. 合同：四条必须写进去

| 条款 | 为什么 | 怎么写 |
|---|---|---|
| **范围以书面确认为准** | 客户口头加的每个需求都是"顺便做一下" | "本合同范围以上述功能清单为准，新增需求另行报价" |
| **验收标准写清** | 否则客户永远说"还差一点" | **写可验证的标准**："能导入 1 万条数据，错误行有提示" |
| **上线后运维另计** | 客户会把你当免费客服 | "上线后运维按 X 元/月，含 N 次修改" |
| **数据归属** | 打官司时这是核心 | "数据所有权归甲方，乙方不得用于其他用途" |

**还有一条，AI 项目特有**：

> **"模型输出内容仅供参考，乙方不对生成内容的准确性承担责任。"**
>
> **这句话必须写。** 因为 AI 会答错，客户如果拿它做决策出了事，责任可能落到你头上。

## 21. 发票与收款

- 你要能开票（个体户或公司才行，**纯个人开不了票**）
- 付款节点：常见 3-4-3（签合同 30%、交付 40%、验收 30%）
- **不要做"验收后一次性付"** —— 你垫了两个月的时间，最后客户不认，你没有任何筹码

## 22. 客户交接文档

**这是"能带人"和"只能自己干"的分界。**

交付时必须给的东西：

- `README.md`：怎么装、怎么跑、怎么部署
- `.env.example`：需要配哪些环境变量（**不填值，只写名字**）
- 一份"常见问题"：客户会问的十个问题加答案
- **一段 3 分钟的录屏**：你操作一遍核心流程

> **为什么这个不能省**：因为你**一定**会在半夜接到"网站打不开了"的电话。有文档，你能让他自己先看一眼；没文档，你每次都从头问。

# 附 · 接活前的 22 个问题

**这一节是整份文档最有用的部分。谈单时照着问，问完你就能决定接不接、报多少。**

## 关于用户和身份（问 4 个）

1. 谁来用？只有内部员工，还是外部客户也要用？
2. 大概几个人？同时在线最多几个？
3. 怎么登录？手机号、微信、还是要和我们现有账号打通？
4. 要不要分角色（管理员/普通用户/只看数据）？

## 关于数据（问 5 个）

5. 数据从哪来？是手工录、Excel 导入、还是对接现有系统？
6. 数据量多大？现在多少条，一年后大概多少？
7. **数据里有客户个人信息吗？**（← 决定能不能用境外模型）
8. **数据能不能出你们内网？**（← 决定要不要私有化部署，**这条能改变整个报价**）
9. 数据丢了怎么办？有没有备份要求？

## 关于 AI 部分（问 5 个）

10. 它具体要干什么活？（**逼客户说具体场景，不要说"智能"**）
11. 回答错了会有什么后果？（决定要不要加人工确认环节）
12. 每次回答能接受等多久？3 秒、10 秒、还是 1 分钟？
13. 每天大概用多少次？
14. **模型费用谁付？** 含在报价里，还是客户自己充？

## 关于交付（问 5 个）

15. 要在哪用？电脑浏览器、手机、企业微信里、还是要独立 App？
16. 上线时间？有没有必须赶的节点？
17. 部署在哪？你们的服务器，还是我帮你们买？
18. 需要过等保吗？（← 国企/政府/医院必问）
19. 上线后谁来运维？我要提供多久支持？

## 关于商务（问 3 个）

20. 验收标准是什么？怎么算"做完了"？
21. 付款节点怎么安排？
22. 后续加功能怎么算？

> **这 22 个问题，问完大概 40 分钟。**
>
> **但它能挡掉三种最坏的情况**：接了做不完的单、接了一个月亏钱的单、接了一个有法律风险的单。
>
> **问了客户还觉得你专业。** 因为不专业的人上来就报价格，专业的人先问清楚。

# 怎么用这份清单（重要）

## 不要把它塞进 70 天

**70 天的节奏已经排满了。** 硬加二十个主题会让它变成 120 天，你会因为看不到头而放弃。

**正确用法：**

| 什么时候 | 用哪部分 |
|---|---|
| **今天** | 只做一件事：把第 22 节的 22 个问题读一遍。**这是唯一现在就有用的** |
| **70 天计划做到 Day 10–28** | 补上「登录」「流式输出」这两项（这两项是 AI 产品的基本配置，不做产品不成立） |
| **第一次接真实客户** | 按 22 个问题问一遍，根据答案决定要补哪些技术 |
| **Week 10** | 部署、监控、备份（基础设施手册已经覆盖） |
| **交付前** | 第 22 节交接文档那一节 |

## 唯一需要现在就加进计划的两项

**如果只能加两个，加这两个：**

1. **SSE 流式输出** —— 不做的话，你的 AI 应用在客户眼里是"卡死的网页"
2. **登录** —— 不做的话，你连"这是谁的数据"都答不了

**理由**：这两个不是"高级功能"，是**AI 产品的默认配置**。缺了它们，你交付的东西算不上一个产品。

**其他的（支付、Excel、企微、多租户）**，等你手上真有那个客户的需求了再学 —— **那时候学得快十倍，因为你有具体问题要解决。**

# 一句话总结

> **技术不缺深，缺"最后一公里"。**
>
> **一人公司最大的优势是决策快，最大的风险是什么都得自己干。**
>
> **所以不要追求全会，要追求"知道有哪些、什么时候需要、最小可用怎么做"。**
>
> **这份清单的作用不是让你现在去学，是让你在被问到的时候，不慌。**
